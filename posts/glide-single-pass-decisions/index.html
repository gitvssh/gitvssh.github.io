긴 추론 없이 선택지를 평가하는 GLiDE

이 글에서 얻는 것

긴 추론 문장 없이 선택 확률을 계산하는 GLiDE를 살펴봅니다. 평가 조건과 공개 코드의 confidence 정의를 구분합니다.

문의 한 건을 담당 팀에 보내기 위해 AI가 매번 긴 설명을 써야 할까요? GLiDE는 미리 정한 선택지의 확률을 계산하는 의사결정 모델입니다. 추론의 도움은 학습 때 받아 두고, 서비스에서는 중간 문장을 생성하는 시간을 줄이는 접근이죠.

글·해설: 다메카솔

답을 쓰는 대신 후보를 평가합니다

저자들은 추론 모델이 생각한 뒤 내놓은 답변 확률을 학습 신호로 활용합니다. 정답 하나뿐 아니라 후보 사이의 상대적인 가능성도 배우는 증류입니다. 연구의 27B 모델은 전체 어텐션층에서 문맥과 후보가 서로를 읽도록 바꾸고, 나머지 순환층은 인과 구조를 유지합니다. 완성된 모델은 질문마다 한 번 계산해 주어진 후보의 확률을 반환합니다.

예를 들어 “로그인은 되는데 보고서가 열리지 않는다”는 문의를 생각해 봅시다. 선택지가 ‘계정·권한’, ‘보고서 기능’, ‘추가 확인’이라면, 서비스가 당장 필요한 것은 설명문보다 어느 경로로 보낼지에 대한 판단일 수 있습니다. 후보를 함께 읽는 모델이라면 단순히 ‘로그인’이라는 단어만 보고 계정 문의로 분류하는 대신, 보고서가 열리지 않는 상황과 각 후보의 설명을 비교하도록 설계할 수 있겠죠.

공개 모델 카드는 상태를 텍스트나 JSON으로 전달하고 질문별 선택지 확률을 받는 Python·HTTP 인터페이스를 안내합니다. 여러 질문을 한 요청으로 보낼 수 있지만, 각 질문은 독립적으로 평가합니다. 따라서 ‘담당 팀’과 ‘긴급 여부’를 함께 묻는 경우에도 두 답의 조합이 업무 규칙에 맞는지는 서비스 쪽에서 다뤄야 합니다.

점수와 속도는 같은 평가 조건으로 읽습니다

논문은 GLiDE V1.2의 분류 성능, 확률 보정, 지연을 함께 보고합니다. 아래는 2026년 10월 22일자 Hugging Face Decision Index 0.4.1의 결과입니다.

항목 GLiDE V1.2의 보고값과 조건
숨김 평가 종합점수 71.52, 알려진 기술·새 영역 점수를 0.6·0.4로 가중
확률 보정 오차(ECE) 2.0%, 확신도 구간별 예측과 실제 정답 비율의 차이
중앙 추론 지연 92.9ms, RTX PRO 6000 GPU 한 장

종합점수를 정답률로 읽으면 안 됩니다. ECE 역시 모든 요청이 그만큼만 틀린다는 뜻이 아니라, 확률이 실제 결과와 얼마나 맞는지를 요약한 값입니다. 후속 GLiDE 27B의 73.37점은 가중치 평균과 일부 층의 반복 계산을 더한 결과이므로, 앞선 92.9ms와 묶어 같은 구성의 성능처럼 제시할 수 없습니다.

공개 모델 카드는 별도 조건의 값을 안내합니다.

공개 모델 카드 항목 값과 조건
GLiDE 27B 공개 점수 72.49, Decision Index 0.3.1 공개 평가셋
Python API 중앙 지연 112ms, RTX PRO 6000·bf16·준비된 모델, 길이가 섞인 750개 요청

이 값은 위의 숨김 평가 결과와 분리해서 읽어야 합니다. 직접 도입을 비교할 때는 모델 이름뿐 아니라 평가셋, 입력 길이, 질문 수와 하드웨어까지 맞춰 봐야 합니다. 분류 자체가 빨라도 대기열이나 후속 API 호출이 길면 사용자가 느끼는 응답 시간은 달라지거든요.

같은 confidence라도 뜻이 다릅니다

논문은 가장 높은 선택 확률을 확신도로 정의합니다. 반면 공개 코드의 choice 응답에서 confidence는 1위와 2위 확률의 차이입니다. 모델 카드와 실제 계산식이 이 정의를 함께 보여 줍니다.

가령 세 후보가 다음 확률을 받았다고 가정해 봅시다.

예시 항목 값
후보별 확률 0.70 / 0.20 / 0.10
논문에서 말하는 최대 확률 0.70
코드의 choice.confidence 0.50, 상위 두 확률의 차이

둘 다 유용한 값이지만 서로 다른 질문에 답하죠. 논문에서 읽은 기준을 같은 이름의 API 필드에 곧바로 대입하면, 생각했던 것과 다른 요청을 자동 처리하거나 보류하게 됩니다.

후보에 없는 답을 골라야 하는 상황도 남습니다. ‘계정·권한’과 ‘보고서 기능’만 주었다면 장애 범위가 불명확한 문의를 어느 쪽으로든 보내게 될 수 있습니다. 여러 질문의 답이 서로 모순되지 않아야 한다는 제약 역시 별도로 표현해야 합니다.

다메카솔의 해석

GLiDE를 검토할 첫 대상은 답의 종류가 비교적 명확하고 반복되는 분류·라우팅 업무라고 봅니다. 먼저 실제 문의를 모아 ‘추가 확인’이 필요한 사례와 여러 팀에 걸치는 사례를 나눠 두고, 후보 설명을 바꿨을 때 판단이 안정적인지 확인하는 편이 좋겠습니다. 모델이 내놓은 확률과 사람이 처리한 결과를 함께 남기면, 어떤 요청에서 자동 처리를 줄여야 하는지도 살펴볼 수 있습니다.

예시의 보고서 문의라면 결과를 곧바로 권한 변경으로 연결하기보다, 우선 담당 팀을 추천하는 단계부터 비교하겠습니다. 오분류를 쉽게 되돌릴 수 있는 흐름에서 시작하면 후보 설명이나 보류 기준을 바꾼 효과를 관찰하기도 수월하죠. 반대로 판단 근거를 길게 설명해야 하는 상담이나, 선택지 자체를 새로 찾아야 하는 조사에는 별도의 생성·추론 흐름이 여전히 필요합니다.

사람에게 넘길 기준을 정하는 문제는 오류 비용에 따라 문의를 보류하는 연구와 이어집니다. 중요한 것은 높은 점수 하나를 고르는 데서 끝내지 않고, 어떤 실패를 감당할 수 있는지에 맞춰 분류와 보류를 함께 설계하는 일입니다.
