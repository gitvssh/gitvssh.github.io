VeriCUA: 끝냈다는 말에서 저장된 결과 확인으로

이 글에서 얻는 것

컴퓨터 사용 에이전트가 “작업을 끝냈다”고 말해도, 그 말만으로 완료를 확정할 수는 없습니다.

컴퓨터 사용 에이전트가 화면에 완료 표시를 띄우며 “작업을 끝냈다”고 보고했는데, 막상 파일을 열어 보니 결과가 비어 있던 경험이 있으실 겁니다. 논문 「VeriCUA」는 실행 뒤 화면과 파일·데이터베이스 같은 실제 상태를 탐색해 요구사항 충족 여부를 확인하는 검증 프레임워크를 제안합니다. 완료 보고를 추가 점검의 방향을 잡는 주장된(asserted) 근거로 다루며, 이 글에서는 검증 구조와 온라인 AndroidWorld 결과를 중심으로 살펴봅니다.

글·해설: 다메카솔

화면에 보이는 것과 저장된 것은 다릅니다

예를 들어 에이전트에게 “빨간 사과 그림을 저장해 줘”라고 지시한 상황을 떠올려 볼까요? 모니터에 빨간 사과가 떠 있다면 화면 표시 근거는 되지만, 디스크나 앱 저장소에 기록됐는지까지 보증해 주지는 못하거든요.

편집기에서 텍스트를 고치는 작업도 마찬가지입니다. 바뀐 문장이 보이는 화면은 ’표시된 내용’을, 파일 읽기는 실제 저장 여부를 확인하며 행동 로그는 ’편집을 시도했다’는 이력만 남깁니다. 같은 요구사항이라도 출처에 따라 답할 수 있는 질문이 달라지는 셈이죠.

그래서 논문은 검증에 쓰이는 근거를 두 층위로 명확히 구분합니다.

  • 주장된 근거(asserted): 완료 메시지나 의도한 조작을 보여주는 조작 전 프레임 같은 기록입니다. 추가 점검을 안내하는 단서로 쓰이며, 이 근거만으로 충족을 확정하지는 않습니다.
  • 관측된 근거(attested): 동작 뒤 화면(조작 후 프레임), 파일 읽기, 데이터베이스 조회처럼 실행 후 상태를 직접 관측한 결과입니다. 하네스는 읽기마다 지속(persistent)·휘발(volatile) 여부와 조작 전후 시점을 기록해 화면과 저장 상태를 가려냅니다.

화면에는 빨간 사과가 떠 있는데 저장소 카드에는 초록 사과가 들어 있다면 요청한 그림이 저장됐다고 바로 결론 내리기 어렵습니다. 화면과 지속 저장소가 어긋날 때는 저장 요구사항을 충족으로 보지 않고 추가 점검으로 실제 상태를 확인해야 합니다.

관측을 모아 요구사항별로 판정하는 절차

VeriCUA는 실행 에이전트의 시도가 끝난 뒤 네 단계로 검증을 진행합니다.

  1. 맥락 점검: 앱 상태와 관측을 살펴 근거 위치를 파악합니다. 찾은 디렉터리는 탐색 장소일 뿐 성공 조건은 아닙니다.
  2. 요구사항 루브릭 작성: 지시와 맥락으로 필수(hard)·보조(soft) 세부 요구사항을 나눕니다.
  3. 맞춤형 근거 수집: 미확인 요구사항에 맞춰 GUI 점검이나 코드 기반 상태 읽기를 실행하고 관측 출처를 연결해 기록합니다.
  4. 규칙 기반 판정: 축적한 근거를 규칙에 대입해 결과를 성공(success), 실패(fail), 보류(abstain) 중 하나로 결정합니다.

각 요구사항은 충족, 미충족, 미확정 중 하나의 상태를 갖습니다. 충족에는 관측된(attested) 지지 근거가 필요하고, 미충족 확정에는 서로 다른 점검에서 나온 반박 근거가 함께 있어야 하거든요. 필수 요구사항이 모두 충족되면 성공, 하나라도 미충족이면 실패로 판정합니다.

미충족은 없지만 일부 필수 요구사항이 미확정으로 남으면 작업은 미해결 상태가 됩니다. 요구사항의 ’미확정’과 작업 전체의 ’판정 보류(abstain)’는 서로 다른 층위이며, 논문 실험은 실행 환경에 따라 미해결 작업을 다르게 처리합니다.

  • 온라인 환경: 실행 뒤 접근 가능한 머신 상태를 직접 확인하며, 근거가 끝내 부족한 미해결 작업은 판정을 보류합니다.
  • 오프라인 환경: 녹화된 화면·행동 로그와 기록된 경우 접근성 트리만 분석합니다. 논문의 오프라인 실험에서는 미해결 작업의 최종 결론을 탐색 전 계산해 둔 단일 패스 VLM 초기 판정으로 대체했으며, 이 대체가 요구사항 자체의 미확정 상태를 해소하지는 않습니다.

일부 필수 요구사항이 미확정으로 남았을 때 온라인 경로는 판정을 보류해 불확실성을 드러냅니다. 반면 오프라인 실험은 초록 체크처럼 탐색 전 초기 판정이 성공이어도 이를 최종 출력의 대체 규칙으로만 쓰며, 추가 탐색으로 성공이 입증됐다고 보지 않고 미확정 요건을 유지합니다.

온라인 AndroidWorld 비교와 판정 범위의 대가

온라인 AndroidWorld 비교는 벤치마크 공식 평가기를 정답 기준으로 삼았습니다. 실행 에이전트와 검증기 모두 gemini-3-flash-preview 백본을 썼고, 평가 집계에서는 보류를 실패로 계산한 설정입니다. 실험은 루트 adb 접근이 가능한 Android 13(API 33) 에뮬레이터의 종료 상태 스냅샷을 검증하는 조건이라, 권한이 제한된 일반 모바일 환경으로 그대로 일반화하기는 어렵습니다.

검증 방식 전체 정확도 판정률 판정 사례 정확도 위양성률
단일 호출 VLM (최종 화면) 78.4% 100% 78.4% 15.4%
자동 생성 검증기 82.4% 100% 82.4% 16.9%
VeriCUA 90.5% 82% 95.1% 7.7%

표에서 핵심은 정확도와 판정 범위의 관계입니다. VeriCUA는 전체 정확도 90.5%로 두 기준선을 앞섰고, 실제 판정을 내린 사례만 추린 정확도는 95.1%까지 올라갔는데요. 대신 전체 에피소드의 82%만 판정하고 나머지는 보류한 반면, 두 기준선은 모든 에피소드에 판정을 내렸습니다.

저자들은 보류를 실패로 집계하면 재현율(recall)이 낮아질 수 있다는 대가도 짚습니다. 실제로 다른 온라인 환경인 OSWorld와 ScienceBoard에서도 위양성률은 VeriCUA가 가장 낮았지만, 재현율은 자동 생성 검증기가 더 높았습니다. 높은 정밀도와 넓은 커버리지 사이에 균형점이 있는 구조죠.

더 많은 근거에는 비용과 운영 제약이 따릅니다

근거를 능동적으로 탐색하는 방식에는 분명한 비용과 환경 제약이 따릅니다. 저자들이 보고한 주요 한계는 세 가지로 정리됩니다.

  • 호출·토큰 비용: 검증 한 번에 궤적당 수십 회 호출이 들어가 단일 호출 판정기보다 대략 10배 규모입니다. 오프라인 OSReward에서 세 기준 판정자 합계(4회 호출)가 33K35K 토큰일 때 VeriCUA는 345K378K 토큰을 썼고, 온라인 첫 번째 세트에서도 자동 생성 검증기(16.2K 토큰, 60초)보다 많은 39.2K 토큰과 97초가 들었습니다. 그래서 저자들은 실시간 대화형보다 데이터 필터링이나 보상 부여에 적합하다고 봅니다.
  • 계측 조건과 관측 공백: 온라인 상태 확인은 저장소 계측이 가능한 환경으로 제한됩니다. 녹화본만 있는 오프라인 WebArena에서도 23%는 기록만으로 결론이 나지 않아 초기 판정 대체 규칙이 쓰였습니다.
  • 읽기 전용과 확률적 변동: 검증 대상 환경에 쓰기 작업을 하지 않는 읽기 전용 원칙을 지키지만, 확률적 검증기인 만큼 실행마다 결과가 달라질 수 있습니다.

다메카솔의 관점에서 완료 판정을 설계하는 개발자라면 두 가지 실무 기준을 챙겨 볼 만합니다. 첫째, 에이전트의 “완료” 메시지는 최종 결과가 아니라 검증할 주장(asserted)으로 기록하는 편이 안전합니다. 둘째, “저장” 같은 지속 상태 요건은 화면보다 파일·데이터베이스 읽기를 우선 연결하고, 근거가 부족할 때 보류할지 대체 판정을 쓸지 환경에 맞춰 기준을 정해 두어야 하죠. 오프라인 기록만 있는 시스템에 온라인 점검을 전제하거나 모든 환경에 일률적인 보류 규칙을 적용하는 설계는 경계할 필요가 있습니다.
