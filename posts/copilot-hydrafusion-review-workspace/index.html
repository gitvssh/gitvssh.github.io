HydraFusion 업데이트: AI가 버린 초안도 파일에는 남습니다

이 글에서 얻는 것

GitHub HydraFusion의 단계별 추론과 병렬 검토, Max의 연구 프리뷰 조건을 정리합니다. 초안을 버린 뒤에도 남는 파일 변경과 커밋 전 확인할 범위를 살펴봅니다.

글·해설: 다메카솔

발행·확인: 2026-10-16

AI가 여러 초안을 검토해 더 나은 최종 답변을 골랐더라도, 작업 폴더에는 이전 시도가 건드린 파일 수정이 그대로 남아 있을 수 있습니다.

GitHub가 10월 14일 발표한 HydraFusion 업데이트와 Max 옵션을 살펴볼 때 꼭 함께 챙겨야 할 조건인데요. 초안 작성과 검토의 역할 분담은 한층 세밀해졌지만, 실제 디스크의 변경분을 확인하는 일은 여전히 개발자의 몫입니다. 공식 발표

초안은 medium, 검토는 high

기존에는 각 모델의 기본 추론 강도를 그대로 썼다면, 이번 업데이트부터는 초안 작성에 medium, 검토 단계에 high 추론 강도를 나누어 배분합니다. 변경 내용

  • Cascade 방식: 초안을 먼저 살펴보고 필요할 때만 더 강한 모델로 넘기는 판단 단계가 들어갈 수 있음
  • Critique 방식: 여러 모델이 병렬로 비평할 때 텍스트 요약에만 기대지 않고, 도구를 써서 실제 작업공간을 직접 확인하는 비중을 높임

또한 HydraFusion은 요청마다 Single·Cascade·Critique 중 알맞은 실행 방식을 고른 뒤 최종 응답 하나를 돌려줍니다. 모든 요청에 무조건 여러 모델을 동원하는 구조로 오해하면 Single 경로를 놓치기 쉬운데요(위 그림의 작업대와 조명은 작성과 검토의 역할 분담을 나타낸 비유입니다). 실행 방식

버린 초안이 바꾼 파일은 어떻게 되나

검토가 끝나고 깔끔한 최종 응답을 받았더라도 커밋 전에는 실제 파일 변경(git diff)을 반드시 확인해야 합니다.

공식 문서는 채택되지 않고 버려진 초안이 이미 작업공간에 만든 파일 수정을 자동으로 되돌리지 않는다고 명시하고 있거든요. 채팅창의 최종 요약만 믿고 변경 범위를 넘겨짚기 쉬운 지점입니다. 제약 사항

저는 이 제약을 ‘응답 선택’과 ‘작업 상태 관리’가 분리되어 있기 때문에 생기는 문제로 봅니다. 화면에 보여 줄 답변을 갈아끼우는 일과 디스크에 기록된 파일 수정을 롤백하는 일은 전혀 다른 작업이니까요. 가령 최종 답변 설명에는 없는 파일 수정이 diff에 남아 있다면, 개발자가 직접 그 수정이 필요한지, 다른 코드와 충돌하지 않는지 가려내야 합니다(이는 동작을 직접 재현한 사례가 아니라 공식 문서의 주의사항을 실무 상황에 대입해 본 예시입니다).

Max도 연구 프리뷰입니다

더 깊은 추론을 위해 새로 추가된 Max를 포함해 두 옵션 모두 아직은 연구 프리뷰 단계입니다. 도입 전에 확인할 조건들을 묶어 보겠습니다. 지원 범위 · 사용 조건과 과금

  • 제공 환경 및 요금제: VS Code·Copilot 앱·CLI에서 Pro, Pro+, Business, Enterprise 사용자에게 제공(실험·프리뷰 기능 활성화 및 조직 모델 정책 적용)
  • Max 옵션: 동일한 구조 위에서 추론 강도를 한 단계 더 끌어올리는 선택지(공식 문서는 extra high 강도도 함께 안내)
  • 지원 수준 및 과금: 연구 프리뷰이므로 SLA가 보장되지 않으며 프로덕션 워크로드용으로 의도되지 않음. 실행에 사용된 각 모델의 표준 요금이 부과되고 Auto 할인은 적용되지 않아, 검토 단계가 늘어날수록 응답 시간과 AI 크레딧 소모가 함께 커질 수 있음

조직 차원의 설정 관리는 앞서 다룬 Copilot 시작 시 정책 확인과도 이어집니다. 여러 모델을 조합해 쓰는 기능과, 조직에서 허용한 모델 정책이 실제 단말에 적용되는 범위를 함께 맞춰 봐야 합니다.

다메카솔의 해석: 결과를 채택하는 기준

제가 이 프리뷰 기능을 실무에서 시험해 본다면, 격리된 작업 브랜치에서 시작해 채팅창의 최종 설명 · 실제 git diff · 테스트 통과 여부를 삼자 대조하는 흐름을 기본으로 두겠습니다.

검토에 참여하는 모델이 늘어날수록 최종 답변이 그럴듯해 보여 그대로 믿고 싶어지지만, 결국 우리가 저장소에 반영하는 실체는 설명문이 아니라 바뀐 코드와 그 동작이기 때문입니다.

이번 글은 공식 발표와 문서를 바탕으로 정리한 해설이며, 성능 향상 폭이나 비용 절감 효과를 직접 측정한 결과는 담지 않았습니다. 분명한 것은 AI의 내부 검토가 정교해질수록 개발자가 결과를 채택하는 기준도 함께 구체화되어야 한다는 점입니다. 답변에 고개를 끄덕이는 데서 멈추지 않고, 작업공간에 남길 파일 변경을 직접 고르는 단계까지가 코드 리뷰의 범위입니다.
