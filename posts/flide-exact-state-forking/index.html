Flide: 같은 문맥은 한 번, 질문은 서로 독립적으로

이 글에서 얻는 것

Flide가 공유 문맥의 계산을 재사용하면서 질문 간 간섭을 막는 방법과, 실험 속도·수학적 정확성·비트 동일성의 조건을 살펴봅니다.

  5. 출처

같은 문서나 긴 에이전트 로그를 두고 여러 판단 질문을 동시에 던질 때, 질문마다 문맥을 처음부터 다시 계산하면 연산 낭비가 큽니다. 그렇다고 질문을 한 줄에 이어 붙여 처리하면 뒤쪽 질문이 앞선 질문을 엿보거나, 구분 토큰 탓에 원래 출력 확률이 달라질 수 있죠. Flide는 공통 문맥 계산을 한 번만 수행하면서도, 각 질문이 혼자 실행될 때 보던 입력과 계산 경로를 지켜 주는 추론 엔진입니다.

글·해설: 다메카솔

같은 문서를 여러 번 읽는 비용

예를 들어 상담 기록 한 건을 받아 ‘환불 대상인가’, ‘긴급 대응이 필요한가’, ‘상담원에게 넘겨야 하는가’를 한꺼번에 판단한다고 해 봅시다. 세 질문은 똑같은 상담 기록을 공유하지만 서로 다른 선택지를 평가해야 하죠.

Bobo Li 외 연구진이 2026년 10월 30일 공개한 논문 Flide: Accelerating Decision Inference with Exact State Forking은 이처럼 공통 상태와 여러 질문으로 묶인 선택형 판단 요청을 다룹니다. 긴 답변을 자유롭게 생성하는 작업 전반보다, 고정된 문맥 아래 여러 질문을 처리하는 결정 추론에 초점을 맞춘 연구거든요.

이런 중복을 줄일 때 흔히 접두어(prefix) 캐시를 먼저 떠올립니다. 코딩 에이전트 실행 기록에서 살펴본 KV 캐시에서도 앞부분 재사용의 효과를 살폈습니다. 다만 기존 엔진에서는 캐시 뒤의 질문들이 여전히 별도 시퀀스로 나뉘어 실행되며, 논문은 하이브리드 모델에서 블록 경계 뒤의 일부 토큰을 재계산하는 비용과 질문별 실행 부담도 지적합니다.

한 흐름에 담고, 참조 경로는 나누기

Flide는 공통 문맥과 질문들을 GPU에서 처리할 하나의 토큰 흐름에 나란히 담습니다. 대신 각 토큰이 어느 요청에 속하는지, 몇 번째 질문 가지인지, 단독 입력 기준 원래 위치는 어디인지를 별도 메타데이터로 남기는데요. 덕분에 물리적으로 한 줄에 놓여도 질문끼리 서로의 내용을 읽지 않고, 각 질문의 위치 인덱스도 단독 실행과 똑같이 유지됩니다.

질문을 구분하려고 입력 중간에 새 구분 토큰을 끼워 넣지도 않습니다. 프롬프트를 변형해 속도를 얻는 대신, 원래 입력을 보존한 채 계산 경로만 분기해 효율을 높이는 설계입니다.

물론 하나의 토큰 흐름을 탄다고 모든 층이 똑같이 동작하는 것은 아닙니다. Flide는 연산 구조에 따라 두 가지 격리 방식을 적용합니다.

  • 일반 어텐션 층: 같은 요청의 공통 문맥과 자기 질문의 앞부분만 참조하도록 가시성을 제한합니다.
  • Gated DeltaNet 순환 층: 이전 토큰을 순환 상태에 누적하는 구조라 앞선 질문이 섞이기 쉬운데요. Flide는 이 층을 두 번의 호출로 나누어 첫 호출에서 공통 문맥의 순환 상태와 합성곱 이력을 계산한 뒤, 두 번째 호출에서 모든 질문을 각자의 공통 문맥 끝 상태에서 시작시킵니다.

따라서 ‘한 번의 실행’이라는 표현을 ‘GPU 커널 한 번’으로 받아들이면 실제 구조와 어긋납니다. Gated DeltaNet 층마다 두 차례 호출이 일어나며, 상태를 복사하지 않고 메타데이터 인덱스로 이어받는 편입니다.

빨라진 실험에는 어떤 조건이 붙을까

저자들은 NVIDIA H200 GPU 한 장에서 bfloat16 정밀도로 주요 엔진을 비교했습니다. 여러 질문이 한 지문을 공유할 때와 질문이 하나뿐일 때의 차이가 크므로, 논문의 Table 2·3에 실린 QuALITY 실험 결과를 나란히 놓고 볼 필요가 있습니다.

모델 · QuALITY 구성 추론 엔진 요청 중앙 지연
Qwen3.5-0.8B · 전체 질문 묶음 vLLM 362 ms
Qwen3.5-0.8B · 전체 질문 묶음 SGLang 359 ms
Qwen3.5-0.8B · 전체 질문 묶음 Flide 37.7 ms
Gemma 4-31B · 단일 질문 vLLM 400 ms
Gemma 4-31B · 단일 질문 Flide 405 ms

Qwen3.5-0.8B 전체 질문 묶음에서는 Flide가 더 빠른 기준선인 SGLang보다 약 9.5배 짧은 지연을 기록했습니다. 한 지문에 딸린 질문을 한 요청에 묶어 보낸 덕분에 문맥 공유 효과가 크게 나타난 셈이죠. 물론 이 배수는 해당 모델과 작업 행에서 나온 수치이므로, 논문 전체의 모든 모델에 똑같이 적용되는 값으로 보기는 어렵습니다.

이 표를 해석할 때는 실험 조건과 엔진별 설정 차이도 함께 확인해야 합니다.

  • 요청 규모와 캐시 격리: Qwen3.5-0.8B 전체 질문 묶음은 115개 요청(총 2,086개 질문)의 단일 클라이언트 중앙값이며, 동시성 수준마다 두 사본을 보내되 서로 상태 캐시를 재사용하지 못하도록 구별 태그를 넣었습니다.
  • 엔진 버전과 설정 차이: 부록 B에서 vLLM은 0.32.0rc1(10월 14일 빌드)과 0.32.1rc1 중 각 셀의 더 빠른 값을 썼고, SGLang은 0.5.21, Flide는 표에 release로만 표기됐습니다. 일부 엔진의 프롬프트 템플릿과 multi-item scoring의 CUDA graph 사용 여부도 다릅니다.
  • 단일 질문 절단 조건: Gemma 4-31B 단일 질문 QuALITY는 지문·질문·가장 긴 선택지가 템플릿 여유를 두고 3,600토큰 안에 들도록 지문을 줄인 구성이라, 위의 전체 질문 묶음과는 입력 구조가 다릅니다.

문맥당 질문이 하나뿐이고 대형 모델 자체의 계산 시간이 지배적이면 이득은 작아집니다. 같은 표의 Gemma 4-31B 단일 질문 실험에서도 두 엔진의 지연 차이는 사실상 사라졌거든요. 공유할 질문 수와 실제 연산 병목을 빼놓고 최고 배수만 가져오면 도입 효과를 잘못 가늠하기 쉽습니다.

같은 계산과 맞는 답은 다르다

논문의 Proposition 1은 인과 모델과 정확한 산술을 가정할 때, 각 질문의 은닉 상태가 단독 실행과 같다는 점을 보입니다. 다만 계산 경로를 그대로 지켜 준다고 해서 모델이 틀린 답까지 맞혀 주지는 않습니다. 모델이 사실관계를 잘못 알거나 분류를 틀렸다면, 같은 연산을 보존해도 그 오류는 남기 때문이죠.

실제 GPU가 부동소수점을 사용한다는 점도 고려해야 합니다. 합산 순서가 달라지면 끝자리 오차가 생길 수 있어, 수학적으로 같은 계산이라는 설명만으로 비트 단위 동일성을 보장하기는 어렵습니다. Flide는 합산 순서를 고정하는 선택 모드를 따로 제공하지만, 논문의 보장 역시 같은 하드웨어·소프트웨어에서 전체 상태를 입력하는 경로를 전제로 하므로 다른 장비나 모든 캐시 재개 경로까지 무조건 같다고 확대하기는 어렵습니다.

다메카솔의 해석: 이런 엔진을 검토할 때는 처리량보다 먼저 ‘질문을 혼자 물었을 때의 입력과 확률 분포를 유지하는가’를 기준으로 세우는 편이 좋습니다. 그다음 실제 요청에서 문맥을 얼마나 공유하는지, 문맥당 질문이 몇 개인지를 살펴야 합니다. 빠른 실행과 질문 의미의 보존을 함께 확인하는 것이 이 논문에서 가져갈 설계 관점입니다.
