도구 스키마가 AI 에이전트의 거절을 약하게 만들 때

이 글에서 얻는 것

같은 모델도 도구 스키마를 받으면 유해 요청 거절이 약해진다는 연구와 SafeKeep의 평문 안전 관문, 평가 범위를 살펴봅니다.

일반 챗봇에서는 위험하다고 판단해 절반 넘게 거절하던 요청도, 에이전트용 도구 명세(schema)를 붙이는 순간 거절률이 한 자릿수로 뚝 떨어집니다. 모델이나 질문이 바뀐 것이 아니라, 도구의 입출력 형식을 설명하는 JSON 구조 자체가 모델 내부의 안전 판별 신호를 흐린 셈이죠. 2026년 7월 31일 공개된 논문 「Tool Specifications Matter: Uncovering and Mitigating Safety Risks in AI Agents」는 이 원인을 파헤치고, 안전 판단 단계에만 평문 도구 설명을 쓰는 2단계 방어 구조 SafeKeep을 제안했습니다.

글·해설: 다메카솔

핵심 내용

  • 거절률·분리도 급락: Llama 3.1 8B Instruct에서 동일 유해 요청 거절률이 챗봇 입력 58%에서 에이전트 입력 3%로, 은닉 상태 AUROC도 0.927에서 0.740으로 하락했습니다.
  • JSON 구조가 원인: 기능·인자 의미는 남기고 JSON 구문·예약 필드·중첩·타입만 뺀 **평문(plain-text)**으로 바꾸자 세 공개 모델 모두 구분 능력을 되찾았습니다.
  • SafeKeep 2단계 방어: 평문 안전 관문과 원 스키마 실행을 나누자 4개 모델 평균 AgentHarm 거절률은 23.8%→70.6%로 오르고, InjecAgent 공격 성공률은 25.6%→2.5%로 낮아졌습니다.

도구를 붙인 뒤 같은 모델의 거절이 달라졌다

이 실험은 모델 가중치나 사용자 질문을 고정한 채 입력 형식만 바꿨다는 점에서 시사점이 큽니다. 일반 챗봇 입력에는 기본 시스템 프롬프트와 질문만 들어가지만, 에이전트 입력에는 역할 설명과 도구 사용 지시, 도구 명세가 함께 붙거든요. 예를 들어 사내 파일 조회나 메일 전송 도구를 JSON 스키마로 연결해 두면, 챗봇에서는 막던 민감 정보 유출 요청도 에이전트 문맥에서는 인자를 채워 실행하려는 쪽으로 기울어집니다.

연구팀이 모델 내부 은닉 상태(hidden state)에서 ‘거절 방향’ 벡터를 추출해 대조해 보니, 표면적 응답 비율만 바뀐 데 그치지 않고 내부 안전 판별 신호까지 크게 무뎌졌습니다. 입력 형식 하나가 모델 내부의 판단 경로까지 흔들어 놓은 셈입니다.

내용보다 스키마 형식이 더 크게 흔들었다

연구팀은 역할 설명, 도구 사용 지시, 도구 명세를 차례로 더해 가며 원인을 좁혔습니다. 세 공개 모델 모두에서 마지막 도구 명세가 붙을 때 유해·무해 구분 성능이 가장 크게 떨어졌는데, 길이만 비슷하게 늘린 챗봇 대조군에서는 같은 하락이 나타나지 않았습니다.

이어서 도구의 ’기능 의미’와 ‘JSON 스키마 구문’ 중 어느 쪽이 원인인지 교차 실험으로 가려냈습니다.

  • 평문 변환(의미 보존 + 구문 제거): JSON 괄호·예약 필드·중첩·타입을 빼고 도구 이름·시그니처·기능·인자 의미만 평문으로 쓰자 세 모델 모두 구분 능력이 회복되었습니다.
  • 가짜 단어 치환(의미 제거 + 구문 유지): 단어 의미를 무의미한 단어로 바꾸고 JSON 스키마 구조만 남겼을 때는 뚜렷한 회복이 일어나지 않았습니다.

은닉 상태 분석에서도 스키마 형식이 만드는 벡터 방향은 모든 레이어에서 거절 방향과 반대로 정렬되었습니다. 적당한 활성화 조향(activation steering)으로는 거절을 되살릴 수 있었지만, 강도를 과하게 높이면 출력 일관성마저 무너졌죠. 구조화된 스키마 형식이 모델을 안전 검토보다 ’구문 채우기 모드’로 끌어당긴다는 단서입니다.

안전 판단과 실행에 서로 다른 표현을 썼다

저자들이 제안한 SafeKeep은 한 번의 호출에 안전 판단과 도구 호출 생성을 동시에 맡기지 않고 역할을 두 단계로 나눕니다.

  1. 1단계 안전 관문 (평문 설명): 기능과 인자 의미를 살린 평문 설명과 요청을 함께 읽어 유해 여부를 먼저 판정하고, 위험하면 즉시 거절합니다.
  2. 2단계 도구 실행 (원래 스키마): 안전하다고 판정된 요청만 기존 파이프라인으로 넘겨 원래 JSON 스키마에 맞춰 도구 호출을 생성합니다.

가중치 재학습이나 내부 활성화 조작이 불필요해 API 기반 상용 모델에도 바로 쓸 수 있습니다. 혹시 안전 판정기를 한 번 더 호출한 덕분은 아닐까요? 1단계에 원래 스키마를 그대로 넣은 2단계 대조군(SafeJudge)과 비교해, 평문을 쓴 SafeKeep이 뚜렷한 추가 방어 이득을 만든다는 점도 확인되었습니다.

두 벤치마크와 네 모델에서 확인한 방어 성능

최종 평가는 공개 모델과 상용 API 모델 4종, 2개 안전 벤치마크를 대상으로 진행되었습니다.

  • 평가 모델: Llama 3.1 8B Instruct, Qwen3 8B, Gemini 3.1 Flash, GPT-5.4 mini
지표 (4개 모델 평균) 기본 SafeKeep 벤치마크 구성
유해 요청 거절률 23.8% 70.6% AgentHarm: 11개 위해 범주 유해 176개 + 유사 무해 176개
간접 주입 공격 성공률 25.6% 2.5% InjecAgent: 외부 관찰 속 악성 지시 1,054개 (기본+강화)
과제 정확도 / 유효 출력률 60.9% / 78.7·78.8% 79.6% / 93.0·94.8% AgentHarm 정확도 / InjecAgent 기본·강화형 유효 출력률

안전 관문을 앞에 세웠음에도 정상 업무 처리 정확도와 유효 출력률까지 함께 올라갔습니다.

실험 범위와 측정되지 않은 운영 비용

실서비스 도입 전에는 논문이 다루지 않은 비용과 검증 범위를 함께 살펴야 합니다. SafeKeep은 실행 전에 안전 판단 호출을 한 번 더 거치므로 응답 지연과 토큰 비용이 늘어나지만, 논문에는 별도 한계 절이나 정량 수치가 빠져 있거든요. 고정 도구 템플릿 기반의 벤치마크 결과인 만큼, 수십 개 도구가 얽힌 장기 멀티턴 대화나 복잡한 권한 체계에서는 따로 검증이 필요합니다.

다메카솔의 해석: 실행 명세와 안전 판단을 분리해 본다

저자 저장소에는 분석 스크립트와 데모, 유해·무해 요청 400쌍이 공개되어 있어 자체 파이프라인의 재현 출발점으로 삼기 좋습니다. 실무에서는 실행용 JSON 스키마를 안전 판정에 그대로 재사용하기보다, 평문 요약으로 위험을 먼저 거르는 앞단 게이트를 적용해 볼 수 있습니다. 배포 전에는 아래 세 가지를 먼저 점검해 보세요.

  1. 정상 요청이 1단계 안전 관문에서 오탐으로 막히지 않는가?
  2. 외부 검색·문서 결과에 숨은 간접 프롬프트 주입이 실행 단계로 넘어가지 않는가?
  3. 2단계 분리로 늘어난 응답 지연과 토큰 비용이 서비스 목표(SLO) 안에 들어오는가?

모델 자체의 안전 정렬만 믿기보다, 도구를 설명하는 인터페이스 형식까지 안전 감사의 대상에 포함해야 한다는 것이 이 연구의 핵심 메시지입니다.
