AI가 만든 SQL, 실행은 됐는데 답이 틀리는 이유

이 글에서 얻는 것

FLINT 논문으로 자연어 SQL의 참조값 연결, 실행 성공과 의미 정확도의 차이, 평가 조건을 살펴봅니다.

Text-to-SQL의 정확도를 높이려면, 질문 속 용어가 데이터베이스의 어느 코드값(ID)에 해당하는지부터 정확히 연결해야 합니다. 사용자가 ‘분기 매출’을 물었는데 쿼리의 WHERE 절에 연간 매출 ID를 넣었다면, 문법 오류 없이 완벽하게 실행된 SQL도 엉뚱한 숫자를 가져옵니다. FLINT 연구진은 이 참조값 탐색을 별도 단계로 분리해 복잡한 금융 데이터베이스 조회 정확도를 끌어올렸습니다.

글·해설: 다메카솔

원문 확인·작성: 2026년 10월 5일

핵심 내용

  • 스키마 문법과 참조값 의미의 간극: metric_id 같은 컬럼 이름만으로는 어떤 코드값이 분기 매출인지 알 수 없으므로, FLINT는 SQL을 작성하기 전에 Lookup Agent로 참조 테이블을 조회해 질문에 맞는 실제 ID 후보와 필터 조건을 먼저 확보합니다.
  • 99% 실행 성공 뒤의 정확도 격차: 비공개 금융 데이터 두 묶음(Financials 221문항·Transactions 138문항, Claude 4.5 Opus 기준)에서 비교 대상 시스템들은 모두 99% 이상 SQL 실행에 성공했지만 정확도는 50% 미만(ReFoRCE 46.6%/47.1%, CHESS 35.6%/49.6%)이었고, FLINT는 **68.8% / 65.2%**를 기록했습니다.
  • 동적 참조값 조회의 기여도: 자주 쓰는 ID의 정적 매핑(질문의 약 78% 커버)만 남기고 Lookup Agent를 제거하자 FLINT의 정확도가 **54.8% / 33.3%**로 떨어져, 질문별 참조값 탐색 단계의 중요성을 보여 주었습니다.

이번에 읽은 논문은 Kensho Technologies의 Arijit Sehanobish 등이 쓴 From Benchmarks to Production: A Text-to-SQL System for Complex Financial Data(2026년 10월 2일 제출 arXiv v1)입니다.

컬럼 이름만 보고는 고를 수 없는 값

실무 데이터베이스에서 metric_id라는 컬럼 이름은 그 칸에 지표 식별자가 들어간다는 사실만 알려 줄 뿐, 그중 어느 번호가 매출이고 어느 번호가 영업이익인지는 별도의 참조 테이블을 열어 봐야 알 수 있습니다. 기간(분기·연간)이나 통화 단위까지 각기 다른 코드값으로 관리되는 금융 스키마에서는, 쿼리가 에러 없이 실행됐다는 사실만으로 올바른 값을 조회했는지 보장할 수 없습니다.

FLINT는 모델이 프롬프트만으로 ID를 추측하게 두는 대신, 앞단에 Lookup Agent와 도메인 연결 단계를 두어 필요한 재료부터 모읍니다.

  1. 참조값 탐색(Lookup Agent): 질문과 관련된 참조 테이블을 고른 뒤 SELECT 쿼리로 후보를 읽어 와 질문 의도에 맞는 ID와 WHERE 조건을 만듭니다. 예를 들어 Financials의 전체 지표 11,412개 중 전문가가 자주 쓰는 약 2,500개를 추려 두고, 질문마다 약 50~100개 후보로 좁혀 98%의 후보 재현율(정답 ID가 후보 안에 포함되는 비율)을 확보합니다.
  2. 예시 검색·엔티티 연결·조인 경로 선택: 전문가가 작성한 유사 질의 예시를 가져오고, 회사 이름을 내부 식별자로 변환하며, 고정된 전체 스키마 위에서 목표 테이블까지의 중간 조인 경로를 찾습니다.
  3. 최종 SQL 작성: 앞 단계에서 확정된 참조 ID, 필터 조건, 조인 경로를 넘겨받아 마지막 SQL 문장을 완성합니다.

거의 다 실행됐지만, 답은 갈렸습니다

저자들의 주 실험(Financials 221문항·Transactions 138문항, 총 359문항, 전 시스템 Claude 4.5 Opus 동일 사용)에서 비교 시스템들은 모두 99% 이상의 SQL 실행 성공률을 보였지만, 실제 정답률에서는 큰 차이를 보였습니다(원문 Table 2·3, 각 시스템을 금융 스키마에 맞춘 조정 내역은 부록 D 참고).

시스템 구성 Financials 정확도 (221문항) Transactions 정확도 (138문항) 비고
FLINT (전체 구성) 68.8% 65.2% 동적 Lookup Agent + 스키마·경로 연결
FLINT (Lookup Agent 제거) 54.8% 33.3% 자주 쓰는 ID 정적 매핑(약 78% 커버)만 제공한 절제 실험
ReFoRCE 46.6% 47.1% 비교 기준선 (실행 성공률 99% 이상)
CHESS (후보 10개 설정) 35.6% 49.6% 비교 기준선 (실행 성공률 99% 이상)

여기서 정확도는 실행 실패를 0점으로 처리하고, 실행에 성공한 SQL은 구문 트리 정규화와 실행 결과 비교를 거친 뒤 남는 경우를 LLM 판정기로 채점한 값입니다(부록 C의 무작위 50건 수동 검수에서는 사람 판정과 47건이 일치했습니다). 자주 쓰는 ID를 프롬프트에 정적으로 적어 주는 것만으로는 부족하고, 질문마다 참조 테이블에서 후보를 좁혀 주는 단계가 정확도를 크게 좌우했음을 알 수 있습니다.

다메카솔의 해석: 의미를 고르는 단계를 관찰하기

자연어 데이터 조회 서비스를 운영한다면 최종 SQL과 실행 성공 여부만 로그에 남기지 않고, 질문 → 선택된 참조 ID 후보 → 확정된 필터 조건 → 최종 SQL로 이어지는 중간 선택 기록을 함께 남겨야 합니다. 사용자가 “분기 수치가 아니라 연간 수치가 나왔다”고 피드백했을 때, 참조 후보 검색에서 애초에 빠졌는지, 후보는 있었는데 잘못 골랐는지, 마지막 SQL 조립에서 조건이 누락됐는지 바로 좁혀 볼 수 있기 때문입니다. 이는 SQL에서 결과 조건과 실행 방법을 구분하는 이야기를 자연어 인터페이스의 검증 파이프라인으로 확장한 셈입니다.

또한 데이터 접근 보안과 의미적 정확도는 서로 다른 장치로 다뤄야 합니다. 논문 부록 H에서 설명하듯 읽기 전용 DB 연결, 행 단위 접근 제어(RLS), 허용 테이블·컬럼 화이트리스트와 자원 제한은 권한과 인프라 안전을 지키고, 기간이나 지표를 잘못 고른 의미적 오류는 단계별 관측과 회귀 테스트로 잡아야 합니다.

아울러 스키마마다 전문가 규칙과 예시를 준비해야 하는 초기 비용과 다회차 후속 질문 미지원 같은 시스템 조건도 에이전트 평가의 실행 설정처럼 함께 고려해야 합니다. 다음 Text-to-SQL 회귀 테스트에는 문법 오류를 내는 질문뿐 아니라 실행은 멀쩡히 되지만 기간·통화·지표 코드가 헷갈리는 질문 묶음을 꼭 별도로 넣어 보기를 권합니다.
