AI 에이전트가 기다리는 이유, 서버와 작업 계획을 나누면 달라질까

이 글에서 얻는 것

검색 도구의 응답을 기다렸다가 AI 에이전트가 다시 말을 이어 갑니다. 방금 읽은 문맥인데도 첫 글자가 나오기까지 한참 걸린다면, 도구를 기다리는 사이 추론 서버가 계산해 둔 KV 캐시를 비웠을 수 있습니다. 실행기는 곧 같은 문맥을 다시 쓸 줄 알았지만 서버는 그 계획을 몰랐던 셈인데, HEAR 연구진은 에이전트 실행기(하네스)의 작업 계획과 추론 엔진의 현재 상태를 양방향으로 주고받아 요청 순서와 캐시 관리를 함께 조정하는 프로토콜을 제안합니다.

글·해설: 다메카솔

원문 확인·작성: 2026년 10월 6일

핵심 내용

  • 하네스와 엔진의 양방향 상태 교환: 에이전트 실행기(하네스)는 작업 준비 상태와 다음 문맥 재사용 의도를 전달하고, 추론 엔진은 현재 KV 캐시·대기열 상태와 실제 처리 결과를 돌려주는 공통 계약(HEAR)을 정의합니다.
  • 캐시 우선 처리와 최대 대기 시간의 절충: SCBench 재생 실험(Qwen3-8B, RTX PRO 6000 1대)에서 캐시 우선 처리는 전체 배치 완료 시간을 481초에서 224초로 줄였으나 첫 토큰 최대 대기는 79.0초에서 93.9초로 늘렸고, 40초 이상 대기 요청을 보호하는 Guard-40을 더해 배치 완료 299초(FCFS 대비 1.61배 가속)·최대 대기 65.0초로 균형을 맞췄습니다.
  • 부하 조건과 역할별 엔진 배치: Mooncake 100% 세션 재생 조건에서는 기능을 모두 켠 구성(분당 108.9회)이 기본 FCFS(122.7회)보다 처리량이 낮아 부하에 따른 점검이 필요하며, 역할별로 추론 방식을 나눈 실험에서는 BrowseComp-Plus(5.69시간 → 4.62시간)와 DeepResearchBench(5.93시간 → 2.42시간)의 전체 실행 시간을 단축했습니다.

이번에 읽은 논문은 하얼빈공업대 선전의 Jiaqi Zhao 등이 쓴 Can Agent Harnesses and Inference Engines Hear Each Other? The HEAR Protocol for Agentic LLM Serving(2026년 10월 5일 제출 arXiv v1)입니다.

다음 작업을 아는 쪽과 캐시를 보는 쪽

에이전트 워크플로에서 작업을 이어 붙이는 **하네스(harness)**와 모델을 계산하는 추론 엔진은 서로 다른 정보를 봅니다. 하네스는 어떤 도구를 호출하고 어느 하위 작업의 결과를 기다릴지 알고 있고, 추론 엔진은 요청 대기열과 모델이 이전 입력을 읽으며 계산해 둔 중간 상태(KV 캐시)를 관리합니다.

재사용할 KV 캐시가 메모리에 남아 있으면 긴 문맥을 처음부터 다시 계산하는 비용을 크게 줄일 수 있습니다. 문제는 하네스가 곧 다시 쓸 문맥을 알아도 서버에 캐시가 남아 있는지 모르고, 서버는 캐시 상태를 알아도 외부 도구 호출 뒤에 어떤 요청이 이어질지 모른다는 점입니다. 백엔드 시스템에서 작업 스케줄러와 스토리지·메모리 관리자가 서로의 상태를 공유하지 않을 때 생기는 비효율과 닮았습니다.

HEAR는 이 빈틈을 메우기 위해 두 계층 사이에 오가는 정보의 의미를 설명·제어·상태·결과 네 가지로 정리합니다. 하네스는 다음 사용 의도와 대기 보호·캐시 준비 요청을 보내고, 엔진은 현재 캐시·대기열 상태와 실제 적용 결과를 응답합니다. 특정 단일 스케줄링 알고리즘을 강제하는 패킷 규격이라기보다, 작업 의존성과 서버 지원 범위를 지키면서 정책을 얹을 수 있게 만든 인터페이스 계약입니다. 앞서 다룬 ContextRender가 반복 실행에서 재사용할 문맥 조각을 고르는 문제를 다뤘다면, HEAR는 그 재사용 계획을 실시간 서버 캐시 상태와 어떻게 맞물릴 것인가를 다룹니다.

캐시를 잘 쓰면 모두가 덜 기다릴까요?

캐시가 남아 있는 요청부터 먼저 처리하면 전체 처리 속도는 빨라지지만, 캐시가 없는 요청은 차례가 계속 밀려 기아(starvation) 상태에 빠질 수 있습니다. 저자들이 Qwen3-8B, RTX PRO 6000 1대, 96 GiB L2 KV 캐시 환경에서 SCBench에 세션 도착 시각과 사용자 생각 시간(평균 5초·표준편차 1초 분포)을 합성해 동일 경로로 재생한 결과(Table 3)에서 이 절충이 선명하게 드러납니다.

같은 SCBench 재생 조건 전체 배치 완료 첫 토큰 대기 중앙값 첫 토큰 최대 대기
도착 순서대로 처리 (FCFS) 481초 63.1초 79.0초
캐시 우선 처리 224초 4.6초 93.9초
캐시 우선 + Guard-40 299초 28.3초 65.0초

원문 Table 3 요약. 전체 배치 완료는 모든 사용자의 다회차 대화를 끝내는 데 걸린 시간이며, 첫 토큰 대기는 답변의 첫 토큰이 나오기까지의 대기 시간입니다.

캐시 우선 처리만 켜면 전체 완료 시간은 481초에서 224초로 절반 가까이 줄어들지만, 가장 오래 기다린 요청의 첫 토큰 대기는 79.0초에서 93.9초로 오히려 늘어납니다. 여기에 40초 넘게 기다린 요청을 후속 캐시 우선 요청이 앞지르지 못하게 보호하는 Guard-40(40초 이내 응답 보장이 아닌 추월 방지 규칙)을 더하자, 전체 완료는 299초(FCFS 대비 1.61배 가속)가 되는 대신 최대 대기가 65.0초로 줄어들었습니다.

한편 실제 운영 로그에서 가져온 Mooncake 경로를 Qwen3-8B와 H100 1대에서 재생한 실험에서는 부하(15분 구간 내 선택 세션 비율 50%·75%·100%)에 따라 유불리가 달라졌습니다. 특히 100% 세션 조건에서는 세션 재사용 예측·캐시 우선·대기 보호를 모두 켠 구성의 처리량이 분당 108.9회로, 단순 FCFS(122.7회)보다 낮게 나타나 부하 수준에 따라 제어 기능의 득실을 따로 따져야 함을 보여 줍니다.

역할별 엔진 구성과 확인 범위

같은 상태 교환 계약을 개발 단계의 역할별 추론 엔진 배치에도 활용할 수 있습니다. GLM-4.7-Flash를 쓰면서 주 에이전트 역할과 문서 읽기 역할을 별도 H100 GPU에 나누어 배치한 실험 결과는 아래와 같습니다.

  • BrowseComp-Plus (208문제): 주 역할에 vLLM, 읽기 역할에 H2O를 배치한 구성이 선택되어, 양쪽 모두 기본 vLLM을 쓴 구성 대비 전체 실행 시간을 5.69시간에서 4.62시간으로 줄였습니다.
  • DeepResearchBench (100개 과제): OmniKV와 H2O 조합이 선택되어 전체 시간을 5.93시간에서 2.42시간으로 줄였습니다.

두 실험 모두 대응 비교의 신뢰구간이 품질 차이 0을 포함해 평균 품질 하락이 관찰되지 않았다고 보고됐으나, DeepResearchBench 대응 분석은 모든 구성에서 유효 점수를 받은 공통 89개 과제를 기준으로 삼았고 BrowseComp-Plus는 심사 GPU 구성에 차이가 있어 모든 작업에서의 무손실을 보장하는 결과로 일반화할 수는 없습니다. 또한 2026년 10월 6일 확인 당시 저자가 안내한 익명 코드 저장소 링크는 403 응답을 반환해, 이번 글은 원문 PDF·HTML만을 대조한 리뷰로 작성했습니다.

다메카솔의 해석: 완료를 확인할 수 있는 최적화

이 논문에서 속도 개선 폭만큼이나 실무적으로 중요한 부분은 캐시 준비 요청의 ‘접수’와 실제 ‘준비 완료’를 구분하는 계약입니다. 하네스가 캐시 프리페치를 요청했더라도 다음 턴이 시작될 때 아직 적재 중일 수 있고, 방금 조회한 캐시 상태도 그사이 다른 요청에 밀려 비워졌을 수 있기 때문입니다.

실제 서빙 환경에 이런 계약을 도입한다면 요청 ID와 문맥 버전을 묶어 상태 관측 시각, 캐시 준비 요청의 수락 여부, 실제 추론 시점의 캐시 적중 결과를 한 줄의 로그로 남기겠습니다. 그래야 지연이 튀었을 때 에이전트의 도구 호출 계획이 바뀐 탓인지, 서버 메모리가 부족해 캐시가 먼저 축출된 탓인지 원인을 바로 분리할 수 있습니다. 에이전트 평가에서 설정을 함께 기록해야 하는 이유와 마찬가지로, 평균 처리량 옆에 꼬리 지연(최대 대기 시간)과 테넌트 간 상태 격리 조건을 함께 두어야 안전한 최적화가 됩니다.
