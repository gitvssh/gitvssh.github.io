OpenAI의 칩 설계 AI: 회로를 바꾸고 동작은 검증한다

이 글에서 얻는 것

AI의 회로 수정과 설계 도구 검증, 실제 제품 반영의 차이를 설명합니다.

“AI가 반도체를 설계한다”는 소식을 접하면 AI가 칩 전체를 새로 그려 내고 곧바로 상용 GPU 속도를 높인 것처럼 받아들이기 쉽습니다. 하지만 실제 칩 설계에서는 회로를 고치는 일만큼이나, 기존과 똑같이 동작하는지 검증해 제조로 넘기는 과정이 중요하거든요. OpenAI가 2026년 11월 18일 공개한 칩 설계 사례도 모델의 회로 수정과 Synopsys 도구 기반 검증 결과를 함께 다루고 있습니다.

글·해설: 다메카솔

수정안과 검증을 함께 보는 이유

OpenAI가 밝힌 핵심은 칩 내부의 계산과 데이터 이동을 기술하는 코드(RTL)를 AI가 고치고, Synopsys 설계 도구로 원래 동작이 유지되는지와 전력·성능·면적(PPA)을 확인했다는 점입니다. 소프트웨어는 배포 뒤에 패치로 오류를 바로잡을 수 있지만, 칩은 한 번 제조에 넘기면 수정이 어렵고 작은 변경도 전력과 성능에 함께 영향을 미칩니다.

가령 여러 단계를 거쳐 값을 임시로 저장하던 연산 회로를 묶어 하나의 계산 블록으로 재구성하는 상황을 떠올려 볼까요? OpenAI는 실제로 연산 회로와 처리 단계를 다시 구성해 하드웨어를 공유하고 중간 저장을 줄였다고 설명합니다. 자체 추론 칩 Jalapeño의 개선은 실제 실리콘 초기 구동에서도 확인했다고 밝혔습니다. 이전 Jalapeño 추론 실측 기사가 완성된 칩의 실행 성능을 다뤘다면, 이번 발표는 내부 회로를 어떻게 다듬었는지에 초점을 맞춘 셈이죠.

수정안이 나오면 Synopsys 도구로 두 가지를 확인합니다. 수정 전과 같은 입력에 대해 블록의 원래 동작이 유지되는지 보는 기능 검증과, 전력·성능·면적(PPA) 목표를 충족하는지 살피는 평가입니다. 다만 특정 블록이 도구 검사를 통과했다는 보고가 칩 전체의 정확성을 보편적으로 보증하는 것은 아니기에, 적용 범위와 조건을 나누어 살펴봐야 합니다.

회로 개선을 제품 전체 성능으로 읽지 않기

이번 발표에는 여러 하드웨어 사례가 함께 나오지만, 사례마다 도달한 검증 수준과 제품 반영 범위는 서로 다릅니다. 사례별 적용 내용과 해석 조건을 표로 나란히 비교해 보면 차이가 또렷합니다.

구분 적용 내용 확인된 단계 해석 시 볼 조건
Jalapeño 연산·처리 단계 재구성, 하드웨어 공유·중간 저장 축소 Synopsys 도구 검증, 실리콘 초기 구동 확인 블록 단위 개선 사례(자사 발표 기준)
AMD GPU GPU 설계 내 일부 변경 적용 제조에 보낸 설계와 향후 버전 파일에 반영 제품 출시·전체 속도 향상 확정 불가
RISC-V 평가 면적 제한 아래 처리량 평가 시뮬레이션 기반 기능·면적 검사 일부 기능 생략 가능, 물리 구현 검증 필요
GPT-Synopsys 전문 모델 공동 개발 계획 9월 30일 다년 계약, 초기 고객 협업 일반 고객 이용 시점 미정

AMD GPU 사례를 보면 일부 변경이 제조에 보낸 설계에 들어갔고, 다른 변경은 향후 버전용 설계 파일에 반영됐습니다. 상용 칩 설계 자산에 AI 수정이 쓰였다는 점은 눈에 띄지만, 이것만으로 소비자 제품 출시나 GPU 전체 처리속도 향상을 단정하기는 어렵습니다. 칩 전체 속도는 단일 블록뿐 아니라 데이터 이동과 소프트웨어 설정 같은 요소가 함께 결정하기 때문이죠.

별도 RISC-V 실험 역시 조건을 빼놓고 읽기 어렵습니다. 시뮬레이션 검사와 면적 제한을 둔 처리량 평가였고, 새로 설계하는 과제 특성상 요구사항에서 일부 기능을 생략할 수 있었거든요. OpenAI도 더 엄격한 면적·물리 구현 검증이 필요하다고 적은 만큼, 실험 점수를 상용 칩의 성능으로 옮겨 읽으면 핵심 조건이 빠집니다.

GPT-Synopsys는 별도의 개발 계획입니다

설계 도구와 AI를 깊게 결합하려는 계획도 구분해서 봐야 합니다. Synopsys가 9월 30일 발표한 협력은 전문 모델 GPT-Synopsys를 공동 개발하는 다년 계약으로, 당시 초기 고객 협업이 진행 중이었지만 일반 고객의 이용 시점은 정하지 않았습니다. 발표가 제시한 에이전트 흐름은 세 단계로 이어집니다.

  1. 목표 설정: 엔지니어가 회로 개선이나 PPA 목표를 에이전트에게 맡깁니다.
  2. 도구 반복 실행: 에이전트가 설계 도구를 실행하고 결과를 해석하며 수정안을 다듬습니다.
  3. 엔지니어 검토: 사람이 검증 결과와 수정 내역을 검토해 채택 여부를 결정합니다.

이 흐름은 AI가 혼자 도면을 완성하기보다, 기존 설계 검증 루프 안에서 반복 탐색을 돕는 보조 체계에 가깝습니다. 지금 바로 쓸 수 있는 상용 기능인지, 향후 공동 개발 로드맵인지 구분해 읽어야 합니다.

다메카솔의 해석

이번 소식에서 주목할 부분은 수정안을 많이 만드는 능력과 그 수정안을 믿을 근거가 함께 다뤄졌다는 점입니다. 코드가 짧아지거나 회로 흐름이 단순해 보여도 같은 동작을 유지하는지, 다른 조건에서도 이득이 남는지는 설계 도구의 검증을 거쳐 따로 확인해야 하거든요.

AI 칩 설계 소식을 읽을 때는 검증 깊이와 적용 범위를 먼저 나누어 보는 편이 좋습니다. 시뮬레이션 통과인지 실제 실리콘 구동인지, 특정 블록 개선인지 제품 전체 성능인지, 그리고 연구 공개인지 일반 고객 출시인지 구분하면 과장을 걸러내기 쉽습니다.
