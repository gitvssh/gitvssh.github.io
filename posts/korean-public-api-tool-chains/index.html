이 글에서 얻는 것

KOPA-Bench와 EDGE 연구를 통해 공공 API 에이전트가 선행 키와 페이지네이션에서 실패하는 이유를 살펴봅니다.

공공 API 하나를 잘 호출하는 것과 여러 호출을 끝까지 잇는 것은 다른 일입니다. **「Multi-Step Tool-Calling over Korean Open Public APIs」**에서 작은 공개 모델은 선행 키를 건너뛰거나 첫 페이지만 읽고 답을 끝냈고, 연구팀은 이 실패를 실제 엔드포인트 실행으로 걸러내는 KOPA-Bench와 EDGE로 다뤘습니다.

글·해설: 다메카솔

핵심 내용

  • KOPA-Bench는 한국 공공 API 10개 플랫폼과 6개 분야의 145개 멀티스텝 과제로 구성됩니다.
  • 과제당 평균 도구 호출은 4.92회였고 59%는 병렬 호출을 포함했습니다.
  • EDGE는 도구 출력과 다음 입력의 연결을 스키마만 보고 확정하지 않고 실제 API에서 실행해 갱신합니다.
  • 저자들이 학습한 Qwen3.5 9B의 pass@1은 0.3275에서 0.4310으로 올랐지만, 벤치마크 재현성은 바뀌는 라이브 엔드포인트에 묶여 있습니다.
  • 공식 저장소는 아직 출시 준비 상태여서 이번 확인은 PDF·TeX·저장소 상태 대조까지이며 독립 재현은 포함하지 않습니다.

에이전트는 선행 키와 나머지 페이지를 놓쳤다

실패는 도구 선택보다 이른 곳에서 시작했습니다. 논문의 교육 과제 예에서 모델은 통계 API를 먼저 호출했다가 인증키 오류를 냈고, 키를 회수한 뒤에도 페이지 1만 집계했습니다. 정답은 75명이었지만 모델은 첫 페이지의 23명을 최종 답으로 냈습니다.

이 사례가 보여 주는 부담은 두 겹입니다. 한국 공공 API는 인증키나 기업·지역 코드를 먼저 찾아야 다음 호출의 인자를 만들 수 있고, 한 번의 응답이 수천 건을 돌려주면 페이지네이션과 축약까지 필요합니다. 단일 함수 호출 정확도만 재면 이 실패가 잘 보이지 않습니다.

실제 한국 공공 API를 잇는 과제를 만들었다

저자들은 교통, 금융, 교육, 법률, 정치, 지방행정 여섯 분야에서 145개 과제를 만들었습니다. 10개 플랫폼의 2,318개 함수를 MCP 서버로 노출했고, 과제마다 정답 행동, 기대 답변이나 서버 상태, 허용 호출 수를 기록했습니다. 평균 단계 수는 3.32, 평균 호출 수는 4.92였으며 최대 14회 호출이 필요한 과제도 있었습니다.

검수는 사람이 만든 정답 경로를 다른 전문가가 다시 읽는 단계와 실제 실행 단계로 나뉩니다. 첫 감사에서 7개 과제에 오류가 발견됐고, 모델 실패를 뺀 실행 검사의 첫 통과율은 80%였습니다. 연구팀은 지적된 과제를 고친 뒤 145개가 모두 통과할 때까지 다시 실행했습니다.

성공 판정도 하나로 뭉치지 않았습니다. RESPONSE는 최종 답을, ENVIRONMENT는 실행 뒤 서버 상태를, ACTION은 도구 호출의 정확성과 낭비를 봅니다. 정답 행동을 한 번 포함했어도 뒤에서 잘못된 호출을 더해 상태를 망칠 수 있으므로 ACTION만으로 과제 성공을 결정하지 않았습니다.

그럴듯한 연결을 실제 호출로 시험했다

EDGE의 첫 단계는 도구 출력 필드와 다음 도구 입력을 잇는 후보 그래프입니다. 검색기가 가까운 도구를 좁히고 LLM이 연결 가능성을 제안하지만, 그 판단은 시작점일 뿐입니다. 시스템은 후보 경로를 라이브 API에서 실행하고 성공과 실패를 Beta 사후분포에 쌓아 그래프를 계속 바꿉니다.

실패의 성격도 가중치가 다릅니다. 스키마·타입 불일치와 필드 누락은 연결 자체의 문제라 크게 감점하고, 호출 제한·타임아웃·서버 오류는 환경 잡음일 수 있어 작게 반영합니다. API가 잠깐 느렸다는 이유로 맞는 연결을 지우는 일을 줄이려는 설계입니다.

저자들의 분석에서 실행 전 후보 연결은 50.2%가 성공했습니다. 정제 뒤 살아남은 그래프는 62.7%, 제거된 연결은 14.8%였습니다. 같은 후보에서 출발했기 때문에 이 차이는 실제 실행 증거가 어떤 연결을 남겼는지 보여 줍니다. 저자들은 기존 합성 시스템 전체를 같은 도구 목록에서 다시 돌린 비교까지 수행하지는 않았습니다.

응답이 하나인지, 몇 개인지, 너무 많은지 구분했다

두 번째 단계의 핵심은 연결 필드의 레코드 수입니다. 값이 하나면 다음 호출로 그대로 넘기고, 2~5개면 각각 호출하며, 더 많으면 최대·최소·임계값·날짜·빈도 같은 결정적 규칙으로 후보를 줄입니다. 비교나 조건 분기처럼 선형 체인으로 표현하기 어려운 과제는 별도 구조로 합성했습니다.

이 과정을 거친 학습 데이터는 1,781개였습니다. 연구팀은 같은 데이터로 SFT와 GRPO를 나눠 효과를 살폈고, 비재현·오류·중복·오래된 레이블을 제거하는 필터만으로도 4B 모델의 pass@1이 0.242에서 0.309로 높아졌다고 보고했습니다. 데이터 양보다 실행 가능한 궤적을 남기는 품질 관리가 결과에 영향을 줬다는 근거입니다.

작은 모델은 가까워졌고 엔드포인트는 계속 움직인다

결과 폭은 눈에 띕니다. KOPA-Bench pass@1에서 Qwen3.5 4B는 0.1758에서 0.3094로, 9B는 0.3275에서 0.4310으로 올랐습니다. 같은 계열의 비학습 27B 모델은 0.4482였으므로, 학습한 9B가 약 세 배 큰 모델에 가까워졌습니다. 각 과제는 네 번 롤아웃했고 pass@1 안정성은 별도의 여덟 시드로 확인했습니다.

분포 밖 BFCL에서도 멀티턴 점수가 4B는 4.04점, 9B는 5.87점 올랐습니다. 연구팀은 멀티스텝 도구 호출 구조가 멀티턴 대화 구조와 맞닿은 신호로 해석했습니다. 한국 공공 API에서 만든 데이터가 모든 상용·비공개 API에 그대로 옮겨진다는 결론은 이 실험 범위 밖입니다.

재현성에는 살아 있는 서비스가 끼어듭니다. 스키마, 가용성, 반환 레코드가 바뀌면 같은 정답 경로도 다른 결과를 냅니다. 연구팀은 실시간 데이터 과제를 걸러내고 서버 상태를 해시로 비교했지만, 외부 기관의 엔드포인트를 고정할 수는 없습니다.

공개 저장소는 아직 출시 준비 상태다

제가 보존한 공식 저장소 commit은 d01a8418fcdaac983cb00fb26bd5e9c0851e3964입니다. 압축 파일에는 README.md, LICENSE, .gitignore 세 파일만 있었고 README는 벤치마크 145개, MCP 서버, 평가 코드, EDGE 파이프라인, 학습 데이터, 체크포인트, 프롬프트를 공개 준비 중이라고 밝혔습니다.

따라서 이번 확인은 PDF 30쪽과 TeX 68개 파일, 저장소 출시 상태를 서로 대조한 수준입니다. 8대의 H100 학습, 라이브 API 호출, 145개 과제와 여덟 시드, BFCL 평가는 다시 실행하지 못했습니다. 위 수치는 논문 저자가 보고한 결과로 읽어야 합니다.

다메카솔의 해석: API 연결은 배포 뒤에도 살아 있는지 물어야 한다

제가 이 논문에서 가져갈 것은 모델 크기보다 연결 검증 방식입니다. API 명세에서 출력 필드와 다음 입력 타입이 맞아도 인증키, 페이지네이션, 호출 제한, 서버 상태가 끼면 경로는 실행 중에 깨집니다. 도구 명세가 에이전트 안전에 미치는 영향을 다룬 글과 함께 보면, 명세 검증 다음에 실행 증거가 왜 필요한지 더 선명합니다.

운영 환경에서는 작은 contract test를 두겠습니다. 배포 전후에 선행 코드 조회, 두 페이지 이상 집계, 다건 응답 축약, 최종 상태 확인을 대표 경로로 실행하고, 구조 오류와 일시적 환경 오류를 다른 알림으로 분리합니다. 결과 캐시는 답만 남기지 않고 호출 시각, 엔드포인트 버전, 페이지 수, 사용한 인자를 함께 보존해야 다음 실패를 재구성할 수 있습니다.

이 운영안은 논문이 직접 시험한 개입이 아닙니다. 공개 자료만으로 판단할 수 있는 범위는 여기까지이며, 실제 서비스에서는 API 사업자별 호출 비용과 이용 약관도 설계 조건에 들어갑니다. 다음 질문은 분명합니다. 라이브 엔드포인트가 바뀐 뒤 어떤 과제를 자동 폐기하고 어떤 과제를 새 정답으로 갱신할 것인가.

자주 묻는 질문

9B가 27B와 같아졌다는 뜻인가요?

KOPA-Bench pass@1은 0.4310과 0.4482로 가까웠습니다. BFCL 세부 점수와 ACTION에서는 순위가 다르고, 학습한 9B와 비학습 27B를 비교한 결과입니다. 모델 전체 능력의 동등성을 뜻하지 않습니다.

라이브 API 벤치마크는 신뢰하기 어렵나요?

정적 스냅샷이 숨기는 호출 제한과 스키마 변화를 드러낸다는 장점이 있습니다. 그 대신 시점이 달라지면 동일한 경로가 같은 답을 보장하지 않으므로, 엔드포인트 상태와 정답 갱신 기록을 평가 결과에 함께 보존해야 합니다.

코드가 공개되면 곧바로 재현할 수 있나요?

코드 외에도 기관별 API 키와 이용 조건, 당시 레코드, 8대 H100 학습 환경이 필요합니다. 공개 뒤에는 먼저 task 파일과 평가기를 정적으로 대조하고, 재현 가능한 일부 도메인부터 실행 범위를 좁히는 편이 현실적입니다.
