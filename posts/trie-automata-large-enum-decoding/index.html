AI 논문 읽기글·해설: 다메카솔발행 2026년 8월 15일수정 2026년 11월 23일

수천 개 선택지를 빠르게 제한하는 트라이 디코딩

이 글에서 얻는 것

큰 유한 선택지 집합에서 일반 문법 디코딩이 느려지는 이유와 트라이 기반 사전 계산의 이점과 적용 경계를 살펴봅니다.

LLM에게 수천 개의 도구 이름이나 상품 코드 중 하나만 고르게 하면 출력 형식은 단순해 보여도 응답 속도가 떨어질 때가 있습니다. 일반 문법 기반 제약 디코딩 엔진이 평평한 목록(enum)을 처리할 때도 매 토큰마다 어휘 전체와 대조하느라 추론보다 제약 검사에 시간을 쓰기 때문이죠. COLM 2026 채택 논문 **「Trie Automata for Constrained Decoding over Large Finite Sets」**는 허용 문자열을 문자 트라이(trie)로 묶고 토크나이저 연결을 사전 계산해 대규모 선택지 디코딩 지연을 줄이는 전용 경로를 제안했습니다.

글·해설: 다메카솔

핵심 내용

  • 평평한 대규모 enum을 일반 문법 엔진으로 처리하면 매 디코딩 단계의 어휘 검사 비용이 커집니다.
  • 논문은 문자 트라이와 Aho-Corasick 매칭을 결합해 상태별 유효 토큰 마스크를 사전 계산합니다.
  • 큰 배치 반복 디코딩(vLLM batch 256, 합성 도구 1,000개)에서 처리량이 초당 7.5요청에서 219.4요청으로 29.3배 높아졌습니다.
  • 작은 일회성 집합이나 자주 바뀌는 목록(컴파일 30~40ms, 증분 갱신 미지원), 중첩 스키마에서는 일반·혼합 경로가 유리합니다.
  • 제약 디코딩은 허용 집합 안의 문자열 출력을 강제할 뿐 의미상 정답 선택까지 보장하지는 않습니다.

선택지는 단순해도 검사 경로는 단순하지 않다

예를 들어 사내 에이전트에 연결된 API가 1,000개를 넘어가고, 요청마다 LLM이 get_weather나 get_weekly_report처럼 비슷한 접두사로 시작하는 이름 하나를 골라야 하는 상황을 떠올려 볼 수 있습니다. 출력값은 문자열 하나뿐이라 단순해 보이지만, 이 목록을 JSON Schema 같은 일반 문법으로 컴파일하면 사정이 달라집니다.

일반 제약 디코딩(constrained decoding)은 현재 상태에서 어떤 토큰이 문법을 깨지 않는지 매 단계 찾아야 하거든요. 그 비용은 모델의 전체 어휘 크기와 토큰 길이에 비례합니다. 선택지가 열 개 안팎이면 눈에 띄지 않지만, 수천 개의 이름이 접두사를 공유하고 같은 스키마로 수많은 병렬 요청을 처리할 때는 평평한 선택지 하나를 고르기 위해 매번 무거운 범용 문법 장치를 통과하는 셈이죠.

문자 트라이와 토큰 매칭을 분리한다

연구진은 허용 문자열을 문자 단위 트라이에 저장해 get_weather와 get_weekly_report처럼 앞부분이 겹치는 이름들이 공통 경로를 공유하고 갈라지는 지점에서만 분기하도록 만들었습니다. 다만 모델은 글자가 아니라 여러 글자를 품은 토큰 단위로 출력을 내므로, 토크나이저 전체 어휘를 Aho-Corasick 오토마톤에 넣어 각 토큰이 트라이의 어느 경로를 이어 갈 수 있는지 미리 연결해 두었습니다.

이 구조는 토크나이저 의존성과 선택지 의존성을 깔끔하게 나눕니다. Aho-Corasick 오토마톤은 같은 토크나이저에서 계속 재사용할 수 있고, 선택지 목록이 달라질 때는 트라이와 상태별 마스크만 새로 만들면 되거든요. 그 결과 디코딩 시점에는 전체 어휘를 훑는 대신 현재 트라이 상태에서 준비된 유효 토큰만 바로 조회하며, 계산량 역시 현재 상태의 유효 토큰 수에 비례하게 줄어듭니다.

큰 배치에서 처리량 차이가 커졌다

저자들은 Qwen3-8B(151K 어휘)와 합성 도구 이름 환경을 중심으로 상태 조회 마이크로벤치마크와 vLLM 통합 실험을 진행했습니다. 조건별 주요 수치를 표로 정리해 보았습니다.

측정 항목 및 조건 제안 방식 (Trie) 비교 기준선 차이 및 비고
상태 마스크 조회 (합성 도구 1,000개) 0.65 $\mu\text{s}$ XGrammar: 5.8 $\mu\text{s}$ 조회 단계 약 9배 단축
vLLM 종단 간 처리량 (A100 80GB, greedy, batch 256, 도구 1,000개) 초당 219.4요청 XGrammar: 초당 7.5요청 처리량 29.3배 (접두사 공유·큰 배치 효과 포함)
배치 마스킹 지연 (batch 128, forward pass 약 10ms) 약 10 $\mu\text{s}$ (0.1%) XGrammar: 783 $\mu\text{s}$ (7.83%)
LLGuidance: 3,716 $\mu\text{s}$ (37.2%)		 병렬 요청이 쌓일수록 추론 파이프라인 병목 완화
초기 컴파일 시간 (선택지 10~10,000개) 30~40 ms XGrammar: 3239 ms
LLGuidance: 124 ms		 일회성·소규모 집합에서는 준비 비용이 더 큼

큰 배치와 반복 요청에서는 사전 계산된 지역 조회가 추론 파이프라인의 지연을 크게 낮추었습니다. 그러나 이 29.3배라는 결과를 모든 환경에서 얻어지는 보편적 속도 향상으로 읽기는 어렵습니다.

  • 컴파일 비용과 동적 갱신 한계: 트라이 컴파일에 30~40ms가 들고(5,000개 혼합 스키마 예시는 컴파일 시간만 약 37ms 측정, 서빙 처리량 제외) 증분 갱신을 지원하지 않아, 자주 바뀌거나 작은 일회성 목록에는 오히려 부담이 될 수 있습니다.
  • 단일 요청과 구현 환경 차이: 단일 요청(batch 1)에서는 공통 어휘 비트마스크 적용 시간(약 31$\mu\text{s}$)이 지배적이어서 조회 단축 효과가 작아집니다. CPU 마스킹과 접두사 공유 합성 도구, Rust 구현과 XGrammar(C++)의 언어 차이도 결과에 반영됐습니다.
  • 유효성과 정확도의 분리: 네 공개 분류 데이터셋과 여섯 모델의 24개 조합에서 허용 레이블을 100% 출력했고 21개 조합에서 최고 정확도를 기록했으며, 1,000개 무작위 표본에서 FSM과 출력 동등성도 확인했습니다. 다만 허용 목록 밖 문자열을 막을 뿐 의미상 정답 선택까지 담보하는 것은 별개의 문제입니다.

다메카솔의 해석: 어디까지 적용할 수 있나

이 연구가 바로 효과를 내는 대상은 크고 평평한 유한 집합입니다. 예를 들어 수천 개 사내 API 호출이나 고정 분류 레이블을 수많은 병렬 요청에서 반복 처리한다면 트라이 전용 경로로 보내는 편이 합리적이죠.

반면 작은 일회성 목록은 컴파일이 빠른 일반 엔진에 맡기는 편이 낫습니다. 중첩 객체나 숫자 범위, 조건부 필드가 섞인 구조 역시 일반 문법 백엔드가 담당하되 큰 enum 하위 노드만 트라이로 빼내는 혼합 경로가 현실적입니다. 운영 도입 시에는 컴파일 시간, 디코딩 마스크 시간, 종단 간 처리량을 분리해 측정해야 손익을 정확히 따질 수 있으며, 저자들은 날짜·시간 패턴과 숫자 범위, 정규식 확장을 후속 과제로 제시했습니다.
