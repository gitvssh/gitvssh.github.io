AI 논문 읽기글·해설: 다메카솔발행 2026년 8월 15일수정 2026년 10월 18일

수천 개 선택지를 빠르게 제한하는 트라이 디코딩

이 글에서 얻는 것

큰 유한 선택지 집합에서 일반 문법 디코딩이 느려지는 이유와 트라이 기반 사전 계산의 이점과 적용 경계를 살펴봅니다.

LLM에게 수천 개의 후보 중 하나만 고르게 하면 출력 형식 자체는 단순해 보이지만, 일반 문법 엔진은 이 평평한 목록(enum)도 매 토큰 단계마다 거대한 어휘 전체와 대조하느라 모델 추론보다 제약 처리가 먼저 병목이 되곤 합니다. COLM 2026 채택 논문 **「Trie Automata for Constrained Decoding over Large Finite Sets」**는 허용 문자열을 문자 트라이(trie)로 묶고 토크나이저 어휘와의 연결을 미리 계산해, 대규모 유한 선택지 디코딩의 지연을 크게 줄이는 전용 경로를 제안했습니다.

글·해설: 다메카솔

핵심 내용

  • 대규모 평평한 enum을 일반 문법으로 처리하면 매 디코딩 단계의 어휘 검사 비용이 커질 수 있습니다.
  • 논문은 문자 트라이와 Aho-Corasick 매칭으로 상태별 유효 토큰 마스크를 사전 계산합니다.
  • 큰 배치의 반복 디코딩(vLLM batch 256, 합성 도구 이름 1,000개)에서는 처리량이 초당 7.5요청에서 219.4요청으로 29.3배 높아졌습니다.
  • 작은 일회성 집합, 자주 바뀌는 집합(컴파일 30~40ms 및 증분 갱신 미지원), 중첩 스키마에는 같은 이득을 기대할 수 없습니다.
  • 허용 집합 안의 문자열을 출력하도록 강제할 뿐 의미상 정답까지 보장하지는 않습니다.

선택지는 단순해도 검사 경로는 단순하지 않다

도구 이름이나 상품 코드, 분류 레이블처럼 출력 후보가 유한한 작업은 흔합니다. 문제는 이 목록을 JSON Schema 같은 일반 문법 표현으로 컴파일했을 때 발생합니다. 일반 제약 디코딩(constrained decoding)은 현재 상태에서 어떤 모델 토큰이 문법을 깨지 않는지 매번 찾아야 하며, 그 비용은 어휘 크기와 토큰 길이에 비례합니다. 선택지가 열 개 안팎이면 눈에 띄지 않지만, 수천 개의 이름이 비슷한 접두사를 공유하고 같은 스키마로 수많은 병렬 요청을 처리할 때는 평평한 선택지 하나를 고르기 위해 범용 문법 장치를 매번 통과하는 셈이 됩니다.

문자 트라이와 토큰 매칭을 분리한다

연구진은 허용 문자열을 문자 단위 트라이에 저장해 get_weather, get_weekly_report처럼 접두사가 겹치는 이름들이 앞부분 경로를 공유하고 갈라지는 지점에서만 분기하도록 만들었습니다. 다만 모델은 글자가 아니라 여러 글자를 품은 토큰 단위로 출력을 내므로, 토크나이저 전체 어휘를 Aho-Corasick 오토마톤에 넣어 각 토큰이 트라이의 어느 경로를 이어 갈 수 있는지 미리 연결해 둡니다.

이 오토마톤은 같은 토크나이저에서 계속 재사용할 수 있고, 실제 선택지 목록에 따른 트라이와 상태별 마스크만 따로 만들면 됩니다. 그 결과 디코딩 시점에는 전체 어휘를 다시 훑는 대신 현재 트라이 상태에서 미리 준비된 유효 토큰만 조회하며, 계산량 역시 전체 어휘 크기가 아니라 현재 상태의 유효 토큰 수에 비례하게 줄어듭니다.

큰 배치에서 처리량 차이가 커졌다

Qwen3-8B(151K 어휘)와 합성 도구 이름 1,000개 조건에서 측정한 마이크로벤치마크 및 vLLM 통합 실험 결과는 다음과 같습니다.

측정 항목 및 조건 제안 방식 (Trie) 비교 기준선 차이 및 비고
상태 마스크 조회 (합성 도구 1,000개) 0.65 $\mu\text{s}$ XGrammar: 5.8 $\mu\text{s}$ 조회 단계 약 9배 단축
vLLM 종단 간 처리량 (A100 80GB, greedy, batch 256) 초당 219.4요청 XGrammar: 초당 7.5요청 처리량 29.3배 (접두사 공유·큰 배치 효과 포함)
배치 마스킹 지연 (batch 128, forward pass 약 10ms) 약 10 $\mu\text{s}$ (0.1%) XGrammar: 783 $\mu\text{s}$
LLGuidance: 3,716 $\mu\text{s}$		 병렬 요청이 쌓일수록 추론 파이프라인 병목 완화
초기 컴파일 시간 (선택지 10~10,000개) 30~40 ms LLGuidance: 1~24 ms 일회성·소규모 집합에서는 준비 비용이 더 큼

이처럼 큰 배치와 반복 요청에서는 사전 계산된 지역 조회가 추론 파이프라인을 훨씬 덜 막았지만, 이를 모든 환경의 보편적 속도 향상으로 읽을 수는 없습니다.

  • 컴파일 비용과 동적 갱신 한계: 트라이 컴파일에 30~40ms(혼합 스키마 5,000개 예시 재컴파일 약 37ms)가 들고 증분 갱신을 지원하지 않아, 목록이 자주 바뀌거나 작은 목록을 한 번만 쓰고 버릴 때는 오히려 손해일 수 있습니다.
  • 단일 요청과 구현 환경 차이: 단일 요청(batch 1)에서는 모든 방식에 공통인 대형 비트마스크 적용 시간(약 31$\mu\text{s}$)이 지배적이었으며, CPU 마스킹 기준이고 제안 구현(Rust)과 XGrammar(C++)의 언어 차이도 존재합니다.
  • 유효성과 정확도의 분리: 네 공개 분류 데이터셋과 여섯 모델의 24개 조합에서 제약 디코딩은 허용 레이블을 100% 출력했고 21개 조합에서 가장 높은 정확도를 기록했으며 무작위 표본 1,000개에서 FSM 방식과의 출력 동등성도 확인했지만, 후보 밖 문자열을 막을 뿐 모델이 의미상 정답 후보를 고르게 보장하지는 않습니다(2026년 8월 15일 기준 원문 PDF·TeX만 공개되고 실행 코드 링크는 출판 시 공개 예정이어서 원문 측정값을 교차 검토했습니다).

다메카솔의 해석: 어디까지 적용할 수 있나

이 연구의 직접 적용 범위는 평평한 대규모 유한 집합입니다. 설계 원칙으로 옮기면 선택지가 크고 접두사를 공유하며 같은 목록으로 많은 요청을 반복 처리할 때만 트라이 전용 경로를 쓰고, 작은 일회성 목록에는 컴파일이 빠른 일반 엔진을, 중첩 객체·숫자 범위·조건부 필드가 섞인 구조에는 범용 엔진이나 큰 enum 하위 구조만 트라이로 빼내는 혼합 경로를 쓰는 편이 합리적입니다. 실제 운영에 도입할 때는 스키마 컴파일 시간, 디코딩 단계 마스크 시간, 종단 간(end-to-end) 서비스 처리량을 반드시 분리해서 측정해야 합니다.
