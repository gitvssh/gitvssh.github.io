AI는 자기 코드를 어떻게 알아볼까

이 글에서 얻는 것

Style, Not Self 논문으로 AI의 코드 작성자 판별이 길이와 주석에 얼마나 기대는지 살펴봅니다. 공개 판정 기록 재집계와 4장 만화로 정규화 효과와 익명화의 한계를 구분합니다.

코드 작성자를 잘 맞히는 AI도 실제로는 코드 길이와 주석 스타일에 기대고 있을 수 있습니다. 코드 리뷰나 평가를 모델에 맡긴다면 꽤 신경 쓰이는 결과인데요. 「Style, Not Self」의 저자들은 추가 학습 없이 코드 작성자를 묻는 실험에서 모델의 판별 정확도를 단순한 ‘길이 비교 규칙’과 대조했습니다. 주석과 변수명 같은 표면 단서를 걷어 내자 여러 제로샷 판별 결과는 우연 수준에 가까워졌지만, 별도로 학습한 분류기는 여전히 남은 흔적을 읽어 냈습니다.

글·해설: 다메카솔

핵심 내용

  • 단순 길이 규칙과의 대조: MBPP 유효 코드 238쌍에서 GPT-5가 자기 코드와 Grok 4 Fast의 코드를 구분한 정확도는 **81.9%(195/238)**였지만, 단순히 **더 긴 코드를 고르는 규칙은 97.5%(232/238)**를 맞혔습니다.
  • AST 정규화 전후의 변화: 주석·독스트링·타입 힌트를 지우고 지역 변수명을 통일한 뒤(유효 210쌍)에는 긴 코드 규칙이 여전히 85.2%(179/210)를 맞혔음에도 GPT-5의 자기 코드 판별률은 **45.2%(95/210)**로 떨어졌습니다.
  • 단일 코드 판별과 문자 패턴 분류기: 코드 1개만 보여 주는 시험(15개 조합 균형 정확도 49.4~58.2%)과 12개 정규화 쌍 비교(Holm 보정 후 10개 비유의)에서 제로샷 모델 판별은 크게 약해졌으나, 별도로 학습한 문자 패턴 분류기는 정규화 후에도 모델 쌍을 구분해 완전한 익명화는 아님을 보여 주었습니다.

같은 문제에 더 단순한 판정기를 세워 봅니다

GPT-5가 자기 코드와 Grok 4 Fast의 코드를 구분한 정확도 81.9%만 따로 떼어 보면 모델이 자기만의 논리 구조를 꽤 잘 알아보는 것처럼 보입니다. 그런데 같은 MBPP 유효 코드 238쌍(빈 코드·동일 코드·응답 형식 오류 제외)에서 **무조건 더 긴 코드를 고르는 단순 규칙은 97.5%(232/238)**를 기록했습니다. (원문 4.2절·표 3)

저자들은 GPT-5, Claude Haiku 4.5, Gemini 2.5 Flash, Grok 4 Fast, DeepSeek-V3-0324 다섯 모델을 중심으로 MBPP(257문제, 쌍 비교 수행), HumanEval(164문제), DS-1000 Pandas 부분집합(150문제) 위에서 네 가지 과제(쌍 비교에서 자기 코드 고르기, 단일 코드가 자기 것인지 답하기, 특정 모델 코드 찾기, 작성자를 가린 품질 평가)를 나누어 시험했습니다. 복잡한 판정기가 높은 점수를 받더라도 코드 길이나 주석 유무 같은 단순 규칙(해당 데이터셋에서 확인한 진단용 대조군)이 같은 점수를 낸다면, 그 점수를 곧바로 깊은 자기 인식 능력으로 해석하기 어렵다는 점이 선명하게 드러납니다.

주석과 이름을 정리하면 무엇이 바뀔까요

그렇다면 코드의 겉모습을 정돈하면 어떻게 될까요? 저자들은 구문 트리(AST) 기반 정규화로 주석, 문서 문자열(docstring), 타입 힌트를 제거하고 지역 식별자 이름을 일관되게 바꿨습니다(MBPP 시험에서 주요 5개 모델의 개별 문제 테스트 통과 여부는 정규화 후에도 그대로 유지됐습니다). (3.4절·4.5절)

GPT-5 대 Grok 4 Fast (MBPP 쌍 비교) 원본 코드 AST 정규화 후
분석에 포함한 유효 판정 238쌍 210쌍 (정규화 후 동일해진 27쌍·요청 실패 1건 제외)
GPT-5 자기 코드 판별 195 / 238 (81.9%) 95 / 210 (45.2%)
더 긴 코드를 고르는 규칙 232 / 238 (97.5%) 179 / 210 (85.2%)

참고: 공개된 원시 판정 기록에서 위 두 행의 정답 수와 길이 규칙 수치를 직접 다시 집계해 일치를 확인했습니다.

정규화 뒤에도 두 모델 코드 사이의 길이 차이(긴 코드 규칙 85.2%)는 상당 부분 남아 있었지만, 정작 GPT-5의 판별 정확도는 81.9%에서 45.2%로 크게 떨어졌습니다. 이는 모델이 순수한 코드 길이라기보다 길이와 함께 따라다니던 주석·문서화 습관에 크게 기대고 있었을 가능성을 시사합니다. 더 넓은 12개 정규화 쌍 재평가에서도 10개 조합은 43.6~57.8% 구간에 머물러 다중비교(Holm) 보정 뒤 통계적으로 유의하지 않았고, 나머지 2개 조합은 우연 수준보다 오히려 낮았습니다(신뢰구간이 넓어 작은 효과의 존재까지 완전히 배제하는 결과는 아닙니다).

늘 같은 대답으로도 올라가는 명목 정답률과 순서 편향

코드 한 편만 보여 주고 “네가 쓴 코드인가?”라고 묻는 시험에서는 모델의 응답 성향도 걸러 내야 합니다. 전체 보기 중 자기 코드가 약 3분의 1이고 남의 코드가 3분의 2라면, 무조건 “내 코드가 아니다”라고만 답해도 명목 정답률이 66.7%가 나오기 때문입니다. 자기 코드를 맞힌 비율과 남의 코드를 부인한 비율을 같은 비중으로 평균 낸 **균형 정확도(balanced accuracy)**로 다시 보면 15개 모델·문제군 조합은 49.4~58.2% 수준이었습니다(보정 후 Grok의 두 조합만 유의). (4.3절·표 12)

또한 초기 실험에서는 프롬프트에 모델 이름을 나열한 순서와 보기 코드의 순서가 맞물려 86~99%라는 높은 점수가 나왔다가, 이름 순서를 코드 위치와 독립적으로 무작위화하자 그 착시가 사라졌습니다. 평가 문항을 설계할 때 내용 바깥의 위치·순서 단서를 왜 점검해야 하는지 잘 보여 주는 사례입니다.

다메카솔의 해석: 작성 이력과 품질 증거를 따로 보관합니다

주석과 변수명을 걷어 내면 제로샷 LLM 판정기는 헷갈려 하지만, 코드 안의 모든 흔적이 사라지는 것은 아닙니다. 저자들이 별도로 학습시킨 문자 패턴 분류기는 정규화된 코드에서도 여러 모델 쌍을 높은 정확도로 구분해 냈으므로, AST 정규화를 완전한 코드 익명화나 워터마크 제거 수단으로 여겨서는 안 됩니다.

실무 코드 리뷰나 에이전트 파이프라인을 설계할 때는 작성 출처(provenance)는 생성 시점의 시스템 메타데이터(모델 버전·요청 ID)로 남기고, 코드 품질은 ExecCritic의 독립 테스트 생성 연구처럼 실행 가능한 테스트와 정적 분석 증거로 판정해야 합니다. 주석이 자세하고 길이가 긴 스타일을 보고 평가 모델이 후한 점수를 주거나 작성자를 추측하게 두면, 겉모습과 실제 동작 품질이 뒤섞이기 때문입니다(이번 연구는 짧은 Python 코드와 기본 추론 설정의 제로샷 판별을 다루었으므로, 대규모 다중 파일 저장소나 미세조정된 감시 모델은 별도 검증이 필요합니다).
