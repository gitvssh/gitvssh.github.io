kubectl drain이 멈췄을 때 PDB를 우회하기 전에 확인할 것

이 글에서 얻는 것

글·해설: 다메카솔

kubectl drain이 같은 파드 이름을 반복해 출력하며 멈춰 서면 강력한 강제 옵션부터 붙이고 싶어집니다. 하지만 멈춘 이유를 네 갈래로 먼저 나누어 보면 필요한 옵션과 감수해야 할 위험이 분명해집니다. 이름은 비슷하게 거칠어 보여도 --force와 --disable-eviction은 서로 전혀 다른 보호 장치를 건드립니다.

핵심 내용

  • drain의 진행 단계 구분: 시작 전에 거부되면 DaemonSet·단독 파드(unmanaged Pod)·emptyDir 같은 사전 조건 문제이고, evicting pod에서 멈춰 기다린다면 PDB·대체 파드 준비·종료 유예(graceful termination) 문제입니다.
  • 강제 옵션의 역할 차이: --force는 컨트롤러 없는 파드 삭제를 허용할 뿐 PDB를 우회하지 않으며, --disable-eviction이 eviction API 대신 delete를 호출해 PDB 가용성 검사를 건너뜁니다.
  • 우회 전 점검 순서: 파드 소유자 → PDB disruptionsAllowed → 대체 replica Ready 여부 → emptyDir 및 종료 유예 시간을 차례로 확인한 뒤 필요한 옵션 하나만 선택해야 합니다.

drain이 하는 일과 네 갈래 원인 진단

drain은 노드를 unschedulable로 표시해 새 파드 유입을 막고, 기존 파드를 eviction API(또는 delete)로 내보낸 뒤 정상 종료(graceful termination)가 끝날 때까지 기다리는 유지보수 절차입니다. 작업이 끝나면 kubectl uncordon으로 스케줄 가능 상태를 되돌려야 합니다.

kubectl drain <node> --ignore-daemonsets
# 유지보수 수행
kubectl uncordon <node>

명령이 멈췄을 때는 다음 네 갈래로 원인을 좁힙니다.

  1. 이 파드는 누가 관리하는가 (--ignore-daemonsets, --force): 노드마다 뜨는 DaemonSet 파드는 drain이 지우지 않으며 --ignore-daemonsets는 이를 건너뛰고 진행하라는 뜻입니다. 반면 ReplicaSet·StatefulSet·Job 같은 컨트롤러가 없는 단독 파드(unmanaged Pod)가 있으면 삭제 후 재생성할 주체가 없어 멈추는데, --force는 이 파드의 삭제를 허용합니다. 
    kubectl get pod <pod> -n <namespace> \
  -o jsonpath='{.metadata.ownerReferences[*].kind}'
  2. PDB가 지금 몇 개의 중단을 허용하는가: disruptionsAllowed가 0이면 eviction API는 대기하는 것이 정상입니다. 대체 replica가 아직 Ready가 되지 못했거나 정책 자체가 maxUnavailable: 0일 수 있으므로 라벨 선택자와 파드 상태를 함께 봅니다. 
    kubectl get pdb -A
kubectl describe pdb <pdb> -n <namespace>
  3. 노드 로컬 데이터(emptyDir)가 있는가 (--delete-emptydir-data): emptyDir을 쓰는 파드는 노드를 떠나면 그 내용을 잃습니다. PVC 데이터와는 별개이며, 단순 캐시인지 미처리 작업인지 확인한 뒤 플래그를 붙여야 합니다.
  4. 종료 유예가 길어지는 중인가: 파드가 이미 종료 신호를 받았다면 terminationGracePeriodSeconds, preStop 훅, 애플리케이션의 연결 정리·데이터 flush 로그를 확인해야 합니다(이 경우 PDB를 지워도 종료 시간은 줄지 않습니다).

force는 PDB 우회가 아닙니다

실무에서 가장 자주 헷갈리는 세 가지 강제 옵션의 차이는 다음과 같습니다.

옵션 해결하는 조건 건너뛰는 보호
--force 컨트롤러가 없는 unmanaged Pod 재생성 소유자가 없다는 경고
--disable-eviction eviction API 대신 delete 사용 PDB의 가용성 검사
--delete-emptydir-data emptyDir 데이터가 있는 Pod 노드 로컬 임시 데이터 보존

제 홈랩에서도 2026년 7월 drain이 vault-0 축출에서 멈췄을 때 원인은 단일 Vault를 가리킨 PDB의 maxUnavailable: 0이었습니다. --force를 붙여도 풀리지 않는 문제였고, 서비스 중단을 감수하며 PDB를 잠시 제거하거나 --disable-eviction을 써야 했습니다(이후 3노드·3멤버로 늘려 중단 여유를 확보했습니다).

우회 옵션을 쓰기 전에는 이 파드를 지우면 어떤 기능이 얼마나 멈추는지, 데이터는 어느 계층에서 복구되는지부터 확인하고 다음 순서대로 진행하는 편이 안전합니다.

대상 파드와 소유자 확인
→ PDB 선택자와 disruptionsAllowed 확인
→ 대체 replica의 Ready 및 배치 노드 확인
→ emptyDir와 종료 유예 확인
→ 예상 중단과 복구 절차 기록
→ 필요한 옵션 하나만 선택
→ 점검 후 uncordon과 워크로드 상태 확인

함께 읽을 글

  • PodDisruptionBudget는 무엇을 보장하나: maxUnavailable 0의 의미: disruptionsAllowed가 만들어지는 범위를 설명합니다.
  • replica 1은 같은 뜻이 아니었습니다: Vault PDB 앞에서 멈춘 drain: 이 체크리스트가 나온 실제 홈랩 사건입니다.

기술 해설

PodDisruptionBudget는 무엇을 보장하나: maxUnavailable 0의 의미

PDB가 자발적 eviction의 중단 예산을 어떻게 제한하는지, disruptionsAllowed 0과 비자발적 장애의 경계를 설명합니다.

기술 해설

애플리케이션 복제와 스토리지 복제는 무엇이 다른가

서비스 인스턴스 복제와 볼륨 블록 복제의 복구 주체를 나누고, 두 replica 수가 곱해질 때의 비용과 결정 순서를 설명합니다.

기술 해설

etcd 쿼럼은 왜 홀수 노드가 필요한가: 1·2·3·5멤버 장애 허용 계산

과반은 floor(n/2)+1, 장애 허용 수는 n에서 과반을 뺀 값입니다. 1·2·3·4·5멤버를 직접 계산해 홀수 구성이 유리한 이유와 멤버를 추가·교체할 때 생기는 위험을 짚습니다.
