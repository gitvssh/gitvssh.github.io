LLM은 왜 조건이 늘면 한꺼번에 무너질까

이 글에서 얻는 것

LLM이 여러 지시를 각각은 따르면서도 동시에 만족시키는 데 실패하는 이유와 단계별 결정적 검증 원칙을 살펴봅니다.

프롬프트에 조건을 몇 개 더 붙였을 뿐인데, 멀쩡하던 LLM 응답이 갑자기 형식을 어기거나 핵심 규칙을 빼먹는 일은 흔한 편입니다. 실제로 조건이 8개에 이르면 개별 조건은 평균 40.7%를 통과하는데도, 여덟 조건을 모두 만족한 응답은 5.7%에 그쳤습니다. **「Large Language Models Can Follow Instructions, But Not Many at Once」**는 LLM 심사자 대신 결정적 규칙 검사기를 쓰는 Constraint Saturation Evaluation (CSE)으로 제약 수에 따른 이 곱셈형 붕괴를 추적했습니다.

글·해설: 다메카솔

핵심 내용

  • 지표의 착시: 개별 평균 통과율(marginal CSR)은 완만히 내려가지만, 동시 통과율(strict CSR)은 k=8에서 5.7%까지 급락했습니다.
  • 곱셈형 실패 누적: 제약 간 쌍별 상관($\phi \approx 0.067$)보다 작은 실패 확률이 곱으로 누적되는 구조가 전체 붕괴를 키웠습니다.
  • 구조 제약의 유지 부담: 문단 수·문장 길이처럼 끝까지 추적해야 하는 제약은 단순 어휘 제약보다 기준 능력을 약 2배 빨리 잃었습니다.
  • 개입 한계와 설계 원칙: 계획·자기수정·재시도는 임계점을 크게 옮기지 못하므로, 작업을 단계로 쪼개 경계마다 결정적으로 검증해야 합니다.

하나씩 통과해도 전부 통과하는 것은 아닙니다

다중 제약 성능을 볼 때는 두 지표부터 구분해야 합니다. marginal CSR은 응답에 걸린 개별 제약의 평균 통과율이고, strict CSR은 모든 제약을 동시에 통과한 비율이죠. 제약이 하나일 때는 두 값이 같지만, 조건이 늘면 간격이 빠르게 벌어집니다.

가령 백엔드 API 응답을 생성할 때 JSON 스키마, 금지어 제외, 문단 수 제한, 안전 경계, 출처 표기라는 다섯 규칙을 한 프롬프트에 넣었다고 봅시다. 이 중 하나만 어겨도 시스템은 실패로 처리해야 하기 때문입니다. 저자들은 특정 제약 쌍의 충돌(평균 쌍별 실패 상관 $\phi \approx 0.067$)보다 각 제약의 작은 실패 확률이 곱으로 겹치면서 전체 성공률이 무너진다고 설명합니다.

CSE는 제약 수를 늘리고 규칙으로 판정했습니다

CSE는 절차적으로 제약 조합을 만들되 양립할 수 없는 조건은 호환성 검사기(compatibility checker)로 걸러냅니다. 만족 가능한 조합만 모델에 제시한 뒤 제약마다 작성된 결정적 함수로 통과 여부를 판정하는 셈이죠. 문자 금지·필수 단어 같은 국소 제약부터 문단 수·문장 길이·관계 순서·자기 단어 수 보고 같은 전역 제약까지 폭넓게 시험했습니다.

평가 대상 15개 모델, 8개 처리 차원 초록·방법 절 기준

규칙 기반 검사기는 판정기의 흔들림을 없애 주지만 분명한 범위 한계도 남깁니다. 문맥 일관성, 정보성, 어조, 사실 정확성처럼 의미 판단이 필요한 조건은 빠지고 모든 제약을 동시에 만족하는 논리곱(conjunction)만 측정하기 때문입니다. 또한 k=12는 극한 스트레스 구간이며, 논문은 실제 시스템이 보통 2~6개 고수준 제약과 암묵 규범을 결합한다고 설명합니다.

완만한 하락이 전체 응답에서는 절벽이 됩니다

실험에서 드러난 핵심은 개별 통과율과 동시 통과율의 큰 괴리입니다. 개별 조건은 제약이 늘어도 완만한 곡선으로 내려가지만, 프로브 전체를 통과하는 비율은 훨씬 앞선 구간에서 무너지거든요. 특히 문단 수나 문장 길이처럼 생성 내내 상태를 유지해야 하는 구조 제약은 어휘 제약보다 기준 능력을 약 2배 빨리 잃었습니다. 저자들은 이를 이해 부족이 아니라 끝까지 유지하지 못하는 comprehension-maintenance gap으로 해석합니다.

관찰 항목 측정 결과 및 조건 실무적 의미
개별 vs. 동시 통과율 개별 $72.0% \times 0.922^{(k-1)}$ (MAE 0.2%p), k=8에서 개별 40.7% vs. 동시 5.7% 35%p 격차로 평균 점수와 전체 성공률 괴리 확인
50% 성공 임계점 최강 모델도 k=7에서 50% 미만, 15개 중 12개는 k<=3에서 50% 미만 단일 프롬프트로 지킬 수 있는 규칙 폭이 좁음
생성 전 계획 3개 시험 모델에서 반감기 일관 개선 실패 (예산 분리 후 동일) 계획 지시만으로 붕괴 임계점이 이동하지 않음
사후 수정·best-of-5 임계점을 한두 제약 늦추는 수준 (동일 프로브 반복 실패) 단순 재시도는 독립 표본 기대치보다 이득이 작음

형식만 맞추는 우회 통과(specification gap) 문제도 함께 보고됐습니다. 모델이 빈 코드 블록을 넣거나 문장을 그대로 복사하고 유니코드 이스케이프를 쓰는 식으로 검사기만 통과한 사례가 확인됐기 때문입니다. 원문 프리프린트(arXiv v1)의 경우 초록에는 코드·데이터 공개가 적혀 있지만 부록 A는 출판 시 공개 예정이라고 밝혀, 2026년 8월 14일 기준 공식 아티팩트 URL은 확인되지 않은 상태입니다.

다메카솔의 해석

이 연구가 주는 실무 교훈은 분명합니다. 단일 프롬프트를 정교하게 늘리는 노력보다, 작업을 단계로 나누고 경계마다 결정적 검증 관문을 두는 편이 훨씬 안정적이거든요. 한 번의 호출에 출력 형식, 분량, 금지어, 근거 표기, 안전 규칙을 겹쳐 얹으면 개별 준수율은 높아 보여도 실제 서비스 응답은 높은 확률로 어딘가 빠지기 마련입니다.

실무 파이프라인에서는 다음 세 가지 원칙으로 역할을 나눠 볼 만합니다.

  1. 요구사항 단계 분리: 초안 생성, 형식 변환, 근거 검증을 별도 호출로 나누어 단계당 제약 수(k)를 낮춥니다.
  2. 경계별 fail-closed 검증: JSON 스키마, 허용값, 출처 URL 존재, 테스트 결과처럼 코드로 확인할 수 있는 조건을 즉시 검사해 실패 시 다음 단계를 막습니다.
  3. 안전 제약 별도 확인: 형식 조건에 밀려 안전 규칙이 누락되지 않도록 안전성 평가는 기능 파이프라인과 분리해 다시 점검합니다.
