AI 에이전트가 도구를 반복 호출하면 작업 기록이 금세 길어집니다. 그렇다고 앞부분을 지우거나 요약하면 뒤쪽 계산 상태까지 다시 만들어야 해서 오히려 손해일 수 있죠. 「Cache Engineering for Agents」는 원문은 유지한 채 다음 계산에 참여할 KV 캐시만 고르는 방법과 AKV 서빙 시스템을 제안합니다.

글·해설: 다메카솔

## 기록을 줄였는데 왜 다시 계산할까

KV 캐시는 모델이 앞선 토큰을 읽어 만든 키(Key)·값(Value) 중간 상태로, 사람이 읽는 대화·도구 원문과 구분됩니다. 뒤쪽 토큰 상태는 앞쪽 문맥에 기대어 계산되므로 앞부분을 지우거나 요약하면 남은 뒷부분을 다시 계산(re-prefill)해야 하죠. 너무 자주 줄이면 재계산 비용이 커지고, 드물게 크게 줄이면 필요한 중간 단서까지 놓치기 쉽습니다.

![원문 편집 후 재계산하는 경로와 활성 캐시만 제외하는 경로를 비교한다](./page-01.webp)

AKV는 원문을 건드리지 않고 다음 토큰을 계산할 때 참조할 활성(active) KV 범위에서만 오래된 항목을 빼고 남은 상태를 재계산 없이 그대로 씁니다. 여기서 '활성'은 GPU 물리 메모리 잔류 여부가 아니라 이후 attention 계산에 참여하는 범위를 뜻합니다.

## 제외, 재배치, 추가를 나눠 다룬다

논문은 캐시 제어를 세 연산으로 정리합니다.

| 연산 | 하는 일 | 구분할 점 |
| --- | --- | --- |
| `append` | 활성 캐시를 참조해 새 토큰을 계산·추가 | 앞선 참조 상태가 새 상태에 반영 |
| `drop` | 선택한 KV를 이후 attention에서 제외 | 남은 항목의 내부 값과 위치 번호 유지 |
| `repos` | 남은 키의 RoPE 위치를 순서대로 재배치 | 값과 기존 내부 상태는 재계산 없이 유지 |

`drop`만 반복하면 읽는 캐시 항목은 줄어도 위치 번호는 계속 커지므로 `repos`로 위치를 따로 당겨 줍니다. 한편 어떤 정보를 직접 참조에서 빼더라도 그 정보를 이미 참고해 계산한 뒤쪽 상태에는 영향이 남고 원문도 그대로 유지됩니다. 이 때문에 `drop`을 개인정보 삭제나 학습 취소 수단으로 쓰기는 어렵습니다.

## 같은 글이 남아도 같은 캐시는 아니다

최종 문맥이 같다고 캐시까지 공유할 수 있을까요? 예를 들어 기록에 A, B, C가 순서대로 쌓였을 때, A를 참조하며 C를 계산한 뒤 A를 뺀 경로와 A를 먼저 뺀 뒤 C를 계산한 경로는 마지막에 남는 B·C가 같아도 C가 참고한 이력이 다릅니다.

![이전 정보를 참조한 뒤 제외하는 경우와 제외한 뒤 계산하는 경우의 차이](./page-02.webp)

이 때문에 텍스트 접두부나 최종 위치만 보고 캐시를 공유하면 엉뚱한 상태를 재사용할 위험이 큽니다. AKV는 요청에 텍스트와 연산 순서를 함께 담아 서버의 확장 radix tree에 연산 이력을 기록하죠. 한 요청이 `drop`해도 다른 요청이 쓰는 상태는 보존하고, 메모리 압박으로 빠진 상태는 과거 참조 범위와 위치를 반영하는 segment-batch attention으로 단일 prefill 안에서 복원하므로 직접 재사용과 복원 계산은 별개 비용입니다.

## 평균 개선과 개별 과제의 차이

저자들은 세 추론 모델과 네 벤치마크로 AKV를 기존 요약 방식과 비교했습니다.

- **평가 대상**: `MiniMax-M2.7`·`MiroThinker-1.7-Mini`(thinking), `GPT-OSS-120B`(high reasoning effort) / `BrowseComp-Plus`, `GAIA-Text`(103과제), `SWE-bench Verified`(500과제·첫 100과제 분석), `xbench-DeepSearch-2510`
- **비교 정책**: `AKV`(최근 도구 응답 12개·추론 KV 유지, 위치 재배치는 Standard 기준) vs `Standard`(`GPT-OSS`·`MiniMax` 96K, `MiroThinker` 192K 요약) vs `Text Engineering`(48K 요약)

다음 표는 원문 Table 1의 네 벤치마크 평균 결과입니다.

| 모델 | 평균 점수 (%, Standard → AKV) | 환산 비용 (센트, Standard → AKV) |
| --- | --- | --- |
| MiniMax-M2.7 | 52.4 → 53.7 | 5.0 → 4.4 |
| GPT-OSS-120B | 51.0 → 53.1 | 11.2 → 7.3 |
| MiroThinker-1.7-Mini | 44.1 → 45.8 | 20.4 → 14.8 |

세 모델 모두 평균 점수와 환산 비용이 개선됐습니다. 다만 네 벤치마크 평균을 다시 평균낸 수치라 전체 과제 합산 성공률로 보기는 어렵고, 반올림 표 수치만으로 통계적 유의성을 단정하기도 이르죠. 개별 항목에는 점수가 내려가거나 비용이 늘어난 반례도 섞여 있습니다.

- **개별 반례**: `MiniMax` SWE 75.2 → 74.4점, `GPT-OSS` xbench 38.5 → 37.5점, `MiroThinker` GAIA 비용 9.2 → 9.5센트

비용은 모델별 고정 토큰 단가로 주 생성·요약 호출과 `repos`(cache-hit 단가)를 합산한 API 추정치입니다. 같은 모델 안의 비교에는 동일 단가를 쓰지만, GPU 운영비나 검색·도구·채점 비용까지 합산한 서비스 총비용이나 현행 상용 요금표와는 별개입니다.

## 속도 수치에는 장비와 재생 조건이 붙는다

서빙 속도는 `GPT-OSS-120B`(BF16)를 별도 클러스터에 올려 측정했습니다.

| 항목 | 측정 조건 및 결과 |
| --- | --- |
| 장비·스택 | `SGLang 0.5.20`, `A800 80GB` GPU 8대(`prefill` 4 · `decode` 4) |
| 최고 처리량 비교 | `Standard` 동시성 12 vs `AKV` 동시성 14 (출력 313 → 369 token/s, 1.18배) |
| P95 요청 지연 | 43.16초 → 28.49초 (1.51배 단축) |
| 재생·측정 창 | `SWE-bench` 긴 문맥 80과제 궤적 재생(도구 미실행) · `AKV`(14·16) 30과제 완료 창 vs `Standard` 1시간 컷오프 |

대표 비교는 동일 동시성이 아니라 각 방식이 최고 처리량을 낸 설정을 비교한 결과입니다. 정책별 궤적을 재생해 턴 수와 출력 길이 조건이 다르고, 저장된 도구 응답을 재사용해 실제 도구를 다시 실행하지 않았거든요. 고동시성 종료 기준도 엇갈렸고 별도 첫 100과제 온라인 실행과도 환경이 달라 두 지연 수치를 합쳐 읽지 않는 편이 정확합니다.

## 다메카솔의 해석

캐시를 설계할 때는 '무엇을 버릴까'만큼 **'남긴 상태가 무엇을 보고 계산됐는가'**를 함께 따져야 합니다. [ContextRender의 실행 결과 재사용](/posts/contextrender-execution-reuse/)이 작업 산출물 재사용을 다뤘다면, AKV는 모델 내부 attention 범위의 연산 이력을 캐시 키에 담아 재사용 단위를 분명히 하죠.

도입을 검토한다면 품질·환산 비용·실제 지연을 따로 재고, 오래된 도구 결과를 뺀 뒤 근거 활용과 축출 후 복원 정확성을 먼저 확인해야 합니다. 또한 이 연구는 사전공개본(`v1`)이며 공개 코드 README(`drop_message`·`reposition`)와 논문 예시(`cache` 하위 필드)의 형식이 달라, 실제 적용에는 해당 연산을 구현한 서빙 환경과 버전 확인이 필요합니다.
