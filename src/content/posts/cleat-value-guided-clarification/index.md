글·해설: 다메카솔

**확인 질문은 답을 들은 뒤 에이전트의 다음 선택이 달라질 때 비로소 가치가 생깁니다.** 사소한 취향까지 일일이 물으면 작업 흐름이 끊기고, 반대로 질문을 아예 줄이면 핵심 요구사항을 놓치기 쉬워서 개발자는 늘 그 경계를 고민하게 되죠.

CLEAT 연구진은 현재 에이전트가 평소대로 이어 간 결과와 특정 질문을 먼저 던진 뒤의 결과를 나란히 비교해, **그 질문이 실제로 더해 주는 이득**을 학습하는 방식을 제안했습니다.

## 핵심 내용

- **잔여 질문 가치(RQV)**: 같은 대화 이력에서 특정 정보를 먼저 물은 뒤 얻은 기대 효용과, 현재 에이전트가 원래대로 진행해 얻은 기대 효용의 차이를 계산합니다.
- **질문 판단과 수행 정책의 공동 학습**: 같은 비교 실행 결과로 질문 가치 예측기와 과제 수행 정책을 함께 갱신하되, 추론 시점에는 예측 RQV가 양수이면서 가장 높은 질문만 선택합니다.
- **최종 정답률과 요구사항 완전 해결률의 차이**: 모의 사용자 평가에서 평균 점수가 올랐지만, AskMind 기준 최종 답 정확도(48.37%)와 모든 요구점을 해결한 과제 비율(34.87%) 사이에는 여전히 간격이 남았습니다.

가령 보고서를 작성하는 에이전트에게 표 색상 취향을 더 알려 주더라도 전달 형식 자체는 그대로일 수 있습니다. 반면 사용자가 자동 집계용 데이터 파일을 원하는지, 사람이 바로 읽을 요약 문서를 원하는지에 따라서는 만들어야 할 결과물이 완전히 달라지죠(표지의 보고서 장면은 이 차이를 보여 주려고 구성한 가상 예시입니다).

저는 단순히 질문 횟수를 줄이자는 목표보다, **어떤 답변이 실제 작업 선택을 바꾸는지부터 따져 보자**는 접근에 눈이 갔습니다. [CLEAT 원문 §1–3](https://arxiv.org/html/2610.12655v1#S1)

## 평소대로 진행했을 때와 무엇이 달라졌나

![같은 대화에서 평소대로 이어 간 결과와 특정 질문 뒤 이어 간 결과를 비교하는 두 갈래](./page-01.webp)

비교하는 방식은 직관적입니다. 저자들은 학습 과정에서 동일한 대화 이력과 사용자 목표를 두고 두 갈래를 실행했습니다.

- **기본 진행(PASS)**: 현재 에이전트 정책이 평소대로 작업을 이어 감
- **선제 질문**: 특정 정보를 먼저 질문해 답을 들은 뒤 작업을 이어 감

이 두 갈래의 평균 과제 효용 차이가 바로 **잔여 질문 가치, RQV(Residual Query Value)**의 학습 목표가 됩니다(비교하는 동안 에이전트 정책은 고정하며, 벤치마크에 정해진 상호작용 비용이 있으면 효용 계산에 함께 반영합니다). [원문 §3.1–3.2](https://arxiv.org/html/2610.12655v1#S3)

여기서 주의할 점은 `PASS`가 ‘질문 전면 금지’를 뜻하지 않는다는 사실입니다. 과제 수행을 현재 에이전트에게 그대로 맡긴다는 뜻이어서, 그 에이전트가 이후 단계에서 스스로 질문할 수도 있습니다. 따라서 RQV는 질문을 전혀 못 하는 모델과의 비교가 아니라, **현재 에이전트의 기본 행동에 지금 이 질문을 먼저 덧붙였을 때 생기는 추가 이득**을 가리킵니다.

결국 질문의 가치는 에이전트가 그 답을 얼마나 잘 활용하느냐에 좌우됩니다. 꼭 필요한 정보를 들어도 이후 단계에서 무시하거나 잘못 적용하면 결과가 나빠질 수 있고, 반대로 이미 스스로 잘 물어보는 에이전트에게 같은 질문을 앞단에 강제하면 추가 이득이 작아지거든요. “아직 모르는 정보가 남았는가”에 더해 **“지금 이 에이전트가 그 답을 받아 실제 행동에 반영할 수 있는가”**까지 함께 살피는 이유입니다.

## 질문 판단과 과제 수행을 함께 학습한다

![실행 결과로 과제 수행과 질문 가치 판단을 함께 갱신하는 학습 과정](./page-02.webp)

그렇다면 에이전트 모델이 학습을 거쳐 점점 똑똑해진 뒤에도 예전에 계산해 둔 질문 점수를 그대로 써도 될까요?

CLEAT는 비교 실행에서 얻은 결과로 **질문 가치를 예측하는 컨트롤러**와 **실제 과제를 수행하는 정책**을 함께 학습합니다. 정책이 업데이트되면 새로 얻은 비교 실행 결과로 질문 가치 예측기도 다시 갱신하고, 마지막에는 최종 정책을 고정한 상태에서 질문 판단 부분을 한 번 더 다듬습니다. [원문 §3.2–3.5·부록 B](https://arxiv.org/pdf/2610.12655v1)

이때 예측 점수와 학습 보상의 역할은 명확히 나뉩니다.

- **질문 가치 예측값**: 학습 중 어떤 비교 갈래를 우선 수집할지 안내하고, 특정 질문을 자주 뽑으면서 생기는 샘플링 편향은 별도 보정 절차로 맞춤
- **과제 수행 정책**: 예측 점수를 보상에 더하지 않고, 실제로 관측한 과제 결과에서 직접 학습함

실제 추론(사용) 시점에는 매번 두 갈래의 미래를 돌려 보지 않습니다. 고정된 후보 생성기가 내놓은 질문 후보들 가운데 예측 RQV가 가장 높고 양수(`> 0`)인 대상을 골라 묻고, 만약 `PASS`가 선택되면 컨트롤러 개입을 끝낸 뒤 과제 정책에 이후 진행을 맡깁니다. 학습할 때의 비교 실행과 실행 시점의 가벼운 예측을 구분해 두어야 전체 비용 구조가 이해됩니다.

## 점수는 올랐지만, 지표의 뜻은 다르다

![완성된 답과 남은 요구사항을 구분하며 실제 사용자 평가를 생각하는 카솔](./page-03.webp)

저자들은 Qwen3-4B를 기반으로 4개 벤치마크의 10개 설정을 비교했습니다(3개 시드의 평균과 표준편차 보고). 사용자 모사와 모델 기반 채점에는 Qwen3-30B-A3B를 사용했으며, 같은 벤치마크 안에서는 동일한 평가 분할과 대화 턴 제한을 적용하되 학습 목적과 최적화 설정은 각 방법의 구성을 따랐습니다(**실제 사람 사용자를 모집한 실험은 아닙니다**). [표 1·부록 C](https://arxiv.org/pdf/2610.12655v1)

아래 표는 10개 설정 가운데 지표의 성격이 뚜렷이 다른 두 가지를 추린 **저자 보고치**입니다(SFT는 해당 열에서 평균이 가장 높았던 비교 방법이며, `±`는 3개 시드의 표준편차입니다).

| 평가 지표 | SFT | CLEAT | 평균 차이 |
| --- | ---: | ---: | ---: |
| UserGym Travel 점수 | 50.48 ± 1.76 | 63.72 ± 0.48 | +13.24점 |
| IN3 정보부족 판단 정확도 | 77.47 ± 5.26% | 83.95 ± 1.42% | +6.48%p |

UserGym Travel에서 13점 넘게 차이가 벌어진 점은 눈에 띕니다. 이 점수는 8개 여행 환경에서 선호 파악·검색·최종 추천 등에 주어지는 보상을 집계해 100배 한 값이어서, 실제 항공권이나 숙소 예약 성공률이 63.72%라는 뜻으로 읽으면 곤란합니다. 마찬가지로 IN3의 판단 정확도는 에이전트가 질문했는지를 정보부족 정답 라벨과 대조한 값이라, 누락된 조건을 실제로 얼마나 되찾았는지와는 구별해야 합니다. [원문 §4.1–4.2·부록 C.1](https://arxiv.org/pdf/2610.12655v1)

CLEAT는 10개 설정 모두에서 가장 높은 평균 점수를 보고했지만, 표의 평균 순위와 모든 비교 쌍에 대한 통계적 유의성 검증은 구분해 읽어야 합니다(이 글에서는 학습이나 평가를 다시 실행하지 않았으며 원문 보고치를 기준으로 설명합니다).

특히 AskMind 벤치마크의 두 지표를 나란히 놓고 보면 실무적으로 중요한 차이가 드러납니다. [그림 4·표 7·부록 C.1](https://arxiv.org/pdf/2610.12655v1)

| CLEAT의 AskMind 지표 | 저자 보고 평균 ± 표준편차 |
| --- | ---: |
| 최종 답의 정확도 | 48.37 ± 2.66% |
| 모든 요구점을 해결한 과제의 비율 | 34.87 ± 2.20% |

최종 답이 정답으로 채점된 사례 안에도 아직 해결하지 못한 세부 조건이 남아 있을 수 있다는 뜻입니다. 두 번째 지표는 개별 조건의 평균 회복률이 아니라 **필요한 요구점을 빠짐없이 해결한 과제의 비율**인데요. 최종 답의 정오만 집계하면 사용자가 왜 답을 받고도 조건을 다시 설명해야 했는지 놓치기 쉬워서, 에이전트 평가 화면에 두 지표를 함께 띄워 둘 가치가 충분합니다.

## 실제 사용자에게 옮기기 전에 남은 조건

이 학습 방식을 실제 서비스에 바로 옮기려면 몇 가지 구조적 전제를 먼저 짚어 봐야 합니다. [원문 §6](https://arxiv.org/html/2610.12655v1#S6)

- **반복 실행 가정의 한계**: 똑같은 대화 이력과 사용자 목표에서 여러 갈래를 반복 실행해 비교하는 학습 가정은 실제 사람과의 실시간 대화에서는 그대로 쓰기 어렵습니다.
- **고정된 질문 생성기**: 질문 후보와 문장 표현을 만드는 모듈이 고정되어 있어, 컨트롤러가 고를 수 있는 질문의 범위도 그 후보 풀 안으로 제한됩니다.
- **변하는 사용자 목표**: 대화 도중 마음이 바뀌는 실제 사용자 환경에서의 효과는 후속 과제로 남아 있습니다.

또한 2026년 10월 14일 확인한 논문과 arXiv 메타데이터에는 별도의 저자 프로젝트 페이지나 공식 코드·데이터 링크가 없었고, 제목·저자 검색에서도 공개 저장소를 찾지 못했습니다. 당장 패키지를 설치해 같은 성능을 재현하는 도구보다는, 질문 가치를 정의하고 평가하는 설계 방법론으로 읽는 편이 알맞습니다.

## 다메카솔의 해석: 질문 뒤의 결정을 기록하자

제가 현업에서 에이전트 모델을 교체하거나 프롬프트를 손본다면, **확인 질문의 변화도 회귀 테스트 항목**으로 넣겠습니다.

같은 요청에서 어떤 정보가 부족하다고 판단했는지, 사용자 답을 들은 뒤 도구 선택이나 출력 형식이 실제로 어떻게 달라졌는지, 그리고 숨은 요구사항을 끝까지 채웠는지를 한 묶음으로 비교하는 식입니다(이는 논문 구조에서 착안한 제 엔지니어링 해석이며, 이번 연구가 실서비스 비용 절감이나 사용자 만족도 개선까지 실증했다는 뜻은 아닙니다).

이를 위해 로그에 남길 단위도 질문과 답변 텍스트 두 줄보다 넓게 잡고 싶습니다.

- 질문하기 직전에 에이전트가 고려하던 선택지
- 적용한 모델·프롬프트·도구 버전
- 답변을 반영해 내려진 최종 결정과 요구사항 충족 결과

이렇게 판단 맥락을 연결해 두면 나중에 모델을 바꿨을 때 왜 특정 질문의 가치가 달라졌는지 역추적하기가 훨씬 수월해집니다. 앞서 소개한 [판단 맥락을 보존하는 Workflow as Knowledge](/posts/workflow-as-knowledge/)와도 자연스럽게 이어지는 지점이죠.

물론 **필수 승인과 보안 권한 확인은 질문 효용 계산과 별개의 규칙으로 강제**해야 합니다. 모델이 추정한 질문 효용이 낮다고 해서 삭제·결제·외부 전송 같은 민감한 작업을 묻지 않고 실행할 권한이 생기지는 않으니까요. 여러 외부 서비스를 엮어 쓸 때는 [도구 연결 사이의 안전 경계](/posts/x-agentred-cross-service-risk/)도 함께 챙겨야 합니다.

결국 제가 잡고 싶은 기준은 명확합니다. **사용자의 시간을 빌리는 질문에는 실제로 달라진 작업 결정으로 보답하고, 성적표에는 최종 정답률과 요구사항 완전 회복률을 나란히 남기는 것**입니다.
