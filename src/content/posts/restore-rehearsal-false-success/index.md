복원 잡(Job)은 종료코드 0으로 끝났고, 마지막 로그 줄도 정합성 검증을 통과했다고 알렸습니다. 그런데 정작 복구 목표 시각 **이전**에 심어 두었던 마커 데이터 하나가 복원본 데이터베이스에서 빠져 있었거든요. 백업 파일이 있어도 시점 복구(Point-in-Time Recovery)가 실제로 작동하는지 확인하지 않으면 이런 '거짓 성공'을 그대로 믿고 넘어가기 쉽습니다.

글·해설: 다메카솔

2026년 7월 10일, 차세대 선불결제 플랫폼의 내부 오픈을 앞두고 첫 시점 복구 리허설을 진행했습니다. 단일 노드 개발 클러스터에 GitOps 배포 루프를 세운 뒤, 운영 DB가 아닌 별도의 복원 전용 인스턴스로 목표 시각 복구를 시험했습니다.

## 핵심 내용

- **거짓 성공 현상**: 복원 잡이 종료코드 0과 정합성 통과를 기록했지만, 일 1회 논리 백업 이후~목표 시각 사이의 두 번째 마커가 누락되었습니다.
- **두 겹의 원인**: MySQL 8.0.34 최소 이미지(Oracle Linux 변형)에 `mysqlbinlog`가 없었고, `sh -e` 파이프라인(`|`)에서 왼쪽 실패(127)가 오른쪽 `mysql`의 정상 종료(0)에 가려졌습니다.
- **해결 및 검증**: Debian 변형 이미지로 바꾸고 `command -v` 검사와 중간 파일(`/tmp/binlog-replay.sql`) 2단계 적재로 분리했습니다. 재검증에서 목표 이전 마커 2개 복원·이후 1개 제외, 정합성 위반 0건, 38초를 확인했습니다.

## 리허설이 판정하려던 것

백업 파일이 잘 쌓이는지는 이미 확인된 상태였습니다. 이번 리허설의 핵심 질문은 **일 1회 논리 백업(full dump)과 15분 주기 binlog 보관 체계만으로 원하는 시각까지 되돌릴 수 있는가**였거든요. 선불결제는 잔액과 원장이 함께 맞아야 하는 도메인이라, 잡이 오류 없이 끝났다는 보고만으로는 데이터 가용성을 장담하기 어렵습니다.

예를 들어 자정 전체 백업 뒤 낮 결제 기록을 살리려 오후 시각을 복구 목표로 잡았는데 binlog 재생이 빠졌다면 어떨까요? 성공 로그가 뜨더라도 반나절 동안의 원장 거래가 통째로 사라진 채 서비스가 올라오는 셈이죠.

그래서 성공 로그 대신 데이터 자체로 판정 기준을 세웠습니다. 목표 시각 **이전**에 두 번(전체 백업 전 1회, 백업 후~목표 전 1회), **이후**에 한 번 식별 마커를 심었습니다. 복구가 정상이라면 앞의 두 마커만 살아남아야 합니다.

![시간축에 놓인 마커 세 개 중 목표 시각 이전의 두 번째 마커 자리가 비어 있고, full dump 시점 이후 구간의 색이 빠져 있는 도식](./page-01.webp)

## 마커 하나가 비어 있었습니다

첫 실행 결과를 대조하자 목표 시각 이전의 두 번째 마커가 보이지 않았습니다. 목표 이후에 넣은 세 번째 마커가 빠진 것은 정상이었지만, 두 번째 마커는 반드시 살아 있어야 할 기록이었거든요. 그럼에도 잡은 실패를 남기지 않았고 정합성 검증 쿼리까지 통과했습니다.

복원본을 들여다보니 경계가 선명했습니다. 논리 백업 파일 시점까지의 기록만 들어 있고, 그 이후 구간은 통째로 비어 있었습니다. binlog 재생이 일부 깨진 게 아니라 첫 줄부터 실행되지 않은 상태였죠.

## 처음 의심한 시각 계산 가설과 방향의 모순

당시 복원 잡은 UTC 문자열을 파싱해 파일 시각과 완료 시각을 목표 시각과 대조하는 검사를 여러 겹 두고 있었습니다. 이 맥락으로 돌아보면, 처음에는 목표 시각과 백업 파일 시각의 경계 계산이 한 칸 어긋났을 가능성을 의심하게 됩니다.

하지만 그 가설이 맞다면 오류는 반대 방향으로 나타났어야 합니다. 목표 시각을 넘겨 재생해 **이후** 기록(세 번째 마커)이 남는 쪽이어야지, **이전** 기록(두 번째 마커)이 사라지는 쪽일 수는 없었기 때문이죠. 오차 방향이 어긋난다는 점을 확인한 뒤에야 binlog 재생 명령 자체를 점검했습니다.

## 셸은 파이프 오른쪽 끝만 봅니다

원인은 컨테이너 이미지 구성과 POSIX 셸 파이프라인 동작이 맞물린 두 겹의 문제였습니다.

첫째, 복원 잡이 쓰던 MySQL 8.0.34 기본 이미지(Oracle Linux 기반 축소 변형)에 `mysqlbinlog` 실행 파일이 빠져 있었습니다. 공식 이미지 문서에는 태그 변형별 클라이언트 도구 유무가 상세히 적혀 있지 않아 실행 시점에야 부재를 확인했습니다.

둘째, 도구가 없다면 즉시 멈춰야 정상인데 스크립트가 그대로 넘어갔습니다. 당시 스크립트는 MySQL 공식 매뉴얼 예시대로 `mysqlbinlog` 출력을 `mysql` 클라이언트로 파이프(`|`)하는 한 줄이었고, 잡의 셸은 `sh -e`로 돌고 있었거든요. POSIX 셸 규격에서 파이프라인의 종료 상태는 **가장 오른쪽 명령의 종료 상태**입니다. 왼쪽에서 `mysqlbinlog: not found`가 나도 오른쪽 `mysql`은 빈 표준 입력으로 정상 종료(종료코드 0)하고, `sh -e`는 이를 성공으로 간주해 다음 줄의 검증과 완료 로그까지 진행해 버립니다.

![왼쪽 관의 공구 걸이가 비어 아무것도 흐르지 않는데 오른쪽 관이 초록 신호를 켜고, 셸을 뜻하는 눈이 오른쪽 끝만 바라보는 배관 단면도](./page-02.webp)

이 동작은 데이터베이스 없이도 로컬 `dash`(2026년 8월 4일 재현)에서 그대로 재현됩니다.

```console
$ sh -ec 'mysqlbinlog --stop-datetime="2026-07-10 03:00:00" bin.000001 | cat > /tmp/replay.txt
> printf "다음 줄 도달, 파이프라인 상태=%s\n" "$?"
> printf "복원 입력 크기=%s바이트\n" "$(wc -c < /tmp/replay.txt)"
> printf "정합성 검증 통과\n"'
sh: 1: mysqlbinlog: not found
다음 줄 도달, 파이프라인 상태=0
복원 입력 크기=0바이트
정합성 검증 통과
$ echo $?
0
```

표준 오류에 `not found`가 찍혀도 스크립트 종료코드는 0입니다. 반면 파이프만 제거하면 같은 스크립트가 종료코드 127로 즉시 멈춥니다. `set -o pipefail`로 막을 수도 있지만 컨테이너 `/bin/sh`가 `dash`로 연결된 환경에서는 지원되지 않아(`bash`에서만 수용) 셸 종류에 무관한 구조적 분리가 필요했습니다.

물론 파이프 문법 자체를 잘못된 절차로 볼 필요는 없습니다. MySQL 공식 매뉴얼에서도 파이프를 표준 절차로 안내하며, 도구 존재 확인이나 `pipefail`, 복원 결과 대조 중 하나만 갖추었더라도 실패가 성공으로 보고될 일은 없었을 테니까요.

## 파이프를 끊고 관문을 세웠습니다

같은 날 두 겹의 결함을 함께 걷어냈습니다. 복원 잡 이미지를 클라이언트 도구가 모두 든 Debian 변형으로 바꾸고, 재생 전에 `command -v`로 도구 존재 여부를 먼저 검사하게 했으며, 파이프라인은 중간 파일을 거치는 두 단계로 나눴습니다.

```sh
command -v mysqlbinlog
mysqlbinlog --start-position="${start_pos}" \
  --stop-datetime="${target_utc}" "$@" > /tmp/binlog-replay.sql
mysql -h "${restore_host}" -uroot < /tmp/binlog-replay.sql
```

이 방식은 MySQL 공식 매뉴얼에서도 파이프 형태와 나란히 안내하는 표준 절차입니다. 두 줄로 나누어 실행하면 각 명령의 종료 상태가 독립 평가되므로 첫 줄 오류 시 `sh -e`가 즉시 스크립트를 멈추거든요.

![도구 확인 게이트를 지나 왼쪽 관이 중간 저장 용기에 내용을 붓고, 오른쪽 관이 그 용기에서 따로 끌어올리는 두 단계 배관 도식](./page-03.webp)

아울러 정합성 검증 쿼리 결과가 하나라도 0이 아니면 종료코드 1로 실패하도록 판정 관문을 강화하고, 리허설 최종 판정은 반드시 사전 마커와 복원본을 대조해 내리도록 고정했습니다.

| 리허설 측정 항목 | 실측 결과 | 비고 |
| --- | --- | --- |
| **시점 복구 (수정 후 재검증)** | **38초** (정합성 위반 0건) | 목표 시각 이전 마커 2개 복원, 이후 마커 1개 미포함 확인 |
| **배포 롤백 (서비스 복구)** | **16초** | 장애 선언부터 서비스 응답 복구까지 소요 시간 |
| **배포 롤백 (Git 되돌림 재수렴)** | **5분 40초** | Git revert 후 Argo CD 완전 재수렴까지 소요 시간 |
| **스키마 마이그레이션 포함 배포 sync** | **1분 26초** | 스키마 변경을 포함한 배포 동기화 시간 |

![남성 카솔이 미리 심어 둔 마커 카드와 복원된 데이터에서 꺼낸 표식을 관문 앞에서 맞춰 보는 장면](./page-04.webp)

다른 리허설 항목 수치도 모두 무난하게 나왔기 때문에, 마커 대조를 생략했다면 복구 항목의 초록색 성공 로그도 그대로 믿고 넘어갈 뻔했던 셈이죠.

## 검증 범위와 남은 과제

이번 리허설의 실측 수치는 아래의 제한된 개발 환경에서 측정한 결과입니다.

- **클러스터 및 배포**: 단일 노드 개발용 Kubernetes 클러스터, Argo CD v3.4.5
- **데이터베이스**: MySQL 8.0.34, ROW 형식 binlog
- **데이터 규모**: 데이터가 거의 없는 빈 스키마에 가까운 상태

따라서 재검증의 38초는 빈 스키마 기준의 초기 참고치일 뿐이며, 실제 운영 데이터 규모와 스토리지 환경에서 목표 시간 안에 들어오는지는 추후 다시 측정해야 합니다. 도구가 통째로 빠진 경우가 아니라 binlog 재생이 **중간에** 끊겼을 때도 현재의 관문이 누락을 걸러내는지 다음 분기 리허설에서 재현해 볼 계획입니다.

이번 리허설에서 얻은 가장 분명한 기준은 한 문장입니다. **백업과 복원 작업이 종료코드 0으로 끝났다는 사실은 복구 가능성의 증거가 아닙니다.** 복구는 복원된 데이터와 미리 심어 둔 표식을 직접 맞춰 봐야 비로소 확인됩니다.
