글·해설: 다메카솔

담당자에게 자료를 보내 달라는 요청을 받은 에이전트가 문서를 읽고, 연락처를 검색한 뒤 메시지를 전송합니다. 개별 API 호출은 모두 정상(`200 OK`)으로 끝났는데 정작 외부인에게 기밀 문서가 넘어갔다면, 단일 호출의 성공 로그만으로는 작업이 안전했다고 말하기 어렵죠.

**X-AgentRed는 이처럼 여러 서비스를 오가는 도구들의 ‘연결 경로’에서 승인되지 않은 위험을 찾아내는 레드티밍 연구**입니다. 저자들은 도구 사이의 선행 조건과 실행 효과를 그래프로 엮은 뒤, 그 위에서 시험할 시나리오를 고르고 실행 결과를 반영해 탐색 범위를 넓혔습니다.

## 핵심 내용

- **HarmFlow 그래프**: 각 도구의 선행 조건·실행 효과·잠재 피해를 분석해, 앞 도구의 효과가 뒤 도구의 조건을 채우는 관계를 연결합니다.
- **결과 기반 경로 탐색**: 피해가 발생한 경로는 다른 도구 조합으로 변형해 넓히고, 중간에 막힌 경로는 부족했던 선행 조건을 보완해 시나리오를 고칩니다.
- **모의 환경 성적과 해석 경계**: 30개 서비스·914개 도구 모의 환경에서 1,000개 시험 후보 중 192개(19.2%) 피해 경로를 찾았으나, 이는 의도적으로 구성한 시험 후보의 비율이며 판정 기준에 따라 수치가 크게 달라집니다.

표지의 장면은 개별 도구는 정상이어도 연결 끝에 정보 유출이 생길 수 있다는 문제를 보여 주려고 만든 가상 예시입니다(실제 상용 제품의 사고를 재현한 것은 아닙니다). 이 연구가 겨냥하는 핵심은 단일 API의 버그가 아니라, **여러 번의 정상 호출이 합쳐지면서 바뀌는 정보와 권한의 흐름**입니다.

## 앞선 도구의 결과가 다음 조건이 된다

![앞선 도구의 효과가 다음 도구의 조건으로 이어지는 연결과 실행 시험의 개념](./page-01.webp)

새로운 문서가 만들어지면 자연히 ‘그 문서를 공유할 수 있는 상태’가 됩니다. 저자들은 이런 연쇄 관계를 포착하기 위해 각 도구마다 **필요한 선행 조건, 실행 뒤 생기는 효과, 그리고 발생 가능한 피해**를 정리했습니다. 앞 도구의 실행 효과가 다음 도구의 선행 조건을 뒷받침할 때 두 도구를 이어 붙인 구조가 바로 **HarmFlow 그래프**입니다. [원문 §3.1](https://arxiv.org/html/2610.13886v1#S3.SS1)

여기서 그래프의 연결선이 뜻하는 바를 정확히 짚어야 합니다.

문서를 생성했다는 사실은 ‘공유할 파일이 존재한다’는 기술적 조건을 채워 줄 뿐, **특정 수신자에게 그 문서를 보내도 좋다는 보안 권한까지 만들어 주지는 않습니다.** 나머지 조건은 앞선 호출이나 환경 설정에서 별도로 충족되어야 하죠. 저는 이 구분이 서비스 통합 아키텍처를 설계할 때 특히 중요하다고 봅니다. API 호출에 필요한 입력값(파일 ID, 이메일 주소)이 준비됐다는 사실과 그 작업을 허락하는 권한 판단을 한 덩어리로 취급하면 보안 경계가 쉽게 무너지기 때문입니다.

X-AgentRed는 잠재적 피해와 맞닿아 있는 마지막 도구에서부터 그래프를 거슬러 올라가 후보 경로를 뽑아냅니다. 그런 다음 이를 **안전하게 처리할 방법도 존재하는 정상적인 사용자 요청**과 초기 환경으로 포장해 대상 에이전트에게 맡깁니다(시험이 겨냥하는 피해는 사용자가 직접 요청했거나 승인한 결과에서 제외됩니다). [원문 §3.2·문제 설정](https://arxiv.org/html/2610.13886v1#S3)

도구를 고르는 단계의 신뢰성이 궁금하다면 앞서 다룬 [RATED의 실행 피드백 기반 도구 선택](/posts/rated-tool-reliability/)과 비교해 읽을 만합니다. RATED가 고장 난 도구를 피해 가용한 도구를 고르는 데 집중한다면, X-AgentRed는 **정상 작동하는 도구들이 이어졌을 때 생기는 부작용**을 추적합니다.

## 실행 기록으로 다음 시험을 바꾼다

![위험이 발견된 경로를 넓히고 막힌 경로를 점검하는 모의 실험](./page-02.webp)

한 번 시험 시나리오를 돌렸다고 해서 탐색이 거기서 끝나지는 않습니다. 실행 결과에 따라 두 갈래로 다음 시험을 조정합니다. [원문 §3.3](https://arxiv.org/html/2610.13886v1#S3.SS3)

- **피해가 발생한 경로**: 위험을 유발한 핵심 흐름은 유지한 채 주변 도구 조합을 바꾸며 탐색 범위를 넓힘
- **중간에 막힌 경로**: 충족되지 않은 선행 조건이 무엇인지 살펴 그래프와 시험 시나리오를 보완함(에이전트 모델 자체를 재학습시키는 과정은 아닙니다)

물론 이 경로 수정 절차는 어디까지나 **보안 취약점을 찾기 위한 레드티밍 시험 기법**입니다. 실제 운영 중인 에이전트가 권한 거부를 만났을 때 다른 우회 경로를 찾아 같은 작업을 강행하라는 지침으로 옮겨서는 안 되며, 운영 시스템에서는 반대로 권한 검사와 중단 규칙을 굳건히 유지해야 합니다.

저자들은 **30개 서비스와 914개 도구가 있는 고정 모의 환경**에서 이 방법론을 시험했습니다. Claude Opus 4.8이 도구 응답과 서비스 상태를 모사했고, 평가 대상 에이전트로는 Claude Opus 4.8, GPT-5.6 Sol, DeepSeek-V4-Pro, GLM-5.2 네 모델을 두었습니다(방법마다 모델당 250개 후보씩 총 1,000개 후보를 1회 실행해 비교했으며, DeepSeek 모델에는 인터페이스 제한 때문에 시나리오 필수 도구와 고정 순서 도구를 합쳐 최대 256개만 제공했습니다). [원문 §4.1·부록 A.3](https://arxiv.org/pdf/2610.13886v1)

아래 표는 두 판정 모델(Claude Opus 5, GPT-5.6 Sol)이 **① 피해 발생, ② 환경 조건의 그럴듯함, ③ 사용자 요청 전체의 정상성**을 만장일치로 인정한 경우만 집계한 **저자 보고치**입니다. [표 2·그림 3·부록 A.6](https://arxiv.org/pdf/2610.13886v1)

| 시험 생성 방법 | 피해가 확인된 후보 | 피해 경로 비율(HPR) | 모델 평균 도구 사용 범위(914개 중) |
| --- | ---: | ---: | ---: |
| X-AgentRed | 192 / 1,000 | 19.2% | 41.5% |
| STAC | 105 / 1,000 | 10.5% | 13.9% |
| TRACE | 27 / 1,000 | 2.7% | 23.7% |

같은 1,000개 후보를 시험했을 때 발견된 피해 경로 수와 한 번이라도 호출된 도구의 범위(실패한 경로에서 호출된 도구 포함) 모두에서 차이가 났습니다.

이 숫자를 읽을 때는 분모와 실험 조건을 함께 챙겨야 합니다. `19.2%`는 위험을 찾기 위해 의도적으로 조합한 **시험 후보 중 피해가 확인된 비율**이지, 일상적인 서비스 트래픽의 사고율이 아닙니다. 또한 비교한 세 방법의 후보 개수(1,000개)는 같았지만 후보 생성에 들인 연산량, 대상 모델 호출 횟수, 후속 요청 방식이 서로 달라서 이 표만으로 그래프 구조 하나의 순수 효과를 분리하거나 동일 비용 대비 개선폭으로 단정하기는 어렵습니다.

## 모의 실험에서 운영 판단으로 건너갈 때

![서비스 사이의 정보 이동과 공유 경계를 확인하는 카솔](./page-03.webp)

모의 실험 결과를 현업 아키텍처로 가져올 때는 세 가지 경계를 더 짚어 봐야 합니다.

첫째, **도구 사용 범위(41.5%)가 넓어졌다는 사실이 곧 새로운 종류의 결함을 그만큼 더 찾았다는 뜻은 아닙니다.** 방법마다 호출 경로의 길이가 달랐고, 앞선 실행 결과에 따라 다음 시험 시나리오가 바뀌는 적응형 탐색이라 독립적인 반복 실험 결과처럼 해석하기 어렵습니다. [원문 §4.4·부록 B.1](https://arxiv.org/pdf/2610.13886v1)

둘째, **모델 판정 기준에 따라 수치가 크게 흔들립니다.** 두 판정 모델의 만장일치 대신 어느 한 모델만 피해를 인정해도 세는 방식으로 완화하면, X-AgentRed의 피해 경로 비율은 대상 모델에 따라 **15.2~30.4%p** 더 높게 나왔습니다. 저자들이 피해로 분류된 192개 경로를 직접 검토해 보상 편법(reward hacking) 징후가 없음을 확인했다고 밝혔지만, 이를 독립적인 인간 판정 정확도 측정으로 볼 수는 없습니다. [원문 §3.3·§4.6](https://arxiv.org/pdf/2610.13886v1)

셋째, **서비스가 바뀔 때마다 그래프를 갱신하는 유지보수 비용**이 듭니다. 새 API가 추가되거나 기존 도구의 동작이 바뀌면 선행 조건과 효과를 다시 분석해 연결을 고쳐야 한다는 점을 저자들도 한계로 명시했습니다. 2026년 10월 13일 확인한 [저자 프로젝트 페이지](https://yeonsungjung.github.io/projects/x-agentred/)는 코드를 공개 예정으로 안내하고 있어, 이번 글에서는 공개된 논문 원문 범위 안에서만 살펴봤습니다.

## 다메카솔의 해석: 호출 사이에도 책임이 이어져야 합니다

저는 이 연구를 보며 **에이전트 통합 테스트의 관찰 단위를 ‘단일 도구 호출’에서 ‘호출 사이의 데이터·권한 이동’으로 넓혀야겠다**는 생각을 굳혔습니다.

각 도구가 정상 응답을 냈는지 확인하는 것에 그치지 않고, **어느 출처에서 읽은 정보가 누구에게 어떤 공유 범위로 넘어갔는지**를 흐름 전체로 추적하는 것입니다. 예를 들어 회의록을 요약해 메일로 보내는 작업이라면, 요약 내용이 맞는지뿐 아니라 수신자 주소를 가져온 문서의 신뢰도와 최종 외부 발송 권한까지 함께 검증해야 합니다(이는 논문에서 영감을 얻은 제 아키텍처 판단이며, 논문이 특정 방어 기법의 효과를 실증한 것은 아닙니다).

무엇보다 **서버 계층의 명시적인 권한 검사**가 마지막 보루로 남아 있어야 합니다. 에이전트가 읽은 문서 본문이나 이전 도구 응답에 특정 이메일 주소가 적혀 있다고 해서, 그 사람에게 기밀 자료를 전송할 권한까지 저절로 생기지는 않으니까요. 모델의 추론에만 기대지 않고 외부 전송·상태 변경 직전에 허용 범위를 다시 검사하는 구조는 [도구 명세와 에이전트 안전성](/posts/tool-specifications-agent-safety/)에서 다룬 실행 경계 원칙과도 맞닿아 있습니다.

새 서비스를 하나 더 연결할 때 기존 단위 테스트만 통과시키고 안심하면, 도구들이 이어지면서 생기는 사각지대를 놓치기 쉽습니다. 가능한 모든 조합을 다 시험할 수는 없으니 **외부 발송·권한 변경·삭제처럼 되돌리기 어려운 끝 도구에서부터 거슬러 올라가며 연결 경로를 점검**해 보는 건 어떨까요? 우리 시스템에서는 어느 두 도구가 만날 때 가장 먼저 확인이 필요한지 돌아보게 하는 연구입니다.
