항공권 변경 버튼을 누르기 직전에 사용자 승인을 다시 받아도, 앞 단계에서 신원 확인이나 운임 자격 심사를 빠뜨렸다면 이미 정책을 어긴 셈입니다. 마지막 도구 호출만 막는 방식으로는 앞선 절차 위반을 바로잡기 어렵거든요. **「PolicyGuide: From Guarding One Action to Guiding the Whole Workflow for Policy-Compliant LLM Agents」**는 정책을 워크플로 그래프로 컴파일하고 요청별 상태를 에이전트 밖에 보관해, 매 사용자 턴마다 첫 미충족 절차부터 안내하는 해법을 제시합니다.

글·해설: 다메카솔

## 핵심 내용

- 마지막 변경 호출만 검사하면 앞서 건너뛴 신원·자격·사용자 확인 같은 절차 위반을 되돌리기 어렵습니다.
- `PolicyGuide`는 정책과 도구를 검증된 워크플로 그래프로 컴파일하고 요청 상태를 외부 런타임 코드에 보관합니다.
- 세 영어 고객지원 도메인에서 네 번 연속 성공률($\text{Pass}^4$) 평균이 약 0.42에서 약 0.62로 상승했습니다.
- 주 지표는 최종 결과만 채점하며, 검증기가 확률적이고 fail-open 방식이라 고위험 작업에는 결정적 게이트가 필요합니다.

## 마지막 호출을 막아도 앞선 위반은 남는다

![요청 토큰이 여러 절차 관문을 건너뛴 뒤 마지막 변경 게이트에서 막히는 장면](./page-01.webp)

기존 행동 단위 가드는 위험한 도구 호출이 일어나는 순간 그 호출을 허용할지 판단합니다. 예를 들어 항공권 변경 API를 호출하기 직전에 사용자가 변경에 동의했는지 확인하는 식이죠. 하지만 정책이 요구한 본인 인증이나 운임 자격 검토를 앞 단계에서 건너뛰었다면, 마지막 호출의 적법성만 따져서는 전체 절차를 지켰다고 보기 어렵습니다.

논문은 이 차이를 지금 호출이 허용되는지 묻는 **단일 행동 준수(action-local compliance)**와 여러 턴에 걸친 선행 조건·순서가 충족됐는지 묻는 **워크플로 수준 준수(workflow-level compliance)**로 구분합니다. 겉보기에 적법한 도구 호출이라도 거기까지 도달한 경로가 이미 정책을 어겼을 수 있기 때문입니다. 모델의 대화 기억에만 기대지 않고 요청별 의무 충족 여부를 감사 가능한 외부 상태로 보관해야 하는 이유이며, [워크플로를 지식으로 바꾸는 설계](/posts/workflow-as-knowledge/)와 맞닿아 실행 중 정책 준수에 초점을 맞춘 접근입니다.

## 정책을 그래프로 만들고 상태를 에이전트 밖에 둔다

![정책 묶음과 외부 상태 저장소가 워크플로 그래프의 첫 미충족 노드를 찾아 에이전트로 안내를 돌려주는 장면](./page-02.webp)

`PolicyGuide`는 먼저 원시 정책 문서와 도구 목록을 요청 유형, 공통 절차, 주 그래프와 하위 흐름으로 컴파일한 뒤 스키마·도구 범위·도달 가능성을 검사해 도메인별 워크플로 번들을 동결합니다.

실행 중에는 별도의 모델 검증기가 매 사용자 턴마다 대화 기록, 근거 도구 결과, 런타임 코드가 보관한 요청 상태와 동결 워크플로를 함께 읽습니다. 열린 요청을 정리한 뒤 저장된 노드에서 순회를 시작해 첫 미충족 노드에서 멈추고, 에이전트가 다음에 할 조치와 교정 안내를 돌려주죠. 이때 런타임 코드가 상태를 지속하면서 알려지지 않은 노드 ID를 거부하고, 현재 상태가 승인하지 않은 첫 변경 도구는 턴 구간마다 한 번 가로채 재검증합니다. 나머지 절차 행동은 차단 대신 교정 안내로 유도해 확률적 가이드와 결정적 검사를 결합한 구조입니다.

## 세 도메인에서 반복 성공률이 높아졌다

![항공 소매 통신 세 고객지원 도메인에서 기준 경로보다 네 번의 성공 토큰이 더 안정적으로 이어지는 장면](./page-03.webp)

주 평가는 영어 합성 고객지원 벤치마크($\tau^2$-bench)의 항공·소매·통신 세 도메인을 대상으로 이뤄졌습니다. 각 과제를 네 번 실행해 모두 성공할 확률의 평균($\text{Pass}^4$)을 비교한 결과는 아래와 같습니다.

| 구분 | 수치 및 비교 결과 | 실험 조건·참고 |
| --- | --- | --- |
| 과제·모델 | 항공 50·소매 114·통신 114개 | GPT-5.4 에이전트·검증기, 동결 GPT-4.1 시뮬레이터, 4회 실행 |
| 평균 $\text{Pass}^4$ | ReAct 약 0.42 → `PolicyGuide` 약 0.62 | 세 도메인 무가드 기준선 대비 |
| 통신 $\text{Pass}^4$ | 전체 0.193 → 0.614 / 허용 변경 0.042 → 0.549 | 절차 순서 제약이 가장 강한 도메인 |
| 그래프 기여도 | `PolicyGuide-Raw` 대비 +0.100 / +0.150 / +0.325 | 항공·소매·통신 순, 외부 추적은 동일 유지 |
| 통신 순서 지표 | `PolicyGuide` 56.2% / ReAct 17.5% / `PolicyGuard` 13.1% | 정답 조건화 탐색 규칙, 이중 주석자 일치도 미측정 |

특히 선행 절차 순서가 까다로운 통신 도메인에서 개선 폭이 두드러졌습니다. 외부 상태 추적은 유지하되 그래프만 원시 정책으로 바꾼 `PolicyGuide-Raw`보다도 점수가 높았는데요. 다만 이 진단 비교는 모든 구성 요소를 완전히 분리한 요인 실험은 아니라는 점을 감안해야 합니다.

## 결과 점수는 전체 절차의 보증이 아니다

![확률적 검증기 옆에 허용으로 열린 우회로가 남아 고위험 구역으로 이어지는 장면](./page-04.webp)

높은 $\text{Pass}^4$ 점수를 곧바로 완전한 절차 준수로 해석하기는 어렵습니다. 표준 평가기가 최종 데이터베이스 상태와 에이전트의 자연어 주장만 채점할 뿐, 신원 확인과 자격 심사가 정확한 순서로 진행됐는지까지 모두 검사하지는 않거든요.

실험 범위와 런타임 구조에서도 세 가지 제약이 확인됩니다.

- **제한된 평가 범위**: 세 영어 합성 고객지원 도메인과 동결 사용자 시뮬레이터 기준이며, 적응형 공격 평가는 빠졌습니다. 소매 도메인의 정책 위반 방지 과제는 10개뿐이라 ReAct 대비 전체 이득이 통계적으로 유의하지 않았습니다.
- **확률적 판단과 비용**: 검증기가 언어 모델이라 노드 판정이 확률적으로 움직이며, 보고된 호출 비용은 대화당 약 0.40달러입니다.
- **턴 사이 빈틈과 fail-open**: 사용자 턴 사이의 위반은 무조건적 보장 밖에 놓이고, 검증기 오류 시 허용으로 넘어가는 fail-open 구조라 고위험 변경에는 별도의 결정적 권한 검사와 승인 게이트가 필수적입니다.

## 다메카솔의 해석: 확률적 안내와 결정적 차단을 나눈다

![성인형 카솔이 에이전트 밖의 상태 금고와 결정적 규칙 게이트를 가리키는 장면](./page-05.webp)

실제 서비스 운영에 이 구조를 도입한다면 세 층의 책임을 코드와 모델 사이에서 분명히 나누는 편이 안전합니다.

| 층 | 책임 |
| --- | --- |
| 절차 상태 | 에이전트 기억과 분리해 요청별 충족 노드와 근거를 코드로 지속 |
| 확률적 안내 | 정책 그래프를 따라 첫 미충족 절차와 교정 방법을 제안 |
| 결정적 차단 | 권한, 금액 한도, 필수 승인처럼 형식화 가능한 규칙을 코드로 거부 |

또한 검증기에 전달되는 대화와 도구 결과 자체가 새로운 민감 데이터 경로가 되므로, 접근 제어와 보존 기간, 감사 로그도 업무 데이터 수준으로 맞춰야 합니다. 배포 전에는 `절차 상태`, `모델 검증기`, `결정적 게이트` 세 요소를 나란히 놓고, 검증기가 응답하지 않을 때 어떤 변경이 허용되는지까지 미리 점검해 두길 권합니다.

## 자주 묻는 질문

### 시스템 프롬프트에 정책을 모두 넣으면 충분한가요?

프롬프트는 규칙을 알려 줄 수는 있어도 요청별 절차 상태를 결정적으로 보존해 주지는 못합니다. `PolicyGuide`는 동결된 워크플로 그래프와 외부 코드 상태를 별도 검증기가 매 턴 대조하는 구조로 이 빈틈을 줄입니다.
