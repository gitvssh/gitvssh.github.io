글·해설: 다메카솔

시놀로지 NAS에 32GB RAM을 장착하고 학습용 k3s를 올렸을 때만 해도 여유가 넘칠 줄 알았습니다. 대시보드를 보면 메모리는 한참 남아 있었으니까요. 그런데 정작 야심 차게 띄운 Airflow DAG는 밤낮없이 실패를 거듭했습니다. 

원인을 파고들어 보니 문제는 두 가지였습니다. **'메모리 총량'이라는 착시 뒤에 가려진 CPU 코어 병목**, 그리고 **'밤마다 꺼지는 NAS'에 묶여 있던 상태 서비스(DB/스토리지)의 가용성 문제**였습니다. 이번 글에서는 이 두 가지 장애 요인을 겪으며 별도의 24시간 홈랩 Kubernetes 클러스터를 구축하게 된 과정을 정리해 보았습니다.

## 이미 NAS에서 k3s를 배우고 있었습니다

처음부터 거창하게 독립된 미니 PC 클러스터로 시작한 것은 아니었습니다. 집에 있던 시놀로지 NAS 위에 경량 쿠버네티스인 k3s를 올리고, 컨테이너 배포부터 스토리지 연결, 네트워크 구성, 장애 복구까지 직접 몸으로 부딪쳐보는 것이 출발점이었습니다. 단순 튜토리얼을 따라 치는 것보다 실제 운영 환경에서 터지는 문제들을 겪어보고 싶었기 때문입니다.

32GB라는 RAM 용량은 홈랩 수준에서는 꽤 넉넉해 보였습니다. 메모리 사용률 그래프가 안정적인 것을 보며 "아직 인프라에 여유가 많다"고 착각하기 쉬웠습니다. 하지만 메모리가 널널하다고 해서 연산 자원까지 넉넉한 것은 아니었습니다.

![시놀로지형 NAS에서 학습용 k3s를 운영하다 넓은 메모리 공간과 좁은 CPU 처리 관문을 비교하는 장면](./page-01.webp)

## 32GB RAM이 CPU 병목을 가렸습니다

RAM은 실행 중인 프로세스와 데이터를 올려두는 '작업대'일 뿐, 실제로 연산을 처리하고 동시에 태스크를 밀어내는 것은 'CPU 코어'입니다. 

저전력 NAS CPU의 한정된 코어를 k3s 시스템 컴포넌트와 Airflow 워커들이 나눠 쓰다 보니, 메모리는 수십 GB가 남아도 CPU 런큐(Run Queue)가 꽉 막히며 작업이 줄줄이 타임아웃으로 밀렸던 것입니다. 단일 하드웨어 지표(RAM)만 보고 서버 자원이 충분하다고 속단하면 이런 동시성 병목을 놓치게 됩니다.

이 경험 이후 장애 분석의 관점을 완전히 바꿨습니다. "단순히 OOM(Out Of Memory)이 났는가?"가 아니라, **"실패 시점에 CPU 런큐에 대기 중이던 태스크는 몇 개였는가?", "동일 노드에서 어떤 백그라운드 데몬이 경합을 벌였는가?"**를 먼저 확인하게 되었습니다.

## 반복 실패는 하나의 원인만 갖지 않았습니다

CPU 경합을 완화했음에도 불구하고 밤만 되면 Airflow DAG가 여전히 실패했습니다.

원인은 어처구니없게도 하드웨어 운영 정책에 있었습니다. 침실 근처에 둔 NAS의 하드디스크 소음과 전력 소모 때문에 야간 자동 종료 스케줄을 걸어두었는데, 하필 그 NAS 안에 Airflow 메타데이터 DB(PostgreSQL)와 원본 데이터용 S3(MinIO)가 함께 올라가 있었던 것입니다. 낮에는 CPU가 부족해 뻗고, 밤에는 의존하는 DB 서버 자체가 꺼져서 뻗었던 셈입니다.

두 문제는 완전히 성격이 다릅니다. CPU 부족은 '주어진 시간 내의 처리 용량' 문제이고, 야간 셧다운은 '시간대별 서비스 가용성(Availability)' 문제입니다. 표면상 똑같이 "Airflow 태스크 실패"라는 에러로 나타나더라도, 컴퓨트 병목과 의존성 가용성을 분리해서 바라보지 않으면 반쪽짜리 해결책에 머물게 됩니다.

![낮의 CPU 경합과 밤의 NAS 종료로 끊긴 데이터베이스·오브젝트 저장소 경로를 나란히 보여 주는 장면](./page-02.webp)

## 메타데이터 DB만 옮기면 절반만 고칩니다

처음에는 "Airflow 메타데이터 DB만 24시간 켜져 있는 다른 장비로 옮기면 되겠지"라고 단순하게 생각했습니다. 하지만 실제 DAG 실행 파이프라인을 추적해 보니, 데이터 수집 태스크가 원본 파일을 NAS의 MinIO 스토리지에 업로드하고 있었습니다. 즉, DB가 살아 있어도 파일 저장소가 꺼져 있으면 `boto3` 연결 단계에서 파이프라인이 다시 중단되는 구조였습니다.

결국 필요한 것은 특정 DB 하나를 옮기는 땜질 처방이 아니었습니다. **24시간 상시 가동되는 컴퓨트 노드, 상태(State) 데이터를 안정적으로 보존할 스토리지, 그리고 DB 계층 전체를 포괄하는 운영 아키텍처**가 필요했습니다. 이 고민이 자연스럽게 "3노드 미니 PC 기반 k3s 클러스터" 구축으로 이어졌습니다.

단일 미니 PC에 Docker Compose를 쓰거나 클라우드로 이전하는 대안도 있었지만, 비용 최적화와 함께 다중 노드 환경에서의 장애 복구(Self-healing), 고가용성(HA), 선언적 인프라 운영을 직접 체득하기 위해 k3s 클러스터를 최종 선택했습니다.

![메타데이터 데이터베이스만 옮기면 오브젝트 저장소 경로가 남고, 두 경로를 함께 상시 클러스터로 옮겨야 하는 의존성 흐름](./page-03.webp)

## 24시간 서비스는 24시간 의존성 위에 둡니다

최종적으로 인프라의 역할을 가동 특성에 맞춰 명확히 재정의했습니다. 24시간 상시 돌아야 하는 컴퓨트 및 상태 서비스(Airflow, DB, MinIO)는 전력 효율과 소음이 적은 미니 PC 클러스터로 이전하고, 야간에 종료되는 NAS는 본연의 역할인 주간 대용량 백업 및 파일 보관용 스토리지로 분리했습니다.

새로운 3노드 클러스터로 이전한 이후 야간 Airflow 파이프라인 실패는 완전히 사라졌습니다. 이제 새로운 시스템을 설계하거나 서버 스펙을 산정할 때 단순히 RAM 용량부터 보지 않습니다. **"이 작업이 대기하는 진짜 병목 자원은 무엇인가?", "이 서비스가 의존하는 백엔드 컴포넌트들이 24시간 동일한 가용성을 보장하는가?"**를 먼저 점검합니다.

![카솔이 상시 컴퓨트·상태 서비스 계층과 주간 백업·파일 서버 역할로 분리한 NAS를 설명하는 장면](./page-04.webp)

## 실무 인프라 점검 체크리스트

시스템 장애를 분석하거나 워크로드를 배치할 때 다음 질문들을 점검해 보시길 권합니다:

1. **자원 병목 분리**: 실패한 태스크가 메모리, CPU 코어, 디스크 I/O 중 정확히 무엇 때문에 블로킹되었는가?
2. **리소스 경합 분석**: 피크 시간대에 동일 노드 내 시스템 데몬과 애플리케이션 파드가 CPU 런큐를 과도하게 점유하지 않는가?
3. **의존성 가용성 매핑**: 애플리케이션이 호출하는 메타 DB, 오브젝트 스토리지, DNS, 인증 서버가 작업 실행 시간대에 상시 살아 있는가?
4. **암묵적 의존성 확인**: 메인 DB 외에 로그 저장소, 임시 파일 볼륨 등 간과하기 쉬운 숨은 의존성이 누락되지 않았는가?
5. **격리 및 스케줄링 검증**: 워크로드의 성격(상시 가동 vs 배치성/야간 백업)에 맞춰 노드 테인트(Taint)나 리소스 리밋이 적절히 분리되어 있는가?

다음 편에서는 굳이 미니 PC 3대를 묶어 클러스터를 구성한 분산 합의(etcd 쿼럼) 이유와, 클러스터 점검 중 엉뚱한 kubectl 컨텍스트를 조회해 혼란에 빠졌던 트러블슈팅 경험을 다룹니다. [홈랩 쿠버네티스 구축기 2편: 3노드여야 하는 이유, 그리고 빈 결과의 함정](/posts/three-node-etcd-quorum-context/)으로 이어집니다.
