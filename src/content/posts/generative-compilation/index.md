AI 코딩 에이전트에게 Rust 코드를 맡겨 생성이 끝나기를 기다렸다가 컴파일하면, 초반 몇 줄의 소유권 오류가 뒤쪽까지 번져 에러가 한꺼번에 쏟아질 때가 있습니다. 그사이 모델은 잘못된 가정 위에 토큰을 끝까지 생성한 셈이라, 수정마다 긴 진단 목록을 다시 읽어야 하죠. 미완성 코드를 생성 도중에 닫아 `rustc`에 먼저 물어보는 **생성형 컴파일(Generative Compilation)**은 사후 피드백의 이 낭비를 어떻게 줄여 줄까요?

글·해설: 다메카솔

## 생성 중 오류를 먼저 잡아야 하는 이유

![코드 중간의 작은 오류가 뒤 블록으로 번지고 카솔이 흐름을 무너뜨리는 장면](./page-00.webp)

예를 들어 메시지에서 고정 길이 헤더를 자른 뒤 로그를 남기는 Rust 함수 `fmt_msg`를 AI가 짠다고 가정해 봅시다. 둘째 줄에서 슬라이스로 불변 빌림을 잡은 뒤 셋째 줄에서 `drain`으로 버퍼를 바꾸고, 넷째 줄에서 다시 그 슬라이스를 읽는 코드입니다.

빌림 충돌은 넷째 줄에서 이미 확정되지만, 기존 **사후 컴파일(`PC`)**은 파일이 끝날 때까지 기다렸다가 오류를 한꺼번에 줍니다. 토큰마다 유효성을 거르는 **제약 디코딩** 역시 `rustc` 프론트엔드(60만 줄 이상) 수준의 규칙을 새로 짜기 버겁고, 설명 없이 토큰만 막으며, 상용 API 모델에는 적용하기 어렵습니다.

## 미완성 코드를 닫아 주는 Sealor의 원리

![열린 부분 코드가 봉합 링을 거쳐 닫힌 코드가 되고 rustc 진단을 받는 세 단계 다이어그램](./page-02.webp)

ETH 취리히·INSAIT·UC 버클리 연구진은 2026년 7월 논문에서 기존 컴파일러를 재사용해 중간 진단을 얻는 **Sealor**를 제안했습니다. 가령 `fmt_msg`가 네 번째 줄에서 `tag`의 메서드를 부르려다 끊겼다면, Sealor는 이미 쓴 코드를 보존한 채 뒤만 닫아 `rustc`에 넘깁니다.

```rust
fn fmt_msg(msg: &mut String) -> String {
    let tag = &msg[..HEADER_SIZE];
    msg.drain(..HEADER_SIZE);
    &tag;
    holeval()
}
```

이렇게 닫힌 코드는 문법 오류 없이 컴파일러를 통과해 차용 충돌(`E0502`)을 곧바로 짚어 냅니다. 연구진은 정상 접두어를 잘못 기각하지 않는 **전역 완전성**을 최우선으로 두고 문장 경계에서 **선택적 건전성**을 증명(핵심 언어 모델 Featherweight Rust, Lean 기계화)한 뒤 실제 Rust로 확장했죠.

`rust-analyzer`를 활용해 약 5천 줄로 구현된 Rust용 Sealor는 세 가지 장치로 동작합니다.

- **분기·루프 마감(`holediv()`)**: 미완성 분기나 루프 끝을 `panic!()`으로 채워 발산(`!`) 처리해 가짜 차용 오류를 막습니다.
- **값 자리표시자(`holeval()`)**: 표현식 빈자리에 `const fn holeval<T>() -> T { panic!() }`를 넣어 문맥 타입을 맞추면서 앞 코드의 빌림 검사는 살립니다.
- **미래 의존 오류 보류·좌표 투영**: 뒤 선언에 의존하는 오류는 파일 끝까지 미루고, 진단 위치는 원래 부분 코드 좌표로 돌려줘 임시 코드가 안 보이게 합니다.

## 스트리밍과 나란히 도는 비동기 검증 루프

![생성, 봉합과 검사, 진단, 수정이 원형으로 이어지는 생성형 컴파일 루프](./page-03.webp)

생성형 컴파일은 LLM과 검증기가 일반 텍스트만 주고받으며 병렬로 움직이도록 구성됐습니다.

1. **스트리밍 전달**: 모델이 토큰을 생성하며 현재 부분 코드를 검증 워커에 넘깁니다.
2. **최신 본 우선**: 검사 중 밀린 옛 조각을 건너뛰고 최신 접두어만 봉합해 `rustc`로 확인합니다.
3. **조기 중단·재시작**: 복구 불가능한 오류가 확인되면 생성을 끊고, 부분 코드와 오류 메시지를 프롬프트에 붙여 처음부터 다시 씁니다.
4. **사후 피드백 폴백**: 조기 재시작 10회 안에 안 풀리면 파일을 완성한 뒤 남은 예산(`UpdatedAPI` 총 15회, `Translation` 총 20회)으로 사후 컴파일을 돕니다.

로짓이나 샘플링 내부에 손대지 않고 텍스트 스트리밍만으로 동작하므로, 폐쇄형 상용 API 모델에도 그대로 붙일 수 있습니다.

## 7개 모델·Rust 저장소 과제 성능

![생성 후 피드백의 큰 오류 눈덩이와 중간 피드백의 작은 오류 묶음, 기능 완주 경로를 비교한 장면](./page-04.webp)

저자들은 두 가지 Rust 저장소 수준 과제를 놓고 최신 모델 일곱 종을 비교했습니다.

- **평가 모델**: 비공개 API 3종(Claude Opus 4.8, GPT 5.3 Codex, Gemini 3.5 Flash)과 오픈 웨이트 4종(Kimi K2.7 Code, GLM 5.2, Qwen 3.5 397B·9B)을 과제당 2회 실행했습니다.
- **벤치마크**: Opus 4.8·GPT 5.3이 피드백 없이 못 푼 CRUST-Bench C→Rust 변환 20건(`Translation`)과, 최근 6개월 내 공개 API가 바뀐 크레이트 30개 CLI 구현(`UpdatedAPI`)입니다.

| 비교 지표 | 피드백 없음 (`LLM`) | 사후 컴파일 (`PC`) | 생성형 컴파일 (`GC`) |
| --- | ---: | ---: | ---: |
| 평균 컴파일 오류율 (14개 조합) | 65.9% | 20.7% | **13.1%** |
| 오류 메시지당 평균 진단 수 | - | 13.8개 | **5.5개** |
| 진단 1~2개 간결 오류 비중 | - | 40% | **65%** |
| 오류 감지 위치 (파일 평균 진행률) | - | 100% (완료 후) | **33.3%** |
| 첫 원인(`Oracle`) 대비 지연 중앙값 | - | 89줄 뒤 | **3줄 뒤** |
| `LLM` 대비 평균 실행 시간 증가 | 기준 | +233초 (+283%) | **+135초 (+170%)** |

중간에 컴파일러를 자주 부르는데도 전체 실행 시간 증가폭이 절반 가까이 줄어든 점이 눈에 띄는데요. 오류를 파일 초반에서 조기 차단해 뒤쪽의 헛생성을 건너뛴 덕분입니다.

- **정답률·오류 개선**: `GC`는 14개 조합 중 11개에서 최고 기능 정답률을 기록했고, GLM 5.2(`UpdatedAPI`: 53.3%→71.7%)와 Kimi K2.7(`Translation`: 39.9%→53.9%)이 크게 뛰었으며 Opus 4.8은 `UpdatedAPI` 오류를 6.7%에서 0.0%로 없앴습니다.
- **조기 차단·속도**: 오류 파일 961건(50토큰/초 재생)에서 평균 33.3% 지점에 오류를 잡아 66.7% 헛생성을 피할 여지를 보였고, Qwen 3.5 9B의 `Translation` 시간도 879초에서 357초로 줄었습니다.

## 다메카솔의 해석: 도입 전에 볼 경계

컴파일러를 '마지막 채점관'에서 '생성 중 가드레일'로 앞당긴 설계는 설득력이 있지만, 논문 데이터에 드러난 한계도 함께 봐야 합니다.

- **소형 모델 편차**: 전체 85.3%가 조기 재시작 10회 안에 끝났지만(55.4%는 테스트까지 통과), Qwen 3.5 9B는 40.9%에서 10회를 넘겼고(GPT 5.3 Codex 2.1%) `UpdatedAPI` 정답률도 `PC`(48.3%)보다 낮은 41.7%였습니다. 작은 모델일수록 같은 틀린 앞부분을 되풀이하는 편이거든요.
- **지연 꼬리·적용 비용**: 지연 상위 25%의 90.5%는 미해결 이름·임포트(63.8%) 등 뒤 선언에 달린 오류라 파일 끝에서 걸러집니다. Sealor는 Rust 1.95.0 수작업 규칙 기반이며, 컴파일 뒤 기능·보안 검증은 별도 테스트로 챙겨야 합니다.

모델 선택과 토큰 비용 균형은 [Claude Opus 5와 GitHub Copilot 지원 분석](/posts/claude-opus-5-github-copilot/)에서, 컴파일 뒤 보안 검증이 필요한 이유는 [Copilot 보안 API 실증 연구와 검증 가드레일](/posts/copilot-security-api-study/)에서 이어서 보실 수 있습니다.
