AI가 만든 긴 코드를 끝까지 기다렸다가 컴파일했더니, 첫 오류가 뒤의 수십 줄까지 망가뜨린 경험이 있나요? 2026년 7월 15일 공개된 **Generative Compilation** 논문은 미완성 코드를 임시로 닫아 표준 컴파일러에 넣고, 코드 생성 도중 오류 진단을 돌려주는 방법을 제안합니다.

핵심은 새 Rust 타입 검사기를 다시 만드는 것이 아닙니다. `sealor`라는 가벼운 변환으로 부분 코드를 컴파일 가능한 형태로 만든 뒤 기존 `rustc`에 검사를 맡깁니다. 저자들의 두 Rust 과제 평가에서는 이 중간 피드백이 생성 완료 뒤의 컴파일 피드백보다 컴파일 오류를 더 줄였고, 대부분의 모델·과제 조합에서 기능 정답률도 가장 높았습니다. 다만 결과는 Rust와 두 과제에 한정되며, 논문이 공개했다고 적은 코드 저장소는 2026년 7월 16일 확인 시 아직 404였습니다.

글·해설: 다메카솔

## 핵심 내용

- 생성 후 컴파일은 오류를 설명할 수 있지만, 파일이 끝난 뒤에야 피드백을 줍니다.
- 생성형 컴파일은 부분 프로그램을 `sealor`로 닫아 생성 도중 기존 컴파일러의 진단을 얻습니다.
- 저자들은 Featherweight Rust에서 핵심 판정 성질을 Lean으로 기계 검증하고, 실제 Rust용 부분 프로그램 검사기를 구현했습니다.
- 7개 모델과 두 Rust 저장소 수준 과제에서 평균 컴파일 오류율은 생성 후 피드백 20.7%에서 생성형 컴파일 13.1%로 낮아졌습니다.
- 이것은 컴파일 가능성에 대한 조기 피드백이지, 기능·보안·요구사항까지 보장하는 만능 검증은 아닙니다.

코드 생성 흐름 한가운데 컴파일러를 놓으면 무엇이 달라질까요? 먼저 기존 방식에서 오류가 어떻게 커지는지 보겠습니다.

## 생성 후 컴파일은 왜 늦을까

![코드 중간의 작은 오류가 뒤 블록으로 번지고 카솔이 흐름을 멈추는 장면](./page-00.webp)

보통은 모델이 파일 전체를 만든 다음에야 컴파일러를 실행합니다. 이 방식은 black-box 모델에도 쓸 수 있고, 실제 컴파일러의 풍부한 진단을 그대로 얻는다는 장점도 있습니다.

문제는 피드백 시점입니다. 중간에 되돌릴 수 없는 오류가 생겨도 모델은 그 뒤의 코드를 계속 만듭니다. 앞의 잘못된 타입이나 빌림 가정이 뒤 코드의 전제가 되면, 마지막에는 한 원인에서 파생된 진단이 한꺼번에 쌓일 수 있습니다. 논문은 이를 단순히 "컴파일 오류가 많다"가 아니라 **오류 위치와 피드백 사이의 지연**, **한 번에 전달되는 진단 수**, **남은 생성량**으로 나눠 측정했습니다.

## 생성 후 검사와 제약 디코딩 사이

![완성된 코드 끝에서 늦게 울리는 경보와 잠긴 모델 내부의 토큰 경로를 비교한 장면](./page-01.webp)

생성이 끝나기 전에 개입하는 방법이 없던 것은 아닙니다. **제약 디코딩(constrained decoding)**은 잘못된 토큰을 생성 시점에 막아 주지만, 다음 토큰 분포와 샘플링 과정에 접근해야 하므로 API로만 제공되는 frontier 모델에는 적용하기 어렵습니다. 또한 Rust의 타입·빌림·수명 규칙처럼 풍부한 정적 의미를 다루려면 언어 의미를 상당 부분 다시 구현해야 합니다.

생성형 컴파일은 이 두 접근의 중간을 노립니다.

- 생성 후 피드백처럼 **표준 컴파일러와 텍스트 진단**을 재사용합니다.
- 제약 디코딩처럼 **완성 전의 부분 프로그램**을 봅니다.
- 토큰을 조용히 차단하는 대신, 모델이 수정할 수 있는 컴파일러 진단을 반환합니다.
- 모델 내부 샘플러를 건드리지 않아 black-box API와 연결할 수 있습니다.

저자들은 실제 Rust용 제약 디코딩 구현이 없어 직접 실험 비교는 하지 못했다고 명시합니다. 따라서 "제약 디코딩보다 항상 낫다"는 결론은 이 논문에서 나오지 않습니다.

## sealor는 미완성 코드를 어떻게 검사할까

![열린 부분 코드가 봉합 링을 거쳐 닫힌 코드가 되고 rustc 진단을 받는 세 단계 다이어그램](./page-02.webp)

`sealor`가 하는 일은 한마디로 봉합입니다. 이미 생성된 부분은 최대한 그대로 두고, 아직 닫히지 않은 구문만 마무리한 뒤 잘 형식화된 placeholder를 채웁니다. 이렇게 만든 **sealed program**은 기존 컴파일러가 받을 수 있는 완전한 프로그램 형태가 됩니다.

예를 들어 함수 본문이 끝나지 않았다면 닫는 구조를 추가하고, 앞으로 어떤 값이 올지 아직 정해지지 않은 자리에는 타입 의무를 불필요하게 늘리지 않는 placeholder를 넣습니다. 그 뒤 실제 `rustc`가 타입, 빌림, 수명 규칙을 검사합니다. 진단 위치는 다시 원래 부분 프로그램의 위치로 매핑돼 모델에 전달됩니다.

저자들은 형식화에서 두 목표를 구분합니다.

1. 앞으로 유효하게 완성할 수 있는 부분 프로그램을 너무 일찍 거부하지 않는다.
2. 이미 어떤 완성으로도 되돌릴 수 없는 오류는 가능한 한 드러낸다.

저자들은 Rust의 핵심 아이디어를 단순화한 Featherweight Rust에서 이 성질을 구성하고 Lean으로 기계 검증했습니다. 실제 Rust 구현은 `rust-analyzer`로 부분 구문을 읽고 `rustc`에 정적 의미 검사를 위임합니다. 논문에 따르면 sealor 본체는 약 5천 줄의 Rust이며, 부분 AST 처리를 위한 최소 패치를 포함합니다.

## 컴파일러가 생성 루프 안으로 들어오는 과정

![생성, 봉합과 검사, 진단, 수정이 원형으로 이어지는 생성형 컴파일 루프](./page-03.webp)

루프 한 바퀴는 다섯 단계로 돕니다.

1. 모델이 코드를 스트리밍합니다.
2. 현재까지의 prefix를 sealor가 닫습니다.
3. `rustc`가 봉합된 프로그램을 검사합니다.
4. 되돌릴 수 없는 오류가 잡히면 진단을 모델에 주고 해당 생성 구간을 다시 씁니다.
5. 문제가 없으면 다음 prefix 검사를 계속합니다.

검사는 토큰 생성과 병렬로 돌아갑니다. 논문 실험에서는 생성형 컴파일이 초기에 오류를 끊어, 컴파일할 수 없는 파일을 끝까지 여러 번 만드는 비용을 줄였습니다. "얼마나 자주 검사할지", "어떤 지점에서 되감을지", "에이전트가 검사 호출을 스스로 결정하게 할지"는 아직 열려 있는 설계 문제입니다.

## 두 Rust 과제에서 무엇이 달라졌나

![생성 후 피드백의 큰 오류 눈덩이와 중간 피드백의 작은 오류 묶음, 기능 완주 경로를 비교한 장면](./page-04.webp)

이 루프가 실제로 이득인지는 실험이 말해 줍니다. 저자들은 frontier black-box 모델 3개와 open-weight 모델 4개, 총 7개 모델을 평가했습니다. 각 모델은 모든 과제에서 두 번 평가됐고, 설정할 수 있는 경우 temperature 0.6을 사용했습니다.

- **Translation**: CRUST-Bench에서 기존 강한 모델이 zero-shot으로 풀지 못한 어려운 20개 C-to-Rust 인스턴스를 파일 단위로 평가했습니다.
- **UpdatedAPI**: 최근 API가 바뀐 Rust crate를 이용해 만든 30개 단일 파일 프로젝트입니다. 과제당 평균 5.9개 함수 본문과 평균 3.23개 테스트가 포함됐습니다.

비교 조건은 피드백 없는 LLM, 생성 완료 뒤 컴파일 피드백(PC), 생성 도중 피드백을 추가한 생성형 컴파일(GC)입니다.

| 평가 관점 | 피드백 없음 | 생성 후 피드백(PC) | 생성형 컴파일(GC) | 조건 |
| --- | ---: | ---: | ---: | --- |
| 평균 컴파일 오류 출력 비율 | 65.9% | 20.7% | **13.1%** | 7개 모델 × 2개 데이터셋의 14개 조합 평균 |
| PC 대비 컴파일 오류 방향 | - | 기준 | **13개 개선, 1개 동률** | 9개 조합은 paired difference test, α=5%에서 유의 |
| 기능 정답률 최고 조합 수 | - | - | **11 / 14** | 모든 조합에서 개선된 것은 아님 |
| LLM 기준 평균 추가 실행 시간 | - | 233초 (+283%) | **135초 (+170%)** | 모델·과제별 편차가 큼 |

기능 정답률의 큰 개선 사례로, UpdatedAPI의 GLM 5.2는 PC 53.3%에서 GC 71.7%로, Translation의 Kimi K2.7은 39.9%에서 53.9%로 올랐습니다. 반대로 Qwen 9B의 UpdatedAPI처럼 GC가 PC보다 낮은 조합도 있습니다. 그러므로 표의 평균을 기능 정확도의 향상 폭은 모델과 과제 조합마다 달랐습니다.

오류 파일 961개를 다시 재생한 분석에서는 GC 진단의 65%가 1-2개 오류만 담았고 평균 진단 수는 5.5개였습니다. PC는 40%만 1-2개였고 평균은 13.8개였습니다. GC는 최종 컴파일러가 표시한 첫 오류 위치보다 중앙값 3줄 뒤에 오류를 보고했고, 파일의 평균 33.3% 지점에서 되돌릴 수 없는 오류를 잡았습니다. 저자들은 이 설정에서 해당 비컴파일 출력의 나머지 66.7% 생성을 피한 것으로 해석합니다.

이 수치는 50 tokens/s로 기존 오류 파일을 재생한 분석과 논문의 고정 harness 조건에 묶여 있습니다. 실제 제품의 네트워크 지연, 모델 응답 형식, 저장소 크기, 병렬 실행 자원에 그대로 대입하면 안 됩니다.

## 어디까지 믿고 적용해야 할까

![Rust 범위, 수작업 규칙, 코드 공개 미확인이라는 세 경계를 카솔이 확대경과 체크리스트로 검토하는 장면](./page-05.webp)

이 논문의 기여는 분명하지만 적용 경계도 분명합니다.

- **Rust와 두 과제**: 다른 언어, 다른 코딩 에이전트 구조, 장기 유지보수 작업에서 같은 효과가 난다고 검증한 것은 아닙니다.
- **수작업 sealor**: Featherweight Rust와 실제 Rust의 봉합 규칙은 저자들이 직접 만들었습니다. 언어 명세에서 규칙을 자동 합성하는 일은 미래 과제입니다.
- **판정과 진단의 차이**: 형식 보증은 컴파일러의 `ok` 판정에 관한 것입니다. 반환된 진단 문구가 원래 부분 프로그램의 진짜 결함을 정확히 설명한다는 성질까지 형식화하지는 않았습니다.
- **공개 코드 확인 불가**: 논문은 proof mechanization, 구현, 벤치마크, 결과를 `eth-sri/generative-compilation`에 공개했다고 적었지만, 2026년 7월 16일 15:14 KST 확인 시 GitHub API와 raw URL은 404를 반환했습니다. 발행 전 다시 확인해야 합니다.

## 다메카솔의 실무 해석

저는 이 논문에서 하나만 가져간다면 **컴파일러를 최종 검수 도구가 아니라 생성 중 조기 피드백 서비스로 배치한다**는 발상이라고 봅니다. 코딩 에이전트 harness를 설계한다면 다음을 따로 점검할 가치가 있습니다.

1. 부분 출력에서도 실행할 수 있는 검증기가 있는가?
2. 오탐 없이 닫히지 않은 구조를 임시 완성할 방법이 있는가?
3. 진단을 원래 코드 위치와 짧은 수정 구간으로 되돌려 줄 수 있는가?
4. 조기 검사의 비용이 끝까지 잘못 생성하는 비용보다 작은가?
5. 컴파일 뒤에도 테스트, 정적 분석, 보안 검토, 요구사항 검증을 별도로 유지하는가?

컴파일러는 Rust의 정적 규칙을 강하게 검사하지만, 비즈니스 로직이 맞는지, 보안 정책이 충분한지, 사용자가 원한 동작인지까지 보장하지 않습니다. 이 논문은 마지막 검사를 없애자는 이야기가 아니라, **검증을 더 일찍 시작하자**는 이야기로 읽는 편이 정확합니다.
