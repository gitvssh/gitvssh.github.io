글·해설: 다메카솔

서버 프로세스는 24시간 멀쩡히 떠 있는데, 새벽만 되면 배치 작업이나 파일 업로드가 줄줄이 실패하는 기이한 현상을 겪어보신 적 있으신가요?

홈랩에서 시놀로지 NAS 기반으로 Airflow를 운영할 때 겪었던 가장 큰 패착이 바로 이것이었습니다. 애플리케이션 파드 자체는 상시 가동 상태였지만, 야간에 전력과 소음 문제로 꺼지는 NAS 안에 Airflow 메타데이터 DB와 결과 파일 저장용 S3(MinIO)가 함께 물려 있었습니다. 앱 서버가 켜져 있어도 **하위 상태 서비스(State Service)가 꺼져 있으면 시스템의 실질 가동시간(Uptime)은 0이 된다는 사실**을 뼈저리게 배웠습니다.

**"애플리케이션의 진짜 가동시간은 필수 의존성들이 함께 살아 있는 공통 시간창으로 결정된다."**  
이번 글에서는 단일 서버 관점이 아닌, 엔드투엔드 의존성 그래프를 기반으로 가용성을 설계하는 방법을 정리했습니다.

## 가동시간은 '겹치는 시간창'의 교집합이다

![소비자는 하루 종일 켜져 있지만 DB와 스토리지는 일부 시간만 켜져 있어 실제 동작 시간이 겹치는 구간으로 좁아지는 도식](./page-01.webp)

아무리 애플리케이션 웹서버를 99.99% 고가용성으로 띄워두어도, 요청 하나를 끝마치는 데 필요한 하위 컴포넌트 중 단 하나라도 죽어 있으면 사용자는 장애를 겪습니다.

- **로그인/인증**: DNS ➡️ Gateway ➡️ Auth DB
- **파일 업로드**: DNS ➡️ API Server ➡️ Meta DB ➡️ Object Storage

만약 API 서버는 24시간 켜져 있는데 메타 DB나 스토리지가 주간 12시간만 켜진다면, 해당 서비스의 실제 유효 가동시간은 **12시간(두 시간창의 교집합)**에 불과합니다. 따라서 시스템의 가용성은 개별 서버 스펙이 아니라 **"비즈니스 기능 하나가 통과하는 엔드투엔드 호출 경로의 공통 가용 시간"**으로 계산해야 합니다.

## 단일 기능 단위로 의존성 맵(Dependency Graph) 그리기

![하나의 워크플로가 메타데이터 DB, 오브젝트 저장소, DNS, 인증에 의존하는 실행 경로를 보여 주는 도식](./page-02.webp)

"우리 서비스는 잘 돌아간다"처럼 뭉뚱그려 생각하면 숨은 장애 지점을 찾을 수 없습니다. "새 파일 1건을 업로드하고 다시 다운로드받는다"처럼 **구체적인 비즈니스 트랜잭션 1건**을 기준으로 호출 경로를 끝까지 추적해 표를 채워야 합니다:

| 의존 대상 | 시스템 내 역할 | 필요 시간대 | 다운 시 증상 | 확인 검증 방법 |
| :--- | :--- | :--- | :--- | :--- |
| **CoreDNS** | 서비스 이름 ➡️ 내부 IP 주소 해석 | 요청 처리 전 시간 | 모든 네트워크 커넥션 시도 전 즉시 실패 | 파드 내부에서 도메인 `nslookup` |
| **인증/Vault** | 시크릿 및 DB 접근 토큰 발급 | 로그인 및 커넥션 풀 초기화 시점 | 인증 만료 에러, 401/403 에러 | 신규 세션 토큰 갱신 테스트 |
| **메타데이터 DB** | 작업 상태 기록 및 락(Lock) 관리 | 트랜잭션 시작~종료 전 구간 | 상태 업데이트 쿼리 타임아웃 | DB 핑 및 INSERT 쿼리 테스트 |
| **오브젝트 스토리지** | 대용량 원본 파일 및 결과 바이너리 저장 | 작업 후반부 업로드/다운로드 | 파일 쓰기 단계에서 Connection Refused | 실제 테스트 파일 Put/Get 호출 |

특히 주의할 점은 **'연결 캐시의 착시'**입니다. 이미 맺어진 DB 커넥션 풀이나 로컬 DNS 캐시 덕분에 기존 파드는 잠시 정상처럼 보여도, 트래픽이 몰려 파드가 스케일아웃되거나 재시작되는 순간 전면 장애로 터질 수 있습니다.

## DB만 옮기는 땜질 처방이 실패하는 이유

![메타데이터 DB는 상시 클러스터로 옮겼지만 오브젝트 저장소가 야간에 꺼지는 NAS에 남아 실행 경로가 여전히 끊기는 장면](./page-03.webp)

인프라를 마이그레이션할 때 가장 흔히 저지르는 실수가 "가장 눈에 띄는 메인 RDBMS 하나만 상시 가동 서버로 옮기는 것"입니다.

하지만 실제 데이터 파이프라인을 뜯어보면, DB 쿼리는 정상 성공하지만 수집된 대용량 원본 로그나 결과 파켓을 S3 저장소에 밀어 넣는 후속 단계에서 커넥션 에러가 터집니다. 결국 DB만 옮겨봤자 파이프라인 전체는 여전히 밤마다 멈추게 됩니다.

마이그레이션의 완료 기준은 "새 서버에 DB 프로세스가 떴는가"가 아닙니다. **"신규 요청이 들어와서 최종 산출물이 저장되고 다시 조회될 때까지, 과거의 불안정한 레거시 경로를 단 한 번도 타지 않는 것"**이 증명되어야 진짜 완료입니다.

## 아키텍처 3계층 분리: 상시 가동 vs 예약 지원 vs 백업 보관

![라이브 의존성은 상시 실행 계층, 백업 NAS는 예약 지원 계층, 독립 사본은 복구 보관 계층으로 나눈 구조](./page-04.webp)

의존성 목록이 정리되었다면, 하드웨어 장비가 아니라 **서비스의 운영 목적과 수명 주기**에 따라 3개 계층으로 분리해야 합니다:

1. **상시 가동 계층 (Live Layer)**: 24시간 실시간 트래픽을 받는 웹/API, 메타 DB, 실시간 오브젝트 스토리지
2. **예약 지원 계층 (Scheduled Layer)**: 정해진 야간 배치 시간대에만 기동되어 무거운 데이터 정제나 대용량 분석을 수행하는 배치 워커
3. **복구 보관 계층 (Backup & Vault Layer)**: 운영 환경과 물리적으로 격리되어 스냅샷 및 오프사이트 백업을 안전하게 보관하는 콜드 스토리지

이렇게 계층을 명확히 나누면 "NAS를 밤에 꺼도 되는가?"에 대한 답이 명확해집니다. NAS가 라이브 스토리지 역할을 겸하고 있다면 절대 끄면 안 되지만, 주간 정기 백업 보관소 역할만 맡는다면 백업 스케줄 외 시간대에는 전원을 내려도 서비스에 아무런 영향이 없습니다.

## StatefulSet과 PDB(PodDisruptionBudget)의 한계

쿠버네티스를 도입했다고 해서 가용성 문제가 저절로 해결되지는 않습니다.

- **StatefulSet**: 파드에 고정된 네트워크 식별자와 PVC를 붙여줄 뿐, 하부 스토리지의 복제(Replication)나 DB 장애 시 자동 페일오버(Failover)까지 대신해 주지는 않습니다.
- **PDB (PodDisruptionBudget)**: 노드 점검(`kubectl drain`) 같은 **자발적 퇴거(Voluntary Disruption)** 상황에서 최소 파드 수를 지켜줄 뿐, 하드웨어 전원 단선이나 커널 패닉 같은 **불시의 비자발적 장애(Involuntary Disruption)**까지 막아주지는 못합니다.

따라서 진정한 가용성을 확보하려면 파드 레플리카 수만 늘릴 것이 아니라, **"파드들이 물리적으로 같은 멀티탭, 같은 네트워크 스위치, 같은 NAS 볼륨에 묶여 있는 것은 아닌가?"**라는 단일 장애 지점(SPOF, Single Point of Failure)을 점검해야 합니다.

## 다메카솔의 해석: RTO/RPO에서 출발하는 복구 엔지니어링

시스템 가용성 설계의 완성은 "절대 죽지 않는 완벽한 서버를 만드는 것"이 아니라, **"장애가 났을 때 얼마나 빠르고 정확하게 이전 상태로 되돌릴 수 있는가"**를 정의하는 데 있습니다.

실무 아키텍처를 검토할 때 다음 3가지를 명확히 수립해야 합니다:

1. **목표 복구 시간(RTO)과 복구 시점(RPO)**: 서비스 장애 발생 후 몇 분 안에 정상화되어야 하는지(RTO), 데이터 유실은 최대 몇 분/몇 시간 전까지 허용 가능한지(RPO)를 비즈니스 관점에서 합의해야 합니다.
2. **복제(Replication)와 백업(Backup)의 역할 분리**: 실시간 복제는 무중단 가용성을 위한 것이고, 백업은 잘못된 데이터 삭제나 랜섬웨어로부터 과거 시점을 복원하기 위한 것입니다. 두 목적을 혼동하면 안 됩니다.
3. **정기적인 재해 복구(DR) 리허설**: 백업 파일이 디스크에 잘 쌓이고 있어도, 실제 새 환경에 복원 쿼리를 돌려보지 않으면 복구 성공을 장담할 수 없습니다. 주기적으로 복구 파이프라인을 직접 가동해 보아야 합니다.
