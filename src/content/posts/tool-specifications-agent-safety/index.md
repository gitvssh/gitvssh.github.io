거절률이 58%에서 3%로 떨어졌습니다. 동일한 Llama 3.1 8B Instruct 모델에 똑같은 유해 요청을 넣었는데, 일반 챗봇 형식에서는 절반 넘게 거절하던 모델이 도구 명세(schema)를 붙인 에이전트 입력에서는 거의 거절하지 않았습니다. 2026년 7월 31일 공개된 **Tool Specifications Matter: Uncovering and Mitigating Safety Risks in AI Agents**가 파고든 출발점입니다.

저자들은 도구의 기능 자체보다 **그 기능을 전달하는 JSON 스키마 형식이 모델 내부의 거절 표현을 약화시킨다**고 보고하며, 안전 판단 단계에는 평문 도구 설명을 쓰고 실제 실행 단계에만 원래 스키마를 쓰는 2단계 방어 구조 **SafeKeep**을 제안했습니다.

글·해설: 다메카솔

## 핵심 내용

- **스키마 부착에 따른 거절률 급락**: Llama 3.1 8B Instruct 기준 동일 유해 요청의 거절률이 챗봇 입력 58%에서 에이전트 입력(역할 설명 + 도구 지시 + 도구 명세) 3%로 떨어졌으며, 은닉 상태(hidden state)의 유해·무해 분리 AUROC도 0.927에서 0.740으로 하락했습니다.
- **의미보다 구조(JSON 스키마)의 영향**: 도구 이름·시그니처·기능·인자 의미는 그대로 두고 JSON 구문·예약 필드·중첩·타입 선언만 걷어낸 **평문(plain-text) 표현**으로 바꾸자 세 공개 모델 모두에서 유해·무해 구분 능력이 회복되었습니다.
- **SafeKeep 2단계 분리 효과**: 1단계 안전 판단에는 평문 도구 설명을, 통과한 요청의 2단계 실행에는 원래 스키마를 사용한 결과, 4개 모델 평균 AgentHarm 유해 요청 거절률이 23.8%에서 70.6%로 오르고 InjecAgent 간접 프롬프트 주입 공격 성공률은 25.6%에서 2.5%로 낮아졌습니다.

## 도구를 붙인 뒤 같은 모델의 거절이 달라졌다

![같은 AI 코어가 대화 경로에서는 위험 행동 앞에 멈추지만 도구 명세 경로에서는 흐려진 안전 신호를 지나가는 장면](./page-01.webp)

이 실험의 핵심은 모델 가중치나 사용자 요청을 바꾸지 않았다는 점입니다. 일반 챗봇 입력에는 기본 시스템 프롬프트와 사용자 요청만 들어가고, 에이전트 입력에는 여기에 역할 설명, 도구 사용 지시, 도구 명세가 추가됩니다. 이 차이만으로 Llama 실험의 유해 요청 거절률이 58%에서 3%로 주저앉았습니다.

표면적인 응답만 달라진 것이 아니었습니다. 연구팀이 모델 내부 은닉 상태(hidden state)에서 유해 요청과 무해 요청을 가르는 ‘거절 방향’ 벡터를 추출해 대조한 결과, 챗봇 형식에서 0.927이던 유해·무해 분리 AUROC가 에이전트 입력에서는 0.740으로 떨어졌습니다. 입력 형식 자체가 모델 내부의 안전 판별 신호를 흐린 것입니다.

## 내용보다 스키마 형식이 더 크게 흔들었다

![도구 의미와 표현 형식을 교차해 바꾸는 네 실험 경로 가운데 의미를 보존한 평문 경로에서 안전 나침반이 회복되는 장면](./page-02.webp)

연구팀은 에이전트 입력의 세 구성요소(역할 설명, 도구 사용 지시, 도구 명세)를 하나씩 더해 가며 원인을 좁혔습니다. 세 공개 모델 모두에서 마지막 **도구 명세**가 붙을 때 가장 큰 AUROC 하락이 나타났으며, 단순히 문맥 길이만 비슷하게 늘린 대조군에서는 같은 하락이 나타나지 않았습니다.

이어서 “도구가 수행하는 기능의 의미”와 “그 기능을 감싼 JSON 스키마 형식” 중 어느 쪽이 원인인지 교차 실험을 진행했습니다.

- **평문 변환(의미 보존 + 스키마 구문 제거)**: JSON 괄호, 예약 필드, 중첩 구조, 타입 선언을 걷어내고 도구 이름·함수 시그니처·기능·인자 의미만 평문으로 풀어 쓰자 세 모델 모두에서 유해·무해 구분 능력이 회복되었습니다.
- **가짜 단어 치환(의미 제거 + 스키마 구문 유지)**: 반대로 단어 의미를 무의미한 가짜 단어로 바꾸고 JSON 스키마 구조만 남겼을 때는 뚜렷한 회복이 일어나지 않았습니다.

은닉 상태 분석에서도 스키마 형식이 만드는 벡터 방향이 유해 요청의 거절 방향과 모든 레이어에서 반대쪽으로 정렬되는 현상이 관찰되었습니다. 도구 자체의 기능보다 구조화된 스키마 형식이 모델을 ‘안전 검토 모드’가 아닌 ‘구문 채우기·실행 모드’로 밀어 넣는다는 인과적 단서입니다.

## 안전 판단과 실행에 서로 다른 표현을 썼다

![요청이 평문 도구 설명을 읽는 안전 관문을 먼저 지나고 안전한 흐름만 원래 스키마가 있는 실행 구역으로 들어가는 장면](./page-03.webp)

저자들이 제안한 **SafeKeep**은 한 번의 모델 호출이 안전 판단과 도구 실행을 동시에 처리하게 두지 않고 두 단계로 나눕니다.

1. **1단계 안전 관문 (평문 설명 기반)**: 도구의 기능과 인자 의미를 보존한 평문 설명과 사용자 요청을 함께 읽어 유해 여부를 먼저 판정합니다. 위험하다고 판단되면 도구 실행으로 넘기지 않고 즉시 거절합니다.
2. **2단계 도구 실행 (원래 스키마 기반)**: 1단계에서 안전하다고 판정된 요청만 기존 에이전트 파이프라인으로 넘겨 원래의 JSON 스키마 명세로 정확한 도구 호출을 생성합니다.

이 방식은 모델 가중치를 재학습하거나 내부 활성화 값(activation)을 직접 조작할 필요가 없어 API 기반 상용 모델에도 바로 적용할 수 있습니다. 또한 “그저 안전 판정기를 한 번 더 호출해서 좋아진 것 아닌가?”라는 의문을 검증하기 위해, 똑같은 2단계 구조를 쓰되 1단계에 원래 JSON 스키마를 그대로 넣은 대조군(`SafeJudge`)과 비교해 평문 변환(`SafeKeep`)이 뚜렷한 추가 방어 이득을 만든다는 점도 확인했습니다.

## 두 벤치마크와 네 모델에서 확인한 방어 성능

최종 평가는 4개 모델(Llama 3.1 8B Instruct, Qwen3 8B, Gemini 3.1 Flash, GPT-5.4 mini)과 2개 벤치마크에서 진행됐습니다.

| 평가 지표 (4개 모델 평균) | 기본 에이전트 | SafeKeep 적용 후 | 평가 벤치마크 구성 |
| --- | --- | --- | --- |
| **직접 유해 요청 거절률** | 23.8% | **70.6%** | **AgentHarm**: 11개 위해 범주의 유해 요청 176개 + 유사 도구를 쓰는 무해 요청 176개 |
| **간접 프롬프트 주입 공격 성공률 (낮을수록 안전)** | 25.6% | **2.5%** | **InjecAgent**: 외부 관찰 결과에 악성 지시가 섞인 공격 1,054개 (기본형 + 강화형 합산) |

무해 요청에 대한 과제 수행 정확도와 유효 출력률 역시 논문이 사용한 벤치마크 지표 안에서 함께 개선되었습니다.

## 실험 범위와 측정되지 않은 운영 비용

![성인형 카솔이 두 벤치마크와 네 모델의 증거 옆에서 아직 측정되지 않은 지연 계기와 실서비스 문을 확인하는 장면](./page-04.webp)

이 결과를 실서비스에 적용할 때는 논문이 측정하지 않은 운영 비용과 범위를 함께 고려해야 합니다.

- **추론 지연과 토큰 비용 미보고**: SafeKeep은 실행 전에 별도의 안전 판단 호출을 한 번 더 거치므로 응답 지연(latency)과 API 토큰 비용이 늘어날 수밖에 없지만, 논문에는 이에 대한 정량 수치가 보고되지 않았습니다.
- **벤치마크와 실서비스 환경의 차이**: 4개 모델과 2개 벤치마크의 고정된 도구 템플릿 안에서 검증된 결과이므로, 수십 개 도구가 얽힌 장기 멀티턴 대화나 복잡한 인증·권한 체계에서도 동일한 폭의 개선이 유지되는지는 별도 검증이 필요합니다.

## 다메카솔의 해석: 실행 명세와 안전 판단을 분리해 본다

저자 저장소에는 분석 스크립트와 SafeKeep 데모, 유해·무해 요청 400쌍이 공개되어 있어 자체 파이프라인에서 재현해 보기 좋은 출발점을 제공합니다. 실무 에이전트에 이 아이디어를 도입한다면 실행용 JSON 스키마를 안전 판정의 유일한 입력으로 재사용하지 않고, 평문 요약 표현으로 위험 여부를 먼저 거르는 앞단 게이트를 시험해 볼 수 있습니다.

이때 배포 전 점검 항목은 세 가지로 압축됩니다.

1. 정상적인 업무 요청이 1단계 안전 관문에서 오탐으로 막히지 않는가?
2. 외부 검색·문서 읽기 결과에 섞인 간접 프롬프트 주입이 도구 실행으로 넘어가지 않는가?
3. 2단계 분리로 늘어난 응답 지연과 토큰 비용이 서비스 목표(SLO) 안에 들어오는가?

모델 자체의 안전 정렬만 믿지 말고, **모델에 도구를 설명하는 인터페이스 형식까지 안전 감사의 일부로 다뤄야 한다**는 것이 이 논문이 남긴 핵심 메시지입니다.
