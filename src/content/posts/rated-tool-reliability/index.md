글·해설: 다메카솔

도구 설명이 사용자의 요청과 의미상 잘 맞아떨어지면 에이전트도 문제없이 일을 끝낼 것이라 기대하기 쉽습니다. 하지만 정작 호출 대상 API가 멈춰 있다면, 의미 검색이 똑같은 도구를 계속 추천하면서 같은 실패가 반복되죠.

**RATED는 의미 기반 검색 뒤에 ‘실행 피드백을 반영하는 재순위(re-ranking) 단계’를 덧붙이는 연구**입니다. 구조적인 아이디어는 실무에서도 참고할 만하지만, 논문의 장애 주입 실험 수치와 공개된 평가 코드 사이에는 짚어 봐야 할 차이도 남아 있습니다.

## 핵심 내용

- **의미 검색과 실행 피드백의 분업**: 미세조정 후 고정한 인코더(DRAGON)로 상위 10개 후보를 추린 뒤, 실행 성공·실패 이력과 메타데이터를 반영해 순위를 조정합니다.
- **고장 회피와 정답 선택의 균형**: 도구 30% 장애 주입 조건에서 RATED는 고장 도구 선택률 2.9%, 정답이면서 가용한 도구 선택률 82.1%를 보고했습니다.
- **논문 설명과 공개 코드의 차이**: 2026년 10월 12일 확인한 공식 저장소(`bc5db40`)의 평가 스크립트는 후보 구성·보상 값·집계 구간이 본문 설명과 달라 그대로 실행해 같은 표를 재현하기는 어렵습니다.

## 실행 결과가 다음 선택에 돌아오게 한다

![의미 검색 뒤 실행 피드백으로 도구 후보 순서를 바꾸는 개념 흐름](./page-01.webp)

도구 검색기가 방금 난 호출 실패를 알아야 다음번 선택도 달라질 수 있습니다.

저자들은 DRAGON 인코더를 합성 데이터(EcoAgent-Syn)로 미세조정한 뒤 고정하고, 의미 검색으로 뽑은 **상위 10개 후보**에 질의 맥락·도구 메타데이터·실행 이력을 결합해 순위를 다시 매긴다고 설명합니다. 이때 실제로 호출한 도구의 결과만 관측하며, **discounted LinUCB** 알고리즘으로 오래된 관측 기록의 비중을 점차 낮춰 최근 상태를 더 크게 반영합니다. [원문 §3](https://arxiv.org/html/2610.13889v1#S3)

저는 이 **역할 분담**에 눈이 갔습니다. 일시적인 외부 API 장애가 날 때마다 거대 언어 모델이나 검색 인코더 전체를 다시 학습시키는 대신, 가벼운 순위 조정 계층으로 실행 피드백을 돌려주는 접근이기 때문입니다. 모델 추론과 실행 환경 제어의 책임을 나눴던 [HEAR의 하네스·엔진 협업 구조](/posts/hear-harness-engine-coordination/)와 나란히 놓고 보면 어느 계층에서 장애에 대응할지 설계 힌트를 얻기 좋습니다.

## 논문이 보고한 성능의 범위

![장애를 주입한 실험과 도구 가용성·정답 선택의 차이](./page-02.webp)

성적표를 읽을 때는 **‘고장 난 도구를 피했는가’와 ‘원래 요청에 맞는 정답 도구를 골랐는가’**를 나누어 봐야 합니다.

저자들이 구축한 EcoAgent는 5,172개 도구 정의를 모은 데이터셋이며, 실제 평가에 쓴 **EcoAgent-Real**은 ToolBench에서 가져온 6,379개 질의를 자동 검색과 모델 판정으로 도구에 연결한 자료입니다(사람이 직접 검수한 200개 표본에서는 판정 일치율 94%를 보고했으며, 실제 상용 서비스의 실시간 장애 로그를 그대로 수집한 데이터는 아닙니다). [원문 §2](https://arxiv.org/html/2610.13889v1#S2)

먼저 장애가 없는 정적 검색에서 정답 도구의 순위를 나타내는 **MRR**은 RATED `0.618`, ToolLLM `0.406`, Ada-002 `0.670`이었습니다. 초록에서 강조한 ‘52.2% 향상’은 ToolLLM과 비교한 상대 개선폭이어서, 모든 비교 모델 중 절대 1위라는 뜻으로 읽으면 곤란합니다. [표 1](https://arxiv.org/html/2610.13889v1#S4.T1)

동적 장애 실험에서는 전체 10,000단계 시뮬레이션 중 등장 빈도 상위 10% 도구를 건너뛴 뒤, 그다음 일정 비율의 정답 도구들을 **고정 장애 집합(계속 실패하는 상태)**으로 만들고 장애 발생 이후 2,001~5,000단계(3,000회 선택)를 집계했다고 설명합니다. 아래는 **도구 30%에 장애를 주입한 조건의 저자 보고치**입니다(매 호출마다 30% 확률로 무작위 실패가 나는 설정과는 다릅니다). [원문 §4.2·표 2](https://arxiv.org/html/2610.13889v1#S4)

| 방법 | 고장 도구 선택률 ↓ | 정답이면서 사용 가능한 도구 선택률 ↑ |
| --- | ---: | ---: |
| ToolLLM | 86.2% | 10.5% |
| 한 번 실패하면 차단 (Blacklist) | 1.9% | 80.2% |
| 최대 3개 후보 재시도 (Retry k=3) | 19.1% | 82.9% |
| RATED | 2.9% | 82.1% |

고장 난 도구를 피하는 비율만 놓고 보면 ‘한 번 실패한 도구를 영구 차단하는 방식(1.9%)’도 무척 강력합니다. 또한 고장 도구 선택률 2.9%의 반대편인 `97.1%`를 곧바로 ‘실제 과제를 끝까지 완수한 비율’로 치환할 수도 없습니다. 두 지표를 나란히 놓고 읽어야 하는 이유입니다.

## 공개 코드가 같은 실험을 실행할까

![논문과 공개 평가 코드의 차이를 살피며 실제 환경의 검증을 구분하는 카솔](./page-03.webp)

이번 글을 준비하며 2026년 10월 12일 확인한 공식 저장소(고정 커밋 `bc5db40`)의 평가 스크립트를 논문 본문과 대조해 보았는데요, 눈여겨볼 구현 차이가 세 가지 있었습니다. [해당 코드 180~308행](https://github.com/Elliotes/EcoAgent/blob/bc5db40a20b254c5249401d2220ea71b06c86a5c/scripts/evaluation/evaluate_rated_full.py#L180-L308)

- **후보 구성 방식**: 논문 본문은 전체 도구에 대한 의미 검색 상위 10개 후보를 재순위한다고 설명하지만, 공개 스크립트는 정답 라벨과 장애 대상 여부를 참조해 후보 풀을 구성함
- **보상 함수**: 논문 알고리즘은 이진 보상(`0` 또는 `1`)을 적었으나, 스크립트는 성공 시 `1`, 장애 시 `-2` 등을 섞은 혼합 보상을 사용함
- **집계 구간**: 본문은 2,001~5,000단계를 집계한다고 설명하지만, 스크립트는 장애 직후 첫 1,000단계에서 성공률을, 장애 이후 전체 구간에서 고장 선택률을 계산함

따라서 현재 공개된 스크립트를 그대로 실행한다고 해서 논문 표 2의 수치가 똑같이 재현된다고 보장하기는 어렵습니다(이 글에서는 모델을 재학습하거나 실험을 직접 다시 돌리지 않았으며, 이 코드 차이가 논문 결과 전체를 무효로 만든다고 단정하지도 않습니다). 저자들 역시 신규 도구(cold-start) 평가와 실제 에이전트 런타임 검증은 후속 과제로 남겨 두었습니다. [결론](https://arxiv.org/html/2610.13889v1#S5)

## 다메카솔의 해석: 실패 신호부터 나누고 싶습니다

제가 현업 에이전트 시스템에 이런 도구 재순위 계층을 넣는다면, 점수를 깎는 알고리즘보다 **‘무엇을 도구 장애로 기록할 것인가’**부터 먼저 분리하겠습니다.

실제 운영 환경에서는 호출 실패의 원인이 제각각입니다.

- **일시적 서버·네트워크 장애 (`503`, 타임아웃)**: 다른 대체 도구나 백오프 재시도를 고려할 신호
- **모델이 잘못 만든 인자 (`400 Bad Request`)**: 도구 고장이 아니라 프롬프트·스키마 보정이 필요한 신호
- **권한 부족 (`403 Forbidden`)**: 다른 도구로 우회해서는 안 되며 즉시 멈추고 권한을 확인해야 할 신호

이 세 가지를 똑같은 실패 점수로 묶어 버리면, 멀쩡한 도구가 모델의 인자 실수 때문에 후보에서 밀려나거나 반대로 권한 거부를 우회하려는 위험한 시도가 생길 수 있습니다(이는 논문 결과와 별개인 제 엔지니어링 설계 기준입니다).

또한 도구 호출이 성공(`200 OK`)했다고 해서 응답 내용이 항상 정확한 것도 아닙니다. **① 도구 선택의 적합성, ② API 가용성, ③ 반환 데이터의 정확성, ④ 최종 사용자 요청 완수 여부**를 각각 따로 기록하고, 결제나 문서 수정처럼 부작용(side effect)이 있는 호출은 대체 도구를 고르기 전에 앞선 요청이 이미 반영됐는지(멱등성)부터 확인해야 합니다.

이 연구에서 가져올 핵심 질문은 **“실행 계층의 실패 신호를 어떻게 도구 선택 계층으로 돌려줄 것인가”**입니다. 실제로 도입을 검토할 때는 기존 서킷 브레이커·재시도 정책과 같은 요청 묶음에서 비교하고, 장애가 복구된 도구를 다시 후보로 받아들이는 조건까지 함께 시험해 보길 권합니다. [에이전트 평가에서 실행 설정을 함께 기록해야 하는 이유](/posts/agent-evaluation-system-configuration/)와도 직결되는 주제입니다.
