**Text-to-SQL의 정확도를 높이려면, 질문 속 용어가 데이터베이스의 어느 값에 해당하는지 먼저 찾아야 합니다.** ‘분기 매출’을 요청했는데 연간 매출의 ID를 넣었다면, 문법이 완벽한 SQL도 다른 답을 가져옵니다. FLINT 연구진은 이 연결을 별도 단계로 만들어 복잡한 금융 데이터 조회를 개선했습니다. 백엔드 개발자에게는 프롬프트 길이보다 **값의 의미를 어디서 공급하는가**가 흥미로운 대목입니다.

*글·해설: 다메카솔*

원문 확인·작성: 2026년 10월 5일

이번에 읽은 논문은 Kensho Technologies의 Arijit Sehanobish 등이 쓴 **From Benchmarks to Production: A Text-to-SQL System for Complex Financial Data**입니다. 2026년 10월 2일 제출된 arXiv v1을 기준으로 설명합니다. 금융 데이터의 의미를 SQL 조건에 연결하는 시스템 연구입니다.

## 컬럼 이름만 보고는 고를 수 없는 값

![질문의 개념을 참조 목록에서 찾고 일치하는 연결 고리를 고르는 과정을 비유한 만화](./page-01.webp)

`metric_id`라는 컬럼 이름은 값이 식별자라는 사실까지 알려 줍니다. 그중 어느 값이 매출인지는 참조 테이블을 읽어야 알 수 있는데요, 기간이나 통화도 별도 ID로 관리하면 간단한 질문 하나에 여러 연결이 필요해집니다. SQL이 실행된다는 사실만으로는 이 선택이 맞았는지 알기 어렵습니다.

예를 들어 사용자가 ‘A사의 분기 매출’을 물었다고 해 보겠습니다. 시스템은 회사, 매출 지표, 분기라는 기간의 뜻을 각각 맞춘 뒤 필요한 테이블을 연결해야 합니다. 회사만 정확하고 기간을 연간으로 골랐다면 쿼리는 정상 종료될 수 있습니다. **틀린 답에도 실행 오류가 없을 수 있다는 뜻입니다.** 이 예시는 논문의 문제를 풀어 쓴 설명이며 실제 고객 질의를 인용한 것은 아닙니다.

FLINT의 **Lookup Agent**는 먼저 질문과 관련된 참조 테이블을 고릅니다. 이어 SELECT로 읽어 온 후보에서 적절한 값을 선택해 WHERE 조건을 만들고, 나중 단계에 넘깁니다. 모델이 ID를 기억해 내는 데 기대기보다 데이터베이스에서 선택 근거를 공급하는 설계입니다.

조회만 추가하면 끝나는 구조는 아닙니다. 전문가가 작성한 질의 예시 중 비슷한 것을 가져오고, 회사 이름을 내부 식별자에 연결하며, 데이터까지 도달하는 중간 테이블과 조인 경로를 고릅니다. SQL 생성은 그렇게 모인 조건과 경로를 받아 마지막 문장을 작성합니다. 스키마 연결 단계는 고정된 전체 스키마를 보므로, 거대한 임의의 데이터베이스를 처음 만나 곧바로 처리하는 구조와는 적용 범위가 다릅니다.

여기에는 사람의 준비도 들어갑니다. Financials의 지표 11,412개는 전문가가 자주 쓰는 약 2,500개로 추린 뒤, 질문별로 약 50~100개 후보까지 좁힙니다. 논문의 후보 재현율 98%는 이 평가셋에서 필요한 값이 후보에 남았다는 뜻입니다. 최종 답변 정확도는 다음 단계까지 거쳐 따로 측정합니다. 그림의 열쇠와 자물쇠는 이 선택 과정을 나타내며, 실제 접근 권한이나 물리적인 데이터베이스 동작을 묘사하지 않습니다.

## 거의 다 실행됐지만, 답은 갈렸습니다

![실행 성공과 질문에 맞는 답을 두 개의 서로 다른 검사로 보여 주는 만화](./page-02.webp)

저자들의 주 실험에서 비교 방법들은 모두 **99% 이상 실행에 성공**했습니다. 그런데 기존 비교 시스템 중 정확도 50%를 넘긴 방법은 없었습니다. 오류 없이 끝났다는 로그만으로 서비스를 평가하면 큰 부분을 놓치는 셈입니다.

이 결과의 범위는 비공개 금융 데이터 두 묶음입니다. Financials는 221문항, Transactions는 138문항으로 총 359문항이며, 모든 방법에 Claude 4.5 Opus를 사용했습니다. 아래는 논문 Table 2에서 발췌한 정확도이며, 순서는 Financials / Transactions입니다.

- **FLINT: 68.8% / 65.2%**
- ReFoRCE: 46.6% / 47.1%
- CHESS, 후보 10개 설정: 35.6% / 49.6%

비교 기반과 일부 구성요소는 공유했고, 각 시스템을 금융 스키마에 맞춘 조정은 부록 D에 설명돼 있습니다. 따라서 이 수치는 해당 데이터와 조정 조건에서 얻은 저자들의 결과로 읽어야 합니다. 모든 데이터베이스에서 같은 차이를 얻는다는 의미로 넓힐 근거는 없습니다.

참조값 조회의 역할은 구성요소를 하나씩 빼는 실험에서 더 잘 보입니다. Table 3에서 Lookup Agent를 제거하자 정확도가 54.8% / 33.3%로 낮아졌습니다. 이때 비교 대상에는 자주 쓰는 ID의 정적 매핑을 제공했고, 저자들은 그 매핑이 약 78%의 질문을 커버한다고 설명합니다. 자주 쓰는 답을 미리 적어 주는 것과 질문마다 후보를 구분하는 것 사이에 차이가 있었던 셈입니다.

‘정확도’의 판정 방식도 함께 봐야 합니다. 실행 실패는 0점이고, 성공한 SQL은 구문 트리의 정규화와 결과값 비교를 거친 뒤 남은 경우를 LLM이 판단합니다. 부록 C의 무작위 판정 50건에서는 사람과 47건이 일치했습니다. 판정 자체에도 오차가 있고, SQL로 풀 수 있는 질문 중심으로 만든 평가셋이라는 제약도 남습니다.

## 다메카솔의 해석: 의미를 고르는 단계를 관찰하기

![선택한 의미와 ID를 확인한 뒤 데이터를 읽는 경로를 정리하는 카솔](./page-03.webp)

저라면 자연어 조회 서비스에서 **질문 → 선택한 ID → 생성한 필터 → SQL**을 함께 추적하겠습니다. 사용자가 기간을 잘못 이해한 결과를 받았을 때, 후보 목록에서 빠졌는지, 후보는 있었는데 다른 값을 골랐는지, SQL 생성 중 조건이 바뀌었는지 나눠 볼 수 있기 때문입니다. 이는 논문을 읽고 얻은 설계 해석이며, 제가 이 시스템을 운영해 효과를 측정했다는 뜻은 아닙니다.

이렇게 단계를 나누면 회귀 테스트도 구체적으로 만들 수 있습니다. 문법과 실행 여부를 검사하는 테스트 옆에, ‘분기’와 ‘연간’처럼 가까운 개념을 구분하는 질의를 두는 방식입니다. 데이터베이스가 바뀌면 참조값 목록과 도메인 규칙을 다시 확인하고, 고친 단계와 관련된 질문을 재실행할 이유가 생깁니다. [SQL에서 결과 조건과 실행 방법을 구분하는 이야기](/posts/sql-declarative-language/)가 여기서는 질문의 뜻과 생성된 조건을 대조하는 문제로 이어집니다.

읽을 수 있는 범위와 답의 정확도는 별도 책임입니다. 저자들은 실제 배포에서 읽기 전용 연결, 행 접근제어, 허용된 테이블·컬럼 검사와 자원 제한을 사용한다고 설명합니다. 이 장치들은 조회 권한과 자원 사용을 다루고, 의미가 잘못된 결과는 이상 징후와 사용자 피드백으로 살핍니다. 오류가 없다는 신호 하나에 두 책임을 모두 맡기지 않는 구성이 인상적입니다.

준비 비용도 설계의 일부입니다. 전문가 규칙과 질의 예시를 새 스키마에 맞춰 작성해야 하고, 논문의 시스템은 이전 대화를 잇는 후속 질문을 지원하지 않습니다. 성능을 비교할 때 모델 이름 외에 이런 입력과 구성 조건을 적어야 하는 이유는 [에이전트 평가의 실행 설정](/posts/agent-evaluation-system-configuration/)에서도 살펴봤습니다.

원문 부록에 적힌 코드 저장소는 10월 5일 확인 시 404를 반환했습니다. 주 금융 평가 데이터도 비공개여서, 이번 글은 공개 원문을 읽은 리뷰에 해당합니다. 저자들이 연결한 제품 페이지는 서비스 소개를 제공하지만, 논문 수치를 독립적으로 재현한 자료는 아닙니다.

다음 자연어 조회 테스트에는 **실행은 성공하지만 기간·통화·지표가 틀린 질문**을 한 묶음 더 넣어 보겠습니다. 그 질문에서 어떤 ID를 골랐는지부터 비교하면, 모델을 바꾸기 전에 손볼 데이터 연결이 보일 수 있습니다.
