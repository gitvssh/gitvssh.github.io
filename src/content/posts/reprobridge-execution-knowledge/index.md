논문에 딸린 공식 GitHub 저장소를 내려받아 실행해 보려다, 문서에 빠진 패키지 버전이나 바뀐 하이퍼파라미터 앞에서 하루를 날린 경험이 한 번쯤 있으실 겁니다. 어렵게 환경을 고쳐 수치를 맞춰 놓아도, 다음 동료나 새 코딩 에이전트가 투입되면 똑같은 시행착오를 처음부터 되풀이한다는 점이 더 답답하죠. ReproBridge는 한 번 복구한 실행 과정과 판단 근거를 코드·환경·실행기·안내서 네 묶음으로 보존해 두면 다음 실행자의 재현이 얼마나 안정되는지 검증한 연구입니다.

글·해설: 다메카솔

## 코드와 함께 남겨야 할 네 가지

공개 코드가 있더라도 어떤 라이브러리를 설치하고 어느 인자로 실행하며, 출력 파일에서 어느 값을 읽어야 하는지는 저장소 곳곳에 흩어져 있곤 합니다. 코딩 에이전트 역시 매 세션마다 이 빈칸을 추측으로 메우다 엉뚱한 결과를 내기 쉽거든요. ReproBridge는 실행 중에 복구한 지식을 네 가지 구성요소로 묶어 다음 실행자에게 넘깁니다.

- **수정한 코드**: 실행 결함을 고치고, 논문 표의 지표를 계산하는 데 빠졌던 기능을 보완합니다.
- **환경 설정**: 하드웨어에 호환되는 의존성 버전과 데이터·체크포인트 준비 절차를 고정합니다.
- **실험 실행기**: 각 과제를 설정·실행 범위·출력·측정값 추출과 연결해 스모크 테스트와 본 채점 실행을 구분합니다.
- **재현 안내서**: 설정과 수정 이유, 논문·코드 불일치, 집계 통계량과 민감도를 근거 위치와 함께 기록합니다.

예를 들어 *Mixture of Concept Bottleneck Experts* 논문에서는 네 개 전문가의 트리 편집 거리를 평균 낼지 합산할지 본문에 빠져 있었고, 공개 저장소에도 표 집계 스크립트가 없었습니다. 원 코드로 실행한 Sonnet 5는 평균 15 대신 합계 60을 보고했지만, 정제 자료에 분모 기준과 수집 스크립트를 담아 둔 뒤에는 정확히 15가 나왔죠.

자료를 만들 때 지키는 기준도 까다롭습니다. 점수를 본 뒤 유리한 설정을 고르는 편향을 막으려 실행 전에 측정 대상과 통계량을 정해 두고, 모든 결과는 실제 출력 파일로 추적할 수 있게 남깁니다. 가령 *Manifold-Aware Perturbations*처럼 논문 본문의 학습률(`10^-4`)과 공개 코드(`10^-3`)가 충돌하면, 논문의 설정을 따르되 불일치 위치와 영향을 받는 과제를 안내서에 적어 둡니다.

## 실험은 어떤 조건에서 비교했을까

연구진은 정제 자료를 만드는 과정(본 실험에서는 Opus 5가 제작)과 이를 받아 재현하는 새 세션을 철저히 분리했습니다. 후속 세션에는 논문과 과제 목록, 그리고 원래 코드나 정제 자료 가운데 하나만 제공했고, 자료 제작 대화와 숨겨진 기준 측정값은 모두 가렸습니다. 평가에 적용된 주요 실험 조건은 크게 세 가지입니다.

- **평가 표본**: 36개 논문의 387개 실험에서 추린 1,029개 과제를 평가했습니다. 처음 정리한 1,463개 과제 중 다섯 명의 사람 검증자가 확인한 기준 측정값과 논문 값이 수치적으로 호환되는 과제만 남겼습니다.
- **모델과 세션**: Sonnet 4.6, Sonnet 5, Opus 5, Gemini 3.8 Flash를 비교했으며, 논문·모델·조건마다 새 세션을 열었습니다.
- **자원과 감사**: 조건별 논문당 24시간 제한을 두었고 GPU 실험에는 H100 80GB 여덟 장을 썼습니다. 제출된 값이 실제 실행 결과인지는 독립 감사자(주 감사자 Codex)가 확인했습니다.

표본과 실행 도구의 경계도 짚어 둘 필요가 있습니다. 사람 검증을 통과한 과제만 후속 비교에 들어간 만큼, 이 수치는 학회 전체 논문의 평균 재현율보다는 검증된 과제 집합 안에서의 개선 폭으로 읽어야 정확합니다. 모델마다 실행 도구가 서로 달라 모델 간 점수 차이 역시 절대 서열보다 경향을 읽는 기술적 관찰로 봐야 합니다.

## 성공률과 비용 수치 읽기

세 차례 평가를 종합하면 네 모델을 동일 가중한 평균 성공률은 원래 코드 76.4%에서 출발해 정제 자료를 적용한 뒤 92.6%까지 뚜렷하게 높아졌습니다. 여기서 성공은 고정된 수치 허용 구간에 들어오고 독립 감사에서 확정된 위반이 없는 경우만 인정하며, 모델이 스스로 성공했다고 보고한 횟수와는 다릅니다. 모델별 세 차례 평균 결과는 아래 표에 정리했습니다.

| 모델 | 원 코드 성공률 | 정제 자료 성공률 | 변화 폭 | 후속 API 비용 (원 코드 → 정제 자료) | 비용 절감 |
| --- | --- | --- | --- | --- | --- |
| Sonnet 4.6 | 72.3% | 91.6% | +19.3%p | $3,165 → $2,512 | -20.6% |
| Sonnet 5 | 76.5% | 93.3% | +16.8%p | $1,726 → $1,317 | -23.7% |
| Opus 5 | 89.2% | 94.7% | +5.5%p | $3,480 → $2,865 | -17.7% |
| Gemini 3.8 Flash | 67.6% | 90.8% | +23.2%p | $392 → $326 | -16.8% |

표에서 눈에 띄는 대목은 모델 간 성공률 격차가 원래 코드의 21.6%p에서 정제 자료를 건넨 뒤 3.9%p로 좁혀지며 네 모델 모두 평균 90%를 넘겼다는 점입니다. 원 코드에서 상대적으로 고전하던 모델일수록 상승 폭이 컸거든요. 빠진 실행 맥락을 메워 주기만 해도 모델 성능 차이에 덜 흔들리는 안정적인 재현이 가능해진 셈입니다.

비용 절감 수치 역시 분모와 제외 항목을 함께 봐야 합니다. 후속 재현 세션의 API 비용은 모델별 원래 코드 비용 기준으로 평균 19.7% 줄었으며 실패한 시도까지 포함됩니다. 반면 정제 자료 제작(36개 논문 기준 초기 API 비용 5,026달러)과 감사·GPU 실행·유지보수·사람 검토 비용은 빠져 있어, 전체 연구 비용이 곧바로 그만큼 줄었다고 판단하기에는 이릅니다.

## 보존된 절차도 검증이 필요하다

수치가 허용 구간에 들어왔다고 해서 과학적 타당성이나 실험 절차 전체의 충실성까지 보증되지는 않습니다. 자동 감사도 일부 위반을 놓칠 수 있고, 정제 자료에 잘못된 가정이 남아 다음 세션으로 이어질 위험도 있거든요. 실제로 첫 평가의 논문별 분석에서는 모든 논문이 개선된 게 아니라, 모델에 따라 일부 논문의 성공률이 오히려 낮아졌습니다.

이번 개입의 성격도 구분해 두어야 합니다. ReproBridge 파이프라인은 조사·수리·검토·포장이 함께 들어간 과정이어서, 똑같은 결과물의 폴더 구조만 정리했을 때의 효과를 따로 측정한 실험과는 다릅니다. 에이전트가 아니라 사람 연구자가 이 자료를 썼을 때의 시간 절약과 이해도 변화 역시 별도 연구가 필요합니다.

## 다메카솔의 해석

실험을 넘겨줄 때는 성공한 명령만 복사해 두기보다, 그 명령이 어떤 설정과 출력·측정값을 연결하는지 이유까지 남기는 편이 유용합니다. 다음 사람이 다시 판단해야 할 부분과 그대로 실행할 부분을 또렷이 구별할 수 있거든요. 다만 초기 정리와 검토에 적지 않은 비용이 들고 프로젝트마다 개선 폭도 달라질 수 있으므로, 팀이 반복 실행할 핵심 실험이나 공개 저장소부터 이 네 가지 틀을 적용해 볼 만합니다.

[Terminal-Bench의 채점기 유지보수 문제](/posts/terminal-bench-maintenance-debt-20261117/)가 점수를 만드는 시험 자체를 점검했다면, ReproBridge는 그 시험을 다시 수행할 사람이나 에이전트에게 무엇을 전달할지 묻습니다. 평가 기준을 다듬는 일 못지않게, 복구한 실행 지식을 유실 없이 건네는 인수인계 구조도 재현성을 지탱하는 축인 셈이죠.
