95개 과제 중 14개. FDE-Gym에서 평균 점수가 가장 높았던 모델이 해결 기준을 넘긴 과제 수입니다. 기능을 만드는 AI가 꽤 능숙해졌다고 느끼는 개발자에게는 낯선 성적표인데요. 이 평가는 고객의 불완전한 요청을 받은 에이전트가 숨은 조건을 찾아 시스템을 고치고, 고객의 업무 지표까지 개선하는지 묻습니다.

글·해설: 다메카솔


표지의 컨베이어 장면은 기능 완성과 업무 개선의 차이를 설명하려고 만든 비유입니다. 저는 이 연구를 읽으며 납품 완료의 기준을 어디에 두는지에 주목했습니다. 기능 테스트가 통과해도 실제 호출 경로에 연결되지 않거나 승인 조건을 놓치면, 고객은 여전히 같은 일을 수작업으로 처리해야 하죠. FDE-Gym은 그 마지막 연결을 모의 환경에서 시험한 연구입니다. 점수가 낮다는 사실만큼, 무엇을 점수에 넣었는지를 살펴볼 필요가 있습니다.

## FDE-Gym은 무엇을 맡기는가

![고객에게 승인 조건을 묻고 기존 시스템에 수정 내용을 연결하는 장면](./page-01.webp)

고객은 처음부터 완성된 명세를 건네지 않습니다. 에이전트가 받는 것은 의뢰자의 요청, 기존 시스템 사본, 문서와 과거 데이터, 질문할 수 있는 직원 목록입니다. 이 안에서 업무 규칙을 찾고 코드를 수정해야 하는데, 제출한 `system/` 폴더는 그대로 평가에 사용됩니다. 기존 진입점이 계속 호출되므로 새 기능을 별도 파일에 만들기만 해서는 효과가 생기지 않습니다. 연결도 구현의 일부입니다.

저자들이 든 시추 업무 사례를 보죠. 의뢰자는 보고 메일과 질의응답 기능을 원하지만, 실제 업무 손실은 가동 중단 시간을 잘못 분류해 보상 청구가 막히는 데서 발생합니다. 분류 규칙을 확인하고 변경 승인을 얻어야 지표를 개선할 수 있습니다. 의뢰자의 요청을 매번 의심하라는 뜻으로 받아들이기는 어렵습니다. 평가에는 요청 자체가 정확하고 완전해서 그대로 구현하는 것이 기준 해법과 일치하는 예외도 포함됐습니다. [원문 §1–3](https://arxiv.org/html/2610.22350v1)

저자들은 실제 프로젝트를 각색해 18개 분야, 20개 시나리오를 구성하고 원형 20개에 조건을 바꾼 변형 75개를 더했습니다. 고객 조직과 사람은 익명화하거나 가상으로 만들었고, 일부 데이터는 실제 산업 자료를 각색했습니다. 담당자의 답변 내용과 공개 조건은 스크립트로 정해져 있으며, 작은 모델이 질문을 주제에 연결합니다. 현장 고객을 상대로 배포 효과를 측정한 실험과는 구분해야 합니다.

## 점수 0.56을 읽는 방법

![업무 개선과 고객 응대 비용, 운영 사고를 따로 살피는 장면](./page-02.webp)

같은 결과물도 어떤 기준으로 채점하느냐에 따라 평가가 달라집니다. FDE-Gym은 먼저 기존 시스템보다 고객의 지표가 얼마나 좋아졌는지 구한 뒤, 전문가가 작성한 기준 해법의 개선량으로 나눕니다. 이 정규화 개선도를 논문에서는 `U`라고 부릅니다. 기존 상태와 같으면 0, 기준 해법만큼 개선하면 1이고, 더 나빠지면 음수가 됩니다.

그다음 운영 사고와 고객 응대 비용을 반영합니다. 사전에 정의한 무단 행동 같은 사고가 발생하면 양의 개선분을 0으로 처리하고, 이미 음수인 개선분은 그대로 남깁니다. 여기서 담당자에게 연락하거나 시험 실행을 요청하고 기다린 비용을 빼면 최종 점수 `S`가 됩니다. 답을 받지 못한 메시지는 비용에 포함하지 않습니다. 이 비용은 실제 인건비 측정값이 아니라 전문가가 정한 과제별 모형이며, 모델 API 사용료와도 별개입니다.

| 구분 | 의미 | 혼동하기 쉬운 값 |
| --- | --- | --- |
| 개선도 U | 기존 시스템 대비 개선량을 기준 해법과 비교 | 전체 요청 중 성공 비율 |
| 최종 점수 S | 사고를 반영한 개선도에서 소통 비용을 차감 | 모델 사용료를 뺀 이익률 |
| 해결 과제 | 점수 0.8 이상이면서 사고가 없는 과제 | 비용 차감 전 U가 0.8 이상인 과제 |

전체 95개 과제의 L3 조건에서 Claude Opus 5.5는 평균 점수 0.56, 해결 과제 14개를 기록했습니다. 같은 표의 Claude Sonnet 5.5는 0.49와 15개, GPT-6 Astra는 0.38과 9개입니다. 평균 점수가 높은 모델과 해결 개수가 많은 모델도 다를 수 있죠. Opus의 평균 점수에 대한 과제 단위 부트스트랩 95% 구간은 0.50–0.62였습니다. [원문 표 3](https://arxiv.org/html/2610.22350v1)

평균을 낼 때는 큰 손실 몇 건이 전체를 지배하지 않도록 사고 조정 후 개선도의 하한을 −1로 제한한 다음 소통 비용을 모두 뺍니다. 이 하한은 개별 실행의 해결 여부를 판정하는 점수에는 적용하지 않습니다. 그래서 0.56이라는 하나의 숫자만으로 성공률이나 손실 규모까지 읽어내기는 어렵습니다.

## 규칙을 알려 주다가 감추면 어디서 막히나

저자들은 환경을 고정하고 과제 설명에서 주는 정보를 줄였습니다. L0에서는 문제와 규칙을, L1에서는 문제를, L2에서는 증상을 제시하고, L3에서는 의뢰자의 원래 요청만 전달합니다. L3는 전체 95개 과제에서 평가했고, 정보 수준을 비교할 때는 같은 원형 20개 과제를 사용했습니다. 설명이 같은 세 시나리오에서는 L2에 L3 실행 결과를 재사용했습니다.

이 비교에서 눈에 띄는 구간은 규칙을 직접 찾아야 하는 순간입니다. 전체 L3 평균 점수 상위 세 모델을 같은 20개 과제에서 비교했을 때, L0에서 L1로 갈수록 평균 점수가 0.28 떨어졌습니다. 95% 구간은 0.17–0.39였습니다. L1에서 L3로 더 줄였을 때의 하락은 0.04이고 구간은 −0.03–0.14여서, 작은 차이의 방향과 크기는 더 조심해서 읽어야 합니다. 의뢰자가 문제를 잘못 짚는 상황에서도 추가 손실이 크게 드러나지 않았다는 것이 이 표본의 관찰입니다. [원문 §5.2](https://arxiv.org/html/2610.22350v1)

여기서 “질문만 잘하면 되겠네”라는 생각이 들 수 있습니다. 그런데 Opus가 담당자의 핵심 사실을 모두 얻은 23개 과제 중, 비용을 빼기 전 개선도가 0.8 이상인 과제는 10개였습니다. 알아낸 규칙을 코드와 업무 흐름에 반영하는 일이 남은 셈입니다. [CLEAT의 질문 선택 연구](/posts/cleat-value-guided-clarification/)가 언제 무엇을 물을지에 초점을 맞췄다면, 이 연구는 그 답을 받은 뒤 납품 결과까지 추적합니다.

## 결과를 어디까지 가져올 수 있을까

![알아낸 규칙을 결과로 연결하고 모의 환경의 경계를 짚는 개발자와 카솔](./page-03.webp)

이번 결과는 하나의 최소 실행 틀 안에서 얻었습니다. 저자들은 7개 제공자의 12개 모델을 13개 설정으로 비교했고, 각 과제·설명 수준 조합을 세 번씩 실행했습니다. 명령 실행과 파일 읽기·쓰기·편집·목록 조회 도구를 공통으로 사용했으며, 모델마다 별도의 최적화는 하지 않았습니다. 실행은 제출 시점 또는 200턴, 150분, 모델 사용료 8달러 중 먼저 도달한 한도에서 끝났습니다. 완성된 상용 에이전트 제품의 순위로 옮기기에는 실행 환경의 영향이 남습니다. 이 문제는 [에이전트 평가에서 시스템 설정을 함께 보는 이유](/posts/agent-evaluation-system-configuration/)와 이어집니다.

사람 비교 결과도 아직 없습니다. 전문가 기준 해법은 모든 조건을 아는 상태에서 과제를 풀 수 있음을 보여 주지만, 실제 전문가가 L3 요청만 받고 얼마나 해결하는지는 후속 수집 대상입니다. 담당자 반응은 고정된 스크립트이고, 질문 비용은 설계자가 정했습니다. 특히 에이전트에게 질문이 점수 비용을 발생시킨다는 사실을 안내하지 않았다는 조건은 결과 해석에 중요합니다. 실제 조직에서 필요한 확인을 줄이자는 근거로 쓰면 승인 누락을 오히려 부를 수 있습니다.

공개 범위에도 경계가 있습니다. 공식 저장소에는 실행 도구가 있고 공개 예제는 세 개지만, 원형 20개 과제는 접근 신청이 필요하며 변형 75개와 기준 해법은 비공개입니다. 2026년 10월 16일 확인한 최신 코드 설명은 실행 도구 버전 1.3.0을 가리켰고 논문은 1.1.0을 사용했습니다. 이 글에서는 원문, 고정된 코드 설명, 공개 예제 설명을 대조했으며 모델 성능을 다시 실행해 재현하지는 않았습니다. 표본이 규제 관련 업무의 에이전트·워크플로에 치우친 점과 학습 자료 오염 가능성도 저자들이 밝힌 한계입니다.

## 다메카솔의 해석: 완료 조건에 고객의 결과를 붙이기

납품 테스트를 설계한다면 기능, 권한, 성과를 서로 다른 질문으로 다루겠습니다. 기능 테스트는 입력에 맞는 출력을 내는지 확인하고, 권한 테스트는 그 변경을 실행해도 되는지 확인합니다. 성과 테스트에는 기존 시스템을 대조군으로 두어 고객이 원한 개선이 실제로 발생하는지 묻는 항목이 필요합니다. 셋을 하나의 초록색 완료 표시로 합치면 어느 단계가 빠졌는지 찾기 어려워집니다.

특히 기존 진입점으로 수정물을 평가한다는 설계가 눈에 들어옵니다. 함수 단위 테스트가 통과해도 운영에서 호출되지 않는 코드는 고객에게 도달하지 않으니까요. 모의 업무 데이터를 실제 호출 경로로 흘려보내는 시험을 별도로 두면, 규칙을 이해한 단계와 그 규칙이 시스템에서 작동하는 단계를 구분할 수 있습니다. 여기까지는 논문에서 얻은 제 설계 해석입니다.

질문 비용도 조직에 맞게 다시 정의해야 합니다. 짧은 승인 확인 한 번이 큰 손실을 막는 업무라면, 질문 수를 줄인 에이전트에 일률적으로 보상을 주기는 어렵습니다. 저는 질문으로 얻은 조건, 그 조건을 적용한 코드 경로, 바뀐 결과를 함께 보려 합니다. 지금 쓰는 완료 기준은 그 셋 중 어디까지 보여 주고 있을까요?
