글·해설: 다메카솔

GitHub Copilot이나 Claude Code에게 "Google OAuth 2.0 로그인 연동 코드 짜줘"라고 부탁하면 10초 만에 그럴듯한 코드를 뽑아줍니다. 실제로 로컬에서 실행해 보면 구글 로그인 창이 잘 뜨고 사용자 토큰도 정상적으로 받아옵니다.

그렇다면 이 코드는 프로덕션 환경에 바로 배포해도 될 만큼 **'보안적으로도 안전'**할까요?

최근 발표된 실증 연구 논문 **Understanding the Impact of AI Code Assistants on Security API Usage**는 44명의 현업 전문 개발자를 대상으로 이를 정밀 측정했습니다. 

연구 결과는 매우 명확합니다: **"AI 코딩 도구는 복잡한 보안 API의 기능 완성 속도를 2배 이상 높여주지만, 정작 CSRF를 막는 `state` 파라미터나 PKCE 검증 같은 핵심 보안 방어선은 100% 누락되어 있었다."**

이번 글에서는 AI가 생성한 보안 코드의 치명적인 맹점과, 실무 개발팀이 갖춰야 할 코드 리뷰 가드레일을 정리합니다.

## 기능 통과(Happy Path)는 보안 안전을 보증하지 않는다

![기능 테스트는 통과했지만 보안 검증은 아직이라는 사실을 카솔이 설명하는 장면](./page-00.webp)

보안 API(TLS/SSL 인증서 검증, OAuth 인증, 암호화 모듈)의 가장 무서운 점은 **"보안 규칙을 심각하게 위반해도 겉으로는 로그인이 아주 잘 된다는 점"**입니다.

- 인증서 검증(`TrustManager`)을 통째로 패스하는 더미 코드를 넣어도 통신은 잘 됩니다 (중간자 공격에 100% 노출).
- OAuth 인증 시 CSRF 방어용 `state` 토큰이나 PKCE 검증을 생략해도 로그인은 정상 완료됩니다 (계정 탈취 공격에 노출).

즉, 유닛 테스트와 기능 테스트가 모두 `PASS`를 띄우더라도 보안 관점에서는 치명적인 백도어가 열려 있을 수 있습니다.

## 44명의 전문 개발자를 대상으로 한 정밀 실험

![전문 개발자들이 AI 사용과 미사용 조건을 교차해 경험하고 기능과 보안을 따로 평가받는 연구 설계](./page-01.webp)

연구진은 1년 이상의 Java 실무 경력을 가진 전문 개발자 44명을 모집하여, Java TLS 통신(JSSE)과 Google OAuth 2.0 연동 과제를 수행하도록 했습니다.

### 1. 기능적 생산성: AI의 압도적인 승리
![단순 과제에서는 두 조건이 모두 도착하고 복잡한 권한 과제에서는 AI 보조 경로가 기능 완성을 돕는 장면](./page-02.webp)

- **OAuth 기능 완성률**: Copilot 사용군 **91%** vs 미사용군 **45%** (2배 이상 성공)
- **작업 소요 시간**: Copilot 사용군 **23분** vs 미사용군 **62분** (시간 60% 단축)

복잡한 보일러플레이트 코드와 API 스펙 문서를 일일이 뒤적일 필요가 없었기에, 기능 구현 속도에서는 Copilot의 기여가 압도적이었습니다.

### 2. 보안 무결성: 충격적인 전원 탈락
![완성된 두 코드가 같은 보안 검사대에 들어가지만 인증, 호스트, 권한 흐름의 누락과 닫힌 보안 게이트 앞에 멈추는 장면](./page-03.webp)

하지만 작성된 코드들을 보안 표준 체크리스트로 정밀 감사한 결과는 충격적이었습니다:
- **두 그룹을 통틀어 보안 표준을 100% 충족한 안전한 구현은 '단 한 건'도 없었습니다.**
- Copilot이 추천한 코드 대부분이 `state` 파라미터 검증 누락, 토큰 교환 시 리디렉션 URI 위조 방지 미흡 등 전형적인 보안 오용(Misuse) 패턴을 그대로 담고 있었습니다.

## 더 무서운 점: 개발자의 근거 없는 자신감

![개발자가 기능 요구만 입력하고 자신의 코드를 안전하다고 생각하지만 실제 검토에서 경고를 발견하는 장면](./page-04.webp)

실험 참가자들은 "보안성도 평가 대상"이라는 사실을 사전에 고지받았음에도 불구하고:
- Copilot에게 명시적으로 "보안 취약점이나 PKCE 설정을 고려해 달라"고 프롬프팅한 개발자는 **44명 중 단 2명**에 불과했습니다.
- 과제를 마친 후 대다수의 개발자가 **"내 코드는 보안적으로 매우 안전하다"고 오판**했습니다.

AI가 순식간에 에러 없는 매끄러운 코드를 만들어주다 보니, 개발자가 비판적인 코드 리뷰를 생략하고 인지적 안도감(Cognitive Ease)에 빠져버린 것입니다.

## "보안도 신경 써줘"라고 다시 물어보면 고쳐질까?

![보안 재검토 뒤 일부 경고는 사라지지만 복잡한 권한 흐름 경고가 남고 카솔이 세 단계 검증을 제안하는 장면](./page-05.webp)

연구진이 사후 실험으로 Copilot에게 "이 코드의 보안 모범 사례를 다시 검토해줘"라고 추가 질문(Re-prompting)을 던져보았습니다.

그 결과 단순한 인증서 검증 누락 같은 쉬운 문제는 일부 수정되었지만, **OAuth의 다단계 상태 검증(`state`, `nonce`, PKCE) 같은 복잡한 프로토콜 레벨의 취약점은 여전히 감지하지 못하고 방치**되었습니다.

## 다메카솔의 해석: 실무 팀을 위한 3단계 보안 가드레일

AI 코딩 도구를 금지하는 것은 올바른 해결책이 아닙니다. 2배 이상의 생산성 혁신을 누리되, **보안 검증의 책임을 시스템적으로 분리하는 파이프라인**을 갖추어야 합니다.

실무 개발팀에 다음 3가지 원칙을 제안합니다:

1. **프롬프트에 보안 요구사항 명시**: "로그인 API 짜줘" 대신 "OAuth 2.0 Authorization Code Grant flow로 구현하되, CSRF 방어용 `state` 검증과 PKCE(`code_verifier`/`code_challenge`)를 필수로 포함해줘"처럼 방어 규격을 직접 지정하세요.
2. **기능 테스트와 보안 SAST 검사의 분리**: CI 파이프라인에 SonarQube, Snyk, Semgrep 같은 정적 분석 도구를 필수 게이트로 걸어두어 하드코딩된 시크릿이나 안전하지 않은 암호화 API 호출을 자동 차단해야 합니다.
3. **AI의 자기 검토 맹신 금지**: 보안 영역만큼은 AI의 "안전합니다"라는 대답을 믿지 말고, 공식 RFC 문서의 보안 체크리스트를 기반으로 시니어 엔지니어의 피어 리뷰(Peer Review)를 거쳐야 합니다.
