Kubernetes에서 데이터베이스나 상태 저장 서비스를 띄울 때, 파드(Pod) replica와 스토리지 볼륨 replica를 모두 3으로 맞춰 두면 막연히 안전할 것 같죠. 하지만 애플리케이션 복제와 스토리지 복제는 같은 데이터를 여러 곳에 둔다는 점만 닮았을 뿐, 장애가 났을 때 누가 복구를 맡고 무엇을 복제하는지부터 전혀 다릅니다. 두 계층의 복제 수를 한 덩어리로 셈하면 디스크와 네트워크 비용만 불어나거나, 정작 필요한 장애 대응이 비어 버리기 쉽습니다.

글·해설: 다메카솔

## 핵심 내용

- **복구 주체의 차이**: CloudNativePG(CNPG) 같은 애플리케이션 계층 복제는 WAL 스트리밍과 리더 승격을 직접 제어하는 반면, Longhorn 같은 스토리지 계층 복제는 PVC가 마운트할 블록 장치 사본을 여러 노드에 동기 유지합니다.
- **곱해지는 복제 비용**: 애플리케이션 인스턴스 3개에 각각 볼륨 replica 3개를 붙이면 물리 데이터 경로가 최대 9개로 늘어나 네트워크·디스크 대역폭과 용량 비용이 겹칩니다.
- **워크로드별 분리 설계**: 자체 복제 엔진이 있는 워크로드(CloudNativePG, 3멤버 Raft Vault)는 볼륨 replica를 줄이고, 자체 복제가 없는 단일 인스턴스 워크로드(SeaweedFS 등)는 볼륨 계층이 노드 실패를 받아 내도록 구성합니다.

## 위층은 서비스를, 아래층은 볼륨을 복제합니다

먼저 두 계층이 각각 무엇을 복제하고 어떤 장애를 책임지는지부터 나눠 볼까요? **애플리케이션 계층 복제**에서는 서비스 인스턴스 여러 개가 각자 별도 PVC를 마운트한 채 데이터 상태와 역할을 나누어 맡습니다. 예를 들어 CloudNativePG로 PostgreSQL 클러스터를 구성하면 기본(primary) 인스턴스에서 대기(standby) 인스턴스로 WAL(Write-Ahead Log)이 전달됩니다. 이때 어느 인스턴스가 쓰기 요청을 받을지와 장애 시 누구를 새 리더로 승격할지는 PostgreSQL과 오퍼레이터가 직접 결정하며, 공식 문서 역시 이를 애플리케이션 계층 복제로 설명합니다.

반면 **스토리지 계층 복제**가 다루는 단위는 서비스 프로세스가 아니라 블록 볼륨입니다. Longhorn의 경우 각 볼륨 엔진이 여러 노드의 블록 replica에 쓰기를 동기 반영하고, 건강한 replica 수가 줄어들면 다른 노드로 다시 채워 넣어 볼륨 가용성을 지킵니다. 그 위에서 돌아가는 PostgreSQL의 리더가 누구이고 어느 인스턴스에 쓰기를 보낼지는 볼륨 엔진이 관여하지 않고 상위 계층에 맡겨 둡니다.

![서비스 인스턴스가 복제되는 위층과 볼륨 블록이 복제되는 아래층을 나눈 장면](./page-01.webp)

장애 유형별로 먼저 반응하는 계층을 나누어 보면 역할의 경계가 한눈에 드러납니다.

| 실패 유형 | 먼저 반응하는 계층 | 확인할 것 |
| --- | --- | --- |
| 프로세스 종료 | 워크로드 컨트롤러·애플리케이션 | 새 Pod 생성과 역할 승계 |
| 데이터베이스 기본 인스턴스 장애 | 데이터베이스 복제 계층 | 대기 인스턴스의 일관성과 승격 |
| 볼륨 replica 또는 디스크 장애 | 스토리지 계층 | 남은 건강한 replica와 리빌드(rebuild) |
| 노드 전체 장애 | 두 계층 모두 관여 가능 | 파드 재배치, 볼륨 접근성, 실패 도메인 |

같은 노드 전체 장애라도 어느 계층에 복구 책임을 두었느냐에 따라 확인 대상이 달라집니다. 파드가 다른 노드로 옮겨 갈 수 있는지, 볼륨 블록이 그 노드에서도 읽히는지, 그리고 복제된 노드와 디스크가 같은 전원이나 네트워크 스위치 같은 실패 도메인을 공유하고 있지는 않은지를 함께 따져 봐야 하죠.

## 3 곱하기 3은 비용도 늘립니다

애플리케이션 인스턴스가 3개이고 각 인스턴스의 볼륨 replica가 3개라면 물리적인 데이터 쓰기 경로는 최대 9개가 됩니다. 가령 CloudNativePG로 기본 인스턴스 하나와 대기 인스턴스 둘을 운영할 때, 쓰기 요청 한 건이 WAL을 타고 대기 인스턴스로 복제되는 동시에 각 인스턴스 아래의 Longhorn 볼륨에서도 세 벌씩 블록 복제가 일어나는 셈이죠.

![세 애플리케이션 사본이 각자 세 볼륨 사본으로 갈라져 아홉 경로가 되는 장면](./page-02.webp)

이렇게 늘어난 쓰기 경로는 평상시에도 네트워크 대역폭과 디스크 용량을 겹쳐 소모합니다. 게다가 장애가 발생하면 손상된 볼륨을 채우는 리빌드(rebuild) 트래픽과 데이터베이스 동기화 트래픽이 한꺼번에 쏟아지거든요. 노드가 몇 대 안 되는 소규모 클러스터일수록 이 복구 부하가 남은 노드 몇 곳에 집중돼 정상 서비스의 지연까지 키우기 쉽습니다.

Longhorn 공식 문서의 $N-1$ 표현도 정확한 범위를 붙여 읽어야 합니다. 볼륨 replica가 $N$개이고 최소 한 개가 건강하다면 최대 $N-1$개의 볼륨 replica 실패를 견딜 수 있다는 조건입니다. 이는 블록 볼륨의 생존 기준이므로, 서비스의 쓰기 리더 승계나 데이터베이스 일관성, 잘못된 삭제를 되돌리는 백업 복원까지 대신 해결해 주는 상위 계층의 보장과는 별개로 챙겨야 합니다.

## 워크로드마다 답이 달라집니다

복제 수는 워크로드의 복제 구조와 데이터 성격에 따라 달라집니다. 제 홈랩에서도 2026년 7월 클러스터를 재구축하면서, 자체 복제 엔진 유무와 데이터 재생성 비용을 기준으로 복제 정책을 네 갈래로 나누었습니다.

| 워크로드 | 애플리케이션 복제 | Longhorn replica | 설계 판단 |
| --- | --- | ---: | --- |
| CloudNativePG | 인스턴스 3개 (자체 물리 복제) | 1 | 앱 계층이 데이터 복제와 승격 담당 |
| Vault (3멤버 Raft) | 인스턴스 3개 (Raft 합의) | 1 | 합의 계층에 복제를 맡기고 볼륨 중복 축소 |
| SeaweedFS 데이터 | 단일 인스턴스 (자체 복제 없음) | 3 | 스토리지 계층이 노드·디스크 실패 흡수 |
| Prometheus·Loki·Tempo | 일부 재수집·재생성 가능 | 2 | 손실 허용도와 저장 비용 사이의 절충 |

이처럼 계층별 역할을 갈라 두면 노드 장애가 났을 때 복구 경로도 선명해집니다. 예를 들어 CloudNativePG처럼 볼륨 replica가 1인 노드가 내려가면 해당 볼륨에는 닿지 못하더라도, 각 인스턴스가 별도 PVC를 쓰기 때문에 다른 노드의 대기 인스턴스가 승격을 맡아 데이터를 이어 갈 수 있거든요. 반대로 단일 인스턴스 SeaweedFS는 스스로 승격할 짝이 없으므로, 볼륨 계층에 replica 3을 두어 다른 노드에 남은 건강한 블록 사본으로 파드 재배치에 대비하도록 구성했습니다.

물론 장비 대수와 디스크 배치, 백업 경로가 달라지면 적정 replica 수치도 환경마다 바뀝니다. 그래도 설정 파일을 열기 전에 점검할 다섯 가지 질문 순서는 어느 클러스터에서나 그대로 재사용할 수 있습니다.

1. 이 애플리케이션은 스스로 데이터를 복제하는가?
2. 장애 시 어느 사본을 정본(primary)으로 승격하는가?
3. 노드와 디스크 중 어느 범위의 실패를 견뎌야 하는가?
4. 온라인 복제가 모두 실패했을 때 어디에서 백업을 복원하는가?
5. 쓰기 지연과 네트워크·용량 비용을 감당할 수 있는가?

![남성 카솔이 복구 주체와 실패 도메인과 복원 경로의 세 점검판을 확인하는 장면](./page-03.webp)

결국 replica 수는 막연한 안전 점수가 아니라, 어느 계층이 어떤 실패를 받아 낼지 적어 놓은 설계 값입니다. 제품별 관성으로 숫자를 채우기 전에 복구 주체와 실패 범위, 그리고 감당할 쓰기·용량 비용부터 먼저 적고 두 계층의 숫자를 따로 정해 두는 편이 좋습니다.
