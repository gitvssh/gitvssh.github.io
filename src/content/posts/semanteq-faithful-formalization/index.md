AI가 만든 수학 증명이 Lean 검증기를 통과했다고 해서, 원래 질문까지 제대로 풀었다고 보기는 어렵습니다. 검증기가 확인하는 대상은 처음 던진 자연어 문제가 아니라, AI가 번역해 입력한 형식 명제 자체이기 때문이죠.

글·해설: 다메카솔

2026년 10월 공개된 **SemantEq** 논문([arXiv:2610.32919v1](https://arxiv.org/abs/2610.32919v1))은 이 틈을 메우려 신뢰할 기준 명제와 AI 후보 명제 사이의 변환 경로, 그리고 완성된 증명 내부까지 함께 감사합니다.

## 서로 다른 참인 문장도 양방향 증명이 됩니다

![각각 참인 별개 수학 명제가 같은 뜻은 아니라는 비교](./page-01.webp)

단순히 "서로가 서로를 증명할 수 있는가"만 따지면 전혀 다른 명제도 동치로 통과해 버립니다. 예를 들어 논문은 "5는 소수다"와 "√2는 무리수다"를 나란히 둡니다. 두 문장 모두 각각 참이고 라이브러리에 증명이 들어 있어, 첫 문장을 가정으로 받고도 그 가정을 전혀 쓰지 않은 채 둘째를 증명할 수 있거든요. 반대 방향도 똑같이 성립하니 논리적 양방향 함의만 보면 같은 뜻처럼 통과하는 셈이죠.

이 허점은 증명기가 강해질수록 오히려 더 잘 드러납니다. 전술 스크립트에 기준 명제의 이름이 들어 있는지 확인하는 방법도 이름만 부른 뒤 다른 라이브러리 정리로 결론을 내는 우회를 막기 어려운데요, 결국 완성된 증명 안에서 해당 전제가 실제로 어떤 일을 했는지 살필 필요가 있습니다.

## 허용된 변환을 정하고 증명 항까지 살핍니다

![기준과 후보 사이의 허용된 변환 경로를 검사하는 비유](./page-02.webp)

SemantEq는 명제가 바뀔 때 논리식 재배열, 라이브러리 등식·동치식 치환, 조건부 변수 변환, 논리적 약화의 네 단계만 허용합니다. 이때 조건 약화는 한 방향으로만 성립하므로 반대 방향의 변환 경로도 따로 통과해야 합니다.

- **SemantEq-Eval**: 모델 없이 허용 변환을 탐색하고 감사까지 수행합니다.
- **SemantEq-ProofAudit**: LLM 같은 외부 증명기가 만든 증명 결과를 받아 감사 기준을 적용합니다.

두 도구가 검사하는 대상은 전술 스크립트가 아니라 Lean 커널이 확인하는 완성된 증명 객체, 즉 '증명 항'입니다. 가령 전제를 빼도 같은 경로로 결론이 나오는지, 라이브러리 정리를 표현 변환에만 썼는지 결론 공급에 썼는지 살피죠. 외부 증명은 탐색기가 만들지 않는 보조 정리나 객체를 포함할 수 있어 ProofAudit에는 별도의 객체 대입 검사와 허용 예외를 두었으므로, 수학적 정의와 실제 도구의 수락 기준은 구분해 읽어야 합니다.

## 정밀도 100% 뒤에 붙은 시험 조건과 비교

첫 번째 비교는 ProofNetVerif 전체 시험 자료 중 고정된 Lean 환경에서 처리할 수 있는 부분 집합만 골라 진행했습니다. 저자들은 기존 '동치' 라벨 상당수를 사람이 재검토해 '비동치'로 바로잡았는데, 그중 대다수는 SemantEq 실행 결과가 재검토의 출발점이 된 사례였습니다.

- **평가 대상**: ProofNetVerif 1,452쌍 중 **1,303쌍**만 처리·평가 (재판정 후 동치 369·비동치 934쌍).
- **라벨 재판정**: 기존 동치 **102쌍**을 비동치로 수정했고, 그중 **88쌍**은 시스템 결과가 계기(최종 결정은 사람).

| 지표 (1,303쌍 평가) | SemantEq-Eval | BEq+ (동일 버전 이식) |
| --- | ---: | ---: |
| 동치 통과 / 미탐 (369쌍) | 242 / 127 | 228 / 141 |
| 비동치 오수락 / 거절 (934쌍) | 0 / 934 | 10 / 924 |
| 정밀도 / 재현율 (재판정) | 100.0% / 65.6% | 95.8% / 61.8% |
| 정밀도 / 재현율 (원래 라벨) | 100.0% / 51.4% | 96.6% / 48.8% |

재판정 기준 Eval은 비동치 오수락을 0건으로 막았지만 동치 127쌍을 놓쳤고, 원래 공개 라벨로 돌리면 순위는 같아도 재현율 분모와 수치가 달라집니다.

LLM 증명과 ProofAudit을 결합한 논문 Table 3은 앞 표와 전혀 다른 별도의 인증 집합을 다룹니다. 여기서 기본 Eval의 재현율이 앞 표와 비슷하게 보여도 시험 문제 자체가 다르므로 같은 선상에서 비교하기는 어렵고, 네 가지 프롬프트 조건 모두에서 비동치 쌍의 양방향 오수락은 0건이었습니다.

| 조건 (별도 511쌍) | 동치 인증 (407쌍) | 비동치 오수락 (104쌍) |
| --- | ---: | ---: |
| SemantEq-Eval | 266쌍 (65.4%) | - |
| Faithful + ProofAudit | 330쌍 (81.1%) | 0건 |
| Expedient (생성 / 감사 후) | - | 43쌍 컴파일 / 0건 |
| Unrestricted (생성 / 감사 후) | - | 45쌍 컴파일 / 0건 |

특히 빠른 해결을 유도한 Expedient와 제한을 푼 Unrestricted 조건에서는 모델이 비동치 쌍 수십 건의 양방향 컴파일 증명을 만들어 냈는데, ProofAudit 감사가 이를 전부 걸러냈거든요. 증명 생성과 수락 판단을 분리해야 하는 이유가 이 격차에서 분명히 드러나는 셈이죠.

- **실험 조건**: 2026년 8월 30일 GPT 5.6 Sol(`medium`), 쌍·프롬프트당 1세션, Lean **4.28.1** 생성 후 **4.30.0-rc1** 재검사(미처리 방향은 거절 집계). 단일 모델·1회 실행이라 일반화에는 한계가 있습니다.

## 기준 명제가 틀렸다면 그 오류도 함께 통과합니다

![기준 명제와 실험의 한계를 설명하는 카솔](./page-03.webp)

SemantEq는 신뢰할 기준 명제를 전제로 동작합니다. 기준 자체가 원래 문제를 잘못 옮겼다면 그 오류를 복사한 후보도 통과하므로, 자연어 문제만으로 올바른 형식화를 보장하는 도구라기보다 믿을 만한 기준과 대조하는 검사기에 가깝습니다. 반대로 거절 판정 역시 탐색과 감사를 통과하는 증명을 못 찾았다는 뜻일 뿐 두 명제가 다르다는 확정은 아니라서 추가 검토가 필요합니다.

통과 결과 역시 라이브러리 등식·동치 정리가 의미를 보존한다는 가정과 구현 예외 위에 놓인 증거로 보아야 합니다. 실제로 저자들은 Table 1에서 빠진 검증 분할의 **Munkres 18.8b**에서 Eval이 목표에 없는 구조를 공급해 비동치 쌍을 잘못 수락했고 ProofAudit의 대입 검사가 이를 거절한 사례를 공개했거든요. 한 프로그램의 시험 정밀도 100%를 전체 무오류로 보기 어려운 이유입니다.

공개 저장소는 고정된 Lean·Mathlib 환경과 재현 스크립트를 제공하며, 실행 조건에 따라 결과가 달라지므로 시간 제한이나 라이브러리 범위를 바꿀 때는 비교 기준을 함께 남겨야 합니다.

- **환경·리소스**: Linux/macOS 지원, **Lean 4.30.0-rc1** 기준, 전체 Mathlib 약 **5GB** 캐시·프로세스당 약 **9GB** RAM 필요, 기본 **20초** 제한(재현 스크립트는 해제).

## 다메카솔의 해석: '통과 여부'보다 먼저 볼 두 질문

AI 검증 결과를 읽을 때는 '주어진 조건 아래 유효한가'와 '그 조건이 원래 의도를 보존했는가'를 나누어 묻는 편이 좋습니다. SemantEq는 수학 명제와 신뢰 기준이 있는 제한된 영역에서 두 번째 질문을 파고들지만, 일반 소프트웨어 요구사항 검증까지 해결하는 도구는 아니거든요. 그래도 [AI 코딩 평가에서 사용자 대화를 다룬 UserSWE](/posts/userswe-dynamic-user-coding/)처럼, AI 채점·게이트 설계에서 통과 기준이 의도와 어디서 연결되는지 점검할 좋은 참고 사례가 됩니다.
