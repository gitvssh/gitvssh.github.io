완성한 보고서를 이어서 수정하라고 맡겼는데, 에이전트가 이미 채운 표의 자료부터 다시 검색하기 시작하면 당황스럽습니다. 결과 파일이 디스크에 남아 있더라도 다음 행동을 고르는 컨텍스트와 끊어지면 똑같은 탐색과 비용이 반복되거든요. **CarryOn**은 다시 꺼내 쓸 작업물과 남은 의무, 최근 행동을 한 묶음으로 보존해 이런 중복 작업을 줄이는 연구입니다.

글·해설: 다메카솔

## 핵심 내용

- **작업물 중심 기록**: 완성 파일이나 찾은 정보, 앱 상태를 재사용 위치·출처·조건과 함께 기록합니다.
- **검증 기반 갱신**: 실제 환경에서 조건을 확인한 뒤에만 맥락을 갱신하고, 실패하면 직전 기록을 유지합니다.
- **평가와 해석 경계**: 같은 모델 비교에서 점수와 토큰 효율이 올랐지만, 파일 점검 통과와 과제 정답 검증은 별개입니다.

## 완성된 작업물이 다음 행동의 출발점이 됩니다

![작업물과 찾은 정보, 앱 상태를 남은 목표 및 최근 행동과 함께 보존하는 구조](./page-01.webp)

동료에게 일을 넘길 때 파일 경로만 주면 남은 요구사항을 놓치고, 말로만 설명하면 결과물을 다시 찾아야 하죠. CarryOn은 대화 전체를 몇 줄로 줄이는 대신, 재사용할 산출물을 **continuation carrier**(작업을 이어받을 기록)라는 단위로 구조화합니다.

- **외부 파일 ([3.2절·부록 A.1](https://arxiv.org/html/2610.18784v2#S3.SS2))**: 디스크에 남은 파일의 위치와 재사용 조건을 남깁니다.
- **검색 정보**: 찾아낸 사실과 출처를 기록 안에 직접 담습니다.
- **앱·세션 상태**: 특정 화면이나 세션 진행 상태에 복귀 환경과 유효 범위를 붙입니다.

같은 대상을 고치면 새 버전을 만들고 영향받지 않은 기록은 그대로 둡니다. 예를 들어 슬라이드 초안을 만든 뒤 “표지는 두고 마지막 장 표만 손보라”는 지시가 남았다면 파일 경로만으로는 이런 제약을 챙기기 어렵습니다. CarryOn은 작업물 기록 옆에 남은 목표·제약·미완료 작업을 담은 **실행 맥락**과 직전 정리 이후의 **최근 기록**을 함께 묶어 연결 고리를 유지합니다.

기억을 구조화한다는 문제의식은 앞서 다룬 [에이전트 기억의 상태 추적](/posts/statemem-agent-memory-state-tracking/)과도 이어집니다. CarryOn은 여기서 한 걸음 더 나아가, 실제로 다시 열어 쓸 산출물과 사용 조건을 맥락의 한가운데에 둡니다.

## 검증을 통과하지 못하면 기존 맥락을 유지합니다

![파일 상태와 출처를 살피고 갱신에 실패한 후보 대신 기존 기록을 유지하는 장면](./page-02.webp)

그런데 파일 경로만 적어 두었다가 정작 파일이 비어 있거나 깨진 상태를 그대로 믿으면 어떻게 될까요? CarryOn은 재사용 후보를 추린 뒤 대화를 접기 전에 실제 작업 환경을 먼저 읽어 보며, 선언된 조건이 확인된 후보만 반영 대상으로 삼습니다.

- **실재와 변경 확인 ([부록 A.2 표 6](https://arxiv.org/html/2610.18784v2#A1.SS2))**: OSWorld 구현에서는 디스크 파일 존재 여부와 최초 상태 대비 해시 변화를 점검합니다.
- **컨테이너 구조 검사**: 빈 파일이 아니고 문서 컨테이너 구조가 정상인지 살핍니다.
- **핵심 텍스트 대조**: 지시문에 나온 핵심 텍스트가 결과물에 들어 있는지 확인합니다.

각 관찰 결과는 특정 후보와 버전·조건에 연결되며, 조건이 모순되거나 미확인 상태인 후보는 대기열에 남기고 검증을 마친 후보부터 처리합니다. 컨텍스트에 반영하기 직전에는 대상·버전·참조·허용 출처·출력 형식을 다시 검사해, 실패하면 **기존 맥락과 최근 기록을 그대로 지킵니다**.

반면 검증을 통과하고 실제 작업물 기록까지 바뀐 경우에만 실행 맥락을 함께 반영한 뒤 과거 대화를 활성 컨텍스트에서 접습니다. 할 일 목록만 고친 채 대화를 접는 일은 막고, 새 맥락 설치에 실패했을 때를 대비한 복원 절차도 따로 두었습니다. 여기서 접어 넣는 대상은 활성 컨텍스트 안의 과거 상호작용이며 원본 로그는 그대로 남고, 파일 상태 점검의 통과 역시 [갱신 일관성을 보호할 뿐](https://arxiv.org/html/2610.18784v2#S3.SS3) 과제의 최종 정답 판정과는 별개입니다.

## 부분 점수와 완전 성공률을 나눠 읽어야 하는 이유

![끝낸 결과를 다시 꺼내 쓰면서 남은 의무를 챙기는 카솔과 개발자](./page-03.webp)

저자들은 별도 학습 없이 같은 모델과 예산으로 기존 에이전트와 CarryOn의 장기 작업 성능을 비교해 보고했습니다.

| OSWorld 2.0 전체 세트 지표 | 원래 에이전트 | CarryOn 적용 | 변화 |
| --- | ---: | ---: | --- |
| 부분 점수 | 43.9% | 49.7% | 5.8%p 상승 |
| 완전 성공률 | 15.7% | 19.4% | 3.7%p 상승 |
| 과제당 평균 누적 토큰 | 4,010만 | 1,930만 | 51.9% 감소 |
| 과제당 명목 모델 비용 | 36.83달러 | 23.62달러 | 35.9% 감소 |

- **OSWorld 2.0 조건 ([표 1·2, 부록 B.3](https://arxiv.org/html/2610.18784v2#S4.SS1))**: v2026.08.08 전체 세트에서 Claude Opus 4.7(최대 추론 노력, 500단계 예산, 맥락 정리 동일 모델)을 사용했습니다. 누적 토큰은 캐시 재읽기 포함 합산치라 컨텍스트 창 크기와 다르고, 명목 비용은 고정 단가에 보조 호출을 더한 값으로 평가기·시뮬레이터·인프라 비용은 제외됩니다.
- **BrowseComp-Plus ([표 3, 부록 A.3·B.1](https://arxiv.org/html/2610.18784v2#S4.SS2))**: 100문항 표본(BM25 검색, 최대 60턴, 512토큰 발췌문 최대 5개, 전체 문서 조회 제외)을 같은 Claude Opus 4.7 에이전트와 Qwen3-32B 공식 채점 프롬프트로 평가해 정확도 49%→56%, 총토큰 22.9%·명목 비용 7.1% 감소를 보고했습니다.
- **OSWorld 40개 과제 비교 ([표 4](https://arxiv.org/html/2610.18784v2#S4.SS4))**: CarryOn 부분 점수는 55.93%로 같은 원리의 줄글 요약 방식(50.93%)을 앞섰으나, 완전 성공률은 원래 에이전트와 CarryOn이 모두 22.50%(줄글 요약 20.00%)로 같았습니다.

중간 진척도가 오르고 누적 토큰이 절반가량 줄어든 흐름은 반가운 성과입니다. 동시에 완전 성공률의 절대 수치는 아직 낮은 구간에 머물러 있어, 맥락 손실을 줄여도 실행 추론 자체에서 막히는 구간이 남아 있음을 알 수 있죠.

주된 비교가 단일 호스트 모델과 두 가지 평가 환경에 모여 있다는 점도 함께 짚어야 합니다. 논문의 비용 곡선에서도 작업 초반에는 맥락 정리 호출 부담이 먼저 발생하다가 긴 실행이 이어질수록 절감분이 쌓이거든요. 따라서 짧은 단발성 작업이나 다른 도메인으로 옮길 때는 손익을 따로 확인해 볼 필요가 있습니다.

## 다메카솔의 해석, 재개할 대상과 남은 의무를 함께 설계하기

실무 에이전트를 설계해 보면 작업 재개 품질은 만들어 둔 결과물과 남은 의무가 얼마나 단단히 맞물려 있는지에 달렸습니다. 분산 시스템의 체크포인트가 스냅샷 시점과 다음 실행 목록을 한 쌍으로 남기는 원리와 같거든요.

직접 에이전트 루프를 구성한다면 결과물 참조마다 **버전과 재사용 조건**을 함께 묶어야 안전합니다. 파일 존재 확인과 내용 검증 완료 상태를 분리해 두고 미해결 요구사항을 별도 필드로 관리하면, 갱신 검증에 실패해도 직전 맥락을 잃지 않고 복구할 수 있습니다. 물론 과제의 최종 정답을 가리는 검사는 이 파일 상태 점검과 별도로 설계해야 하며, 판단 근거를 구조화해 남기는 관점은 [워크플로우의 의미 지속성](/posts/workflow-as-knowledge/)과도 통합니다.

논문에서 안내한 공식 저장소는 현재 구조 설명만 공개했고 실행 코드는 심사 이후 올릴 예정이라, 당장 현업 루프에 붙이려면 공개 일정과 자체 구현 비용을 함께 가늠해야 합니다. 다음에 에이전트 재개 테스트를 만든다면 **완료된 결과 파일 하나와 미해결 요구사항 하나를 세트로 남겨** 확인해 볼 만합니다. 컨텍스트 압축 뒤에도 에이전트가 파일을 다시 열어 점검하고 남은 일만 정확히 이어서 처리하는지 보면, 작업의 연결 고리가 살아 있는지 가장 분명하게 검증할 수 있습니다.
