공공 API 하나를 단발성으로 호출하는 것과 여러 호출을 끝까지 이어서 답을 내는 것은 전혀 다른 문제입니다. **「Multi-Step Tool-Calling over Korean Open Public APIs」** 연구에서 작은 공개 모델들은 선행 인증키 조회를 건너뛰거나 첫 페이지만 읽고 답을 끝내 버렸는데요. 연구팀은 이러한 다단계 실패를 실제 엔드포인트 실행으로 걸러내는 벤치마크 **KOPA-Bench**와 합성 파이프라인 **EDGE**를 제시했습니다.

글·해설: 다메카솔

## 핵심 내용

- **KOPA-Bench 구성**: 한국 공공 API 10개 플랫폼(2,318개 함수)과 6개 분야를 아우르는 145개 멀티스텝 과제로 구성됩니다(과제당 평균 단계 3.32, 평균 호출 4.92회, 병렬 호출 포함 비중 59%).
- **실행 기반 그래프 정제 (EDGE)**: 도구 출력과 다음 입력의 연결을 스키마만 보고 확정하지 않고, 실제 라이브 API에서 실행해 성공·실패 증거로 갱신합니다.
- **소형 모델 학습 성과**: EDGE 데이터(1,781개)로 학습한 Qwen3.5 9B의 KOPA-Bench `pass@1`은 **0.3275에서 0.4310**으로 올라 비학습 27B 모델(0.4482)에 근접했습니다.
- **라이브 환경과 확인 범위**: 실제 공공 엔드포인트에 의존하므로 시간이 지나면 응답과 상태가 달라질 수 있으며, 공식 저장소는 출시 준비 상태(`README.md`, `LICENSE`, `.gitignore`)여서 이번 검토는 원문(PDF·TeX) 대조까지 수행했습니다.

## 에이전트는 선행 키와 나머지 페이지를 놓쳤다

![작은 에이전트 토큰이 키 관문을 건너뛰고 긴 레코드 흐름에서 첫 번째 묶음만 집는 장면](./page-01.webp)

다단계 API 호출의 실패는 도구 선택보다 더 이른 지점에서 시작됐습니다. 논문이 소개한 교육 분야 과제 예시를 보면, 모델은 필요한 선행 조회 없이 통계 API를 먼저 호출했다가 인증키 오류를 냈고, 뒤늦게 키를 회수한 뒤에도 **페이지 1만 집계**하고 멈췄습니다. 실제 정답은 전체 페이지를 합산한 75명이었지만 모델은 첫 페이지에 나온 23명을 최종 답으로 제출했습니다.

이 사례는 한국 공공 API 환경이 안기는 두 겹의 부담을 잘 보여 줍니다. 인증키나 기업·지역 코드를 먼저 조회해야 다음 API 호출의 인자를 채울 수 있고, 한 번의 응답이 수천 건의 레코드를 돌려주면 페이지네이션과 결과 축약까지 수행해야 합니다. 단일 함수 호출 정확도만 재는 기존 평가에서는 이런 연쇄 실패가 잘 드러나지 않습니다.

## 실제 한국 공공 API를 잇는 과제를 만들었다

![여섯 종류의 공공 서비스 구역에서 나온 결과가 다음 API 관문의 열쇠가 되는 연결 구조](./page-02.webp)

저자들은 교통·금융·교육·법률·정치·지방행정 6개 분야에서 **145개 과제**를 설계했습니다. 10개 플랫폼의 **2,318개 함수**를 MCP 서버로 노출하고, 과제마다 정답 행동과 기대 답변(또는 서버 상태), 허용 호출 수를 기록했는데요. 과제당 평균 단계 수는 3.32, 평균 호출 수는 4.92회였으며 최대 14회 호출이 필요한 과제도 포함됐습니다(전체 과제의 59%는 병렬 호출을 포함합니다).

과제 검수는 사람이 만든 정답 경로를 다른 전문가가 교차 검토하는 단계와 실제 실행 단계로 나뉘었습니다. 첫 감사에서 7개 과제의 오류가 발견됐고 모델 실패를 제외한 실행 검사의 첫 통과율은 **80%**였는데, 연구팀은 지적된 과제를 수정해 145개 과제가 모두 통과할 때까지 재실행했습니다. 또한 성공 판정 지표도 하나로 뭉뚱그리지 않고 다음 세 가지로 분리했습니다.

- **`RESPONSE`**: 최종 답변의 정확성을 평가합니다.
- **`ENVIRONMENT`**: 실행이 끝난 뒤 서버 상태 변화를 확인합니다.
- **`ACTION`**: 도구 호출 자체의 정확성과 불필요한 호출(낭비) 여부를 봅니다. 중간에 정답 행동을 한 번 포함했더라도 뒤이어 잘못된 호출을 덧붙여 상태를 망칠 수 있으므로 `ACTION`만으로 과제 성공을 판정하지는 않았습니다.

## 그럴듯한 연결을 실제 호출로 시험했다

![후보 연결 부품들이 실제 흐름 시험대를 지나 성공한 연결만 남고 구조적으로 깨진 연결은 제거되는 장면](./page-03.webp)

합성 파이프라인인 **EDGE**의 첫 단계는 앞선 도구의 출력 필드와 다음 도구의 입력 인자를 잇는 후보 그래프를 만드는 일입니다. 검색기가 관련 도구를 좁히고 LLM이 연결 가능성을 제안하지만 그 판단은 출발점일 뿐이며, 시스템은 후보 경로를 실제 라이브 API에서 실행한 뒤 성공과 실패를 Beta 사후분포에 누적해 그래프를 계속 갱신합니다.

이때 실패의 성격에 따라 감점 가중치를 달리 둡니다. 스키마·타입 불일치나 필수 필드 누락은 연결 구조 자체의 결함이므로 크게 감점하고, 호출 제한(rate limit)·타임아웃·일시적 서버 오류는 외부 환경 잡음일 수 있어 작게 반영하는 식입니다. API 서버가 잠깐 느렸다는 이유만으로 실제로는 유효한 도구 연결까지 지워 버리는 일을 막으려는 설계입니다.

저자들의 분석에서 실행 전 후보 연결의 성공률은 **50.2%**였지만, 실행 정제를 거친 뒤 살아남은 그래프에서는 **62.7%**로 높아졌고 전체 후보의 **14.8%**가 제거됐습니다(동일한 후보에서 출발해 실제 실행 증거가 어떤 연결을 남겼는지 보여 주는 수치이며, 기존 타 합성 시스템 전체를 같은 도구 목록에서 재실행한 직접 비교까지는 수행하지 않았습니다).

## 응답이 하나인지, 몇 개인지, 너무 많은지 구분했다

![하나의 레코드는 직진하고 소수 레코드는 갈라지며 대량 레코드는 선택 장치를 지나 줄어드는 장면](./page-04.webp)

두 번째 단계의 핵심은 연결 필드가 돌려주는 **레코드 수(기수성)**에 따른 분기 처리입니다.

- **단일 레코드 (1개)**: 다음 도구 호출의 인자로 그대로 넘깁니다.
- **소수 레코드 (2~5개)**: 각 레코드에 대해 병렬·반복 호출을 수행합니다.
- **대량 레코드 (6개 이상)**: 최대·최소·임계값·날짜·빈도 같은 결정적 규칙을 적용해 후보를 먼저 추려 냅니다(비교나 조건 분기처럼 단순 선형 체인으로 표현하기 어려운 과제는 별도 구조로 합성했습니다).

이 과정을 거쳐 만들어진 학습 데이터는 총 **1,781개**였습니다. 연구팀은 동일한 데이터셋 위에서 지도 미세조정(SFT)과 강화학습(GRPO)의 효과를 나누어 살폈는데, 비재현·오류·중복·오래된 레이블을 걸러내는 품질 필터만 적용해도 4B 모델의 `pass@1`이 **0.242에서 0.309**로 올랐다고 보고했습니다. 단순 데이터 양보다 실제로 실행 가능한 궤적을 남기는 품질 관리가 성능을 좌우한다는 근거입니다.

## 작은 모델은 가까워졌고 엔드포인트는 계속 움직인다

![작은 모델 엔진이 큰 엔진을 따라잡는 동안 성인형 카솔이 시간에 따라 움직이는 API 관로를 점검하는 장면](./page-05.webp)

EDGE 데이터로 학습한 소형 모델의 성능 변화와 분포 밖(OOD) 일반화 지표는 다음과 같습니다(KOPA-Bench는 과제당 4회 롤아웃, `pass@1` 안정성은 별도 8개 시드로 확인).

| 모델 구성 | KOPA-Bench `pass@1` (기본 → 학습 후) | 분포 밖 BFCL 멀티턴 점수 변화 | 비고 |
| --- | :---: | :---: | --- |
| **Qwen3.5 4B** | 0.1758 → **0.3094** | **+4.04점** | 품질 필터만 적용 시 0.242 → 0.309 |
| **Qwen3.5 9B** | 0.3275 → **0.4310** | **+5.87점** | 비학습 27B 모델(0.4482)에 근접 |
| **Qwen3.5 27B (비학습 비교군)** | **0.4482** | — | 약 3배 큰 비학습 기준 모델 |

연구팀은 분포 밖 벤치마크인 BFCL에서도 멀티턴 점수가 함께 오른 것을 두고, 멀티스텝 도구 호출 구조가 멀티턴 대화 구조와 맞닿아 있다는 신호로 해석했습니다(다만 한국 공공 API에서 합성한 데이터가 모든 상용·비공개 API에 그대로 일반화된다는 결론은 이 실험 범위 밖입니다).

무엇보다 재현성에는 **살아 있는 외부 서비스**라는 변수가 끼어듭니다. 공공 API의 스키마, 가용성, 반환 레코드가 시간에 따라 바뀌면 똑같은 정답 경로를 실행해도 다른 결과가 나올 수 있습니다. 연구팀이 실시간 변동 데이터 과제를 걸러내고 서버 상태를 해시로 비교했더라도 외부 기관의 엔드포인트 자체를 영구 고정할 수는 없기 때문입니다.

이번 검토에서 확인한 공식 저장소(`d01a8418fcdaac983cb00fb26bd5e9c0851e3964` 커밋)에는 `README.md`, `LICENSE`, `.gitignore` 세 파일만 올라와 있었고, README를 통해 벤치마크 145개 과제·MCP 서버·평가 코드·EDGE 파이프라인·학습 데이터·체크포인트·프롬프트를 공개 준비 중이라고 안내하고 있었습니다. 따라서 이번 확인은 30쪽 분량의 PDF와 68개 TeX 파일, 저장소 출시 상태를 교차 대조한 수준이며, 8대의 H100 학습이나 라이브 API 호출, 145개 과제(8개 시드) 및 BFCL 평가는 직접 재실행하지 못했습니다.

## 다메카솔의 해석: API 연결은 배포 뒤에도 살아 있는지 물어야 한다

이 논문에서 가장 눈여겨볼 부분은 모델 크기보다 **연결 검증 방식**입니다. API 명세 문서상으로는 출력 필드와 다음 입력 타입이 맞아 보여도 막상 실행해 보면 인증키, 페이지네이션, 호출 제한, 서버 상태 때문에 경로가 중간에 깨지기 일쑤입니다. 앞서 [도구 명세가 에이전트 안전에 미치는 영향을 다룬 글](/posts/tool-specifications-agent-safety/)과 함께 읽으면, 정적 명세 검증 다음에 왜 실제 실행 증거가 필요한지 한층 선명해집니다.

실제 운영 환경이라면 배포 전후에 가벼운 **계약 테스트(contract test)**를 두는 편이 좋습니다. 선행 코드 조회, 두 페이지 이상 집계, 다건 응답 축약, 최종 상태 확인을 대표 경로로 묶어 실행하되, 스키마 불일치 같은 **구조 오류**와 타임아웃 같은 **일시적 환경 오류**를 별도 알림으로 분리하는 방식입니다. 또한 결과 캐시에는 최종 답만 남기지 않고 호출 시각·엔드포인트 버전·페이지 수·사용한 인자를 함께 보존해야 나중에 실패 원인을 재구성하고 바뀐 엔드포인트에 맞춰 정답을 갱신할 수 있습니다(이는 논문이 직접 시험한 개입이 아니라 공개 자료를 바탕으로 정리한 운영 제안이며, 실제 서비스에서는 API 사업자별 호출 비용과 이용 약관도 함께 고려해야 합니다).

## 자주 묻는 질문

### 9B가 27B와 같아졌다는 뜻인가요?

KOPA-Bench `pass@1` 기준으로는 학습한 9B(0.4310)와 비학습 27B(0.4482)가 가까워졌습니다. 하지만 BFCL 세부 점수와 `ACTION` 지표에서는 순위가 다르고, 도메인 데이터로 학습한 9B와 비학습 27B를 비교한 결과이므로 모델의 전반적인 능력이 동등해졌다는 뜻은 아닙니다.

### 라이브 API 벤치마크는 신뢰하기 어렵나요?

정적 스냅샷이 가려 버리는 호출 제한과 스키마 변화를 그대로 드러낸다는 장점이 있습니다. 대신 측정 시점이 달라지면 동일한 호출 경로가 같은 답을 보장하지 않으므로, 엔드포인트 상태와 정답 갱신 기록을 평가 결과에 함께 보존해야 합니다.

### 코드가 공개되면 곧바로 재현할 수 있나요?

코드 외에도 각 공공기관의 API 키와 이용 조건, 당시 반환 레코드, 8대 H100 학습 환경이 필요합니다. 공개 이후에는 먼저 과제 파일과 평가기를 정적으로 대조한 뒤, 재현 가능한 일부 도메인부터 실행 범위를 좁혀 가는 편이 현실적입니다.
