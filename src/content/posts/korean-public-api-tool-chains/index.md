공공 API 하나를 단발로 호출하는 것과 여러 도구를 끝까지 이어 답을 내는 일은 전혀 다릅니다. **「Multi-Step Tool-Calling over Korean Open Public APIs」** 연구에서 작은 공개 모델들은 선행 인증키 조회를 빠뜨리거나 첫 페이지만 읽고 멈췄는데요. 저자들은 이런 연쇄 실패를 실제 실행으로 걸러내는 벤치마크 **KOPA-Bench**와 데이터 합성 파이프라인 **EDGE**를 내놓았습니다.

글·해설: 다메카솔

## 핵심 내용

- **KOPA-Bench**: 한국 공공 API 10개 플랫폼(2,318개 함수)·6개 분야의 145개 멀티스텝 과제
- **EDGE 정제**: 스키마상 연결 후보를 라이브 API에서 직접 실행해 Beta 사후분포로 가지치기
- **소형 모델 성과**: EDGE 데이터(1,781개)로 학습한 Qwen3.5 9B(`0.4310`)가 비학습 27B(`0.4482`)에 근접
- **재현 한계**: 라이브 API 변동성과 출시 준비 중인 공식 저장소 상태가 결과 재현의 제약

## 에이전트는 선행 키와 나머지 페이지를 놓쳤다

![작은 에이전트 토큰이 키 관문을 건너뛰고 긴 레코드 흐름에서 첫 번째 묶음만 집는 장면](./page-01.webp)

다단계 API 실패는 도구 선택보다 앞선 지점에서 터집니다. 예를 들어 논문의 교육 분야 과제에서 작은 모델은 선행 조회 없이 통계 API를 먼저 불렀다가 인증키 오류를 냈고, 뒤늦게 키를 얻고도 **첫 페이지만 집계**해 75명 대신 23명을 답으로 냈는데요.

이 사례는 한국 공공 API의 두 겹 부담을 압축해 보여 줍니다. 인증키나 기업·지역 코드를 먼저 조회해야 다음 인자를 채울 수 있고, 수천 건 응답이 오면 페이지네이션과 결과 축약까지 마쳐야 하거든요. 단일 호출 정확도만 재는 기존 평가에서는 이런 연쇄 실패가 좀처럼 드러나지 않습니다.

## 실제 한국 공공 API를 잇는 과제를 만들었다

![여섯 종류의 공공 서비스 구역에서 나온 결과가 다음 API 관문의 열쇠가 되는 연결 구조](./page-02.webp)

연구팀은 교통·금융·교육·법률·정치·지방행정 6개 분야 공공 API를 MCP 서버로 노출해 **KOPA-Bench**를 만들었습니다. 과제마다 정답 행동과 기대 답변(또는 서버 상태), 호출 한도를 묶어 겉보기에만 그럴듯한 호출을 걸러내게 설계한 셈이죠.

- **규모**: 10개 플랫폼·2,318개 함수, 145개 과제(평균 3.32단계·4.92회, 최대 14회, 병렬 호출 59%)
- **검수**: 교차 검토로 7개 오류를 수정하고, 모델 실패 제외 초기 통과율 80%에서 전수 통과까지 보완
- **3분할 지표**: 최종 답변(`RESPONSE`), 서버 상태(`ENVIRONMENT`), 호출 정확성·낭비(`ACTION`)를 분리해 중간 정답 뒤 상태를 망친 호출은 실패로 판정

## 그럴듯한 연결을 실제 호출로 시험했다

![후보 연결 부품들이 실제 흐름 시험대를 지나 성공한 연결만 남고 구조적으로 깨진 연결은 제거되는 장면](./page-03.webp)

**EDGE**의 1단계는 검색기와 LLM이 제안한 도구 입출력 연결 후보를 실제 라이브 API에서 실행해 검증하는 과정입니다. 성공·실패 기록을 Beta 사후분포에 누적하되, 스키마 불일치·필수 필드 누락 같은 구조 결함은 크게 감점하고 호출 제한·타임아웃·일시 오류 같은 외부 잡음은 작게 반영하는데요. 잠깐 느린 서버 때문에 유효한 연결까지 지우지 않으려는 장치죠.

실행 정제를 거치자 후보 연결 성공률은 **50.2%에서 62.7%**로 높아졌고 전체 후보의 **14.8%**가 제거됐습니다. 같은 후보 풀 안에서 실행 증거의 필터링 효과를 측정한 수치로, 기존 합성 기법 전체와의 동일 조건 비교는 후속 과제로 남아 있습니다.

## 응답 크기에 따라 분기하고 품질로 걸렀다

![하나의 레코드는 직진하고 소수 레코드는 갈라지며 대량 레코드는 선택 장치를 지나 줄어드는 장면](./page-04.webp)

2단계에서는 앞선 응답의 **레코드 수(기수성)**에 따라 다음 실행 흐름을 세 갈래로 나눕니다.

- **단일 레코드 (1개)**: 다음 도구 입력 인자로 그대로 전달
- **소수 레코드 (2~5개)**: 레코드별 병렬·반복 호출 수행
- **대량 레코드 (6개 이상)**: 최대·최소·임계값·날짜·빈도 같은 결정적 규칙으로 후보 축약(비교·분기 과제는 별도 합성)

연구팀이 비재현·오류·중복·오래된 레이블을 빼는 품질 필터 효과만 따로 확인했을 때도 4B 모델의 `pass@1`이 **0.242에서 0.309**로 뛰었습니다. 합성 데이터 양보다 끝까지 실행되는 궤적만 남기는 품질 관리가 성능을 좌우한다는 방증입니다.

## 작은 모델은 가까워졌고 엔드포인트는 움직인다

![작은 모델 엔진이 큰 엔진을 따라잡는 동안 성인형 카솔이 시간에 따라 움직이는 API 관로를 점검하는 장면](./page-05.webp)

필터링된 **1,781개** 데이터로 소형 모델을 GRPO 학습한 결과는 아래와 같습니다.

| 모델 구성 (학습 설정) | KOPA-Bench `pass@1` | 분포 밖 BFCL 멀티턴 변화 | 비고 |
| --- | :---: | :---: | --- |
| **Qwen3.5 4B** (8×H100 GRPO) | 0.1758 → **0.3094** | **+4.04점** | 품질 필터만으로 0.242 → 0.309 |
| **Qwen3.5 9B** (4롤아웃·8시드) | 0.3275 → **0.4310** | **+5.87점** | 비학습 27B(`0.4482`)에 근접 |
| **Qwen3.5 27B** (비학습 비교군) | **0.4482** | — | 약 3배 큰 기준 모델 |

BFCL 멀티턴 점수 상승은 도구 체인 학습이 일반 대화 흐름에도 보탬이 된다는 신호로 풀이됩니다. 다만 `pass@1`과 달리 BFCL 세부 점수나 `ACTION`에서는 9B와 27B의 순위가 갈리며, 상용·비공개 API 일반화는 이번 실험 범위 밖입니다.

더 큰 변수는 **살아 있는 외부 서비스**라는 점입니다. 공공 API 스키마와 가용성, 반환 레코드가 바뀌면 같은 경로도 시점에 따라 다른 결과를 내거든요. 공식 `EDGE-KOPA` 저장소도 현재 `README.md`, `LICENSE`, `.gitignore`만 공개된 상태여서, 향후 과제와 코드가 열리더라도 기관별 API 키와 당시 엔드포인트 상태가 재현의 관건이 됩니다.

## 다메카솔의 해석: 배포 뒤에도 연결을 검증해야 한다

실무 에이전트에서 중요한 요소는 모델 체급보다 **실행 기반 계약 검증**입니다. 명세상 타입이 맞아도 실제 호출에서는 인증키 순서와 페이지네이션 때문에 경로가 끊기기 일쑤니까요. 앞서 [도구 명세가 에이전트 안전에 미치는 영향을 다룬 글](/posts/tool-specifications-agent-safety/)과 나란히 놓고 보면 정적 명세 이후 왜 실행 증거가 필요한지 더 또렷해집니다.

운영 환경이라면 선행 키 조회, 다중 페이지 집계, 대량 응답 축약, 최종 상태 확인을 묶은 가벼운 **계약 테스트**를 배포 전후로 돌리는 편이 안전합니다. 스키마 불일치와 일시 타임아웃 알림을 분리하고, 캐시에 호출 시각·엔드포인트 버전·페이지 수·인자를 함께 남겨 두어야 장애 원인을 추적하기 수월하죠. 실제 적용 단계에서는 API 제공처별 호출 비용과 이용 약관 확인도 함께 챙겨야 합니다.
