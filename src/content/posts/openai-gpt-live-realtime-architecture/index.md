OpenAI는 2026년 8월 3일 실시간 음성 시스템 **GPT-Live**의 엔지니어링 구현 구조를 공개했습니다. 7월부터 ChatGPT Voice에 순차 적용 중인 이 아키텍처의 핵심은 **말을 끊김 없이 이어 가는 오디오 경로와 검색·깊은 추론·도구 호출을 처리하는 비동기 경로를 분리한 것**입니다.

글·해설: 다메카솔

## 핵심 내용

- **별도 턴 감지기 제거와 전이중(Full-duplex) 처리**: 오디오 경로 앞단의 별도 턴 감지기를 빼고, 음성 모델이 짧은 간격으로 듣기·말하기·기다리기·끼어들기·도구 호출을 동시에 판단하도록 바꿨습니다.
- **오디오 경로와 비동기 RPC 분리**: 프레임 단위 지연에 민감한 오디오는 전용 미디어 경로로 흐르고, 검색·깊은 추론·도구 호출·대화 저장은 비동기 RPC 경계 뒤로 격리해 무거운 작업이 음성 흐름을 막지 않게 설계했습니다.
- **무중단 상태 전환과 런타임 개선**: 긴 대화에서 인스턴스 교체와 문맥 압축을 백그라운드 워밍업으로 처리하고, WARP(IETF Internet-Draft)로 WebRTC 연결 시작 왕복을 6회에서 1회로 줄였습니다. 또한 미디어 프런트엔드와 추론 로직을 Python `asyncio`에서 Go로 이관해 새 시스템의 p95 프레임 전달 지연을 기존 p50 수준으로 낮췄습니다(OpenAI 내부 측정 기준).

## 턴이 끝나기를 기다리지 않습니다

![멈춤 감지 뒤 응답하던 이전 흐름과 듣기·말하기를 함께 처리하는 연속 흐름을 비교한 만화](./page-01.webp)

기존 음성 AI 파이프라인은 사용자가 말을 끝냈는지 별도의 턴 감지기로 먼저 판정한 뒤에야 메인 모델을 호출하는 경우가 많았습니다. 감지기가 너무 일찍 반응하면 사용자의 말을 끊고, 너무 늦게 반응하면 답변이 굼떠집니다.

GPT-Live는 이 별도 감지기를 오디오 경로에서 제거하고 음성 모델이 듣기와 말하기를 동시에 처리하는 전이중(full-duplex) 구조를 채택했습니다. 연속 처리라고 해서 무조건 먼저 말하는 것이 아니라, 모델이 짧은 시간 간격마다 계속 듣기, 말하기, 기다리기, 끼어들기, 도구 호출 중 무엇을 수행할지 직접 결정해 잠시 생각하느라 멈춘 사람과 발화를 마친 사람을 더 자연스럽게 구분합니다.

## 오디오와 깊은 작업은 다른 길로 갑니다

![오디오는 중앙 실시간 경로로 흐르고 검색·추론·도구 호출은 옆 비동기 경로에서 처리되는 구조를 보여 주는 만화](./page-02.webp)

OpenAI가 공개한 시스템 구조는 작업의 시간 민감도에 따라 세 가지 경로를 명확히 가릅니다.

| 경로 구분 | 담당 작업 | 지연 격리 및 최적화 방식 |
| --- | --- | --- |
| **전용 미디어 경로** | 실시간 오디오 프레임 입출력 및 음성 모델 반응 | 외부 도구나 저장 지연에 블로킹되지 않도록 독립 경로 유지, Python `asyncio`에서 Go로 전환해 p95 프레임 전달 성능을 기존 p50 수준으로 단축 |
| **비동기 RPC 경로** | 웹 검색, 프런티어 모델 깊은 추론, 외부 도구 호출, 대화 저장 | 음성 세션 시작 시 프런티어 모델 세션과 도구를 미리 열어 초기 문맥을 채우고, 프롬프트 캐싱으로 후속 응답 시간을 단축 |
| **백그라운드 상태 경로** | 긴 세션의 모델 인스턴스 교대, 대화 문맥 압축 | 기존 인스턴스가 대화를 이어 가는 동안 새 인스턴스를 미리 데우고 문맥을 채운 뒤 무중단 전환 |

이 구조 덕분에 특정 도구 호출 하나가 늦어지더라도 해당 결과만 늦게 합류할 뿐, 음성 프레임의 흐름 자체는 멈추지 않습니다.

## 긴 대화는 상태를 뒤에서 갈아탑니다

![기존 모델 인스턴스가 대화를 이어 가는 동안 새 인스턴스가 문맥을 준비하고 카솔이 교대 원칙을 설명하는 만화](./page-03.webp)

실시간 음성 세션은 길게 유지될수록 문맥이 계속 불어납니다. 모델 인스턴스를 교체하거나 문맥을 압축할 때마다 대화가 멈춘다면 몰입이 깨지기 때문에, GPT-Live는 기존 인스턴스가 발화를 이어 가는 동안 뒤에서 새 인스턴스를 데우고 문맥을 미리 채운 뒤 준비가 끝나는 순간 전환합니다.

초기 연결 지연에는 네트워크 프로토콜 개선도 함께 들어갔습니다. OpenAI는 **WARP(WebRTC Abridged Roundtrip Protocol)** 제안을 통해 WebRTC 미디어·데이터 시작에 필요한 네트워크 왕복(roundtrip)을 6회에서 1회로 줄였다고 설명했습니다. 다만 WARP는 2026년 8월 4일 기준 IETF Internet-Draft 단계이며 최종 표준 확정 여부는 아직 열려 있습니다.

## Shadow 경로 검증과 공개 범위의 경계

OpenAI는 정식 배포 전에 기존 Voice가 사용자에게 응답하는 동안 새 시스템을 읽기 전용 shadow 경로에서 나란히 실행해 검증했습니다. 이 과정에서 GPU 처리량 지표만으로는 보이지 않던 주변 지원 컴포넌트 포화, 리전별 네트워크 지연, 장기 세션의 메모리 누수 및 복구 문제를 사전에 발견했다고 밝혔습니다. 모델 추론 속도만 재면 실시간 시스템 전체의 병목을 놓치기 쉽다는 점을 잘 보여주는 대목입니다.

한편 이번 발표에 포함된 성능 수치(Go 이관 후 p95 프레임 전달 성능이 기존 p50과 유사해졌다는 보고 등)는 절대 지연 시간과 표본 크기가 공개되지 않은 회사 내부 관측치입니다. 또한 ChatGPT Voice 내 GPT-Live 적용은 현재 순차 진행 중이며, 함께 언급된 GPT-Live API는 출시 일정이 정해지지 않은 예정 단계입니다.

## 다메카솔의 해석

이번 아키텍처 공개의 핵심은 “더 빠른 단일 음성 모델”보다 **실시간 임계 경로(critical path)를 좁게 유지한 분리 설계**에 있습니다. 사용자가 즉각 체감하는 오디오 스트림은 작고 예측 가능한 경로에 두고, 검색·추론·도구·저장은 지연되더라도 대화 자체를 멈추지 않는 비동기 경로로 격리했습니다.

실시간 음성 에이전트를 직접 설계한다면 “모든 작업을 어떻게 빨리 처리할까?”보다 **“무엇이 늦어져도 대화를 멈추지 않게 만들까?”**를 먼저 물어야 합니다. 프레임마다 제시간에 도착해야 하는 미디어 작업, 비동기로 합류해도 되는 추론·도구 작업, 그리고 백그라운드에서 미리 준비할 수 있는 상태 전환 작업을 가르는 기준은 어떤 실시간 AI 시스템에나 바로 적용할 수 있는 설계 원칙입니다.
