**코드 작성자를 잘 맞히는 AI도 코드 길이와 주석에 기대고 있을 수 있습니다.** 코드 리뷰나 평가를 모델에 맡긴다면 꽤 신경 쓰이는 결과입니다. 「Style, Not Self」의 저자들은 추가 학습 없이 작성자를 묻는 실험에서, 모델의 정답률을 단순한 길이 비교 규칙과 대조했습니다. 표면 단서를 정리한 뒤에는 여러 판별 결과가 우연 수준에 가까워졌지만, 학습한 분류기는 남은 흔적을 여전히 읽었습니다.

글·해설: 다메카솔

## 같은 문제에 더 단순한 판정기를 세워 봅니다

![같은 길이 차이를 가진 리본 쌍을 두 방식으로 비교하는 비유](./page-01.webp)

GPT-5가 자기 코드와 Grok 4 Fast의 코드를 구분한 정확도는 81.9%였습니다. 숫자만 보면 자기 흔적을 꽤 잘 알아보는 것 같습니다. 그런데 같은 항목에서 **긴 코드를 고르는 규칙은 97.5%**를 기록했습니다. 모델이 무엇을 읽었는지부터 다시 물어야 하는 대목입니다.

이 비교는 MBPP의 유효한 코드 238쌍에 한정됩니다. 빈 코드와 구분할 수 없는 동일 코드, 정해진 형식으로 답하지 않은 판정을 제외했으며, 정답은 각각 195개와 232개였습니다. 그림의 긴 리본과 짧은 리본은 코드의 길이 차이를 설명하는 비유이고 실제 측정 비율을 그린 도표는 아닙니다. [원문 4.2절·표 3](https://arxiv.org/html/2609.30048v1#S4.SS2)

저자들은 자기 코드 고르기, 코드 하나가 자기 것인지 답하기, 특정 모델의 코드 찾기, 작성자를 가리고 품질 평가하기를 나눠 시험했습니다. 주요 모델은 GPT-5, Claude Haiku 4.5, Gemini 2.5 Flash, Grok 4 Fast, DeepSeek-V3-0324입니다. MBPP 257문제, HumanEval 164문제, DS-1000의 Pandas 부분집합 150문제를 사용했고, 쌍 비교는 MBPP에서 수행했습니다. 특정 작성자 판별에는 별도의 생성 모델도 추가했습니다.

평가에서 저는 이 단순한 대조군이 특히 유용하다고 봅니다. 복잡한 판정기가 높은 점수를 받아도 길이나 문서화 여부만으로 같은 결과를 얻는다면, 점수가 곧바로 원하는 능력을 뜻하지는 않으니까요. 여기서 가장 잘 맞는 규칙은 같은 자료를 보고 고른 것이므로, 별도 시험 자료에서 검증한 최적 규칙으로 받아들여서는 안 됩니다.

## 주석과 이름을 정리하면 무엇이 바뀔까요

![주석과 이름을 뜻하는 리본 장식을 덜어도 속 구조가 남는 비유](./page-02.webp)

이번에는 코드의 겉모습을 바꿉니다. 저자들은 구문 구조를 다루는 AST 기반 정규화로 주석·문서 문자열·타입 힌트를 제거하고 지역 이름을 바꿨습니다. 연구에 사용한 MBPP 시험에서는 주요 5개 모델의 개별 항목 통과 여부가 그대로 유지됐습니다. 리본의 장식을 떼는 장면은 이 처리를 재작화한 것입니다. [3.4절·4.5절](https://arxiv.org/html/2609.30048v1#S4.SS5)

| GPT-5 대 Grok 4 Fast의 MBPP 코드 | 원본 | 정규화 후 |
| --- | ---: | ---: |
| 분석에 포함한 판정 | 238쌍 | 210쌍 |
| GPT-5 자기 코드 판별 | 195/238, 81.9% | 95/210, 45.2% |
| 긴 코드를 고르는 규칙 | 232/238, 97.5% | 179/210, 85.2% |

정규화 뒤 모델의 점수는 크게 내려갔습니다. 동시에 길이 규칙은 여전히 잘 맞혔다는 점이 흥미롭습니다. 저자들은 GPT-5가 길이 자체보다 길이와 함께 나타나는 문서화 단서에 기대었을 가능성을 제시합니다. 이 설명은 결과에 대한 해석이며, 모델 내부의 판단 과정을 직접 관찰한 결과와는 구분해야 합니다.

**두 열의 분모가 다릅니다.** 정규화 후 동일해진 27쌍을 제외했고 요청 실패로 판정 하나가 빠졌습니다. 빈 코드와 응답 형식 제외도 적용했으므로, 같은 238개 항목의 정답 여부만 앞뒤로 바꿔 센 표가 아닙니다. 제가 공개 기록에서 다시 집계한 범위는 위 두 행의 정답 수와 길이 규칙입니다. 모델을 다시 호출하거나 생성 코드의 테스트를 재실행하지는 않았습니다.

더 넓은 12개 정규화 재평가 중 10개는 43.6~57.8%였고, 여러 비교에 따른 우연한 발견을 줄이는 Holm 보정 뒤 유의하지 않았습니다. 나머지 두 결과는 남아 있는 길이 차이를 따라 우연 수준보다 낮았습니다. 통계적으로 유의하지 않았다는 결과는 작은 효과까지 사라졌다는 증명과는 다릅니다. 논문도 넓은 신뢰구간을 한계로 남깁니다.

## 늘 같은 대답으로도 정답률은 올라갑니다

코드 하나만 보여 주는 시험에서는 응답 습관도 살펴야 합니다. 자기 코드는 대략 3분의 1이고 다른 모델의 코드는 3분의 2이므로, 단순히 계속 “내 코드가 아니다”라고 답하는 규칙의 명목 정답률도 66.7%입니다. 이때 필요한 지표는 자기 코드를 인정한 비율과 남의 코드를 부인한 비율을 같은 무게로 평균한 **균형 정확도**입니다.

저자들이 보고한 15개 모델·문제군 조합의 균형 정확도는 49.4~58.2%였습니다. 보정 뒤에도 Grok의 두 조합은 유의했으므로, 전부 무작위라고 뭉뚱그릴 결과는 아닙니다. 일반 정답률만 나열하면 잘 알아보는 모델과 자주 부인하는 모델을 혼동하기 쉽다는 것이 이 비교의 요점입니다. [4.3절·표 12](https://arxiv.org/html/2609.30048v1#S4.SS3)

문항을 쓰는 순서도 점수를 바꿨습니다. 초기 실험에서는 모델 이름을 나열한 순서와 코드 순서가 맞물려 86~99%가 나왔고, 저자들은 이 결과를 정식 작성자 판별 비교에서 제외했습니다. 수정한 프롬프트는 이름 순서를 코드 위치와 독립적으로 무작위화했습니다. 제가 평가 문항을 검수한다면 정답이 내용 밖의 순서에 새어 있는지도 함께 확인하겠습니다.

## 다메카솔의 해석: 작성 이력과 품질 증거를 따로 보관합니다

![돋보기 아래 남은 직조 무늬를 보며 판별과 품질 검사를 구분하는 카솔](./page-03.webp)

장식을 덜어낸 뒤에도 코드에는 작성 모델을 구분할 흔적이 남았습니다. 저자들이 학습한 문자 패턴 분류기는 정규화된 여러 모델 쌍을 구분했고, 일부 쌍에는 길이 차이도 남았습니다. 따라서 정규화는 이번 제로샷 판정기가 사용한 단서를 줄이는 처리로 이해하는 편이 정확합니다. 완전한 익명화나 감시 모델의 안전성까지 확보한 결과는 아닙니다.

저는 코드 리뷰 시스템에서 **작성 이력은 생성 시점의 기록으로, 품질은 실행과 검토의 증거로 남기겠습니다.** 모델에게 작성자를 추측하게 해서 그 결과로 신뢰도를 올리면, 주석을 많이 쓰는 스타일을 품질이나 책임의 증거로 잘못 사용할 위험이 있기 때문입니다. 모델 버전·입력·산출물 식별자를 기록하고, 테스트 결과와 검토 의견은 별도 항목으로 연결하면 판단 근거를 되짚기도 쉬워집니다. 이는 이 연구를 바탕으로 한 운영 설계 제안입니다.

판정기를 시험할 때에는 코드 위치와 이름 순서를 바꾸고, 정규화 전후의 유효 항목 수도 함께 보관하겠습니다. 문서 문자열을 지운 코드만 운영에 쓰자는 권고는 아닙니다. 실제 코드에서는 문서와 이름이 유지보수에 필요하며, 변환이 동작을 보존하는지도 따로 확인해야 합니다. 품질 평가를 더 살펴보려면 [ExecCritic의 독립 테스트 생성 연구](/posts/execcritic-independent-tests/)가 이어집니다. 작성자를 맞히는 문제와 오류를 잡는 문제의 차이를 비교해 볼 수 있습니다.

이번 결과가 다루는 범위는 선택한 모델과 프롬프트, 짧은 Python 코드의 추가 학습 없는 판별입니다. 주요 평가기에는 소형·고속 모델이 많고, 원래 실험과 후속 실험은 2026년 3월과 9월에 나뉘었습니다. OpenRouter의 제공자는 고정하지 않았으며 기본 추론 설정을 사용했습니다. 의도적으로 넣은 신호나 추가 학습한 감시자, 다른 언어와 큰 저장소에 대한 결론은 별도 실험이 필요합니다.

다음 판정기를 붙이기 전에, 같은 자료에서 “긴 코드를 고른다”는 규칙이 몇 점을 받는지부터 확인해 보겠습니다. 간단한 대조군 하나가 높은 점수의 의미를 바꿔 놓을 수 있습니다.
