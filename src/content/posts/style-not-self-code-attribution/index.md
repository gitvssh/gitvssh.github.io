AI 모델에게 코드 리뷰나 품질 평가를 맡길 때, 혹시 모델이 자기 코드를 은근히 편애하거나 작성자를 알아채지는 않을지 신경 쓰이곤 합니다. 그런데 최근 연구를 보면 정작 모델이 기대는 단서는 깊은 논리 구조보다 코드 길이와 주석 스타일일 가능성이 높거든요. 「Style, Not Self」의 저자들은 추가 학습 없이 코드 작성자를 묻는 실험에서 모델의 판별 정확도를 단순한 길이 비교 규칙과 나란히 세워 검증했습니다.

글·해설: 다메카솔

## 핵심 내용

- **단순 길이 규칙과의 대조**: MBPP 유효 코드 238쌍에서 GPT-5가 자기 코드와 Grok 4 Fast 코드를 구분한 정확도는 **81.9%(195/238)**였지만, 단순히 더 긴 코드를 고르는 규칙은 **97.5%(232/238)**를 기록했습니다.
- **AST 정규화 후 판별력 하락**: 주석·독스트링·타입 힌트를 지우고 지역 변수명을 통일한 뒤(유효 210쌍)에는 길이 규칙이 **85.2%(179/210)**를 유지했는데도 GPT-5의 자기 코드 판별률은 **45.2%(95/210)**로 떨어졌습니다.
- **응답 편향과 익명화의 한계**: 단일 코드 판별(15개 조합 균형 정확도 **49.4~58.2%**)에서는 제로샷 판별력이 약해졌지만, 별도로 학습시킨 문자 패턴 분류기는 정규화 뒤에도 모델 쌍을 구분해 완전한 익명화와는 거리가 있었습니다.

## 높은 판별 점수 뒤에 숨은 단순한 규칙

![같은 길이 차이를 가진 리본 쌍을 두 방식으로 비교하는 비유](./page-01.webp)

가령 여러 모델이 작성한 파이썬 함수를 다른 모델에게 평가하게 하는 코드 리뷰 파이프라인을 떠올려 보겠습니다. 어떤 모델은 꼼꼼한 독스트링과 주석을 붙여 코드를 길게 쓰는 반면, 다른 모델은 군더더기 없이 간결하게 작성합니다. 만약 평가 모델이 둘을 잘 구분한다면 자기 코드의 논리를 알아보는 것처럼 보이지만, 단순히 더 긴 쪽이나 주석이 붙은 쪽을 고르는 규칙만으로도 비슷한 점수가 나올 수 있습니다.

저자들은 이런 착시를 가려내기 위해 다섯 개 주요 모델을 중심으로 세 가지 파이썬 벤치마크 위에서 네 가지 제로샷 과제를 시험했습니다.

- **평가 모델과 기준선**: GPT-5, Claude Haiku 4.5, Gemini 2.5 Flash, Grok 4 Fast, DeepSeek-V3-0324 등 5개 모델이 주축이며, 특정 모델 지목 과제에는 7개 생성 모델을 더했습니다([원문 4.2절·표 3](https://arxiv.org/html/2609.30048v1#S4.SS2)).
- **벤치마크와 과제**: MBPP(257문제, 쌍 비교 수행), HumanEval(164문제), DS-1000 Pandas 부분집합(150문제) 위에서 자기 코드 고르기(쌍 비교·단일 코드), 특정 모델 코드 찾기, 작성자를 가린 품질 평가를 진행했습니다.

실제로 MBPP 유효 판정 쌍에서 GPT-5가 자기 코드와 Grok 4 Fast 코드를 맞힌 비율은 8할을 넘겨 꽤 인상적으로 보입니다. 하지만 같은 문제 묶음에서 무조건 긴 코드를 선택하는 규칙이 거의 모든 쌍을 맞혔다는 점을 나란히 두면 해석이 달라집니다. 단순 진단 규칙과 비슷하거나 못 미치는 점수라면, 이를 깊은 자기 인식 능력으로 받아들이기 어렵습니다.

## 주석과 변수명을 지우면 판별력은 어떻게 달라질까요

![주석과 이름을 뜻하는 리본 장식을 덜어도 속 구조가 남는 비유](./page-02.webp)

그렇다면 코드의 겉장식을 벗겨 내면 모델의 판별력도 달라질까요? 저자들은 구문 트리(AST) 기반 정규화로 주석, 문서 문자열, 타입 힌트를 모두 지우고 지역 식별자 이름을 일관된 규칙으로 바꿨습니다.

| GPT-5 대 Grok 4 Fast (MBPP 쌍 비교) | 원본 코드 | AST 정규화 후 |
| --- | ---: | ---: |
| 분석에 포함한 유효 판정 | 238쌍 (빈 코드·동일 코드·응답 형식 오류 제외) | 210쌍 (정규화 후 동일해진 27쌍·요청 실패 1건 제외) |
| GPT-5 자기 코드 판별 | 195 / 238 (**81.9%**) | 95 / 210 (**45.2%**) |
| 더 긴 코드를 고르는 규칙 | 232 / 238 (**97.5%**) | 179 / 210 (**85.2%**) |

표의 변화를 보면 흥미로운 대목이 드러납니다. 정규화 뒤에도 두 모델 코드 사이의 길이 차이는 여전히 남아 긴 코드 규칙이 높은 적중률을 지켰거든요. 그런데 정작 GPT-5의 자기 코드 판별률은 절반 아래로 주저앉았습니다. 순수한 길이보다 길이를 부풀리던 주석과 문서화 습관에 크게 기대고 있었던 셈이죠.

- **기능 보존과 재평가 결과**: 정규화 후에도 MBPP 문제에서 주요 5개 모델의 개별 테스트 통과 여부는 유지됐습니다. 다만 12개 정규화 쌍 재평가 중 10개 조합은 **43.6~57.8%**로 Holm 보정 후 유의하지 않았고, 나머지 2개는 남은 길이 차이를 따라 우연 수준보다 낮았습니다([원문 3.4절·4.5절](https://arxiv.org/html/2609.30048v1#S4.SS5)).
- **해석 시 유의점**: 신뢰구간이 넓어 작은 잔여 신호가 전혀 없다고 단정하기는 어렵지만, 표면 단서 제거만으로 제로샷 판별이 크게 약해지는 경향은 뚜렷합니다.

## 응답 성향과 프롬프트 순서가 만드는 착시

코드 한 편만 보여 주고 직접 작성했는지 묻는 시험에서는 모델의 응답 성향도 걸러 내야 합니다. 전체 보기 가운데 자기 코드가 3분의 1 안팎이고 남의 코드가 3분의 2라면, 내용을 살피지 않고 무조건 내 코드가 아니라고만 답해도 명목 정답률은 높게 치솟기 때문이죠.

저자들은 이 편향을 걷어 내기 위해 자기 코드를 맞힌 비율과 남의 코드를 부인한 비율을 같은 비중으로 평균 내는 균형 정확도(balanced accuracy)로 결과를 다시 집계했습니다.

- **무조건 '아니다' 기준선과 균형 정확도**: 자기 코드 비중이 약 1/3일 때 전부 부인해도 명목 정답률 **66.7%**가 나오지만, 균형 정확도로 보면 15개 모델·문제군 조합이 **49.4~58.2%**에 머물러 Holm 보정 후 Grok의 두 조합만 유의했습니다([원문 4.3절·표 12](https://arxiv.org/html/2609.30048v1#S4.SS3)).
- **프롬프트 순서 편향**: 초기 실험에서는 프롬프트의 모델 이름 순서와 보기 코드 순서를 맞췄을 때 **86~99%**라는 높은 점수가 나왔다가, 이름 순서를 코드 위치와 독립적으로 무작위화하자 그 착시가 사라졌습니다.

이처럼 문항 배치나 클래스 비율 같은 내용 바깥의 단서만으로도 그럴듯한 점수가 만들어질 수 있습니다. AI 평가 파이프라인을 점검할 때 위치 단서와 기저 비율을 먼저 확인해야 하는 이유입니다.

## 작성 출처와 코드 품질 검사를 분리해야 하는 이유

![돋보기 아래 남은 직조 무늬를 보며 판별과 품질 검사를 구분하는 카솔](./page-03.webp)

주석과 변수명을 지우면 제로샷 LLM 판정기는 갈피를 잡지 못하지만, 코드 안의 흔적이 모두 지워지는 것은 아닙니다. 별도로 학습시킨 문자 패턴 분류기는 정규화된 코드에서도 여러 모델 쌍을 높은 정확도로 구분해 냈거든요. AST 정규화를 완전한 코드 익명화나 워터마크 제거 수단으로 보기는 어렵습니다.

따라서 실무 코드 리뷰나 에이전트 파이프라인에서는 작성 출처와 품질 검사를 분리해 다루는 편이 안전합니다. 누가 코드를 생성했는지는 생성 시점의 시스템 메타데이터(모델 버전·요청 ID)로 남기고, 품질 판단은 [ExecCritic의 독립 테스트 생성 연구](/posts/execcritic-independent-tests/)처럼 실행 가능한 테스트와 정적 분석 증거에 맡기는 방식이죠. 주석 스타일과 길이에 기대어 모델이 작성자를 추측하거나 후한 점수를 주게 두면, 겉모습과 실제 동작 품질이 뒤섞이기 쉽습니다.

이번 연구는 짧은 파이썬 코드와 기본 추론 설정의 제로샷 판별을 다루었습니다. 대규모 다중 파일 저장소나 미세조정된 감시 모델에서는 다른 양상이 나타날 수 있으므로, 실제 적용 환경에 맞춘 별도 검증을 병행하시기 바랍니다.
