글·해설: 다메카솔

미니 PC 3대를 마련해 k3s 클러스터를 올렸을 때만 해도 인프라의 가장 큰 고비는 넘겼다고 생각했습니다. 그런데 설치 직후 야심 차게 날린 `kubectl get svc -A` 명령어 창에는 아무런 서비스도 출력되지 않았습니다. 에러 메시지도, 권한 거부도 없이 그냥 깨끗하게 비어 있는 화면이었습니다. "아, 아직 아무 서비스도 안 띄워서 그런가 보다" 하고 무심코 넘기기 딱 좋은 순간이었습니다.

하지만 실상은 달랐습니다. 터미널의 kubectl 기본 컨텍스트가 새로 만든 홈랩 클러스터가 아니라, 다른 토이 프로젝트용으로 띄워둔 **로컬 kind 클러스터**를 가리키고 있었던 것입니다. 하마터면 자동화 스크립트가 로컬 클러스터의 토큰을 긁어다가 홈랩 Vault 인증 설정에 덮어씌우는 대형 배포 사고를 낼 뻔했습니다.

미니 PC를 굳이 3대로 구성한 이유는 1대가 죽어도 etcd 과반(Quorum)을 유지하기 위해서였지만, 정작 첫 실무 운영에서 마주한 가장 큰 복병은 하드웨어 대수가 아니라 **'내가 지금 어느 클러스터를 바라보고 있는가'라는 기본 검증**이었습니다.

## 1편에서 남은 과제: 24시간 가용 인프라

시놀로지 NAS 기반 k3s는 메모리는 남았지만 CPU가 부족했고, 소음 때문에 밤에 NAS를 끄면 Airflow DB와 스토리지가 함께 증발하는 가용성 한계가 있었습니다. 

이를 해결하기 위해 24시간 저전력으로 켜둘 수 있는 미니 PC(GMKtec M5 Ultra, Ryzen 7 7730U 8코어 16스레드, 32GB RAM, 512GB NVMe) 3대를 도입했습니다. 이번에는 단순한 스펙 합산보다, **1대가 불시에 죽어도 제어면(Control Plane)이 살아남을 수 있는지**, 그리고 백업 복원 시 네트워크 병목이 없는지를 중심에 두고 설계했습니다.

![동일한 미니PC 세 대가 성능 합계가 아니라 한 대 장애 뒤의 제어면 운영과 저장장치 확장성을 위해 선택된 장면](./page-01.webp)

## 복원 리허설에서 드러난 무선 네트워크의 한계

초기 세팅 때는 선 연결이 귀찮아서 3개 노드를 모두 Wi-Fi로 묶었습니다. 클러스터 자체는 정상 기동했지만, 84GB 용량의 테스트 DB를 복원하는 리허설을 돌려보니 무려 88분이 걸렸습니다.

분석해 보니 무선 대역폭과 지연 시간(Latency)이 대용량 데이터 복원의 발목을 잡고 있었습니다. 이후 3개 노드를 2.5GbE 유선 스위치로 연결하고 고정 IP를 할당했습니다. CPU와 RAM 지표만 볼 때는 보이지 않던 **'네트워크 전송 경로'**가 실제 서비스 복구 시간(RTO)을 결정짓는 핵심 병목이었던 셈입니다.

![무선 경로의 좁은 복원 통로를 지나던 데이터가 유선 2.5GbE 경로로 전환되고 세 노드의 주소가 고정되는 장면](./page-02.webp)

## 굳이 3대여야 하는 이유: etcd 쿼럼의 법칙

K3s의 내장 고가용성(HA embedded etcd) 아키텍처는 분산 합의 알고리즘(Raft)을 따릅니다. 클러스터 상태를 확정하려면 반드시 **'전체 멤버의 과반수(Quorum)'** 동의가 필요합니다.

- **2노드 구성**: 과반수는 `(2 / 2) + 1 = 2대`입니다. 1대만 죽어도 남은 노드는 1대뿐이므로 과반을 잃고 클러스터가 멈춥니다. 즉, 장애 허용 대수가 0대입니다.
- **3노드 구성**: 과반수는 `(3 / 2) + 1 = 2대`입니다. 1대가 죽더라도 남은 2대가 과반을 형성하므로 정상 동작합니다.

이것이 K3s와 etcd에서 HA 구성을 위해 **홀수(3, 5...) 노드**를 필수 요구사항으로 두는 이유입니다.

![두 멤버는 둘 모두가 필요하지만 세 멤버는 한 대가 멈춰도 두 대가 과반을 유지하는 etcd 쿼럼 비교](./page-03.webp)

## 빈 화면의 함정: kubectl 컨텍스트 오염

클러스터를 구성한 뒤 `kubectl get svc -A`를 쳤을 때 빈 결과가 나온 것은 홈랩의 상태가 아니었습니다.

```bash
kubectl get svc -A
// 아무 출력 없이 정상 종료 (Exit code 0)
```

에러가 났다면 즉시 이상함을 눈치챘겠지만, 명령어가 `0`으로 정상 종료되었기 때문에 "아직 초기 상태라 서비스가 없나 보다" 하고 넘어가기 쉬웠습니다. 하지만 실제로는 kubeconfig의 `current-context`가 로컬 개발용 kind 클러스터로 잡혀 있었던 것입니다.

![빈 서비스 목록을 보고 새 홈랩이 비었다고 착각했지만 실제 요청은 작은 로컬 kind 클러스터로 향한 장면](./page-04.webp)

조회 결과가 비어 있다는 것은 "데이터가 없다"는 뜻일 뿐, **"내가 의도한 타깃 시스템을 올바르게 찔렀다"는 보증이 되지 않습니다.** 침묵하는 성공이 오히려 가장 위험한 신호였습니다.

## 자동화 파이프라인의 아찔했던 순간과 방어벽

더 아찔했던 점은 그다음 자동화 파이프라인이었습니다. 스크립트는 방금 조회한 클러스터에서 ServiceAccount 토큰(JWT)을 추출해 홈랩 Vault의 쿠버네티스 인증 백엔드에 밀어 넣으려 하고 있었습니다. 만약 그대로 실행되었다면 로컬 토이 클러스터의 인증 정보가 홈랩 보안 저장소에 박혀 연쇄 인증 장애를 일으킬 뻔했습니다.

![남성 카솔이 컨텍스트, API 서버, 예상 노드의 세 지문을 확인한 뒤에만 자격 추출과 쓰기 관문을 여는 장면](./page-05.webp)

이 사건 이후 인프라 자동화 스크립트에는 치명적인 쓰기(Write) 작업 전에 **'클러스터 지문(Fingerprint)'을 3중으로 검증하는 가드레일**을 필수로 추가했습니다:

```bash
// 1. 현재 컨텍스트 이름 검증
kubectl config current-context

// 2. API 서버 엔드포인트 확인
kubectl cluster-info

// 3. 노드 호스트명 목록 검증
kubectl get nodes -o name
```

| 검증 단계 | 검증 항목 | 불일치 시 동작 |
| :--- | :--- | :--- |
| **1단계** | Context 명칭 | 즉시 스크립트 중단 |
| **2단계** | API 서버 IP / 도메인 | 자격 증명 추출 및 쓰기 차단 |
| **3단계** | 등록된 노드 이름 목록 | 타깃 환경 재확인 요구 |

홈랩 운영 환경에서는 운영 클러스터의 인증 정보를 로컬 머신의 글로벌 kubeconfig에 섞지 않고, SSH 배스천을 통해 노드 내부에서 격리된 권한으로 작업하는 정책을 수립했습니다.

## 다메카솔의 해석: 인프라 안전은 화려한 쿼럼보다 기본 가드레일에서 시작된다

분산 쿼럼(etcd)을 계산해 고가용성을 확보하는 것은 아키텍처의 기본이지만, 정작 현업에서 대형 장애를 유발하는 것은 **"잘못된 컨텍스트에 날린 `terraform apply`"**나 **"스테이징인 줄 알고 프로덕션에 날린 스크립트"** 같은 기본 식별 오류입니다.

실무 인프라 엔지니어링에서는 다음 3가지 방어 전략을 항상 고려해야 합니다:

1. **'0건' 결과의 위험성 인지**: 빈 목록 조회가 정상 성공(Exit 0)했다고 해서 타깃 시스템이 맞다고 확신하지 마세요.
2. **파괴적 작업 전 지문(Fingerprint) 검증**: 컨텍스트 명칭뿐 아니라 API 서버 엔드포인트, 클러스터 ID 등 불변 지표를 스크립트 진입점에서 검증해야 합니다.
3. **환경 간 kubeconfig 물리적 분리**: 로컬, 개발, 운영 환경의 컨텍스트를 단일 설정 파일에 통합하기보다 디렉터리 및 환경 변수(`KUBECONFIG`) 단위로 격리하는 것이 안전합니다.
