글·해설: 다메카솔

AI 에이전트가 코딩이나 데이터 분석 작업을 끝내면 LLM API 토큰 비용 청구는 즉시 멈춥니다. 하지만 서버 디스크에는 무엇이 남아 있을까요?

세션 데이터베이스(SQLite), 체크포인트 스냅샷, 디버그 트레이스, 대화 히스토리 로그가 기하급수적으로 쌓여갑니다. 

최근 발표된 논문 **The Hidden Footprint: Making Storage a First-Class Metric for LLM Agent Evaluation**은 LLM 에이전트의 성능을 평가할 때 '정확도'와 '토큰 비용'뿐만 아니라 **'실행 후 디스크에 남겨지는 스토리지 발자국(Storage Footprint)'을 1급 평가지표로 다루어야 한다고 제안한 매우 실무적인 연구**입니다.

이번 글에서는 에이전트 프레임워크들이 왜 이렇게 많은 중복 데이터를 남기는지, 그리고 **세션 복원력(Resilience)을 잃지 않으면서 스토리지를 최적화하는 방법**을 살펴보겠습니다.

## 산출물은 39바이트인데 남겨진 찌꺼기는 131MB?

![작업공간을 떠난 AI 에이전트 뒤로 로그와 체크포인트를 상징하는 데이터 흔적이 디스크에 남는 장면](./page-00.webp)

논문에서 측정한 실제 공급망 견적 에이전트의 사례는 충격적입니다:
- 사용자가 최종적으로 전달받은 유효 산출물(JSON 파일): **2.6MB**
- 에이전트 프레임워크가 실행 후 디스크에 남겨둔 잔여물(체크포인트/로그): **79MB (산출물의 30배 이상)**

심지어 39바이트짜리 짧은 텍스트 요약을 생성하는 과제에서는 프레임워크 오버헤드로 인해 산출물의 무려 **24,033배**에 달하는 디스크 쓰기가 발생했습니다.

물론 세션 상태를 저장해두는 것은 장애 발생 시 중간부터 재개(Resume)하거나 실행 과정을 디버깅하기 위해 필수적입니다. 하지만 "무조건 많이 저장할수록 좋다"는 안일한 설계는 프로덕션 환경에서 디스크 풀(Disk Full) 장애와 막대한 클라우드 스토리지 비용으로 직결됩니다.

## 파일 크기만 보면 안 보이는 '직렬화 중복'의 함정

![실행 전 스냅샷과 에이전트 실행, 실행 후 파일시스템 차이를 같은 샌드박스에서 비교하는 장면](./page-01.webp)

연구진은 LangGraph, AutoGen, CrewAI, OpenAI Agents SDK 등 대표적인 8개 프레임워크를 1,061회 독립 샌드박스에서 실행하며 6가지 핵심 지표를 측정했습니다.

그중 가장 흥미로운 발견은 **'직렬화(Serialization) 뒤에 숨겨진 거대한 중복'**이었습니다.

![같은 데이터 블록이 SQLite 페이지와 JSON 이스케이프를 거치며 다르게 보이다가 논리 내용 분석에서 중복으로 드러나는 장면](./page-02.webp)

- **파일 레벨 단순 청킹 검사**: LangGraph의 SQLite 체크포인트 파일 중복 계수는 `1.01` (중복이 거의 없어 보임)
- **논리 스트림 디코딩 검사**: SQLite 셀과 JSONL 이스케이프 문자를 풀어내어 실제 텍스트 내용을 비교하자 중복 계수가 **`12.1`로 12배 폭증**

즉, SQLite 내부의 페이지 헤더나 JSON 특수문자 이스케이프 때문에 바이트 레벨에서는 다른 데이터처럼 보였지만, 실상은 **동일한 대화 히스토리가 매 턴(Turn)마다 통째로 중복 직렬화되어 저장**되고 있었던 것입니다.

## 성공률 100% 뒤에 숨겨진 복원력(R 등급)의 격차

![같은 성공 신호를 받은 두 AI 에이전트 뒤에 크기가 다른 데이터 더미와 복원 고리가 남는 장면](./page-04.webp)

연구진은 에이전트 프로세스가 불시에 죽었을 때 이전 세션을 얼마나 완벽하게 복원할 수 있는지를 **복원력 등급(R0~R3)**으로 정의했습니다:
- **R3**: 새 프로세스에서 이전 대화와 상태를 완벽히 재개 가능
- **R1**: 로그는 남아 있으나 구조화된 상태가 깨져 세션 재개 불가
- **R0**: 아무것도 복원 불가 (비휘발성 저장 없음)

실험 결과, 100% 동일한 정답률을 기록한 프레임워크들 사이에서도 디스크 저장량은 무려 **15.7배**나 차이 났습니다. 또한 CrewAI 같은 일부 프레임워크는 디스크에 바이트를 남겼음에도 상태 구조가 불완전해(R1) 프로세스 재기동 시 세션을 이어가지 못했습니다.

성공률 지표 하나만 보면 모든 프레임워크가 동등해 보이지만, **"진짜 프로덕션 레벨의 장애 복구 능력을 갖추었는가"**를 따져보면 천차만별이었던 셈입니다.

## 해결책: 콘텐츠 주소화(CAS) 기반 중복 제거

![동일 데이터 블록을 한 번만 보관하고 참조선으로 연결한 저장소 앞에서 성인형 카솔이 네 운영 지표를 점검하는 장면](./page-05.webp)

연구진은 이 문제를 해결하기 위해 **콘텐츠 주소화 스토리지(Content-Addressed Storage, CAS)** 기법을 적용한 프로토타입을 테스트했습니다.

1KB 이상의 텍스트나 프롬프트 블롭(Blob)을 해시(SHA-256)값으로 인덱싱하여 **디스크에는 딱 한 번만 저장하고, 매 턴의 체크포인트에는 가벼운 해시 참조값(포인터)만 남기는 구조**입니다.

그 결과:
- 디스크 저장량이 **4.8배 ~ 32.7배 획기적으로 감소**
- 세션 복원력(R3 등급)은 100% 완벽하게 유지

## 다메카솔의 해석: 에이전트 아키텍처 관점의 스토리지 거버넌스

AI 에이전트를 프로덕션 서비스에 서빙하는 백엔드 아키텍트라면 모니터링 대시보드에 토큰 비용뿐 아니라 **스토리지 수명주기(Lifecycle)**를 반드시 포함해야 합니다.

1. **상태 저장 정책의 차등화**: 모든 임시 추론 단계를 영구 저장하지 말고, 최종 결정된 컨텍스트와 Tool Call 결과만 선별적으로 스냅샷하세요.
2. **슬라이딩 윈도우 & 증분 체크포인팅**: 전체 대화 히스토리를 매 턴마다 풀 덤프(Full Dump)하지 말고, Git처럼 증분(Delta) 또는 최근 N개 턴 위주로 상태를 유지해야 초선형적 용량 폭증을 막을 수 있습니다.
3. **GDPR 및 데이터 삭제 파이프라인**: 세션 DB에 사용자의 민감 개인정보가 비가역적으로 엮여 들어가지 않도록, 세션 만료 후 영구 삭제(TTL) 및 비식별화 아키텍처를 사전에 설계해야 합니다.
