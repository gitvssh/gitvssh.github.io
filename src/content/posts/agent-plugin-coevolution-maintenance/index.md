문서로 기록된 커밋 10개 가운데 8개는 실제로 기능을 더하거나 고친 변경이었습니다. **「On the Maintenance and Co-evolution of Agent Plugins」**는 Claude Code 플러그인 마켓플레이스의 저장소 1,926개와 커밋 77,773개를 분석해, AI가 읽는 자연어 지침이 어떻게 유지보수되는지 추적한 연구입니다.

결론은 실무와 가깝습니다. 에이전트용 Markdown은 사람만 읽는 설명서가 아니라 실행 시점의 행동을 구성합니다. 스크립트의 호출법·경로·출력 계약이 달라지면 지침도 같은 변경 단위에서 확인해야 합니다.

글·해설: 다메카솔

## 핵심 내용

- 저자들은 2026년 4월 Claude Code 플러그인 마켓플레이스를 수집해 저장소 1,926개, 마켓플레이스 항목 2,018개, 유효 플러그인 8,351개를 분석했습니다.
- 플러그인 관련 커밋 77,773개를 다시 분류하자 `docs` 비중은 10.3%에서 1.7%로 줄었고 `feat`는 39.6%를 차지했습니다.
- 같은 `skills/` 디렉터리에서 스크립트와 Markdown이 함께 바뀐 사람 라벨 표본 64건 중 50건은 기능적으로 연결돼 있었습니다.
- 이 자료는 수집 당시 저장소 나이 중앙값이 80일인 한 생태계의 스냅샷입니다. 다른 에이전트 플랫폼에서 같은 패턴이 나오는지는 후속 검증이 필요합니다.
- 공식 재현 저장소의 일부 데이터와 출력 표는 대조했지만, 빠진 원시 입력과 캐시 때문에 전체 분석을 독립 재현하지는 못했습니다.

## 스크립트만 고치면 예전 경로가 남는다

![새 스크립트 장치와 맞지 않는 예전 지침 경로를 에이전트 토큰이 따라가는 장면](./page-01.webp)

플러그인은 실행 코드만으로 동작하지 않습니다. Skill·Command·Agent 같은 자연어 파일이 도구를 언제, 어떤 인자로, 어느 경로에서 호출할지 정합니다. 저자들은 이 조합이 반복해서 고쳐지는 소프트웨어인지, 한 번 쓰고 방치되는 산출물인지 물었습니다.

문제는 변경의 비대칭입니다. 스크립트에 새 플래그를 넣고 `SKILL.md`의 호출 예를 그대로 두면, 구현은 새 상태인데 에이전트는 낡은 경로를 읽습니다. 파일 형식이 Markdown이라는 이유만으로 이 변경을 일반 문서 작업으로 분류하면 실제 동작 변화가 가려집니다.

## 실제 마켓플레이스의 변경 기록을 모았다

![여러 저장소 상자가 두 단계 여과 장치를 지나 지침 리본과 스크립트 기어, 설정 블록으로 정리되는 장면](./page-02.webp)

수집 파이프라인은 GitHub Code Search에서 `.claude-plugin/marketplace.json`을 찾는 데서 시작합니다. 저자들은 저장소 이름으로 중복을 제거하고 별 10개 이상인 저장소를 남긴 뒤, 로컬 경로로 해석되는 플러그인만 분석했습니다. 그 결과 2,018개 마켓플레이스 항목에서 유효 플러그인 8,351개가 남았습니다.

커밋 분석 단위는 플러그인 구성요소 파일을 한 개 이상 건드린 변경입니다. 이 기준으로 3,948명의 작성자가 만든 커밋 77,773개를 모았습니다. 소프트웨어 엔지니어링 용도는 저자 분류에서 전체 플러그인의 61.3%였고, 둘 이상의 구성요소 유형을 담은 플러그인은 34.4%였습니다.

활동량도 빠르게 늘었습니다. 공식 출시 직후인 2025년 10월에는 월간 플러그인 관련 커밋이 2,923개였고, 2026년 3월에는 25,618개였습니다. 논문이 말한 8.8배 성장은 이 여섯 달 구간을 가리킵니다.

## AI가 읽는 Markdown은 일반 문서와 달랐다

![평범한 서류로 보이던 지침 조각이 기계에 들어가 출력 경로를 바꾸는 장면](./page-03.webp)

저자들은 먼저 커밋 메시지 규칙으로 51,141개를 분류하고, 규칙에 맞지 않는 26,632개는 GPT-5-mini로 분류했습니다. 그다음 `docs`, `ci`, `style`로 적힌 변경의 diff를 읽어 실제 작업 성격을 다시 판정했습니다.

재분류는 표면과 기능의 차이를 드러냈습니다. 원래 `docs`였던 커밋 8,007개 중 80%가 `feat`나 `fix`로 이동했고, 최종 `docs` 비중은 10.3%에서 1.7%로 내려갔습니다. AI가 런타임에 읽는 지침을 추가하거나 고친 작업은 행동을 바꾸기 때문입니다.

전체 분포에서 `feat`는 39.6%, `chore`는 21.0%였습니다. 논문이 인용한 전통 오픈소스의 `feat` 17.2%와 비교하면 새 기능 중심의 성격이 강했습니다. 이 비교는 같은 저장소를 맞춰 본 대조 실험이 아니라 선행 연구의 기준선이라는 점도 함께 읽어야 합니다.

공동 작성자 표식을 찾는 휴리스틱에서는 전체 커밋의 34.9%가 Claude 공동 작성으로 잡혔습니다. 사람이 AI 결과를 직접 commit하면 표식이 남지 않으므로, 저자들은 이 값을 실제 AI 관여의 하한으로 해석했습니다.

## 스크립트와 지침은 같은 변경에서 만났다

![스크립트 장치의 입출력 위치가 바뀌자 연결된 지침 리본도 새 위치로 맞춰지는 장면](./page-04.webp)

구성요소 전체를 보면 모든 파일이 한 덩어리로 움직이지는 않았습니다. 우연 기대보다 자주 함께 바뀐 구성요소 쌍은 Agents와 Commands였고 lift는 1.40이었습니다. Skills가 다른 구성요소와 자주 함께 등장한 현상은 Skills 자체가 널리 쓰인 영향도 받았습니다.

같은 `skills/` 디렉터리 안으로 들어가면 다른 모습이 나옵니다. Python·Shell 스크립트와 Markdown의 공동 변경은 우연 기대보다 자주 나타났습니다. 저자 두 명이 pull request 64건을 읽어 보니 50건, 78%에서 스크립트 변경과 지침 변경이 기능적으로 연결돼 있었습니다.

연결의 이유는 네 갈래였습니다. 새 플래그나 명령을 더한 인터페이스 변경, 출력이나 검증을 바꾼 내부 로직 변경, 모델 이름·환경 변수·버전의 동기화, 파일 경로와 설정 형식의 재구성입니다. 64건의 사람 라벨과 GPT-5-mini 판정 사이 Cohen의 카파는 0.62였고, 저자들은 남은 259건에도 같은 분류기를 적용했습니다.

## 한 생태계의 짧은 스냅샷이다

![하나의 젊은 플러그인 생태계만 유리 돔 안에서 관찰되고 다른 생태계는 밖에 남은 장면](./page-05.webp)

이 결과의 시간 범위는 2026년 4월입니다. 수집 시점 저장소 나이 중앙값은 80일이었고, 생태계가 빠르게 커지는 초기 구간이었습니다. 지금의 유지보수 비율이나 장기 생존 패턴까지 같은 값으로 이어진다고 볼 근거는 아직 없습니다.

플랫폼 범위도 좁습니다. 연구진은 Claude Code용 플러그인을 조사했습니다. Cursor, Copilot, Gemini, Codex처럼 지침 구조와 배포 방식이 다른 생태계에서 커밋 의미와 공동 변경이 반복되는지는 시험하지 않았습니다.

분류 과정에는 모델 판단이 들어갑니다. 논문은 사람 표본으로 일치도를 점검했지만 GPT-5-mini와 Qwen 기반 분류는 프롬프트와 모델 버전에 민감할 수 있습니다. 공동 작성자 탐지도 표식이 남은 commit만 잡습니다.

## 공개 저장소의 표까지만 대조했다

저는 arXiv PDF와 TeX, 공식 저장소의 고정 commit `7b50b30f3cc92ced5b1ec525b0317c3282555a05`를 보존했습니다. 공개 CSV에서 마켓플레이스 2,018행과 플러그인 8,351행을 확인했고, 공개 JSON도 플러그인 레코드 8,351개를 담았습니다. 분류 요약에는 전체 커밋 77,773개, 규칙 분류 51,141개, LLM 분류 26,632개가 기록돼 있었습니다.

Script-Markdown 표도 파일끼리 맞았습니다. 사람 라벨 CSV는 64건이었고, 공개 JSONL의 남은 259건을 세면 인터페이스 87건, 내부 로직 68건, 값·버전 33건, 저장소 구조 24건, 비연결 47건으로 배포된 Table 8과 일치했습니다.

여기까지는 공개 산출물의 일관성 검사입니다. 저장소 README가 언급한 대형 mined input과 `ccs_labels.jsonl`, `relabeled.jsonl`, `plugin_registry.json`, `pr_plugin_records.jsonl`은 고정 commit에 없었습니다. GitHub 재수집과 hosted-model 분류를 다시 수행하지 않았으므로 RQ2·RQ3 전체를 독립 재현했다는 뜻은 아닙니다.

## 다메카솔의 해석: 코드와 지침을 한 쌍으로 검사한다

![성인형 카솔이 스크립트 장치와 지침 경로가 함께 맞아야 열리는 배포 관문을 가리키는 장면](./page-06.webp)

제가 이 연구에서 가져갈 판단은 간단합니다. 에이전트용 자연어 지침을 문서 디렉터리에 있다는 이유로 비실행 산출물처럼 다루면, 리뷰와 테스트가 동작 변화의 절반만 보게 됩니다. [워크플로 자체를 판단 근거로 보존해야 한다는 연구](/posts/workflow-as-knowledge/)와 이어서 읽으면, 지침 파일도 실행 경로의 일부라는 점이 더 선명해집니다.

실무에서는 세 군데를 묶어 보겠습니다. 첫째, 스크립트의 플래그·경로·출력 필드가 바뀐 pull request는 연결된 지침 파일을 함께 검토합니다. 둘째, 지침에 적힌 호출 예를 작은 contract test로 실행해 경로와 인자가 살아 있는지 확인합니다. 셋째, 모델 이름·환경 변수·스키마 값은 가능하면 한 정의에서 생성해 수동 동기화 지점을 줄입니다.

자연어 의미 검토는 사람에게 남습니다. 문장이 더 매끄러워졌어도 트리거 조건이나 금지 규칙이 달라지면 행동 변경입니다. diff 리뷰에서 “문서만 바뀌었다”보다 “에이전트가 무엇을 다르게 하게 되는가”를 먼저 묻는 편이 안전합니다.

이 짝 검증은 논문이 직접 시험한 개입이 아닙니다. 관찰된 결합을 운영 규칙으로 옮긴 다메카솔의 해석입니다. 효과를 말하려면 실제 플러그인 저장소에서 stale instruction defect와 회귀율을 따로 측정해야 합니다.

## 자주 묻는 질문

### Markdown을 코드와 똑같이 취급해야 하나요?

파일 형식이 같다는 뜻은 아닙니다. 에이전트가 런타임에 읽는 지침은 호출 조건과 절차를 바꾸므로 행동 영향도에 맞춰 리뷰하자는 뜻입니다. 사람용 README의 설명 수정과 Skill의 실행 규칙 수정은 같은 `docs` 라벨로 묶기 어렵습니다.

### 78%면 모든 스크립트 변경이 지침 변경을 요구하나요?

78%는 스크립트와 Markdown이 이미 함께 바뀐 사람 라벨 표본 64건 가운데 기능적으로 연결된 50건의 비율입니다. 모든 스크립트 변경을 분모로 삼은 값이 아닙니다. 어떤 변경이 지침 동기화를 요구하는지 판단하는 단서로 읽어야 합니다.

### 다른 에이전트 플러그인에도 그대로 적용되나요?

현재 논문은 Claude Code 플러그인 마켓플레이스만 분석했습니다. 다른 플랫폼에도 자연어 우선 산출물이 있지만 디렉터리 구조, 배포 방식, 작성자 표식이 다릅니다. 같은 분석을 반복하기 전에는 일반화보다 점검 가설로 두는 편이 정확합니다.
