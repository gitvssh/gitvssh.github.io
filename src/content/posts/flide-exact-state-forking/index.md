Flide는 같은 문맥에 여러 질문을 던질 때 문맥 계산을 공유하면서, 각 질문이 혼자 실행될 때 보던 입력을 유지하려는 추론 엔진입니다. 질문을 한 줄에 이어 붙이는 것만으로는 충분하지 않습니다. 함께 실행되는 질문들이 서로의 내용을 읽지 않도록 계산 경로도 분리해야 합니다.

글·해설: 다메카솔

## 같은 문서를 여러 번 읽는 비용

예를 들어 한 상담 기록에 대해 ‘환불 대상인가’, ‘긴급한가’, ‘사람에게 넘겨야 하나’를 각각 판단한다고 합시다. 세 질문은 같은 상담 기록을 사용하지만 서로 다른 선택지를 평가합니다. 이는 원리를 설명하기 위한 예시입니다.

2026년 10월 30일 제출된 Bobo Li 외의 논문 **Flide: Accelerating Decision Inference with Exact State Forking**은 이런 선택형 판단 요청을 다룹니다. 긴 답변을 생성하는 작업 전체를 빠르게 만든다는 주장이 아니라, 공통 상태와 여러 질문으로 구성된 요청을 어떻게 실행할지에 관한 연구입니다. 

접두어 캐시는 같은 앞부분을 다시 계산하는 비용을 줄여 줍니다. [코딩 에이전트 실행 기록에서 살펴본 KV 캐시](/posts/agentic-coding-production-traces/)도 이 재사용을 다뤘습니다. Flide가 더 살피는 지점은 캐시 뒤의 질문들이 여전히 각각 별도 시퀀스로 실행된다는 점입니다. 논문은 하이브리드 모델에서 블록 경계 뒤의 일부 토큰을 다시 계산하는 비용과 질문별 실행 부담을 지적합니다.

## 한 흐름에 담고, 참조 경로는 나누기

![공통 문맥에서 서로 연결되지 않은 질문 세 갈래로 분기하는 계산 경로](./page-01.webp)

Flide는 공통 문맥과 질문들을 GPU에서 처리할 하나의 토큰 흐름에 담습니다. 대신 어느 요청에 속하는 토큰인지, 어느 질문의 가지인지, 원래 위치는 어디인지를 별도 메타데이터로 남깁니다. 물리적으로 나란히 놓였다고 해서 모든 토큰을 서로 읽게 하지는 않습니다. 각 질문의 위치도 단독 입력에서의 위치를 유지합니다. 

일반 어텐션 층에서는 같은 요청의 공통 문맥과 자기 질문의 앞부분만 참조하게 제한합니다. Gated DeltaNet처럼 이전 내용을 순환 상태에 누적하는 층은 주의가 더 필요합니다. 다른 질문을 이미 거친 상태에서 시작하면 그 내용이 섞일 수 있기 때문입니다. 논문의 방식은 먼저 문맥의 상태와 합성곱 이력을 계산하고, 모든 질문을 각자의 공통 문맥 끝 상태에서 시작시킵니다. 이 층은 두 번의 호출로 처리하므로 ‘한 번의 실행’이라는 표현을 ‘GPU 커널 하나’로 이해하면 안 됩니다. 

질문들을 구분하려고 새 구분 토큰을 입력에 끼워 넣지도 않습니다. 입력을 바꾸어 얻은 빠른 답과, 원래 입력의 계산을 공유해서 얻은 빠른 답을 구별하는 설계입니다.

## 빨라진 실험에는 어떤 조건이 붙을까

저자들은 NVIDIA H200 한 장에서 bfloat16으로 비교했습니다. 다음은 논문 Table 2·3의 **Qwen3.5-0.8B, QuALITY의 한 지문에 딸린 모든 질문을 묶은 요청** 결과입니다. 115개 요청에 총 2,086개 질문이 포함되며, 표의 지연은 단일 클라이언트 요청의 중앙값입니다. 실험은 이 작업에 수준별 두 사본을 보내되 서로의 상태 캐시를 재사용하지 못하도록 구별 태그를 넣었습니다. 

| 추론 엔진 | 요청 중앙 지연 |
| --- | ---: |
| vLLM | 362 ms |
| SGLang | 359 ms |
| Flide | 37.7 ms |

이 행에서는 더 빠른 기준선인 SGLang 대비 약 9.5배의 지연 차이가 납니다. 논문 전체의 모든 모델·작업에 적용되는 배수가 아닙니다. 부록 B에서 vLLM은 0.32.0rc1(10월 14일 빌드)과 0.32.1rc1 중 각 셀의 더 빠른 결과를 사용하며, SGLang은 0.5.21입니다. Flide 버전은 표에 `release`로만 표기돼 있습니다.  일부 엔진의 프롬프트 템플릿과 multi-item scoring의 CUDA graph 사용 여부도 다릅니다. 이 글은 저자 측 측정의 소개이고 독립 재현 결과가 아닙니다.

질문이 하나이고 큰 모델의 계산 시간이 대부분을 차지하면 개선 폭은 작아집니다. 같은 Table 3에서도 **Gemma 4-31B, 단일 질문 QuALITY**는 vLLM 400 ms, Flide 405 ms입니다. 이 작업은 지문·질문·가장 긴 선택지가 템플릿 여유를 두고 3,600토큰에 들어오도록 지문을 줄인 단일 질문 구성으로, 위의 전체 질문 묶음과 다릅니다. 공유할 질문 수와 실제 부하를 빼고 최고 배수만 가져오면 기대를 잘못 세우게 됩니다. 

## 같은 계산과 맞는 답은 다르다

![함께 실행하는 경로와 단독 경로를 비교하며 정확성의 조건을 짚는 카솔](./page-02.webp)

논문의 Proposition 1은 인과 모델과 정확한 산술을 가정합니다. 그 조건에서 각 질문의 은닉 상태가 단독 실행과 같다는 주장입니다. 모델이 사실관계를 잘못 알거나 분류를 틀렸다면, 같은 계산을 보존해도 그 오류까지 해결되지는 않습니다. 

실제 GPU는 부동소수점을 사용합니다. 합산 순서가 달라지면 끝자리 오차가 생길 수 있어, 수학적으로 같은 계산이라는 설명만으로 비트 단위 동일성을 보장할 수 없습니다. Flide는 합산 순서를 고정하는 선택 모드를 따로 제공합니다. 논문의 보장은 같은 하드웨어·소프트웨어에서 전체 상태를 입력하는 경로를 전제로 설명됩니다. 다른 장비나 모든 캐시 재개 경로까지 무조건 같다고 확대하면 안 됩니다.

**다메카솔의 해석:** 이런 엔진을 비교할 때는 처리량뿐 아니라 ‘질문을 혼자 물었을 때의 입력과 확률 분포를 유지하는가’를 기준으로 두면 좋겠습니다. 그다음 실제 요청에서 문맥을 얼마나 공유하는지, 문맥당 질문이 몇 개인지를 살펴야 합니다. 빠른 실행과 질문 의미의 보존을 함께 확인하는 것이 이 논문에서 가져갈 설계 관점입니다.
