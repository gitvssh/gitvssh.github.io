서비스에서 AI 응답을 JSON으로 받을 때, 키 순서는 크게 신경 쓰지 않는 경우가 많습니다. 파싱하는 코드 입장에서는 `{"answer": "판정", "reason": "근거"}`나 `{"reason": "근거", "answer": "판정"}`이나 똑같은 데이터 구조거든요. 하지만 한 토큰씩 답을 이어 붙이는 언어 모델에게는 어느 필드를 먼저 쓰느냐가 정확도를 좌우하는 작업 조건이 됩니다.

글·해설: 다메카솔

## 핵심 내용

- **생성 순서의 제약**: 자기회귀 모델은 이미 출력한 답 토큰을 뒤의 설명으로 되돌려 고치기 어렵기 때문에, 추론 필드를 먼저 쓰는지 답변 필드를 먼저 쓰는지에 따라 결과가 달라집니다.
- **과제와 모델별 편차**: 수학 과제(GSM8K)에서 GPT-4o는 추론 먼저 JSON(95.60%)이 답변 먼저 JSON(55.34%)을 크게 앞섰지만, 논리·SQL 과제에서는 순서 효과가 줄거나 자유형 출력이 더 높은 예외가 나타났습니다.
- **파서와 채점 코드 분리 점검**: 논문 부록 A.3에 보고된 Gemma3-4B 자유형 응답 추출기 버그(MMLU 29.8%, LogicBench 45.2% 빈 답 추출)는 모델 실력과 추출기 오류를 구분해 측정해야 할 이유를 보여 줍니다.

## 같은 JSON 키 묶음인데 왜 결과가 달라질까

![답을 먼저 확정하는 흐름과 추론을 먼저 만드는 흐름의 개념 비교](./page-01.webp)

한 토큰씩 앞선 출력을 조건으로 다음 토큰을 만드는 자기회귀 모델에서는 이미 확정된 답을 뒤의 설명으로 되돌려 고치기 어렵습니다. 답변 필드를 먼저 출력하면 모델은 이후에 이어질 근거를 보지 못한 상태에서 답부터 내놓아야 하므로, 뒤의 설명이 앞선 답을 바꿀 수 없게 됩니다. 반대로 추론 필드를 먼저 쓰게 하면, 앞서 전개한 풀이 과정을 문맥으로 삼아 최종 답을 고를 수 있습니다.

예를 들어 고객 문의의 환불 가능 여부를 판별하는 API에서 아래 두 가지 JSON 형식을 비교해 볼까요?

```json
// 1) 답변 먼저: 판정부터 출력한 뒤 사유를 이어 붙임
{"eligible": false, "reason": "구매 후 14일이 지나 환불 대상에 해당하지 않습니다."}

// 2) 추론 먼저: 근거를 먼저 전개한 뒤 최종 판정을 확정
{"reason": "구매 후 14일이 지났으므로 규정상 환불이 어렵습니다.", "eligible": false}
```

읽는 프로그램에는 두 객체가 동일하지만, 모델의 생성 과정에서는 전혀 다른 경로를 밟는 셈이죠. 여기서 말하는 순서는 서버가 완성된 JSON의 키를 화면 표시용으로 재정렬하는 일이 아니라 모델이 텍스트를 실제로 내보내는 순서입니다. 「Structure Tax」 연구진은 프롬프트 지시로 형식을 지정해 자유형 출력과 JSON·XML의 두 순서를 비교했으므로, 토큰 선택을 강제하는 구조화 출력 API나 내부 추론을 별도로 수행하는 모델에 적용할 때는 환경에 맞춘 추가 확인이 필요합니다.

## 어떤 조건에서 차이가 났을까

![수학 과제의 개선과 다른 과제의 예외를 구분하는 개념 장면](./page-02.webp)

논문 저자들은 다섯 개 모델을 수학·지식·논리(답 일치 여부)와 SQL 생성(실행 결과 일치 여부) 네 가지 과제에서 평가했습니다. 모든 비교는 temperature 0 조건에서 다섯 번 반복 실행한 평균과 표준편차(±)를 기준으로 보고됐습니다.

- **평가 모델(5종)**: GPT-4o, Gemini-Flash-2.0, Claude-Sonnet-4.5, Llama-3.1-8B, Gemma3-4B
- **과제 및 분할 규모(4종)**: GSM8K 수학(평가 1,319개), MMLU 지식(검증 1,531개), LogicBench 논리(평가 500개), Spider SQL 생성(검증 1,030개)

| 과제 (평가 문항 수) | 모델 | JSON 답변 먼저 | JSON 추론 먼저 | 자유형 출력 |
| --- | --- | ---: | ---: | ---: |
| GSM8K (1,319개) | GPT-4o | 55.34±1.58% | 95.60±1.01% | 88.78±1.02% |
| LogicBench (500개) | Llama-3.1-8B | 76.00±1.05% | 74.60±2.05% | — |
| Spider 검증 (1,030개) | Llama-3.1-8B | — | 54.84±2.71% | 64.99±1.85% |

수학 문제인 GSM8K에서는 필드 순서를 바꾼 것만으로 GPT-4o의 정답률이 크게 뛰었고, 자유형 출력보다도 높은 점수를 기록했습니다. 반면 논리 과제인 LogicBench에서는 라마(Llama) 모델의 답변 먼저와 추론 먼저 결과가 비슷한 수준에 머물렀고, SQL을 생성하는 Spider 과제에서는 오히려 자유형 출력이 추론 먼저 JSON을 앞섰습니다.

이처럼 형식과 순서의 유불리는 과제 성격과 모델에 따라 갈리는 편입니다. 따라서 특정 형식을 만능 해법으로 믿기보다는 실제 서비스의 모델과 질문 묶음에서 직접 비교해 볼 실험 변수로 다루어야 합니다. 모델 이름뿐 아니라 출력 스키마와 실행 조건을 함께 기록해야 한다는 점은 [에이전트 평가의 설정 문제](/posts/agent-evaluation-system-configuration/)와도 맞닿아 있습니다.

## 부록의 추출기 버그를 함께 읽어야 하는 이유

![답변 추출 과정과 정답 검사를 따로 점검하는 카솔](./page-03.webp)

본문 수치만 보고 구조화 출력이 자유형보다 항상 우수하다고 결론 내리기 전에 부록의 파서 기록도 짚어 볼 필요가 있습니다.

- **추출기 버그 보고(부록 A.3)**: Gemma3-4B의 자유형 답변을 읽는 추출기에 결함이 있어 빈 답으로 추출된 비율이 MMLU에서 29.8%, LogicBench에서 45.2%에 달했습니다.
- **결과 해석의 경계**: 공개 원문만으로는 이 버그의 수정 전후 결과가 본문 집계에 어떻게 반영됐는지까지 확인되지 않으므로, 해당 모델에서 구조화 출력이 높게 나온 수치를 곧바로 추론 능력 향상으로 단정하기는 어렵습니다.

또한 내부 표현 분석은 공개 가중치 모델인 라마와 젬마 두 계열에서만 수행됐고, 저자들은 더 복잡한 스키마나 훈련을 통한 적응, 다언어 확장을 후속 과제로 남겼습니다. 본문 표와 부록 기록을 나란히 읽어 보면, 모델이 실제로 생성한 결과와 평가 코드가 읽어 낸 값을 왜 분리해 점검해야 하는지 분명해지죠.

## 다메카솔의 해석: 스키마 변경도 회귀 검사에 넣기

서비스에서 AI 응답 스키마를 바꾼다면 기존 평가 요청 묶음을 고정한 뒤, 변경 전후를 한 덩어리 정답률로만 보지 말고 아래 세 지표로 나누어 기록해 두는 편이 좋습니다.

- **형식 통과율**: 모델 응답이 지정한 JSON 스키마로 오류 없이 파싱되는 비율
- **추출 실패율**: 파서나 정규식 단계에서 빈 값이나 누락으로 빠지는 비율
- **최종 정답률**: 추출된 값이 기준 정답이나 SQL 실행 결과와 일치하는 비율

이렇게 지표를 쪼개 두고 실패한 원시 응답을 열어 보면 모델이 계산을 틀렸는지, 파서가 답을 놓쳤는지, 먼저 쓴 답과 뒤의 추론이 서로 어긋났는지가 또렷이 보입니다. 한편 사용자 화면에서는 결론부터 먼저 보여 주는 편이 읽기 좋을 때가 많습니다. 모델이 생성하는 JSON 순서(추론 먼저)와 화면에 렌더링하는 순서(결론 먼저)를 분리해 설계하면 정확도와 가독성 두 가지를 함께 만족시킬 수 있습니다.
