AI 에이전트에 연결하는 도구가 많아질수록, 당장 쓰지 않을 도구의 상세 정의까지 매 요청마다 모델에 읽히는 부담이 커집니다. Google이 2026년 11월 19일 프리뷰로 공개한 **Gemini API Tool Retrieval**은 도구의 이름과 설명만 먼저 보여 주고, 호출에 필요한 매개변수 구조는 그 도구가 실제로 필요해질 때 불러오는 기능입니다. 공식 문서 기준으로는 Interactions API의 `v1beta`에서 제공되며, 기존 `generateContent` 경로는 지원 대상에서 제외됩니다.

글·해설: 다메카솔

## 이름과 매개변수 구조를 나눠 읽는 방식

에이전트에 도구를 붙일 때는 이름과 용도 설명뿐만 아니라, 호출할 때 넘길 값의 규칙도 함께 전달합니다. 예를 들어 배송 조회 도구를 연결한다면 주문 번호의 자료형과 필수 여부 같은 세부 조건이 매개변수 스키마에 들어가죠. 연결된 도구가 늘어날수록 매 요청의 초기 문맥에 실리는 이런 상세 정의도 함께 커집니다.

Google이 안내한 기본 방식은 요청에 `tool_search`를 추가하고, 나중에 불러올 도구에 `defer_loading: true`를 설정하는 것입니다. 이렇게 설정하더라도 도구 선언 자체는 요청마다 계속 보내야 하며, 뒤로 미루는 대상은 모델의 초기 문맥에 들어가는 상세 스키마뿐이거든요. 모델은 초기 문맥에 남아 있는 이름과 설명을 보고 알맞은 도구를 찾고, API가 해당 스키마를 불러오면 그때 인자를 채운 함수 호출을 만듭니다.

![모든 공구를 펼친 상태에서 필요한 공구만 선택한 상태로 바뀌는 두 컷. 이름·설명은 먼저 보고 매개변수는 나중에 읽는 흐름의 비유](./page-01.webp)

실제로 감추는 것은 도구의 존재나 실행 권한이 아니라 처음 문맥에 넣을 상세 스키마입니다. 모델이 처음에 참고할 단서가 이름과 설명뿐인 만큼, 두 항목이 모호하면 선택 정확도도 함께 흔들릴 수밖에 없습니다. 상세 정보를 덜어 내는 설정과 더불어 각 도구의 이름과 역할을 또렷하게 적어 두는 설계를 함께 챙겨야 합니다.

실행 주체의 경계도 기존 함수 호출과 똑같이 유지됩니다. API가 스키마를 불러와 모델이 함수 호출을 생성하더라도, 직접 만든 함수를 실행해 결과를 돌려주는 일은 여전히 애플리케이션이 맡습니다. 도구 검색이 임의의 함수를 대신 실행해 주는 구조는 아닌 셈이죠.

## 지원 범위와 과금 조건에서 확인할 것

프리뷰 단계인 만큼 지금 바로 쓸 수 있는 환경과 비용이 계산되는 방식을 먼저 확인해 두어야 합니다. 공식 발표와 문서의 핵심 조건은 아래와 같습니다.

| 항목 | 공식 안내 내용 | 실무 확인 포인트 |
| --- | --- | --- |
| API·상태 | Interactions API `v1beta` 프리뷰 | `generateContent` 미지원, 정식 출시 전 변경 가능 |
| 지원 모델 | 발표: Gemini 3.6 이후·4 계열 / 문서: `gemini-4-hydrogen`, `gemini-4-argon`, `gemini-3.8-flash`, `gemini-3.6-flash` | 적용 전 문서상 지원 모델 ID 재확인 필요 |
| 검색 방식 | 서버 측 검색 / 클라이언트 측 검색 | 클라이언트 방식은 자체 필터 관리 가능, 검색마다 추가 왕복 발생 |
| 과금 조건 | 기능 자체 별도 요금 없음 | 고정 토큰·불러온 스키마·검색당 추가 모델 호출 입력 과금 |

검색 방식을 고를 때는 지연 시간과 제어 범위 사이의 균형을 따져 볼 필요가 있습니다. 서버 측 검색은 같은 API 요청 안에서 바로 처리되지만, 별도 도구 목록이나 사용자별 필터를 직접 관리해야 한다면 클라이언트 측 검색을 택하게 되거든요. 다만 클라이언트 방식을 쓰면 검색마다 애플리케이션과 한 차례 추가 왕복이 발생합니다.

비용 역시 기능 자체에 별도 요금이 붙지 않는다는 점만 보고 낙관하기는 어렵습니다. 검색 기능을 켤 때 소량의 고정 입력 토큰이 들어가고, 불러온 스키마도 입력으로 과금되거든요. 여기에 서버 측 검색이 일어날 때마다 전체 문맥과 새 스키마를 넣은 추가 모델 호출이 발생해 그 입력까지 과금 대상이 됩니다. 결국 처음에 건너뛴 스키마가 많더라도 검색 횟수와 캐시 효율을 함께 봐야 실제 절감 폭을 가늠할 수 있습니다.

## 다메카솔의 해석, 도구 수보다 작업 성공을 먼저 보자

Tool Retrieval은 도구를 많이 연결하는 에이전트에서 초기 문맥 부담을 줄여 주는 현실적인 선택지입니다. 도입을 검토할 때는 같은 요청 묶음을 기준으로 기존 방식과 나란히 대조해 세 가지를 함께 점검해 볼까요?

- **입력 토큰 변화**: 초기 스키마를 줄여 얻은 절감분이 고정 토큰과 검색당 추가 모델 호출 비용을 실제로 상쇄하는지 확인합니다.
- **전체 응답 시간**: 서버 측 추가 호출이나 클라이언트 측 왕복이 전체 지연 시간에 어떤 영향을 주는지 살핍니다.
- **올바른 도구 선택 여부**: 상세 스키마 없이 이름과 설명만으로 모델이 상황에 맞는 도구를 빠짐없이 찾아내는지 점검합니다.

입력 토큰을 줄였더라도 필요한 도구를 놓쳐 작업이 실패한다면 지연 로딩의 의미가 흐려집니다. 관련해서 [필요한 스킬만 노출하는 SkillBrowser 연구](/posts/skillbrowser-selective-skill-exposure/)도 선택적 정보 노출이라는 다른 접근을 다룹니다. 별개의 연구인 만큼 그 평가 결과를 이번 Gemini API 기능의 성능 근거로 바로 옮겨 쓰기보다는, 문맥 부담을 줄이는 설계 흐름으로만 참고하는 편이 알맞겠습니다.
