코딩 에이전트가 수정 패치를 만들고 그 패치를 승인할 테스트까지 직접 작성한다면 겉보기에는 무척 편리합니다. 하지만 요구사항을 잘못 이해한 한 가지 실수가 패치와 테스트 양쪽에 동시에 들어갈 수 있다는 점이 문제인데요. 「ExecCritic: Learn to Test, Test to Improve for Coding Agents」는 테스트를 만드는 에이전트와 코드를 고치는 에이전트를 분리하고, 테스트 실행 결과를 고정된 피드백으로 활용하는 구조를 실험했습니다.

글·해설: 다메카솔

## 핵심 내용

- **역할과 권한의 분리**: 독립된 Test 에이전트가 테스트 패치(`test.patch`)와 실행 명령(`test_command`)을 만들고, 별도의 Repair 에이전트는 소스 코드만 수정합니다.
- **Base 게이트 검증**: 생성된 테스트는 버그가 남아 있는 Base 체크아웃에서 정상 실행된 뒤 깨끗하게 실패해야만(fail-closed) 수정 루프에 들어갑니다.
- **테스트 품질의 양날**: SWE-bench Verified에서 생성 테스트의 품질에 따라 동일한 기본 수정 에이전트의 해결률이 **57.3%**로 떨어지거나 **65.3%**로 올랐습니다(무테스트 기본 61.2%).
- **학습 효과와 난도별 한계**: 학습된 Test·Repair 조합은 Verified에서 **72.6%**를 기록했지만, 더 어려운 SWE-bench Pro에서 단일 생성 테스트의 개선 폭은 **0.7%포인트**(Oracle 피드백은 11.8%포인트)에 그쳤습니다.
- **로컬 통과와 최종 판정 구분**: 고정 테스트 통과는 수정 루프의 종료 조건일 뿐 정답 증명이 아니며, 최종 해결 여부는 별도의 전체 공식 평가(F2P·P2P)가 판정합니다.

## 패치와 테스트가 같은 빈틈을 공유할 수 있다

![같은 로봇이 깨진 코드 블록과 맞지 않는 측정 틀을 동시에 만들며 같은 모서리를 놓치는 장면](./page-01.webp)

코드 수정 과정에서 테스트는 단순한 실행 버튼이 아니라 이슈가 요구한 행동을 검사하는 별도의 명세입니다. 만약 패치와 테스트를 같은 에이전트 흐름 안에서 함께 작성하면, 요구사항을 잘못 해석한 흔적이 두 산출물에 나란히 남기 쉽습니다. 잘못된 패치가 그 잘못된 테스트를 통과하며 스스로를 증명하는 ‘자기확인’ 구조가 되는 셈입니다.

ExecCritic은 이 결합을 역할과 권한 분리로 끊어 냅니다. **Test 에이전트**는 저장소에 맞는 `test.patch`, 그 테스트를 실행할 정확한 `test_command`, 행동 계약을 담은 JSON을 하나의 번들로 묶어 제출하고, **Repair 에이전트**는 이 번들을 건드리지 않은 채 소스 수정에만 집중합니다. 여기서 ‘독립’이라는 말은 두 모델의 실수가 통계적으로 완전히 무관하다는 뜻이 아니라, 테스트 작성과 소스 수정을 별도 정책과 단계로 나누어 수정 단계가 검사 기준을 임의로 바꾸지 못하게 막았다는 뜻입니다.

## 테스트 에이전트가 먼저 요구를 검사한다

![파란 테스트 로봇이 버그 기계를 검사해 세 개의 물리적 산출물을 초록 게이트로 넘기고 주황 수정 로봇은 분리된 공간에서 기다리는 장면](./page-02.webp)

Test 에이전트가 만든 번들은 곧바로 수정 에이전트에게 전달되지 않습니다. 하네스는 먼저 버그가 남아 있는 Base 체크아웃에 테스트 패치를 적용하고, 지정된 명령이 정상적으로 실행된 뒤 깨끗하게 실패하는지 확인합니다. 만약 테스트 자체가 실행되지 않거나 버그가 있는 상태인데도 이미 통과해 버리면 fail-closed 원칙에 따라 탈락합니다.

물론 이 **Base 게이트**가 증명하는 범위는 좁습니다. 테스트가 현재의 버그 상태를 거부한다는 뜻일 뿐, 테스트에 적힌 기대값이 이슈의 진짜 요구사항과 완벽히 일치한다는 보증은 아니기 때문입니다. 저자들은 정답인 Gold 패치에서도 해당 테스트가 통과하는지를 `Base-to-Gold` 지표로 감사하지만, 이 Gold 패치는 테스트 생성 중에 보이지 않으며 배포형 수정 단계의 입력이나 테스트 선별 근거로도 쓰이지 않습니다.

이 경계가 중요한 이유는 명확합니다. Gold 패치를 보고 테스트를 고르면 실제 운영 환경에서는 결코 얻을 수 없는 정답 정보가 평가 루프에 새어 들어가기 때문입니다. 따라서 ExecCritic은 오직 Base 체크아웃에서 자격을 확인한 번들만 고정해 Repair 단계에 넘기고, Gold 평가는 모델 학습과 오프라인 분석에만 사용합니다.

## 수정 에이전트는 고정 테스트를 바꿀 수 없다

![봉인된 측정 장치 아래에서 주황 코드 블록만 차례로 교체되는 장면](./page-03.webp)

번들을 넘겨받은 Repair 에이전트는 고정된 테스트 패치와 실행 명령을 수정할 수 없으며, 오직 소스 코드 패치만 고칠 수 있습니다. 테스트가 실패하면 실행 피드백을 받아 최대 다섯 차례까지 소스 패치를 개정합니다.

이 구조는 테스트 기대값을 느슨하게 바꾸거나 아예 테스트 파일을 지워 실패를 덮어 버리는 지름길을 원천 차단합니다. 테스트가 답을 알려 주는 해설지가 아니라 바꿀 수 없는 ‘측정 지그(jig)’로 작동하기 때문에, 에이전트는 소스 코드 쪽의 원인을 다시 파고들어야 합니다. 다만 이 로컬 테스트의 초록불은 해당 수정 루프를 멈추는 조건일 뿐 최종 정답 판정이 아니며, 전체 공식 F2P(Fail-to-Pass)·P2P(Pass-to-Pass) 테스트가 기존 동작 보존과 이슈 해결을 따로 확인한 뒤에야 최종 벤치마크 해결로 집계됩니다.

## 생성 테스트는 좋으면 돕고 약하면 해친다

![주황 수정 로봇 앞에서 휘어진 빨간 측정 레일과 정밀한 초록 레일이 코드 블록을 서로 다른 방향으로 이끄는 장면](./page-04.webp)

그렇다면 실행 피드백을 붙이는 것만으로 항상 성능이 오를까요? SWE-bench Verified와 SWE-bench Pro에서 확인된 주요 수치를 비교해 보면 테스트 자체의 품질이 얼마나 결정적인지 드러납니다.

| 평가 항목 및 구성 | 기본/비교 기준 | 테스트 피드백 적용 결과 | 비고 |
| --- | ---: | ---: | --- |
| **Verified**: 기본 Repair + 기본 Qwen Test | 61.2% (무테스트 1회) | **57.3%** | 약한 테스트가 해결률을 오히려 낮춤 (3회 수정 실행 평균) |
| **Verified**: 기본 Repair + GPT-5.6-sol Test | 61.2% (무테스트 1회) | **65.3%** | 정교한 테스트로 해결률 상승 (3회 수정 실행 평균) |
| **Verified**: Test 에이전트 Base-to-Gold 성공률 | 22.2% (기본) | **39.6%** (SFT) → **62.2%** (RL) | 사후학습 단계에 따라 테스트 생성 품질 향상 |
| **Verified**: 학습된 Repair + 학습된 RL Test | 68.3% (피드백 없는 첫 수정) | **72.6%** | 무테스트 기본 Repair(61.2%) 대비 +11.4%p |
| **SWE-bench Pro**: GPT-5.6-sol 생성 테스트 vs Oracle | +0.7%p (생성 테스트) | **+11.8%p** (Oracle 피드백) | 고난도 과제에서 단일 생성 테스트의 포착 범위 한계 |

표에서 보듯 실행 피드백 자체가 이득을 보장하지는 않습니다. 요구사항을 정확히 짚어낸 테스트는 탐색 범위를 좁혀 주지만, 약한 테스트는 올바른 패치를 밀어내거나 잘못된 국소 목표로 에이전트를 이끌 수 있습니다. 또한 학습된 Test·Repair 조합이 SWE-bench Verified에서는 72.6%까지 올라갔지만, 더 복잡한 SWE-bench Pro에서는 GPT-5.6-sol 생성 테스트의 개선 폭이 0.7%포인트에 머물러 단일 생성 테스트가 포착할 수 있는 행동 범위의 한계도 함께 보여 줍니다.

## 실행 비용과 언어 일반화는 아직 열린 문제다

성능 수치 이면의 운영 조건도 함께 짚어 봐야 합니다.

- **추가 실행 비용**: 피드백 수정이 실제로 일어난 120개 궤적은 평균 13개의 추가 에이전트 턴을 사용했습니다. 여기에 테스트를 만드는 단계 자체가 별도 비용으로 추가되는데, 논문은 토큰·지연 시간·금전 비용을 동일 조건으로 맞춘 효율 비교를 제시하지 않으므로 해결률 상승을 곧바로 ‘더 저렴한 시스템’으로 읽을 수는 없습니다.
- **언어별 전이 격차**: Python 과제로만 사후학습한 Test 에이전트의 타 언어 Base-to-Gold 성공률은 Rust **66.7%**, C++ **58.3%**, C **26.1%**, Java **2.4%**였습니다. 일부 언어로의 전이 가능성은 보이지만 모든 저장소 생태계에 고르게 일반화됐다고 보기는 어렵습니다.
- **분리 정책과 향후 과제**: 현재 Test와 Repair는 별도 정책으로 학습됩니다. 저자들은 가중치를 공유하는 공동학습을 미래 과제로 남겼는데, 한 모델 안에 두 역할을 합칠 때는 서로의 허점을 이용하거나 실제 과제 대신 상대 정책에 맞춰지는 퇴행(collusion)을 막아야 합니다.

## 로컬 테스트와 최종 평가는 권한이 다르다

![성인형 카솔이 작은 로컬 테스트 게이트와 그 뒤의 더 큰 독립 전체 평가 장치를 구분해 소개하는 장면](./page-05.webp)

이 논문에서 가장 실용적인 설계는 테스트를 여러 번 실행한다는 점보다 **증거의 권한을 나눈 구조**에 있습니다. Test는 요구사항을 검사하고, 하네스는 실행 가능한 실패를 확인하며, Repair는 소스만 바꿉니다. 고정 테스트는 수정 방향을 안내할 뿐 최종 전체 평가는 별도 권한으로 남습니다.

공식 저장소(`1891f8efa473d1917c716cd4d80db1a6186721ad` 커밋)에는 실행 코드와 테스트가 공개돼 있지만, 논문 결과·궤적·체크포인트·데이터셋·자격 증명·샌드박스 상태는 공개 아카이브에 포함되지 않았습니다(공식 README가 가리키는 일부 빌더 경로도 아카이브에 없으며 프로젝트 환경에 새 의존성을 추가 설치하지 않았습니다). 따라서 이번 검토는 PDF·TeX·공식 메타데이터·고정 코드 아카이브를 대조해 방법과 공개 범위를 감사한 것이며, 벤치마크 수치를 독립 재계산한 결과는 아닙니다.

## 다메카솔의 해석: 검증 근거를 수정 권한 밖에 두자

코딩 에이전트 운영 파이프라인에 이 연구를 적용한다면 핵심 원칙은 **검사자와 수정자의 권한 분리**입니다. 이슈에서 검증 가능한 행동을 뽑아내는 단계가 먼저 테스트를 만들고, 버그 상태에서 실행 가능한 실패를 확인한 뒤 그 번들을 해시와 함께 고정합니다. 이후 수정 에이전트에는 소스 코드 경로에만 쓰기 권한을 주고 테스트와 평가 설정은 읽기 전용으로 묶어 두는 방식입니다.

아울러 수정 루프의 성공 증거와 배포 성공 증거도 명확히 나눠야 합니다. 고정 테스트 통과는 다음 단계로 넘어갈 수 있다는 로컬 신호일 뿐이며, 전체 회귀 테스트·정책 검사·빌드·실제 배포 검증은 별도의 최종 게이트로 남겨 두어야 합니다(이는 논문이 실제 조직 배포에서 검증한 결과가 아니라, 논문의 구조를 운영 절차로 옮긴 해석입니다).

## 자주 묻는 질문

### 테스트 에이전트를 따로 두면 항상 더 좋아지나요?

아닙니다. 같은 기본 Repair 에이전트를 쓰더라도 약한 생성 테스트를 붙이면 해결률이 61.2%에서 57.3%로 오히려 낮아졌습니다. 역할 분리는 자기확인 위험을 줄이는 구조일 뿐, Test 에이전트 자체의 품질과 최종 독립 평가가 여전히 뒷받침되어야 합니다.

### Base에서 실패하고 Gold에서 통과하면 완벽한 테스트인가요?

버그 상태와 정답 패치 두 체크아웃을 구분하는 행동을 포착했다는 점에서 강력한 오프라인 신호입니다. 하지만 숨은 요구사항 전체를 빠짐없이 검사하거나 다른 회귀를 모두 막는다는 보증은 아니므로, 실제 수정 루프에서는 Gold를 쓰지 않고 최종 공식 평가를 따로 수행합니다.

### 고정 테스트를 통과하면 배포해도 되나요?

고정 테스트는 수정 루프 안의 로컬 종료 기준입니다. 전체 회귀 여부, 기존 통과 테스트 보존, 빌드와 정책 검사, 실제 배포 상태는 별도 게이트로 확인해야 합니다.
