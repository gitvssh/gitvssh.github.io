코딩 에이전트가 패치를 만들고 그 패치를 승인할 테스트까지 함께 만든다면 편리해 보입니다. 문제는 요구사항을 잘못 이해한 한 가지 실수가 패치와 테스트에 동시에 들어갈 수 있다는 점입니다. 「ExecCritic: Learn to Test, Test to Improve for Coding Agents」는 테스트를 만드는 에이전트와 코드를 고치는 에이전트를 분리하고, 실행 결과를 고정된 피드백으로 쓰는 방법을 실험했습니다.

글·해설: 다메카솔

## 핵심 내용

- ExecCritic은 독립된 Test 에이전트가 테스트 패치와 실행 명령을 만들고, 별도의 Repair 에이전트가 소스만 수정하게 합니다.
- 생성된 테스트는 버그가 있는 Base에서 정상적으로 실행된 뒤 실패해야 수정 루프에 들어갑니다.
- SWE-bench Verified에서 생성 테스트의 품질에 따라 같은 기본 수정 에이전트의 해결률이 57.3%로 떨어지거나 65.3%로 올랐습니다.
- 학습된 Test·Repair 조합은 72.6%를 기록했지만, 단일 생성 테스트의 효과는 더 어려운 SWE-bench Pro에서 0.7%포인트에 그쳤습니다.
- 고정 테스트 통과는 수정 종료 조건일 뿐 정답 증명이 아닙니다. 최종 판정은 별도의 전체 공식 평가가 맡습니다.

## 패치와 테스트가 같은 빈틈을 공유할 수 있다

![같은 로봇이 깨진 코드 블록과 맞지 않는 측정 틀을 동시에 만들며 같은 모서리를 놓치는 장면](./page-01.webp)

코드 수정에서 테스트는 단순한 실행 버튼이 아닙니다. 이슈가 요구한 행동을 검사하는 별도의 명세입니다. 패치와 테스트를 같은 에이전트 흐름이 함께 작성하면 요구를 잘못 해석한 흔적이 두 산출물에 나란히 남을 수 있습니다. 잘못된 패치가 그 잘못된 테스트를 통과하는 자기확인 구조가 되는 셈입니다.

ExecCritic은 이 결합을 역할과 권한으로 끊습니다. Test 에이전트는 저장소에 맞는 `test.patch`, 그 테스트를 실행할 정확한 `test_command`, 행동 계약을 담은 JSON을 하나의 번들로 제출합니다. Repair 에이전트는 이 번들을 만들지 않고 소스 수정에 집중합니다.

여기서 독립이라는 말은 두 모델의 실수가 통계적으로 완전히 무관하다는 뜻이 아닙니다. 논문이 구현한 핵심은 테스트 작성과 소스 수정을 별도 정책과 별도 단계로 나누고, 수정 단계가 검사 기준을 바꾸지 못하게 하는 것입니다.

## 테스트 에이전트가 먼저 요구를 검사한다

![파란 테스트 로봇이 버그 기계를 검사해 세 개의 물리적 산출물을 초록 게이트로 넘기고 주황 수정 로봇은 분리된 공간에서 기다리는 장면](./page-02.webp)

Test 에이전트가 만든 번들은 곧바로 수정 에이전트에게 가지 않습니다. 하네스는 먼저 버그가 남아 있는 Base 체크아웃에 테스트 패치를 적용하고, 지정된 명령이 정상 실행된 뒤 깨끗하게 실패하는지 확인합니다. 테스트가 실행되지 않거나 이미 통과하면 fail-closed로 탈락합니다.

이 Base gate가 증명하는 것은 좁습니다. 테스트가 현재 버그 상태를 거부한다는 뜻이지, 기대값이 이슈의 진짜 요구와 일치한다는 뜻은 아닙니다. 저자들은 정답 Gold 패치에서도 테스트가 통과하는지를 Base-to-Gold 지표로 감사하지만, Gold는 테스트 생성 중 보이지 않습니다. 배포형 수정 단계의 입력이나 테스트 선별 근거로도 쓰지 않습니다.

이 경계가 중요합니다. Gold를 보고 테스트를 고르면 실제 운영에서는 얻을 수 없는 정답 정보가 평가 루프에 새어 들어갑니다. ExecCritic은 Base에서 자격을 확인한 번들만 고정해 Repair에 넘기고, Gold 평가는 학습과 오프라인 분석에 남깁니다.

## 수정 에이전트는 고정 테스트를 바꿀 수 없다

![봉인된 측정 장치 아래에서 주황 코드 블록만 차례로 교체되는 장면](./page-03.webp)

Repair 에이전트는 고정된 테스트 패치와 명령을 바꾸지 못합니다. 할 수 있는 일은 소스 패치를 수정하는 것뿐입니다. 테스트가 실패하면 실행 피드백을 받고 최대 다섯 차례 패치를 개정합니다.

이 구조는 실패를 지우는 쉬운 길을 막습니다. 수정 중에 테스트 기대값을 느슨하게 만들거나 테스트 파일을 제거할 수 없다면, 에이전트는 소스 쪽 원인을 다시 찾아야 합니다. 테스트는 답을 알려 주는 해설이 아니라 바꿀 수 없는 측정 지그로 작동합니다.

그래도 로컬 초록불은 최종 정답이 아닙니다. 고정 테스트 통과는 해당 수정 루프를 멈추는 조건입니다. 전체 공식 F2P·P2P 테스트가 기존 동작 보존과 문제 해결을 따로 확인한 뒤에야 벤치마크 해결로 계산됩니다.

## 생성 테스트는 좋으면 돕고 약하면 해친다

![주황 수정 로봇 앞에서 휘어진 빨간 측정 레일과 정밀한 초록 레일이 코드 블록을 서로 다른 방향으로 이끄는 장면](./page-04.webp)

SWE-bench Verified에서 기본 Repair 에이전트를 고정했을 때, 테스트 없이 한 번 수정한 해결률은 61.2%였습니다. 기본 Qwen Test가 만든 피드백을 붙이면 57.3%로 낮아졌고, GPT-5.6-sol이 만든 테스트를 쓰면 65.3%로 올랐습니다. 세 값은 고정된 생성 테스트 번들로 전체 과제를 세 차례 수정 실행한 저자 보고 평균입니다.

즉 실행 피드백 자체가 이득을 보장하지 않습니다. 요구를 잘 잡은 테스트는 탐색을 좁히지만, 약한 테스트는 올바른 패치를 밀어내거나 잘못된 국소 목표로 이끌 수 있습니다. 논문의 Test 에이전트 학습에서도 Base-to-Gold 성공률은 기본 22.2%, 지도 미세조정 뒤 39.6%, 강화학습 뒤 62.2%로 단계적으로 달라졌습니다.

학습된 Repair는 피드백 없는 첫 수정에서 68.3%, 학습된 RL 테스트 피드백 뒤 72.6%를 기록했습니다. 학습된 Test·Repair 조합의 72.6%는 원래 무테스트 Base Repair 61.2%보다 11.4%포인트 높습니다. 다만 더 어려운 SWE-bench Pro에서는 GPT-5.6-sol 생성 테스트의 개선이 0.7%포인트였고 Oracle 피드백은 11.8%포인트였습니다. 단일 생성 테스트가 포착하는 행동 범위의 한계를 함께 보여 줍니다.

## 실행 비용과 언어 일반화는 아직 열린 문제다

피드백 수정이 실제로 일어난 120개 궤적은 평균 13개 추가 에이전트 턴을 썼습니다. 그러나 테스트를 만드는 단계는 별도 비용입니다. 논문은 토큰, 지연 시간, 금전 비용을 같은 조건으로 맞춘 효율 비교를 제시하지 않습니다. 해결률 상승을 곧바로 더 싼 시스템이라고 읽을 수 없는 이유입니다.

언어별 차이도 큽니다. Python 과제로만 사후학습한 Test 에이전트의 Base-to-Gold 성공률은 Rust 66.7%, C++ 58.3%, C 26.1%, Java 2.4%였습니다. 몇몇 언어로의 전이는 보이지만, 모든 저장소 생태계에 고르게 일반화됐다고 보기는 어렵습니다.

현재 Test와 Repair는 별도 정책으로 학습됩니다. 저자들은 공유 가중치의 공동학습을 미래 과제로 남겼습니다. 한 모델 안에 두 역할을 합칠 때는 서로의 허점을 이용하거나 실제 과제 대신 상대 정책에 맞춰지는 퇴행을 막아야 합니다.

## 로컬 테스트와 최종 평가는 권한이 다르다

![성인형 카솔이 작은 로컬 테스트 게이트와 그 뒤의 더 큰 독립 전체 평가 장치를 구분해 소개하는 장면](./page-05.webp)

이 논문에서 가장 실용적인 설계는 테스트를 많이 실행한다는 사실보다 증거의 권한을 나눈 점입니다. Test는 요구를 검사하고, 하네스는 실행 가능한 실패를 확인하며, Repair는 소스만 바꿉니다. 고정 테스트는 수정 방향을 안내하지만 최종 전체 평가는 별도 권한으로 남습니다.

공식 저장소 commit `1891f8efa473d1917c716cd4d80db1a6186721ad`에는 실행 코드와 테스트가 있습니다. 하지만 공개 아카이브에는 논문 결과, 궤적, 체크포인트, 데이터셋, 자격 증명, 샌드박스 상태가 포함되지 않았습니다. 프로젝트 Python 환경에 `pytest`도 없어서 새 의존성을 설치하지 않았고, 공개 스냅샷만으로 논문의 벤치마크 수치를 독립 재현했다고 주장하지 않습니다.

소스 패킷에서는 PDF와 TeX, 공식 메타데이터, 고정 코드 아카이브를 대조했습니다. 공식 README가 가리키는 일부 빌더 경로는 공개 아카이브에 없어 그 단계도 실행하지 않았습니다. 이번 확인은 방법과 공개 범위를 감사한 것이며 결과 재계산은 아닙니다.

## 다메카솔의 해석: 검증 근거를 수정 권한 밖에 두자

제가 코딩 에이전트 운영에 가져갈 원칙은 검사자와 수정자의 권한 분리입니다. 이슈에서 검증 가능한 행동을 뽑는 단계가 테스트를 만들고, 실행 가능한 실패를 확인한 뒤 그 번들을 해시와 함께 고정합니다. 수정 에이전트에는 소스 경로만 쓰게 하고 테스트와 평가 설정은 읽기 전용으로 둡니다.

수정 루프의 성공 증거와 배포 성공 증거도 나누겠습니다. 고정 테스트 통과는 다음 단계로 갈 수 있다는 신호입니다. 전체 회귀 테스트, 정책 검사, 빌드, 실제 배포 검증은 별도의 최종 게이트로 남겨야 합니다. 이 권고는 논문이 실제 조직 배포에서 검증한 결과가 아니라, 논문의 구조를 운영 절차로 옮긴 다메카솔의 해석입니다.

## 자주 묻는 질문

### 테스트 에이전트를 따로 두면 항상 더 좋아지나요?

아닙니다. 같은 기본 Repair에서도 약한 생성 테스트는 해결률을 61.2%에서 57.3%로 낮췄습니다. 역할 분리는 자기확인 위험을 줄이는 구조이고, Test 자체의 품질과 최종 독립 평가가 여전히 필요합니다.

### Base에서 실패하고 Gold에서 통과하면 완벽한 테스트인가요?

두 체크아웃을 구분하는 행동을 잡았다는 강한 오프라인 신호입니다. 그래도 숨은 요구 전체를 검사하거나 다른 회귀를 모두 막는다는 보증은 아닙니다. 실제 수정 루프에서는 Gold를 쓰지 않고 최종 공식 평가를 따로 수행합니다.

### 고정 테스트를 통과하면 배포해도 되나요?

고정 테스트는 수정 루프의 로컬 기준입니다. 전체 회귀, 기존 통과 테스트 보존, 빌드와 정책 검사, 실제 배포 상태는 별도 게이트로 확인해야 합니다.
