AI 코딩 에이전트가 수정 패치와 검증 테스트를 함께 작성하면 편리해 보이지만, 요구사항을 잘못 이해한 실수가 양쪽에 동시에 들어갈 수 있습니다. 결국 틀린 코드가 틀린 테스트를 통과하며 스스로를 증명하는 셈이 되죠. 「ExecCritic: Learn to Test, Test to Improve for Coding Agents」는 테스트 생성과 코드 수정을 별도 에이전트로 분리해 실행 피드백으로 활용하는 구조를 검증했습니다.

글·해설: 다메카솔

## 핵심 내용

- **역할·권한 분리**: Test 에이전트가 `test.patch`와 `test_command`를 제출하면, Repair 에이전트는 소스 코드만 수정합니다.
- **Base 게이트**: 버그가 남은 Base 체크아웃에서 정상 실행 뒤 깨끗하게 실패해야(fail-closed) 수정 루프에 들어갑니다.
- **테스트 품질의 영향**: SWE-bench Verified(무테스트 기본 61.2%)에서 약한 테스트는 57.3%로 떨어뜨렸고, RL 학습 조합은 72.6%까지 올랐습니다.
- **평가 경계**: 로컬 통과는 수정 루프 종료 조건일 뿐, 최종 해결 여부는 전체 공식 평가(F2P·P2P)가 판정합니다.

## 패치와 테스트가 같은 빈틈을 공유할 때

![같은 로봇이 깨진 코드 블록과 맞지 않는 측정 틀을 동시에 만들며 같은 모서리를 놓치는 장면](./page-01.webp)

테스트는 단순한 실행 버튼이 아니라 이슈가 요구한 동작을 검사하는 별도의 명세입니다. 예를 들어 경계값 조건을 `<` 대신 `<=`로 오해한 에이전트가 패치와 테스트를 한 흐름에서 함께 쓰면, 두 산출물이 같은 오류를 공유한 채 통과해 버리기 쉽거든요.

ExecCritic은 두 Qwen-3.5-35B-A3B 정책을 분리해 이 결합을 끊습니다. **Test 에이전트**는 저장소 네이티브 `test.patch`, 실행 명령 `test_command`, JSON 행동 계약을 한 번들로 제출하고, **Repair 에이전트**는 이를 건드리지 못한 채 소스만 고칩니다. 여기서 독립이란 통계적 무관성이 아니라 수정 단계가 검사 기준을 임의로 바꾸지 못하게 권한을 나눴다는 뜻입니다.

## 버그 상태에서 먼저 실패해야 통과하는 Base 게이트

![파란 테스트 로봇이 버그 기계를 검사해 세 개의 물리적 산출물을 초록 게이트로 넘기고 주황 수정 로봇은 분리된 공간에서 기다리는 장면](./page-02.webp)

생성된 번들은 하네스의 **Base 게이트**를 통과해야 수정 단계로 넘어갑니다. 버그가 남아 있는 Base 체크아웃에 테스트를 적용했을 때 정상 실행 뒤 깨끗하게 실패하는지 확인하며, 실행 오류가 나거나 버그 상태에서 이미 통과하면 fail-closed 원칙으로 탈락시킵니다.

다만 Base 게이트는 테스트가 현재 버그를 거부한다는 사실만 확인해 줍니다. 저자들은 정답 패치 통과 여부를 `Base-to-Gold` 지표로 감사하지만, 이 Gold 패치는 테스트 생성 중 가려져 있으며 수정 단계의 입력이나 선별 근거에서도 빠집니다. 실전에서는 얻을 수 없는 정답 정보가 평가 루프로 새는 일을 막으려는 설계죠.

## 수정 에이전트는 검사 기준을 건드릴 수 없다

![봉인된 측정 장치 아래에서 주황 코드 블록만 차례로 교체되는 장면](./page-03.webp)

번들을 넘겨받은 Repair 에이전트는 고정된 테스트와 실행 명령을 바꿀 수 없으며, 실패 피드백을 받아 최대 다섯 차례까지 소스 패치만 고칩니다.

이처럼 테스트를 고정된 '측정 지그'로 묶어 두면, 에이전트가 검증 조건을 느슨하게 바꾸거나 테스트를 지워 실패를 덮는 지름길을 차단할 수 있습니다. 물론 로컬 테스트의 초록불은 수정 루프의 종료 조건에 해당하며, 최종 성적은 기존 동작 보존과 이슈 해결을 함께 확인하는 전체 공식 F2P(Fail-to-Pass)·P2P(Pass-to-Pass) 평가가 결정합니다.

## 테스트 품질이 성능을 가르기도, 깎기도 한다

![주황 수정 로봇 앞에서 휘어진 빨간 측정 레일과 정밀한 초록 레일이 코드 블록을 서로 다른 방향으로 이끄는 장면](./page-04.webp)

그렇다면 실행 피드백을 붙이기만 해도 해결률이 항상 오를까요? SWE-bench Verified(3회 수정 평균)와 SWE-bench Pro 수치를 비교해 보면 테스트 품질의 영향이 뚜렷합니다.

| 평가 구성 | 비교 기준 | 피드백 적용 결과 | 핵심 관찰 |
| --- | ---: | ---: | --- |
| **Verified**: 기본 Repair + 기본 Qwen Test | 61.2% (무테스트 1회) | **57.3%** | 약한 테스트가 해결률을 낮춤 |
| **Verified**: 기본 Repair + GPT-5.6-sol Test | 61.2% (무테스트 1회) | **65.3%** | 정교한 테스트로 해결률 상승 |
| **Verified**: Test Base-to-Gold 성공률 | 22.2% (기본) | **39.6%**(SFT) → **62.2%**(RL) | 사후학습에 따른 품질 향상 |
| **Verified**: 학습 Repair + RL-35B Test | 68.3% (Round 0) | **72.6%** | 무테스트 기본(61.2%) 대비 +11.4%p |
| **SWE-bench Pro**: 생성 테스트 vs Oracle | +0.7%p (GPT-5.6-sol) | **+11.8%p** (Oracle) | 고난도 과제의 단일 테스트 한계 |

표에서 보듯 실행 피드백 자체가 성능을 보장해 주지는 않습니다. 정확한 테스트는 탐색 범위를 좁혀 주지만, 부실한 테스트는 올바른 패치를 밀어내거나 잘못된 목표로 수정을 이끌거든요. 복잡한 SWE-bench Pro에서 생성 테스트의 개선 폭이 0.7%포인트에 그친 점도 단일 테스트의 포착 범위 한계를 보여 줍니다.

## 실무 적용 전에 따져 볼 비용과 언어 한계

수치 이면의 운영 조건도 함께 점검해야 합니다.

- **추가 턴과 미측정 비용**: 피드백 수정이 일어난 120개 궤적은 평균 13개의 추가 에이전트 턴을 썼고 테스트 생성 비용도 따로 듭니다. 토큰·지연·금전 비용을 동일 조건으로 맞춘 비교는 빠져 있어 효율성까지는 따로 따져 봐야 합니다.
- **언어별 전이 격차**: Python으로만 사후학습한 Test 에이전트의 Base-to-Gold 성공률은 Rust **66.7%**, C++ **58.3%**, C **26.1%**, Java **2.4%**로 격차가 컸습니다.
- **공동학습의 퇴행 과제**: 현재 두 에이전트는 별도 정책으로 학습되며, 가중치를 공유하는 공동학습에서는 서로의 허점에 맞춰지는 퇴행(collusion)을 막는 과제가 남아 있습니다.

## 다메카솔의 해석: 검증 근거를 수정 권한 밖에 두기

![성인형 카솔이 작은 로컬 테스트 게이트와 그 뒤의 더 큰 독립 전체 평가 장치를 구분해 소개하는 장면](./page-05.webp)

실무 에이전트 파이프라인에 적용할 핵심은 **검사자와 수정자의 쓰기 권한 분리**입니다. 이슈에서 검증 가능한 행동을 뽑아 테스트 번들을 고정한 뒤, 수정 에이전트에는 소스 코드 경로에만 쓰기 권한을 열어 두는 편이 안전하죠.

아울러 로컬 통과 신호와 배포 승인 증거도 분리해 둬야 합니다. 고정 테스트의 초록불은 다음 단계로 넘어가는 루프 종료 기준일 뿐이며, 전체 회귀 테스트·정책 검사·빌드 검증은 별도의 최종 게이트에서 판정해야 신뢰도를 지킬 수 있습니다.
